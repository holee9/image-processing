## (a) 무엇으로 바꿨나 — **큐 내용의 지문**

### 제품 경로가 있습니다 (축 3과 다릅니다)

`xpe_get_pending_alert(index, msg, msgLen, &severity)` 는 **인덱스 접근자**이고, 헤더가 계약을 적습니다:

> *"The alert queue is not modified; call `xpe_clear_alerts()` to drain it."* (`xpe_error.h:111`, SRS-ALERT-003 / api-spec.md 5.17)

**그래서 "제품에 읽을 경로가 없다" 보고가 아니라 구현입니다.** 축 3(품질 메타)은 복구 경로가 없어 보고만 하다 시작했는데, 이 축은 **읽는 경로도 비우는 경로도 처음부터 공개**입니다. 시험 전용 접근자는 만들지 않았습니다.

### 선택: FNV-1a 지문

메시지 바이트 + 심각도를 **큐 순서대로** 해싱합니다.

**왜 이것인가:**

| 후보 | 왜 안 골랐나 / 골랐나 |
|---|---|
| **지문 (채택)** | 공개 접근자만으로 계산되고, 상태를 따로 들고 있지 않아도 됩니다 |
| 누적 밀린 수를 따로 세기 | **제품에 그 카운터가 없습니다.** `g_alertsDropped` 는 축출만 셉니다 — 세려면 `xpe_alert_push` 에 계측을 넣어야 하고, 그것은 시험을 위해 제품을 고치는 것입니다 |
| 드레인 여부 플래그 | 같은 이유로 제품 변경이 필요하고, **비웠다는 사실보다 무엇이 남았는가**가 후임에게 닿는 것입니다 |

**심각도를 넣은 이유**: 두 알림이 같은 글을 갖고 심각도만 다를 수 있습니다.
**순서를 세는 이유**: 같은 두 알림이 뒤바뀐 큐는 다른 큐이고, **뒤바꾸는 것 자체가 후임에게 하면 안 되는 일**입니다.

**개수는 별도 필드로 남겼습니다.** 두 수가 다른 질문에 답합니다 — *"2건 남겼다"* 와 *"2건을 바꿔치웠다"* 는 읽는 사람을 **다른 줄로** 보냅니다. 해시는 전자를 말할 수 없습니다.

읽기 실패(버퍼보다 긴 메시지 등)는 인덱스를 해시에 접어 넣어, **짧은 큐와 같은 값으로 조용히 떨어지지 않게** 했습니다.

## (b) 가짜 음성 재현 — **§4 방식 양방향**

임시 시험 둘을 넣었습니다(측정 후 걷어냈습니다):

```cpp
TEST(QA139DemoTest, ALeavesOneAlert)          { push("alert A", INFO); }
TEST(QA139DemoTest, BSwapsTheQueueContents)   { xpe_clear_alerts(); push("alert B, entirely different", WARNING); }
```

`B` 는 진입 개수 1, 종료 개수 1 — **수가 같습니다.**

### ① 지금 가드(개수만) — **가짜 음성 재현**

지문 검사만 런타임 거짓 조건으로 껐습니다. **`BUILD_EXIT=0` 확인 후**:

```
QA139DemoTest.ALeavesOneAlert -- pending alerts 0 -> 1 (drain with xpe_clear_alerts());
NonlinearityCorrect.UnknownModeIsNoLongerAnError -- pending alerts 1 -> 0 (...);
```

**`BSwapsTheQueueContents` 가 명단에 아예 없습니다.** 통과입니다 — 가짜 음성 그대로.

### ② 고친 가드(지문) — 빨강 + 지목

```
QA139DemoTest.ALeavesOneAlert -- pending alerts 0 -> 1 (drain with xpe_clear_alerts());
QA139DemoTest.BSwapsTheQueueContents -- pending alert queue replaced (1 alerts, different contents; drain with xpe_clear_alerts());
```

**이름으로 지목하고, 이유도 다른 문장으로 적습니다.**

### ③ 대조군

임시 시험을 걷어낸 지금 상태에서 **위반 0건**, 다른 세 축도 0건.

> 셋을 다 보였으므로 **고친 것이 무엇을 고쳤는지** 말할 수 있습니다: 개수가 같은 교체를 놓치던 것을, 이름과 이유까지 붙여 잡습니다.

## 비용 — **잡음과 분리되지 않습니다. 없다고는 적지 않습니다**

추가되는 일은 시험마다 `xpe_get_pending_alert_count()` **2회**(진입·종료)와, 큐에 알림이 있을 때만 건당 `xpe_get_pending_alert` **1회**입니다. **가드가 양 경계에서 큐를 비우도록 강제하므로 루프 본문은 사실상 돌지 않습니다** — 정상 상태에서 지문은 빈 큐의 상수 해시입니다.

## 미검증

- **`xpe_get_pending_alert` 구현이 계약대로 큐를 안 바꾸는지** 코드로 확인하지 않았습니다. 헤더 계약만 근거입니다. 만약 바꾼다면 가드가 스스로 상태를 오염시킵니다 — 다만 위반 0건이 유지되므로 관측된 증상은 없습니다.
- **해시 충돌**은 다루지 않았습니다. 서로 다른 큐가 같은 64비트 지문을 갖는 경우 가드가 놓칩니다.
- **512바이트를 넘는 메시지**가 이 저장소에 있는지 세지 않았습니다. 있으면 그 알림은 인덱스만 해시에 들어가, 같은 자리의 다른 긴 메시지와 구별되지 않습니다.
- **비용을 시험 단위로 재지 않았습니다** — 전체 벽시계만입니다. 분리하려면 별도 계측이 필요합니다.
- 시드 1·2·9 외의 순서는 돌리지 않았습니다.
- 공백 ②(다른 모듈 바이너리에 이 가드가 없음)는 **손대지 않았습니다** — 리더가 후속으로 잡아 뒀습니다.

## 잔여 위험

- **가드가 스스로 상태를 읽는 양이 늘었습니다.** 674 × 2회 조회는 지금 문제가 아니지만, 시험 수가 크게 늘거나 큐가 상시 비어 있지 않게 되면 루프가 실제로 돌기 시작합니다.
- **지문은 "다르다" 만 말하고 "무엇이 다른지" 는 말하지 않습니다.** 실패 메시지가 개수와 "replaced" 까지만 알려 주므로, 지목된 시험의 큐를 직접 봐야 원인을 압니다. 메시지를 통째로 싣지 않은 것은 실패 출력이 길어지는 것을 피하려는 선택입니다.
