## ① 열 수 없는 파일

**빨강** (`02_red1_run.txt`): 시험이 세 종류 모두에 대해 캐시한 뒤 읽기를 거부하는 핸들을 잡는다 (Windows: 공유 모드 0 으로 연 핸들; POSIX: mode 000, root 는 건너뜀). 통제 조건이 먼저 성립한다: 속성 조회(`file_size`·`last_write_time`)는 성공하고, 평범한 로더는 `-9`(IO_FAILED). 그런데 캐시 호출은 `0`(OK)이었고 저장소가 바뀌었다 (보정 결과 700 대신 900 등). 수정 후 초록: 미스와 같은 `IO_FAILED`, 저장소 불변, 핸들을 놓으면 같은 포인터로 적중이 돌아온다(엔트리가 지워지지 않음).
**반증 팔 W1**: 열기 확인 제거 → 이 시험만 빨강.
**비용** (3072×3072, 30회 중앙값, 3회): 적중 6.5~6.9 ms (직전 6.8 ms) — 열기 한 번의 추가분은 측정 오차 안 (`14_`).

## ② 예외와 부분 커밋 — 시험 방법

DLL 링크 시험 실행 파일에서는 이 시험이 **불가능했다**. 제품이 공유 DLL 이라 실행 파일에서 `operator new` 를 바꿔도 DLL 안의 할당에는 닿지 않는다. 그래서 같은 소스 목록(`XPE_PREPROCESS_SOURCES`)을 컴파일해 넣은 별도 실행 파일 `xpe_preprocess_oom_tests` 를 만들고 (CMake: `modules/preprocess/CMakeLists.txt`), `K = 1, 2, 3, …` 번째 할당만 `std::bad_alloc` 으로 실패시키는 스윕을 돌린다. 한 번의 호출에서 할당이 K 보다 적어지면 스윕이 끝난다. 매 K 마다 (a) 예외가 C ABI 밖으로 나가지 않는지, (b) 오류를 돌려준 평범한 로더·적중이 전역 저장소를 호출 전과 똑같이 두었는지 본다. 통제: `TheInjectionReachesAnAllocationMadeInsideAProductLoader` 가 첫 할당 실패가 실제로 제품 로더 안에 닿는지 확인한다. 스윕이 덮은 할당 지점 수는 `evidence/12_green_oom_run3.txt` 에 있다 (평범한 로더 5~7, 캐시 로더 미스 9~15, 적중 3).

**빨강** (`04_red2_run.txt`, 수정 전 제품): 7건 실패.
- 평범한 게인 로더: 할당 #7 이 실패하면 `-2`(OUT_OF_MEMORY)를 돌려주는데 **저장소가 바뀌어 있었다 (부분 커밋)**. 원인은 커밋 블록 안의 설정 JSON 복사, 그리고 커밋 뒤의 JSON 복사·품질 메타 해석·알림.
- 캐시 로더 미스 3건·적중 3건: **예외가 C ABI 밖으로 나갔다.** 덤으로 관측한 것: 예외가 나간 직후 저장소 뮤텍스가 **잠긴 채 남았다**(`try_lock` 실패, 다음 호출이 `resource deadlock would occur`). MSVC `/EHsc` 는 `extern "C"` 함수를 던지지 않는 함수로 가정해 그 함수 안 지역 객체(`lock_guard`)의 정리를 보장하지 않기 때문이다. 즉 이 가드는 "예외가 새어 나가는 것을 막는다"에 그치지 않고 잠금 누수를 막는다.

**수정**
- 캐시 로더 셋: 함수 try 블록으로 `std::bad_alloc` → `XPE_ERR_OUT_OF_MEMORY`, 그 밖은 `XPE_ERR_PROCESSING_FAILED`. 적중의 엔트리는 이제 설정 JSON 문자열 대신 **해석된 품질 메타**(평범한 구조체)를 들고 있어, 적중 경로의 할당은 키 문자열뿐이다.
- 게인 로더: 설정 JSON 복사, 품질 메타 해석, 다항식 용량 범위 해석을 모두 **커밋 앞에서** 끝낸다. 커밋은 포인터 이동과 값 복사뿐이고 던지지 않는다. 다항식 용량 범위는 전에는 커밋 뒤에 두 번째 잠금으로 썼는데 첫 커밋 블록에 합쳤다. 경고 알림은 커밋 뒤라서 `try/catch` 로 감쌌다(알림을 올리다 실패해도 적재는 성공으로 남고 경고만 유실).
- 품질 메타 갱신을 `해석`(던질 수 있음)과 `확정`(던지지 않음)으로 나눴다 (`xpe_calib_parse_quality_meta_json`, `xpe_calib_commit_quality_meta`). 이전의 `xpe_calib_apply_quality_meta_json` 은 `noexcept` 이면서 내부에서 할당했다(할당 실패 시 `std::terminate`) — 사용처가 둘뿐이라 지웠다.

**초록**: 위 13건. **반증 팔** (`11_arms_summary.txt`, 매 팔 `BUILD_EXIT=0`, 원복 후 파일 동일):

**W4 가 가르지 못하는 이유**: 알림 큐는 `xpe_common` DLL 안에서 할당하므로 이 실행 파일의 주입이 닿지 않는다. 알림 `try/catch` 는 코드 읽기에만 의존한다.

## 범위 밖에서 본 것 (고치지 않음)

- `xpe_alert_push` (`modules/common/src/xpe_common.cpp`)는 `extern "C"` 이고 가드가 없는데 `std::string` 복사와 `push_back` 으로 할당한다. 할당 실패 시 예외가 C ABI 를 넘고, 위에서 본 것과 같은 이유로 그 함수 안의 잠금이 풀리지 않을 수 있다. 이 카드의 범위가 아니라 고치지 않았고, 로더 쪽은 `try/catch` 로 막아 두었다.
- 같은 종류(`extern "C"` 안의 `lock_guard` + 할당)가 다른 수출 함수에도 있을 수 있다. 감사하지 않았다 (평범한 보정 로더 셋은 자체 `try/catch` 가 있어 스윕으로 확인됐다).
- `put_locked` 에서 목록에 넣은 뒤 색인 삽입이 던지면 목록에만 엔트리가 남는다(다음 `cache_clear` 까지 해제되지 않는 누수에 그친다). 가드 덕에 예외는 밖으로 나가지 않는다. 스윕이 이 지점을 덮었을 수 있으나 일관성 검사는 하지 않았다.

## ③ 동시 쓰기 (문서만)

`preprocess_api.h` 세 `*_cached` 문서에 "동시 쓰기는 지원하지 않는다: 보정 파일을 적재하는 동안 쓰거나 바꾸지 않는다. 속성은 조회 앞에서 한 번 볼 뿐이고, 설치 직전의 재확인도 모든 동시 재작성을 잡지 못하므로 넣지 않았다"를 적었고, `calibration_cache.cpp` 머리말과 QA-A-198 문안(REQ-P1A-102 계약)에도 같은 문장을 넣었다. 시험은 없다 (지원하지 않는 상황을 시험으로 고정하지 않는다).

## QA-A-198 문안 반영

`QA-A-198/spec_text_final.md`: REQ-P1A-102 의 문장에 "열 수 없으면 `XPE_ERR_IO_FAILED`, 저장소·엔트리 불변"과 "예외는 함수 밖으로 나가지 않는다"를, 계약 불릿에 동시 쓰기 미지원·OOM 의미(미스에서 캐시에 못 넣어도 저장소에 맵이 이미 올라가 있을 수 있음; 실패한 적중은 저장소 불변)를, REQ-P1A-103 에 커밋 전 계산과 품질 메타 보관 방식을 더했다. 근거 표에 열기 확인·할당 실패 스윕 행과 "시험이 못 가름" 두 행(알림 유실, 동시 쓰기)을 추가했다. `QA-A-191/verdict.md` 머리에는 최종 문안이 198 에 있다는 안내를 넣었다.

## Gaps / Residual-risk

- 할당 실패 스윕은 이 실행 파일에서 컴파일한 제품 소스에만 닿는다. `xpe_common`·gtest 등 DLL 안의 할당 실패(알림 큐 포함)는 주입하지 못했다.
- 스윕은 "K번째 할당 하나만 실패"를 본다. 연속 실패나 서로 다른 스레드에서의 실패는 보지 않았다.
- `XPE_ERR_OUT_OF_MEMORY` 를 미스에서 받았는데 저장소에 맵이 이미 올라가 있는 경우(캐시에 넣지 못함)는 오류 코드와 저장소 상태가 어긋난다. 문서에 적었고, 호출자가 이를 알아야 한다.
- ① 의 POSIX 쪽(`chmod 000`)은 이 Windows 기계에서 실행하지 못했다. Windows 쪽만 관측했다. 리눅스 CI 잡이 이 시험을 돌린다면 root 이면 건너뛰고 아니면 `chmod` 경로를 처음 타게 된다.
- 열기 확인과 이후 설치 사이에 파일이 잠기거나 지워지는 경쟁은 막지 않는다 (③ 과 같은 종류, 동시 쓰기 미지원에 포함).
- `xpe_preprocess_oom_tests` 는 제품 소스를 한 번 더 컴파일하므로 빌드 시간이 늘어난다 (이 기계에서 측정하지 않았다).
