# QA-A-173 (`#230`) — 병합 조건 **충족**. 312장·469,207,386 화소가 변경 전과 비트 단위로 같습니다

**병합 조건**(사용자 결정): 정확도 픽스처 전부에서 결함 지도가 비트 단위로 같을 것. 한 화소라도 뒤집히면 병합하지 않고 원인 보고.

**모든 절대 ms 의 조건**: 3072×3072 FLOAT32, AVX2, 단일 스레드, `i7-12700`, RelWithDebInfo, 워밍업 1회 폐기. 성능은 **변경 전 바이너리와 변경 후 바이너리를 번갈아 10번씩 띄워**(발사당 12라운드, 각 120관측) 최솟값을 취했습니다. 프로브 값(`117.4 → 86.1`)은 인용하지 않았습니다.

## 1. 카드가 지목한 구멍은 **실재합니다** — 그리고 그 크기를 쟀습니다

카드 §2: *"스칼라와 AVX2 는 수학적으로 같아도 결합 순서가 달라 문턱에 엡실론 거리로 붙은 화소가 뒤집힐 수 있다."*

**측정**(`evidence/01`): 무작위 `(mad, ref)` 5천만 쌍, `w = 0.10`, 값 범위 `[1, 200]`.

| σ 식 | 스칼라 `ResolveSigma` 와 **비트가 다른 비율** |
|---|---|
| 출하 벡터 식 `w*(mad*mad) + refSq` | **4.05%** (2,024,048건) |
| 스칼라와 같은 결합 `(w*mad)*mad + refSq` | **0건** |

즉 "화소의 4% 에서 σ 가 마지막 자리에서 다르다" 가 **실측**입니다. 기존 등가 시험이 그동안 통과한 것은 두 식이 같아서가 아니라 **문턱 ±1 ulp 에 붙은 화소가 프레임에 없었기 때문**입니다.

### 구현 방침이 여기서 정해졌습니다

걸침 묶음은 옛 출하에서 **스칼라 규칙**이 결정하던 화소이고, 걸치지 않는 묶음은 **옛 벡터 식**이 결정하던 화소입니다. 두 부류가 옛 출하와 같은 답을 내려면 **각자 옛 식을 그대로** 써야 합니다:

| 묶음 | 옛 출하가 쓰던 것 | 새 코드 |
|---|---|---|
| 한 타일 안 (94%) | 벡터 `w*(mad*mad)` | **그대로** |
| 타일을 걸침 (6%) | 스칼라 `(w*mad)*mad` | **레인별 참조 + 스칼라 결합** (벡터 명령으로) |

식을 하나로 통일하면 코드는 깔끔해지지만 **지도가 바뀝니다.** 그래서 주석에 *"Unifying them would be tidier and would change the map. Do not."* 이라 적었습니다.

## 2. 구현 — `runtime_detection.h` 안 `inline` 함수 둘

| 함수 | 변경 |
|---|---|
| `DetectEightPixelsAvx2` | 걸침 묶음이면 좌우 타일 참조를 `_mm256_blendv_ps` 로 레인별로 가르고, σ 를 **스칼라 결합**으로 계산. 걸치지 않으면 옛 코드 그대로 |
| `DetectRowRange` | `oneTile` 분기를 **`vectorisable`** 로 바꾸고, 스칼라 폴백은 **타일 < 8** 에만 남김 |

**제품 소스 변경은 이 헤더 하나**이고 실행 코드는 두 군데입니다. `runtime_detection.cpp` 는 그대로입니다.

### 카드 §3 넷 — 각각 어떻게 처리했는가

| 조건 | 처리 | 확인 |
|---|---|---|
| **타일 < 8** | 스칼라 폴백을 **남김**. 한 묶음이 세 타일에 걸칠 수 있어 참조 둘로는 부족. `DetectRowRange` 가 `narrowTile` 로 그 묶음을 커널에 보내지 않고, 커널도 `tileSize >= 8` 일 때만 `cut` 을 계산 | 경계 화소 시험 `Tile7`·`Tile4`, 하니스 타일 `{4, 7}` |
| **`tileSize == 0`** | `cut` 계산이 `tileSigma != nullptr && tileSize >= 8` 안에서만 일어나 **나눗셈에 닿지 않음** | 시험 `NoTileTable…`, 하니스 `__notable` |
| **`blendWeight == 0`** | `else` 가지(옛 규칙) **미수정** | 시험 `HistoricalRuleIsUnchanged`, 하니스 `__historical` |
| **스레드 경로** | 변경 없이 같은 `DetectRowRange` 를 받음. **기존 시험은 이 조합을 덮지 않았음** ↓ | 새 시험 `ThreadedRunsMatchOneThread`, 하니스 364회 |

### 넷째의 답 — **덮지 않았습니다. 실험으로 확인했습니다**

기존 `ThreadParityTest` 는 `RuntimeDetection_DefaultConfig()` 를 쓰는데, 그 기본값은 `blendWeight = 0`, `tileSigma = nullptr`, `tileSize = 0` 이라 **타일 경로 자체를 타지 않습니다.** 읽기로만 두지 않고, **스레드에만 존재하는 결함**(두 번째 밴드부터 타일 표를 무시)을 출하 코드에 심었습니다(`evidence/11`, `12`):

| | 결과 |
|---|---|
| 새 `ThreadedRunsMatchOneThread` | **실패** — 첫 불일치가 정확히 두 번째 밴드의 시작 행(2스레드 512, 3스레드 341, 5스레드 204) |
| 기존 `ThreadParityTest` 6개 | **전부 통과** |

*"덮지 않으면 단일 스레드만 검증하고 출하하는 것"* 이라는 카드의 우려가 그대로 성립했고, 이제 덮입니다.

> **정직하게 적을 한계**: `DetectFrame`(스레드 분할)은 **출하 진입점이 아닙니다.** 출하 `xpe_defect_detect_runtime` 은 단일 스레드 `DetectRowRange` 를 직접 부릅니다. 스레드 검증은 API 호출자 경로에 대한 것이고, 출하 경로의 등가는 게이트의 `__ship_rows`·`__ship_dll` 이 증명합니다.

**첫 버전이 이 위험에 약했습니다.** 뒤집히려면 σ 가 갈리고(4%) 두 문턱 사이(간격 ~1.5e-5)에 표현 가능한 화소값(간격 ~2.4e-4)이 있어야 해서(~6%) 곳당 ~0.25% 입니다 — 프레임 한 장의 2~3천 곳으로는 운이 좋아야 걸립니다(하니스가 ~3.2만 곳에서 18개를 찾은 것과 같은 비율).

### 제 시험 결함 하나 — 실패 메시지로 구분했습니다

첫 실행에서 올바른 코드에도 4개가 **실패**했습니다. 화소 불일치가 아니라 제가 넣은 공허성 단언(`EXPECT_LT(flagged, sites)`)이었습니다: 합성 타일 표(8~47)가 프레임의 실제 잡음과 안 맞아 자연 화소도 다수 표지되므로(`17,083 대 2,373`) 전체 표지 수를 경계 화소 수와 비교할 수 없었습니다. **공허성을 경계 화소 자리에서만 세도록** 고쳤습니다. 화소 불일치 단언(`EXPECT_EQ(0u, d)`)은 처음부터 통과했습니다.

### 조건·기준에 대한 주의 — 두 가지

1. **오늘 절대값은 `QA-A-172` 때보다 높습니다** — 변경 전 최솟값이 오늘 `134.4`, 그때 `117.4`(같은 조건). 기계가 느린 국면이거나 부하가 있는 것으로 보이나 **원인은 가리지 않았습니다**(카드 §3 지시). 따라서 **절대 ms 는 세션 사이에 비교할 수 없고, 같은 세션 안의 비(0.71)만 유효**합니다. 참고로 프로브가 낸 비는 `86.1 / 117.4 = 0.733` 이었습니다.
2. **하한 `76 ms` 와의 비를 오늘 값으로 적지 않습니다.** 하한은 다른 세션의 측정이고, 오늘 값과 나누면 *"두 항이 같은 기준이어야 한다"*(카드 §4)를 어깁니다. **같은 세션의 하한 재측정 없이는 `≤ 1.3배` 판정을 하지 않았습니다** — 필요하면 리더가 정하십시오. 오늘 **변경하지 않은** 타일 σ 단계도 `73.4 ~ 77.5` 로 `QA-A-172` 의 `63.1` 보다 16~23% 높아, 전체가 느려진 것(변경 전 최솟값 +15%)과 **같은 방향**입니다 — 기계 국면 탓이라는 **가설과 부합하지만 확인은 아닙니다.**

## 12. 미검증 / 잔여 위험

- **비트 동일은 증명이 아니라 관측입니다.** 근거는 셋: ① 구성(걸침은 옛 스칼라 결합, 아닌 것은 옛 벡터 식, 참조 식은 같은 순서), ② 50M 표본에서 스칼라 결합의 불일치 0건, ③ 게이트 312장. ②의 표본은 `w = 0.10`, `mad, ref ∈ [1, 200]` 범위이고 **그 밖은 재지 않았습니다**
- **실영상은 `CalData_6` 한 검출기 7장**입니다. 다른 장비·프레임 크기·다른 노출 조건은 덮지 않습니다
- **경계 프레임의 타일 표는 프레임과 무관한 고정값**입니다(문턱 화소를 정확히 세우려고). 프레임에서 유도한 실제 표(`__ship_rows`)에는 별도 픽스처가 있으나, 경계 화소는 **표를 고정한 구성에서만** 정확합니다
- **`DetectFrame` 의 스레드 검증은 출하 경로가 아닙니다**(§2)
- **위험 화소 시험은 `#if XPE_DETECT_HAS_AVX2` 안**에 있습니다. AVX2 가 없는 빌드는 이 시험을 건너뜁니다(`SPEC §4.6` 이 AVX2 를 최소 요건으로 하므로 저장소 빌드에는 해당 없음)
- **위험 화소 탐색은 확률적**(사이트당 최대 12,000회 시도)이고 찾지 못한 사이트는 건너뜁니다. 시험이 `sites > 40` 을 단언하지만 시드 변경 시 사이트 수가 달라질 수 있습니다
- **오늘 절대 성능은 이전 세션보다 느린 기계에서 잰 값**이고 원인을 가리지 않았습니다. 변경 후 `전체 − 합 = 8.9 ms` 는 설명하지 못했습니다
- 게이트는 **`RelWithDebInfo`·MSVC 2022** 에서만 돌렸습니다. 다른 컴파일러가 `mul+add` 를 FMA 로 융합하면 결합이 달라질 수 있습니다(지금 빌드에서는 오라클과 실제 코드가 일치함을 팔 B 가 확인)
- 반증 팔은 **임시 헤더 편집 → 재빌드 → 복원**이었고 복원은 해시로 확인했습니다. 최종 게이트는 복원 뒤 바이너리로 **다시** 돌렸습니다(`evidence/03`, `04`)
