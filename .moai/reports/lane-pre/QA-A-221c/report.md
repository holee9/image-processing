## 1. 원인 값이 앞 단계의 것일 수 있다

### 1.1 확인한 것

Codex 의 지적이 맞다. `capture_io_reason()` 은 `errno` 와 `GetLastError()` 를 읽는데 둘 다 성공한 호출이 지우지 않는다. 옛 코드는 임시 파일을 연 직후 **한 번** 지운 뒤 헤더·설정·payload·flush·close 를 차례로 실행하고 마지막에 한 번 캡처했다. 주석("실패 동작 직전에 지운다")과 구현이 달랐다. 운영체제가 설명하지 않는 실패(스트림 자신의 failbit — 스트림 안에서 버퍼 할당이 실패한 경우 등)는 앞의 **성공한** 단계가 남긴 값으로 보고된다.

### 1.2 시험을 만들 수 있었다 (그래서 "원인 불명" 폴백으로 대신하지 않았다)

시험 전용 이음새를 하나 두었다. 각 스트림 동작 직후, 결과를 판정하기 전에 불리는 `xpe_xcal_write_step_hook(step, stream)`(1 헤더, 2 설정, 3 payload, 4 flush, 5 close). **할당 실패 시험 실행 파일만** `XPE_CACHE_TEST_HOOKS` 로 컴파일하고, 출하 DLL 에는 선언도 호출도 없다 — DLL 바이트에서 `xpe_xcal_write_step_hook` 0건, `xcal_step` 0건, 대조군 `xpe_preprocess_init` 1건(`evidence/20`).

시험 `AWriteFailureIsReportedWithItsOwnCauseNotWhatAnEarlierStepLeftBehind`: 고른 단계 **앞의** 모든 단계 뒤에 `errno = EINVAL`, `SetLastError(1234)` 를 남기고, 고른 단계는 OS 오류 없이 스트림 상태(`badbit`/`failbit`)로만 실패시킨다. 알림은 `the system reported no error code` 여야 하고 `1234`·`errno 22` 를 담으면 안 된다. 먼저 실패를 넣지 않은 실행으로 어느 단계가 도는지 확인하고(1·2·3·4·5 모두 돎), 도는 단계마다 반복한다.

### 1.3 수정 전 빨강, 수정 후 초록

- 수정 전(`evidence/10`): 단계 **2·3·4·5 가 빨강** — 알림이 `errno 22: Invalid argument, Windows error 1234` 를 원인으로 적었다. 단계 1 은 통과했다(앞에 남은 단계가 없다).
- 수정 후(`evidence/11`): 통과.

### 1.4 수정

`xcal_writer.cpp`: 쓰기 블록을 동작마다 `clear_io_reason()` → 동작 → `settle(step)`(훅 호출, 결과 판정, 실패면 곧바로 `capture_io_reason()`)으로 바꿨다. 열기 직후의 한 번짜리 지움은 헤더 쓰기 직전의 지움이 대신한다. 열기 실패 쪽의 지움(블록 맨 앞)은 그대로다.

### 1.5 반증 (한 번에 하나, 전체 빌드, `evidence/30_arm_*`)

| 손상 | 빨강이 된 단계 |
|---|---|
| c1 설정·payload·flush·close 직전의 지움을 모두 제거 | 단계 **2·3·4·5**(옛 동작과 같다) |
| c2 flush 직전의 지움만 제거 | 단계 **4 만** |
| c3 close 직전의 지움만 제거 | 단계 **5 만** |

그래서 각 지움이 따로 시험으로 지켜진다. 단계 1(헤더) 직전의 지움은 헤더 앞에 성공 단계가 없어 이 시험으로는 가려지지 않는다 — 열기 직후의 값이 헤더 쓰기 실패 원인으로 새는 경로는 212d 의 `ATemporaryFileThatCannotBeCreated…` 계열이 열기 쪽에서만 다룬다. 이 카드에서 단계 1 앞의 지움을 따로 반증하지 않았다(§5).

## 2. 다이제스트 (낮음)

`storeDigest()`(`test_oom_injection.cpp`)가 세 **너비**와 맵 바이트만 보고 **높이와 맵의 존재 여부를 보지 않았다.** 이제 맵마다 존재 여부·너비·높이·(있으면) 바이트를 섞는다. 포함하지 않는 것: 게인 다항식, 비선형 LUT, 품질 메타데이터, 타임스탬프, 만료값(코드 주석에도 적었다).

시험 `TheStoreDigestTellsStoresApartByPresenceAndByEveryDimension`: 적재된 저장소에서 한 번에 하나만 바꿔(높이 셋, 오프셋 너비, 맵 셋의 부재) 다이제스트가 달라지는지, 원복하면 원래 값으로 돌아오는지(대조) 본다.

| 손상 | 결과 |
|---|---|
| d1 다이제스트가 높이를 무시 | 시험 빨강: `offset/gain/defect height + 1` 셋 모두 못 봄 |
| d2 다이제스트가 존재 플래그를 무시 | **빨강이 안 됨** |

**d2 가 안 터진 이유**: 맵이 있으면 그 바이트가 해시에 들어가므로 "맵 부재"는 존재 플래그 없이도 이미 다르게 보인다. 플래그가 혼자서만 구별하는 두 저장소는 맵 바이트가 0 개일 때뿐인데 이 시험의 맵은 항상 N > 0 이다. 즉 이 장치에서 플래그는 **프레이밍(가변 길이 표현의 명시)** 이지 새 구별력이 아니다. 카드가 존재 여부를 넣으라 했고 비용이 없어 남겼으나, 반증이 안 터졌다는 사실은 숨기지 않는다.

221b 의 기존 빈 저장소 시험 3건(`AFailedPipelineThatStartedOnAnEmptyStore…`·`AFailedCachedOffsetLoad…`·원자적 교체)은 새 다이제스트로도 통과한다.

## 3. "알림 없는 IO_FAILED 0" 한정 (낮음)

- 이 문장은 QA-A-221 이 아니라 **QA-A-212d 보고서**(9행, 76행)에 있었다. 두 곳을 "알림 구성이 성공하는 한"으로 한정하고, 구성이 메모리 부족으로 실패하면 알림 없이 -9 가 나간다고 적었다(`report_*` 함수가 문자열 구성·푸시 예외를 삼킨다, `xcal_writer.cpp` 주석에 이미 있음).
- 헤더 `xpe_calib_save` 의 `XPE_ERR_IO_FAILED` 항목에: 실패한 저장은 단계와 시스템 오류를 담은 `XPE_ALERT_ERROR` 를 내되 알림 문구를 만들 수 있는 동안만이며, 만들다 메모리가 부족하면 알림은 버려지고 반환 코드가 항상 오는 유일한 신호라고 적었다.
- 무할당 진단 경로는 만들지 않았다(카드 지시).
- 같은 진술이 221b 보고서에도 있었다: "디지스트는 맵 세 개와 치수를 본다"는 사실과 달랐다(너비·바이트뿐). 그 문장을 정정했다.

## 5. 미검증 (Gaps)

- 시험은 **오류 코드를 시뮬레이션**한다(훅이 `errno`·`SetLastError` 를 직접 심음). 실제 OS 가 앞 성공 단계에서 이런 값을 남기는지는 이 카드에서 관측하지 않았다. 실제 OS 가 보고하는 쓰기 실패(바이트 범위 잠금)는 212d 시험이 이미 다룬다.
- 단계 1(헤더) 직전의 지움은 반증하지 않았다(§1.5).
- 훅은 Windows 용 `SetLastError` 부분을 `_WIN32` 에서만 쓴다. POSIX 에서는 `errno` 만 검사하며 이 환경에서 돌려 보지 않았다.
- 존재 플래그의 구별력은 확인하지 못했다(§2).
- 알림 구성 실패(OOM 겹침)로 알림 없이 -9 가 나가는 경로는 시험하지 않았다. 문장 한정과 헤더 한 줄뿐이다.

## 6. 잔여 위험
