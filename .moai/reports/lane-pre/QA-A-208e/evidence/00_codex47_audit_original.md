# QA-A-208d 독립 검토

범위: `D:/workspace-github/xpe-pre`의 `96a67d97..79d2e9c5 -- modules`, 레인 보고서와 ABI 비교 증거, 이전 #45 지적. 코드·시험을 대조했으며 빌드와 시험을 새로 실행하지는 않았다.

## 발견 1 — 보통·차단: 공개 API 설명에 옛 표지값 규칙이 남음

- **무엇:** `modules/preprocess/include/xpe/preprocess_api.h:1622-1629`의 `xpe_calib_get_quality_meta` 설명은 여전히 `r_squared != -1.0`인 유효 기록만 이력이 된다고 하며, `-1.0`을 “not given”으로 설명한다. 같은 헤더의 새 구조체 설명과 `r2_history_after` 구현은 `has_r_squared`·`has_previous_r_squared`로 존재를 판단하고 실제 `-1.0`을 허용한다. `valid=0`일 때 `previous_r_squared` 이외 모든 필드가 0이라는 문장도 새 `has_previous_r_squared=1` 이력과 충돌한다. #45의 공개 계약 동기화가 헤더 전체에서는 끝나지 않았다.
- **재현:** 첫 기록 A의 R²를 정확히 `-1.0`으로 적재하고 다음 기록 C를 적재한다. 새 구현에서 C의 `previous_r_squared=-1.0`, `has_previous_r_squared=1`이지만 위 API 설명을 따르면 이력을 “없음”으로 해석한다. 품질 없는 기록 뒤에도 이력 플래그가 1일 수 있다.
- **고칠 방향:** 해당 함수 설명을 플래그 기준으로 고치고, 품질 없는 기록에서는 현재 기록 필드만 비며 이전 값과 `has_previous_r_squared`는 유지된다고 명시한다. 헤더의 Fields·멤버·함수 설명을 한 계약으로 맞춘다.

## 발견 2 — 보통·차단: 새 헤더와 구 DLL의 플래그 읽기 제한이 공개 계약에 없음

- **무엇:** ABI 증거는 세 헤더의 `sizeof=88` 및 기존 멤버 오프셋 일치를 보여준다. 새 DLL을 구 헤더 호출자가 읽는 구조 크기는 맞지만 구 호출자는 새 두 플래그를 알 수 없어 실제 `-1.0`과 부재를 구분하지 못한다. 반대로 새 헤더 호출자가 구 DLL의 `xpe_calib_get_quality_meta`를 호출하면 오프셋 4·73은 구 DLL의 패딩이며 새 플래그 값은 미정이다. 레인 보고서는 이 제한을 인정하지만 공개 헤더의 구조체 및 함수 설명에는 구 DLL과 섞어 쓰지 말라는 경고나 버전 확인 방법이 없다. 크기·오프셋 일치만으로 의미상 양방향 호환이 보장되지는 않는다.
- **재현:** 새 헤더로 `has_r_squared`를 읽는 호출자를 빌드해 208d 이전 DLL과 조합한다. 해당 DLL은 오프셋 4를 플래그로 쓰지 않으므로 값 0/1의 의미를 보장하지 않는다. 구 헤더 호출자는 208d DLL의 정확히 `-1.0` 이력 존재 여부를 표현할 필드가 없다.
- **고칠 방향:** 공개 헤더의 `XpeCalibQualityMeta` 및 getter 문서에 양방향 제한을 명시하고, 새 플래그를 사용하는 호출자는 지원 DLL 버전을 확인하도록 안내한다. 필요하다면 버전 확인이 가능한 ABI 경로를 제공한다.

## 확인한 구현과 체인

- #45의 값 충돌은 구현상 해결됐다. 파서는 `fit_r_squared` 키가 있으면 유한한 `≤1.0` 값을 플래그 1로 받고, 생성 기록은 플래그 1을 세운다. `r2_history_after`는 값이 아닌 두 플래그를 세 경로(생성·품질 적재·무품질 적재)에 전달한다. 캐시의 적중 설치도 품질 사본을 `xpe_calib_commit_quality_meta_locked` 또는 `xpe_calib_commit_no_quality_locked`로 넘긴다. 정확히 `-1.0`의 파일·기록·이력 시험과 ABI 정적 단언을 확인했다. 실제 생성기 입력에서 `-1.0`이 나오는 전체 생성→재적재 시험은 레인도 미실시로 기록했다.
