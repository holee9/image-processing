# QA-A-210e — 생성기가 성공이라 기록한 다항식은 적용기가 쓸 수 있어야 하고, 보고하는 R² 는 적용 결과의 것이어야 한다 (Codex #61, Refs #233)

기준: `main`(`08ea24fd`)을 받은 dev/preprocess(`117b3b75`, 210d 위). 증거: `evidence/`.

## 1. 바꾼 것

1. **적용기와 생성기가 같은 산술을 쓴다 — 공유** (`xpe_preprocess_internal.h`): `xpe_gain_poly_eval_f32`(저장 float32 계수를 float32 Horner 로, 화소값을 float 으로 평가), `xpe_gain_value_valid` + 상수 `XPE_GAIN_APPLIED_MIN/MAX`(적용기가 받아들이는 게인 범위 [0.001, 1000]). `gain_correct.cpp` 의 Horner 루프와 `is_valid_gain` 은 이 함수를 부른다(동작 불변 — 아래 실데이터 비교). 두 번 구현하지 않았다.
2. **저장 후 검증** (`xpe_calib_generate_gain.cpp`): 단조 검사를 통과한 차수마다, 저장할 float32 계수를 **적용기와 같은 산술**로 모든 측정 선량에서 평가해 (a) 적용기가 받아들이는 게인이고 (b) 의도한 값(같은 적합의 double 계수를 double 로 평가)과 `kApplyTolerance = 0.1%` 이내일 때만 채택. 아니면 차수를 낮춘다(비단조와 같은 경로). 곡선이 단조이므로 구간 전체의 극값은 첫·마지막 선량에 있어 측정 선량에서 검사하면 범위 전체의 유효성을 덮는다.
3. **1차에서도 실패하면 그 화소를 명시적으로 거부**: 세어 두고 루프 뒤에 생성 전체를 `XPE_ERR_INVALID_CALIB_DATA` 로 거부 — 품질 기록·파일 쓰기 **전**에. (비유한 게인 값, 해석 불가 적합과 같은 "이 데이터로 보정을 만들 수 없다" 코드.) 알림 `XPE_WARN_GAIN_POLY_NOT_APPLICABLE: <N> pixel(s) (first: <i>) have no gain polynomial whose float32 coefficients the applier can use …; no file was written` (XPE_ALERT_ERROR) — 문구는 레인 간 계약이므로 보고서에 적는다(`preprocess_api.h` 에도).
4. **R² 를 적용 기준으로**: 화소별 잔차를 저장 float32 계수 + float32 Horner + float 선량으로 계산(이전엔 double 계수·double 산술). `max/mean_residual_pct` 도 같은 예측.

저장 형식은 바꾸지 않았다(원시 계수 유지). 중심화 유지(리더 결정).

### 허용치 근거 (`kApplyTolerance = 1e-3`)

적용기가 만든 게인과 적합이 의도한 게인의 상대 차이 0.1%. (i) 게인 검증이 허용하는 평탄장 잔차 1% 의 10분의 1, (ii) 실데이터의 준위 간 흩어짐(약 0.3%, QA-A-210b)보다 작아 정상 데이터에서는 발동하지 않는다(아래 실데이터 비교: 9.4M 화소 전부 불변), (iii) 이를 넘으면 저장된 다항식은 더 이상 그 적합이 아니다.

## 3. 정상 데이터에서의 변화 — cyan_test 전체 (3072² = 9,437,184 화소, 5준위)

옛(`6d363524` DLL 사본)과 새 생성기, 같은 입력 (`11_old_vs_new_full_cyan_test.txt`):

| | 최대 차수 2 | 최대 차수 3 |
|---|---|---|
| 채택 차수가 바뀐 화소 | **0** | **0** |
| 양쪽 2차 이상 화소의 계수 비트 동일 | **100%** (1,248,644) | **100%** (1,351,162) |
| 같은 차수에서 비트가 다른 화소 | 0 | 0 |
| 파일 R² 옛 → 새 | 0.252129038 → 0.252129036 | 0.253331175 → 0.253331174 |

저장된 계수는 전 화소 비트 동일이고, 기록되는 R² 만 1e-9 단위로 달라진다(float32 산술 기준이 됐으므로). 정상 데이터에서는 새 검증이 아무 화소도 거부하거나 차수를 바꾸지 않는다.

## 4. 미검증 (Gaps)

- 허용치 0.1% 는 근거를 댄 선택이지 SRS 의 값이 아니다. 바꾸려면 `kApplyTolerance` 한 곳.
- 검증은 **측정 선량**에서만 평가한다. 단조 곡선의 극값이 끝점에 있다는 논리로 범위 전체를 덮지만, 반올림이 곡선의 내부에서 유효 범위를 넘기는 병적인 경우(게인이 범위 경계에 거의 닿은 데이터)는 보지 못한다.
- 적용기는 화소값을 정수로 받아 `float` 으로 쓰고(선량이 정수가 아닌 경우 측정 선량의 float 과 정확히 같은 화소값은 없다), 구간 밖은 클램프한다. 생성기는 측정 선량(`float(선량)`)에서 평가하므로 그 사이의 정수 화소값은 직접 평가하지 않는다.
- `xpe_calib_generate_gain`(단일 선량 게인 맵)에는 이 검증이 필요 없어(다항식이 아님) 건드리지 않았다.
- 데이터는 cyan_test 한 세트.

## 5. 잔여 위험

- 이전에 "성공" 으로 만들어지던 병적 입력(가까운 선량, 범위 밖 게인)은 이제 `INVALID_CALIB_DATA` 로 실패한다 — 호출자가 그 코드를 처리해야 한다. 이미 만든 파일은 그대로 읽힌다.
- 알림 문구 `XPE_WARN_GAIN_POLY_NOT_APPLICABLE:` 는 레인 간 계약이다.

## 6. 보충 (리더 질문): 한 화소만 실패해도 교정 전체가 실패하나? 결함 화소가 있는 데이터에서는?

**예 — 한 화소라도 1차에서 실패하면 생성 전체가 `INVALID_CALIB_DATA` 다.** 그 이유는 적용기가 이미 그렇게 동작하기 때문이다: `xpe_gain_correct` 는 프레임의 **모든** 화소의 게인을 평가해 하나라도 `is_valid_gain` 을 통과하지 못하면 프레임 전체를 `CONFIG_INVALID` 로 거부한다. 이전 생성기는 그 파일을 "성공"으로 쓰고 실패를 적용 시점으로 미뤘다. 이번 변경은 같은 실패를 생성 시점으로 당겼다(카드 요구).

**결함 화소가 있는 실데이터에서 잰 것** (`evidence/13_bpm_data_rejections.txt`, `15_old_file_on_caldata6.txt`; 스크립트 `12_m210e_bpm.py`, `14_m210e_bpm2.py`):

| 데이터 | 입력 | 새 생성기 | 옛 생성기의 파일을 적용하면 |
|---|---|---|---|
| **CalData_6** (3072², 6준위, 결함 맵 `BPMap.map` 23,505 화소 = 0.249%) | `generate_gain` 의 게인 맵에 값 0 이 있고 최대 186.8 (적용기 범위 [0.001, 1000] 밖 값 7개) | **42 화소(결함 맵의 0.18%)** 가 걸려 생성 전체 거부 (`INVALID_CALIB_DATA`, 최대 차수 2·3 모두) | 옛 생성기는 `OK` 로 파일을 썼고, 적재는 `OK`, 그러나 **`xpe_gain_correct` 가 시험한 세 프레임 모두 `CONFIG_INVALID`** |
| cyan_test (5준위, `BPM.raw` 결함 250 화소 = 0.0026%) | 결함 화소의 게인도 정상 범위(0.807~1.115) | 0 화소, 정상 생성 | 정상 |

- 걸린 42 화소는 **전부 결함 맵 안**에 있다(밖 0). 결함 화소 23,505 개 중 나머지 23,463 개는 걸리지 않는다. 걸리는 화소는 게인이 0(죽은 화소) 또는 수백인 극단 값이다.
- 즉 CalData_6 같은 결함 화소 데이터에서는 새 생성기가 교정을 만들지 않지만, **이전에 만든 파일도 어떤 프레임에도 쓸 수 없었다** — 사용성은 줄지 않았고 실패가 일찍 보이게 됐다.
- 다만 이것이 의도한 정책인지는 리더 결정 사항이다. 선택지:
  1. **현행(거부)**: 단순하고 적용기와 일관된다. 결함 화소를 미리 처리한 게인 맵(또는 결함 화소를 정상 게인으로 치환한 맵)을 호출자가 넘겨야 한다. 스칼라 게인 맵도 같은 철학이다(`xpe_calib_load_gain` 이 [0.1, 10] 밖 값을 가진 맵 전체를 거부).
  2. **결함 화소를 중립 다항식(게인 1)으로 저장하고 개수를 알림으로 알림**: 생성은 성공하지만, 결함 화소의 게인이 틀렸다는 사실을 파일이 품는다(결함 보정 단계가 그 화소를 나중에 고치므로 영향은 작다). 생성기에 결함 맵 입력이 없으므로 "어느 화소가 결함인가" 는 모르고 "적용기가 못 쓰는 화소" 만 안다 — 정상 화소의 진짜 문제도 조용히 덮을 위험이 있어 개수에 상한(예: 0.5%)을 두는 것을 권한다.
  3. 생성기에 결함 맵 입력 추가(API 확장): 가장 정확하지만 공개 API 변경.
  이 보충에서는 코드를 바꾸지 않았다. 결정이 나면 카드로 받겠다.
