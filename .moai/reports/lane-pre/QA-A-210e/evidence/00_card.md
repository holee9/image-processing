# QA-A-210e — Codex #61 보류: 저장 계수로 적용하면 유효한 게인이 거부됨 (#233)

보낸이: xpe-leader · 감사 원문: 메인 리포지토리 `.moai/state/codex-archive/61.md`.

**알림**: pre 체인(`2ffd7160` 까지)은 main 에 푸시됐다(`cacb34c9`, CI 초록). api-spec §6.20 에 209~210c 계약을 적었다.

Codex 확인: #58 두 건 해소 — 해석적 단조 판정이 차수 1–4 의 모든 분기(퇴화·중근·끝점)를 덮고 저장 float32 계수로 판정, 비유한 선량은 모든 부작용 전에 거부, 게인 비유한은 품질 기록·파일 쓰기 전에 거부.

## 발견 (높음)

R² 는 반올림 전 double 계수와 double 선량으로 계산하는데, 실제 `xpe_gain_correct` 는 저장된 float32 계수를 float32 Horner 로, uint16 화소에서 만든 float32 선량에 평가하고 하한 0.001 을 검사한다. 큰 절편·기울기의 상쇄가 float32 에서 사라지면 생성기가 R² ≈ 1 로 기록한 파일이 적용 시 `CONFIG_INVALID` 가 된다. 재현(Codex 계산, DLL 실행 아님): 선량 `[1000, 1000.00001, …, 1000.00004]`, 게인 `0.001 + 5×(dose−1000)`, 차수 1 → 저장 `[-5000, 5.000000953674316]`, 화소 1000 에서 float32 Horner 0.0009765625 < 0.001.

리더 판단: 입력은 병적이다(선량이 1e-5 ADU 차이). 그러나 원칙은 같다 — **생성기가 성공이라 기록한 파일은 적용기가 쓸 수 있어야 하고, 보고하는 품질은 실제 적용 결과의 것이어야 한다.** 중심화 유지 결정은 그대로다.

## 할 것

1. 저장 형식은 바꾸지 않는다(원시 계수 유지 — 형식 변경은 적용기·파일 호환까지 번진다). 대신 **저장 후 검증**: 저장할 float32 계수로, 적용기와 같은 산술(float32 Horner, 화소 → 선량 변환, 클램프·하한)을 써서 각 측정 선량에서 예측 게인을 계산하고, 유효 범위 밖이거나 측정값과의 차이가 정한 허용치(근거를 대고 정할 것 — 예: 측정 잡음 크기)를 넘으면 차수를 낮추고, 1차에서도 실패하면 그 화소를 **명시적으로 거부**(어떤 코드로, 어떤 알림/품질 표시로 — 기존 실패 경로와 일관되게)
2. 보고하는 R² 를 이 저장·적용 기준 예측으로 계산(옛 값과 실데이터에서 비교해 차이를 보고)
3. 적용기와 생성기가 같은 평가 함수를 공유할 수 있으면 공유(두 번 구현하지 말 것). 못 하면 이유
4. 시험: 위 재현을 생성 → 적재 → `xpe_gain_correct` 종단 시험으로(빨강 먼저). 정상 데이터(cyan_test 축소본)에서 결과 불변 또는 차이 보고. 반증: 저장 후 검증을 지우면 종단 시험 빨강
