# QA-A-108 — 성능 게이트 `Frame3072SquaredWithinMachineRatio` 추적 (#179)

## 1. 주장

1. **분모가 빨라진 것이 아니라 분자가 느려졌다.** 두 실패 실행 모두 기준 커널은 평소 범위 안(110.9 / 123.1 ms)인데 검출기가 107.8 / 144.3 ms 로 통과 표본(53.2–106.4 ms)의 위 끝을 넘었다.
2. **검출기 코드 경로에 닿은 변경은 0줄이다** — 소스·빌드 옵션·공용 헤더·링크 라이브러리 전부.
3. **비율은 기계를 상쇄하지 못한다.** 분자와 분모가 서로 다른 것에 병목이 걸려 있고, 컴파일 옵션까지 다르다. 이것이 로컬 0.65–0.70 대 CI 중앙값 0.567 차이의 원인이다.
4. 따라서 **게이트 설계가 약하다.** 코드 회귀 없이 비율이 1.17 까지 오를 수 있다면 0.85 한계는 코드가 아니라 러너를 재고 있다.
5. 다음 실패를 바로 읽을 수 있도록 **러너 프로필 출력을 시험에 추가**했다(단언·기준 커널 불변).

## 2. 증거

### 2.1 두 실패 실행의 분모/분자 (아티팩트 `Temporary/LastTest.log`)

| 실행 | 기준 커널 | 검출기 3072² | 비율 | 검출기 1024² | 3072/1024 |
|---|---|---|---|---|---|
| 35279494289 시도1 (f1bafba) | 110.9 | 107.8 (126.8/145.4/139.8/119.5/107.8) | 0.972 | 10.9 | 9.89 |
| 35279494289 시도2 | 123.1 | 144.3 (173.4/172.2/171.0/144.3/150.2) | 1.172 | 11.0 | 13.1 |
| c72f0e8 (통과) | 122.1 | 57.6 | 0.472 | 6.5 | 8.86 |
| cedce22 (통과) | 163.8 | 91.1 | 0.556 | 10.2 | 8.93 |
| e119331 (통과) | 163.7 | 93.0 | 0.638 | 10.4 | 8.94 |
| 로컬 (i7-12700) | 97.1 | 63.1 | 0.649 | 6.6 | 9.56 |

읽는 법 두 가지:
- **분모는 정상이다.** 실패 실행의 기준 커널 110.9·123.1 ms 는 가장 빠른 통과 실행(112.7·122.1)과 같은 등급이다. 분모가 작아져서 비율이 오른 것이 아니다.
- **분자가 크기에 비례해 더 느려진다.** 실패 실행에서 1024² 는 통과 실행 대비 +5~70% 인데 3072² 는 +55~160% 다. 시도2 의 3072/1024 비(13.1)는 통과 실행 세 건(8.86–8.94)에서 완전히 벗어난다. 명령어 집합이 달라졌다면 두 크기가 같은 비율로 느려졌을 것이므로, **크기 의존적 — 즉 메모리 쪽** 원인이다.

### 2.2 검출기 코드 경로 재확인 (카드 2항)

```
git diff --stat cedce22..f1bafba -- modules/preprocess modules/common   → 출력 없음
git diff --name-only cedce22..f1bafba  → enhance_basic / enhance_advanced / SPEC 문서만
```
- 빌드 옵션: `modules/preprocess/CMakeLists.txt:77` `/W4 /arch:AVX2` — 구간 내 변경 없음.
- 링크: `bcrypt` 는 QA-A-106(`6f06266`)에서 추가됐고 그 뒤 통과 실행 두 건(c72f0e8 0.472, cedce22 0.556)이 있다.
- `modules/common` 에 -17(`XPE_ERR_INVALID_CALIB_DATA`)이 추가된 것은 `2d08cdc` 로, 실패 실행 `f1bafba` **이후**다. 이 실패의 원인일 수 없다.
- 러너는 `runs-on: windows-2025`(GitHub 호스팅, 잡마다 별도 VM) — 레인 간 경합은 배제된다.

### 2.3 비율이 기계를 상쇄하지 못하는 구조적 이유

| | 분자 (검출기 3072²) | 분모 (기준 커널) |
|---|---|---|
| 접근하는 데이터 | 36 MB 프레임 + 9.4 MB 맵 | 16 MB 버퍼 12회 스윕 |
| 병목 | 메모리 대역폭 | 캐시 상주 후 연산 |
| 컴파일 | `xpe_preprocess`, `/arch:AVX2` | 시험 바이너리, 기본 아키텍처 |

두 축(대역폭 / 코어 처리량)이 기계마다 독립적으로 변하므로 비율은 "기계"라는 하나의 값으로 약분되지 않는다. 문서에 이미 적힌 P코어 0.651 대 E코어 0.630 도 같은 현상의 작은 판이고, 이번 CI 실패는 큰 판이다.

### 2.4 러너 프로필 출력 (카드 3항)

`test_runtime_detection_performance_gate.cpp` 에 `PrintMachineProfile()` 추가 — CPU 브랜드 문자열(`__cpuid` 0x80000002–4), 논리 코어 수, AVX2 지원 비트, 그리고 **스트리밍 읽기 대역폭 프로브**(256 MB, 캐시 라인당 1 float, 최소 3회). 대역폭을 넣은 이유는 2.3 의 가설을 다음 실패에서 바로 확인·반박할 수 있게 하기 위해서다.

로컬 실행 결과(`BUILD_EXIT=0`, `RUN_EXIT=0`):
```
[perf-gate-machine] cpu="12th Gen Intel(R) Core(TM) i7-12700" logical=20 avx2=1 bandwidth=25.5 GB/s
[perf-gate-machine] numerator=xpe_preprocess(/arch:AVX2) denominator=in-test kernel(default arch)
[perf-gate-ratio] 3072 ratio=0.649 limit=0.850
```
단언·한계·기준 커널은 손대지 않았다. 워크플로 변경은 필요 없다(시험이 직접 출력하므로 아티팩트에 남는다).

## 3. 기준 귀속
- CI 값: `gh api .../artifacts/<id>/zip` 로 내려받은 `Temporary/LastTest.log`(실행 35279494289 시도1·2, 아티팩트 10522528723 포함).
- 로컬 값: `build/ci-preprocess` RelWithDebInfo, i7-12700, 위 로그 원문.
- 코드 경로: 위 `git diff` 두 명령의 실제 출력.

## 4. 미검증
- CI 러너의 CPU 모델·대역폭은 **아직 모른다.** 새 출력은 다음 실행부터 남는다. 2.3 은 그때 확인되거나 반박된다.
- 실패 실행 시점의 러너 동시 부하는 관측 수단이 없다.
- 대역폭 프로브 자체는 로컬 한 기계에서만 검증했다.
- 기준 커널을 `/arch:AVX2` 로 맞췄을 때 비율이 어떻게 변하는지는 재지 않았다(모든 과거 비율이 이동하므로 리더 결정 없이 하지 않는다).

## 5. 잔여 위험 · 선택지 (결정은 리더)

한계 상향(D)은 여전히 권하지 않는다 — 통과 표본 최대가 0.638 이고, 1.17 을 통과시키려면 가장 가까운 회귀(E코어 1.289)와의 간격이 9% 로 좁아져 게이트가 사실상 사라진다.

| 선택지 | 내용 | 영향 |
|---|---|---|
| **A. 여러 실행의 최소값 (권장)** | 같은 잡에서 비율을 3회 재고 **최소값**으로 판정 | 일시적 대역폭 변동에 강하다. 진짜 회귀는 세 번 다 느리므로 그대로 잡힌다. 비용 약 +2×3초 |
| B. 절대 시간 + 기준 기계 | 러너 프로필로 기계 등급을 식별하고 등급별 ms 예산 | 가장 정확하지만 기계 목록 유지가 필요. 프로필 출력이 그 전제를 만든다 |
| C. 통계적 판정 | 최근 N회 CI 비율의 분포로 이상치 판정 | 이력 저장소가 필요(현재 없음) |
| D. 한계 상향 | 0.85 → 1.2 등 | **반대.** 근거 없고 회귀와의 간격이 사라진다 |
| E. 기준 커널을 검출기와 같은 특성으로 | 대역폭 병목 커널로 교체 | 문서가 금지(기준이 대상을 따라가면 회귀를 못 본다). 다만 `/arch` 불일치만 맞추는 것은 별개 논의 |

main 이 이 시험 하나로 빨간 상태이므로, A 를 다음 카드로 받거나 그 사이 이 시험만 한시적으로 제외(사유·복구 조건·#179 링크를 코드에 명기)하는 선택지도 있다 — 둘 다 리더 결정 사항이다.
