# QA-A-68 — 컴파일러가 한다는 주석을 확인한다

**카드**: `.moai/lanes/pre/inbox/QA-A-68.md` · **브랜치**: `dev/preprocess` · **기계**: Intel Core i7-12700 · **컴파일러**: MSVC 19.44.35228.0

---

## 1. 주장 (Claim)

| # | 주장 |
|---|---|
| C1 | **주석은 틀렸다.** MSVC 는 `MedianSortCE` 를 `vminss`/`vmaxss` 로 낮추지 않고, `MedianOfEight` 는 **분기가 4개 남아 있다** |
| C2 | 확인 방법은 `/FAs` 어셈블리 출력이며, 배송 라이브러리와 같은 플래그로 컴파일했다 |

## 2. 증거 (Evidence)

### C2 — 무엇으로 확인했는가

스크래치패드에 작은 TU 하나(`a68_asm.cpp`)를 두고, 배송 라이브러리와 같은 플래그로 어셈블리를 뽑았다:

```
cl /c /O2 /arch:AVX2 /DNDEBUG /EHsc /std:c++17 /FAs
   /I modules\preprocess\include /I modules\common\include a68_asm.cpp
ASM_EXIT=0
; Listing generated by Microsoft (R) Optimizing Compiler Version 19.44.35228.0
```

각 대상은 `__declspec(dllexport)` 래퍼로 감싸 인라인으로 사라지지 않게 했다. **도구를 설치하지 않았다** — `/FAs` 는 빌드 플래그다.

### C1 — 주석의 두 주장이 모두 틀렸다

기존 주석: *"One compare-exchange: after it, a <= b. **Branchless on MSVC (vminss/vmaxss)**."*

생성된 코드 (`probe_ce`, 한 번의 compare-exchange):

```asm
vmovss   xmm4, DWORD PTR [rcx]
vmovss   xmm3, DWORD PTR [rdx]
vcomiss  xmm4, xmm3
seta     r8b
xor      r9d, r9d
movzx    eax, r8b
vmovd    xmm0, eax
vmovd    xmm1, r9d
vpcmpeqd xmm2, xmm0, xmm1
vblendvps xmm0, xmm3, xmm4, xmm2      ; lo
vmovss   DWORD PTR [rcx], xmm0
movzx    eax, r8b                      ; (다시)
vmovd    xmm0, eax
vmovd    xmm1, r9d
vpcmpeqd xmm2, xmm0, xmm1
vblendvps xmm0, xmm4, xmm3, xmm2      ; hi
vmovss   DWORD PTR [rdx], xmm0
```

**`vminss` 도 `vmaxss` 도 없다.** 대신 `vcomiss` + `seta` + `movzx` + `vmovd` + `vpcmpeqd` + `vblendvps` 가 두 번 — 열 개가 넘는 명령이다. 부울을 레지스터로 만들었다가 다시 벡터 마스크로 되돌리는 경로를 돈다.

`MedianOfEight`(19번의 compare-exchange) 전체 명령 분포:

```
30 vmovaps   28 vmovd     20 vblendvps   14 vpcmpeqd   14 movzx
11 vcomiss    8 vmovss     7 seta         6 vcmpltss    4 ja
 2 mov        1 xor        1 vmulss       1 vaddss      1 sub
```

**`ja` 가 4개** — 조건부 분기다. 즉 "branchless" 도 **부분적으로만** 참이다. 19개 중 일부는 블렌드로, 일부는 비교+분기로 내려간다.

주석의 두 주장(명령 쌍, 무분기)이 **둘 다** 사실과 다르다.

### C3 — 비중을 먼저 쟀다 (카드 지시)

A-67 이후 분해가 완전히 달라졌다:

```
[decompose-threads] 3072x3072, best of 3
  threads   TOTAL   sigma  memset   rows_situ
  1          63.2    49.6     0.2       13.4
  8          18.9    16.1     0.2        2.5
  16         22.5    19.6     0.2        2.7
```

σ 가 여전히 78.5% 다. 화소 루프는 13.4 ms(21.2%).

**그리고 스칼라 `MedianSortCE` 가 도는 곳은 화소 루프 전체가 아니다.** A-65 이후 내부는 AVX2 로 가고, 스칼라는 `DetectRowRange` 가 남긴 **테두리**만 돈다 — 0행, h-1행, 각 내부 행의 0열과 벡터 런이 끝난 뒤의 꼬리. 직접 셌고 직접 쟀다:

```
  border pixels taking the SCALAR path: 30704 of 9437184 (0.33%), 2.149 ms
```

**2.149 ms / 63.2 ms = 3.4%.** 그 안에서 중앙값 망의 몫은 화소 단계 분해 기준 34.5%~46.4% 이므로 **약 0.7~1.0 ms, 검출기의 1.1~1.6%**.

중앙값 망을 **두 배 빠르게 만들어도 0.5 ms 미만**이 돌아온다. 같은 실행의 게이트 표본 폭이 66.5~71.8 ms(8%)이므로, **게이트가 이미 허용하는 실행 간 분산보다 작다.**

**그래서 고치지 않았다.** 카드가 적은 그대로다 — "주석이 틀렸다"와 "코드를 고칠 값이 있다"는 다른 발견이고, 여기서는 앞의 것만 참이다.

### C4 — 주석을 관측으로 교체

`MedianSortCE` 의 Doxygen 을 다시 썼다. 담은 것: 실제 생성 명령열, `MedianOfEight` 의 분기 4개, 확인 방법(`/FAs`)·컴파일러 버전·날짜, 그리고 **왜 그래도 안 고치는지**(측정된 비중). 옛 문장은 남기지 않았다 — 틀린 주장을 "예전에는 이렇게 적혀 있었다"로 보존하면 다음 사람이 다시 읽는다.

### C5 — 벡터 쪽은 의도대로였다

같은 패스에서 A-65/A-66 이 설계한 피연산자 순서가 실제로 그렇게 나오는지 확인했다:

```asm
SelectCeUpper:  vmovups ymm0, [rcx]        ; a
                vmaxps  ymm0, ymm0, [rdx]  ; max(a, b)   <- 설계대로
SelectCeLower:  vmovups ymm0, [rdx]        ; b
                vminps  ymm0, ymm0, [rcx]  ; min(b, a)   <- 설계대로
MedianSortCE8:  vminps  ymm0, ymm2, ymm1   ; min(b, a)
                vmaxps  ymm1, ymm1, ymm2   ; max(a, b)
```

**소스에서 추론한 것이 아니라 명령 스트림에서 확인했다.** A-65 의 ±0 논증이 기계 수준에서 성립한다는 뜻이다.

### C6 — Doxygen (리더가 전달한 CI 실패 1건)

```
runtime_detection.h:41: error: Member XPE_DETECT_HAS_AVX2 (macro definition) is not documented
```

`@def` 블록을 붙였다. 내용은 카드가 요구한 대로 **무엇을 켜고 끄는지**와 **정의되지 않았을 때 어떻게 되는지**이고, 코드에서 읽어 썼다:

- 항상 정의된다(두 갈래 모두 값을 준다) → `#if` 가 맞고 `#ifdef` 는 틀리다(스칼라 빌드에서도 참이 된다).
- 1일 때 무엇이 컴파일되는지 열거(네 래퍼, `MedianSortCE8`, `MedianOfEight8`, `DetectEightPixelsAvx2`, `DetectRowRange` 의 분기).
- 0일 때 모든 화소가 `DetectDefectivePixel` 로 가고, 파리티 스위트는 실패가 아니라 **SKIP** 한다.
- 0이 되는 조건(`_MSC_VER` 도 `__AVX2__` 도 없을 때)과, **A-66 이 그 갈래를 실제로 빌드해 C4127 로 깨진 것을 발견했고 지금은 고쳐졌다**는 경계.

**대책은 만들지 않았다** — #159 의 선택지는 리더 판단이라고 카드에 적혀 있다.

## 3. baseline 귀속 (Baseline-attribution)

- 어셈블리는 이번 세션에서 생성했고, 컴파일러 버전은 출력 헤더에서 읽었다(19.44.35228.0).
- 63.2 ms / 49.6 ms / 13.4 ms / 2.149 ms 는 전부 이번 실행의 측정값이다.
- "중앙값 망이 테두리 비용의 34.5~46.4%" 는 **화소 단계 분해의 몫을 적용한 추정**이며, 테두리 화소만 따로 단계 분해한 것이 아니다. 추정으로 표시한다.
- CI 비율 0.552(런 `f19321a`)는 리더가 읽어 전달한 값이며 이번에 재지 않았다.

## 4. 미검증 (Gaps)

- **테두리 안에서의 단계 분해를 하지 않았다.** 중앙값 망의 몫은 내부 화소에서 잰 비율을 옮긴 것이다. 테두리 화소는 이웃이 5~7개라 망이 다른 경로(`ComputeMedianGeneric`)를 타므로, **그 비율이 그대로 적용된다는 보장은 없다.** 결론(비중이 작다)은 상한인 2.149 ms 로도 서기 때문에 더 재지 않았다.
- **다른 컴파일러·다른 버전은 확인하지 않았다.** 관측은 MSVC 19.44.35228.0 하나에 대한 것이고, 주석에 버전을 적은 이유가 그것이다.
- **`ja` 4개가 실제로 예측 실패를 내는지 재지 않았다.** A-67 의 함정을 피해 말하면 — 분기의 존재는 비용의 증거가 아니다. 비중이 3.4%라 재지 않기로 했다.
- **꼬리 화소를 벡터로 덮을 수 있는지 시도하지 않았다** (§5 참조).
- **Doxygen 로컬 확인 불가** — 여전하다. CI 결과는 리더가 읽는다(#159).

## 5. 잔여 위험 / 올리는 관찰

- **꼬리가 예상보다 크다.** 테두리 30,704 화소 중 **내부 행의 꼬리가 24,560개**다 — 행마다 8개(선두 1 + 후미 7). 벡터 런이 `x + 8 <= w - 1` 에서 멈추기 때문이고, 3072 폭에서 마지막 런이 3065 에서 끝나 3065~3071 일곱 화소가 스칼라로 떨어진다. 스칼라는 화소당 ~70 ns, AVX2 는 ~1.2 ns 이므로 **이 0.33% 가 화소 루프의 16%(2.149 / 13.4)를 쓴다.**
  마지막 런을 겹쳐서 배치하면(`x = w - 9` 에서 한 번 더) 꼬리가 사라진다. **이번 카드에서 하지 않았다** — 카드의 대상이 아니고, 겹친 런은 같은 화소를 두 번 판정하므로 멱등성 논증과 파리티 테스트가 따로 필요하다. **판정을 올립니다.**
- **주석 한 줄이 두 카드를 살렸다가 한 카드를 낭비시킬 뻔했다.** A-67 에서 내가 "확인하지 않았다"고 적어 이 카드가 생겼고, 확인해 보니 주석이 틀렸지만 **고칠 값은 없었다.** 미검증으로 적는 것과 고칠 값이 있는 것은 별개이고, **비중을 먼저 재라는 카드의 순서가 그 구분을 만들었다.**
- **이 파일에는 코드 생성에 대한 주장이 더 있을 수 있다.** 이번에 확인한 것은 `MedianSortCE` 하나와 벡터 래퍼 세 개다. 전수 조사는 하지 않았다.
