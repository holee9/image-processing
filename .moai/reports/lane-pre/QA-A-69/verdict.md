# QA-A-69 — 벡터 런의 꼬리를 없앤다

**카드**: `.moai/lanes/pre/inbox/QA-A-69.md` · **브랜치**: `dev/preprocess` · **기계**: Intel Core i7-12700

## 1. 주장 (Claim)

| # | 주장 |
|---|---|
| C1 | `w - 9` 에서 시작하는 **겹치는 런 하나**로 꼬리를 덮었다. 마지막 내부 열에서 정확히 끝나므로 테두리를 건드리지 않는다 |

## 2. 증거 (Evidence)

### C1 — 배치

내부 열은 1..w-2 다. 전진 walk 는 `x += 8` 로 `x <= w-9` 인 동안만 런을 시작할 수 있어 나머지를 스칼라에 남긴다. **그 나머지는 폭과 무관하게 행당 7열** — 보폭의 성질이지 프레임의 성질이 아니다. 그래서 `w - 9` 에 런을 하나 더 놓는다:

```cpp
for (; x + 8u <= w - 1u; x += 8u) DetectEightPixelsAvx2(pixels, w, x, y, config, map);
if (x + 1u < w) {
    DetectEightPixelsAvx2(pixels, w, DetectRowLastRunStart(w), y, config, map);
}
scalarSpan(y, w - 1u, w);
```

`w-9 + 7 == w-2` 이므로 마지막 내부 열에서 정확히 끝나고, `w >= 10` 에서 `w-9 >= 1` 이므로 왼쪽 테두리도 건드리지 않는다. 공식을 `DetectRowLastRunStart` 라는 이름으로 분리해 **테스트가 가리킬 수 있는 대상**으로 만들었다.

### C2 — 꼬리가 실제로 사라졌는지 세어서 확인

카드 지시대로 A-68 과 같은 방식으로 셌다.

| | 스칼라 화소 | 비용 |
|---|---|---|
| A-68 (전) | 30,704 (0.33%) | 2.149 ms |
| **A-69 (후)** | **12,284 (0.13%)** | **0.985 ms** |

**18,420 이 사라졌다.** 리더가 예상한 24,560 과 다른데, 이유는 **열 0과 열 w-1 은 스칼라로 남아야 하기 때문**이다 — 이웃이 8개가 아니라 다른 계산이고, 느린 계산이 아니다. 행당 8개 중 7개(꼬리)가 사라지고 2개(양 끝)가 남는다. 남은 12,284 = 위아래 두 행 6,144 + 내부 행 양 끝 6,140.

**폭별 효과** (`--decompose`, 각 크기 3회, 최솟값):

| 폭 | 꼬리 있음 | 꼬리 없앰 | 차이 |
|---|---|---|---|
| 512 | 2.0 ms | 1.8 ms | −10% |
| 1024 | 7.0 ms | 6.3 ms | −10% |
| 3072 | 63.0 ms | 61.3 ms | −2.7% |

**좁을수록 큰 것이 이 변경의 이유**이고, 측정이 그 방향을 보인다. 다만 실행 간 분산이 3072 에서 61.3~67.1 로 넓어 **2.7% 는 분산 안**이다 — 3072 의 숫자는 방향만 말하고, 확실한 것은 §C2 의 직접 측정(2.149 → 0.985 ms)이다. `--decompose` 에 512 를 추가했다. 폭에 따라 결론이 달라지는 항목을 3072 에서만 재면 못 본다.

### C3 — 열 방향 중복 (물려받지 않고 확인)

겹친 런은 최대 7열을 두 번 판정한다. A-61 이 **행** 방향에서 "중복이 이 설계에서 원리적으로 무해하다"를 측정으로 확인했지만, **이번은 열 방향**이므로 같은 성질이 적용되는지 따로 물었다.

`JudgingAColumnTwiceStoresTheSameByte`: 정상 실행으로 맵을 만든 뒤, 내부 열을 3칸 보폭으로(즉 일부러 겹치게) 다시 판정하고 **한 바이트도 변하지 않을 것**을 요구한다. 통과.

근거는 코드에 적었다 — 판정이 프레임과 config 만 읽으므로 결정적이고, 쓰기가 누산이 아니라 **바이트 전체 덮어쓰기**라 두 번째 쓰기가 첫 번째와 같은 값을 넣는다.

### C4 · C5 — 반증: 비트 파리티로는 부족하다

카드가 "A-67 에서 배운 것을 쓰라 — 비트 파리티만으로 충분한지 먼저 보라"고 했다. **충분하지 않았다.**

**주입**: `DetectRowLastRunStart` 를 `w - 8` 로(한 칸 오른쪽). 이러면 런이 열 w-1 을 판정하고, 그 오른쪽 이웃은 행 밖이다. `BUILD_EXIT=0`:

```
[       OK ] Avx2ParityTest.FrameMapsAreIdenticalPixelForPixel
[       OK ] Avx2ParityTest.OverlapBoundaryWidthsStillMatchTheScalarRule
[       OK ] Avx2ParityTest.ShippedEntryPointAgreesWithTheScalarRule
[  FAILED  ] Avx2ParityTest.LastRunStartLandsExactlyOnTheFinalInteriorColumn
```

**프레임 파리티가 전부 통과한다.** 이유는 뒤에 오는 `scalarSpan(y, w-1, w)` 이 열 w-1 을 올바른 값으로 **덮어쓰기 때문**이다. 맵은 맞고, 읽기는 틀렸다 — 마지막 내부 행에서는 로드가 버퍼 끝을 **한 원소 넘어간다**.

그래서 맵을 보지 않는 단언을 추가했다. `VectorRunsNeverReadPastTheFrame` — 프레임의 마지막 float 가 `PAGE_NOACCESS` 페이지에 정확히 맞닿게 배치하고, 한 원소라도 넘어 읽으면 접근 위반이 나게 한다(A-63 의 픽스처를 쓰기가 아니라 **읽기**에 겨눈 것). 같은 주입을 다시 넣었을 때:

```
w=17: a load reached past the end of the frame (tail run starts at 8)
w=24: a load reached past the end of the frame (tail run starts at 15)
w=64: a load reached past the end of the frame (tail run starts at 55)
w=129: a load reached past the end of the frame (tail run starts at 120)
[  FAILED  ] Avx2ParityTest.VectorRunsNeverReadPastTheFrame
```

**이 단언만이 잡는다.** 그리고 이것이 A-65 의 구조(비트 단위 / 프레임 단위)와도, A-67 의 구조(두 층이 겹침)와도 다른 세 번째 형태다 — 여기서는 **맵이 아니라 메모리 접근**이 관측 대상이다.

주입은 원복했고, 원복 후 10/10 통과한다.

### C6 — 게이트: 움직이지 않았다

카드가 예고한 대로다. 3회씩:

```
변경 전  ratio 0.659 / 0.659
변경 후  ratio 0.632 / 0.662 / 0.656   (limit 0.850)
```

**비율이 표본 분산 안에서 움직이지 않았다.** 3072 에서의 이득(2.7%)이 게이트 표본 폭(같은 실행에서 62.4~67.8 ms, 약 8%)보다 작기 때문이다. **상한을 재유도하지 않았다** — 대역이 바뀌지 않았으므로 옮길 근거가 없다. SPEC `60a81c1` 의 [HARD] 는 "큰 성능 변경마다"이고, 이번은 게이트가 볼 수 있는 크기의 변경이 아니다.

SPEC 개선 목표 60 ms 대비: 이 기계에서 **1.0~1.1배**(62.4~63.9 ms). **"도달"이라고 쓰지 않는다** — 실행에 따라 60 ms 위아래이고, CI 는 A-68 시점에 1.6배였다. 어느 기계 어느 조건인지만 적고 판단은 리더에 맡긴다.

## 3. baseline 귀속 (Baseline-attribution)

- 전/후 폭별 시간은 **같은 세션에서 같은 방식으로** 잰 것이다. "전" 은 꼬리 런을 제거한 빌드(`BUILD_EXIT=0` 확인)에서 3회, "후" 는 복원한 빌드에서 3회.
- 스칼라 화소 수는 도구 안의 **복제 열거**이고 그렇게 표시했다. 그 수가 맞다는 근거는 같이 측정한 시간(2.149 → 0.985 ms)이다.
- 게이트 "변경 전" 비율 0.659 는 A-67/A-68 실행에서 나온 값이며 이번에 재측정하지 않았다.
- CI 비율(0.552, 런 `f19321a`)은 A-67 코드의 값이다.

## 4. 미검증 (Gaps)

- **꼬리 런이 제거되는 것을 어떤 테스트도 잡지 못한다.** 스칼라 경로가 같은 값을 내므로 맵이 안 바뀌고, 가드 페이지도 안 터지며, 게이트는 2.7% 를 못 본다. **이 변경은 정확성으로는 지켜지지만 자기 삭제로부터는 지켜지지 않는다.** 대책(예: 스칼라 화소 수를 세는 계측)은 만들지 않았다 — 제품 코드에 계측을 넣는 판단이 필요하고 카드 범위 밖이다.
- **폭별 이득의 분산.** 512/1024 의 −10% 는 각 3회 최솟값 비교다. 512 의 실행 간 폭이 1.8~2.2 ms 라 **10% 가 분산과 같은 크기**다. 확실한 것은 세어서 잰 스칼라 비용(2.149 → 0.985 ms)이고, 폭별 총시간은 방향만 말한다.
- **높이 방향 꼬리는 없다** — 행은 하나씩 도므로 남는 것이 없다. 확인할 것이 없어 확인하지 않았다.
- **중복 판정의 비용을 재지 않았다.** 행당 최대 7열이 두 번 판정되지만, 8열 런 하나가 스칼라 7화소보다 훨씬 싸다는 것이 측정된 결과일 뿐 중복분만 따로 재지는 않았다.
- **Doxygen 로컬 확인 불가** — 여전(#159). 새 함수 `DetectRowLastRunStart` 에 `@param`/`@return` 을 붙였지만 **CI 결과로만 확인된다.**
- **CI 측 성능은 재지 않았다.**

## 5. 잔여 위험 (Residual-risk)

- **테두리가 올바른 이유가 두 겹이다.** 벡터 런이 테두리를 안 건드리는 것(공식)과, 그 뒤 스칼라 패스가 테두리를 다시 쓰는 것(순서). 반증에서 드러났듯 **뒤의 것이 앞의 것의 오류를 가린다.** 지금은 둘 다 맞지만, 순서를 바꾸면 가려주던 것이 사라진다 — 가드 페이지 테스트가 그때의 방어선이다.
- **`w < 10` 에서는 전부 스칼라다.** 그 경로는 파리티 테스트가 덮지만(9×10 케이스), 성능은 재지 않았다. 아주 좁은 프레임에서는 꼬리 문제가 아니라 벡터화 자체가 없다.
- **SPEC 목표선에 걸쳐 있다.** 실행마다 60 ms 위아래라 "도달"을 주장할 수 없고, 다음 변경이 작아도 선을 넘나들 것이다. **목표 도달 여부를 실행 하나로 판단하지 않는 것**이 필요하다.
