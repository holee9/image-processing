# QA-A-118 (#179) — 성능 게이트가 새 CPU 에서 무너졌습니다

`BUILD_EXIT=0`. **문턱을 넓히지 않았고, 코드도 고치지 않았습니다** — 리더가 지목한 가설을 재 본 결과 **기각**됐고, 구분에 필요한 진단만 넣었습니다.

## 1. 리더 가설 — 측정으로 기각

> "분자는 AVX2, 분모는 기본 아키텍처. 이 비대칭이 새 CPU 에서 안 상쇄된다."

개발 PC(i7-12700)에서 네 가지 빌드로 쟀다(매번 전체 빌드, 3라운드 최소값):

| 빌드 | 검출기 | 기준 커널 | 비율 |
|---|---|---|---|
| 현재 (분자 AVX2 / 분모 기본) | 66–68 ms | **51.1 / 51.0 ms** | 1.324 / 1.324 |
| **분모도 AVX2** | 66.1 / 67.6 ms | **50.7 / 50.9 ms** | **1.305 / 1.328** |
| 분자 AVX2 **끔** | 69.0 ms | 51.2 ms | 1.288 |

- **분모에 AVX2 를 켜도 기준 커널은 0.8% 밖에 안 빨라진다**(51.1 → 50.7 ms). 비율은 1.324 → 1.305 로, 실행 간 산포(1.288–1.328) 안이다.
- **분자의 AVX2 를 꺼도 검출기는 4% 밖에 안 느려진다**(66.1 → 69.0 ms).

즉 **양쪽 다 AVX2 의존도가 작다.** 이 비대칭으로는 Xeon 6973P-C 의 **1.6배 비율 점프(1.32 → 2.06)를 설명할 수 없다.** 가설대로 고쳤다면 원인을 못 잡은 채 분모만 바꿔 과거 비율을 또 무효로 만들었을 것이다.

**그래서 아키텍처 플래그는 바꾸지 않았다.**

## 2. 새로 알게 된 것 — 기준 커널은 대역폭이 아니라 **지연**에 묶여 있다

넣은 진단이 개발 PC 에서 이렇게 찍는다:

```
[perf-gate-machine] cache L1=48KB L2=1280KB L3=25600KB
[perf-gate] round 1/3 reference kernel: 49.6 ms (5.7 GB/s effective)
[perf-gate-machine] ... bandwidth=26.0 GB/s
```

**기준 커널의 유효 전송률은 5.7 GB/s 로, 같은 실행의 스트리밍 탐침값(26.0 GB/s)의 22% 다.** QA-A-115 에서 "대역폭에 묶었다" 고 적었지만, 실제로는 대역폭 상한의 4분의 1 에서 돌고 있다 — 이웃 한 칸 읽기(`frame[i-1]`, `frame[i]`, `frame[i+1]`)와 바이트 쓰기가 섞여 **접근 지연과 캐시 계층**이 더 지배한다.

이것이 Xeon 6973P-C 의 관측과 맞물린다:

| CPU | 검출기 | 기준 커널 | 비율 |
|---|---|---|---|
| AMD EPYC 7763 | 93.3 ms | 70.9 ms | 1.316 |
| **Intel Xeon 6973P-C** | **119.6 ms** | **58.1 ms** | **2.060** |

기준 커널이 **빨라졌다**(70.9 → 58.1). 대역폭 탐침은 오히려 낮았다(19.5 대 23.3 GB/s). 대역폭에 묶인 커널이 대역폭 낮은 기계에서 빨라질 수는 없다 — **그 커널이 대역폭에 묶여 있지 않다는 증거다.** 캐시 계층(작업 집합 47 MB 가 그 기계의 LLC 에 들어갔을 가능성)이 유력한 후보이고, **그것을 확인할 수 있는 값이 지금까지 로그에 없었다.**

## 3. 넣은 것 — 다음 실행에서 판정할 진단 (코드 동작 불변)

| 출력 | 무엇을 가르나 |
|---|---|
| `cache L1=.. L2=.. L3=..` (CPUID leaf 4) | 47 MB 작업 집합이 그 기계의 LLC 에 들어가는지. 들어가면 기준 커널이 메모리를 안 건드리고, 한계를 유도한 전제가 깨진다 |
| `reference kernel: X ms (Y GB/s effective)` | 커널이 실제로 얻는 전송률. 스트리밍 탐침값과 크게 어긋나면 그 기계에서 대역폭에 묶이지 않은 것 |

단언·한계·커널은 **바꾸지 않았다.** QA-A-108 에서 러너 프로필을 넣어 다음 실패를 판정했던 것과 같은 방식이다.

## 4. (b) main 을 초록으로 — 선택지 (결정은 리더)

**문턱 상향은 선택지가 아니다**, 그리고 그 이유가 이번에는 수치로 분명하다: Xeon 을 통과시키려면 한계가 **2.06 위**여야 하는데, QA-A-115 가 잰 **가장 가까운 회귀는 1.496**(+2 패스)이다. 즉 **게이트가 잡아야 할 회귀보다 문턱이 높아진다** — 게이트를 끄는 것과 같고, 끈 줄도 모르게 된다.

| 선택지 | 내용 | 대가 |
|---|---|---|
| **A. 이 시험만 CI 에서 한시 제외** | `ctest -E` 또는 코드에 `GTEST_SKIP`, 사유·복구 조건·`#179` 를 주석에 명기 | main 이 초록으로 돌아오고 다른 회귀를 다시 본다. 이 게이트는 그동안 아무것도 못 잡는다 |
| **B. 단언을 보고로 낮춤** | 비율을 계속 찍되 실패시키지 않음. 같은 주석 요건 | A 와 같되 **분포가 계속 쌓인다** — 다음 판정에 쓸 자료가 는다 |
| C. 문턱 상향 | 2.06 위로 | **반대.** 위 이유로 게이트가 무력화된다 |
| D. 기계 목록으로 분기 | 알려진 CPU 만 단언 | 새 러너가 나올 때마다 손이 간다. GitHub 러너는 기종이 바뀐다 |

**B 를 권한다** — 복구 조건이 명확하다: §3 의 진단으로 Xeon 6973P-C 의 캐시·유효 전송률을 읽고, 원인이 확정되면 커널이나 한계를 근거와 함께 고친 뒤 단언을 되살린다.

## 5. (c) 이 게이트가 본 CPU 목록

새 CPU 가 나올 때마다 여기 붙인다. 비율은 3라운드 최소값.

| CPU | 대역폭 | L3 | 검출기 | 기준 커널 | 비율 | 판정 |
|---|---|---|---|---|---|---|
| Intel i7-12700 (개발 PC) | 23.3–28.0 | 25.6 MB | 66–69 ms | 49.6–51.2 ms | 1.267–1.369 | 초록 |
| AMD EPYC 9V45 | 43.2–45.7 | — | 51.9–53.4 | 38.4–40.4 | 1.302–1.388 | 초록 |
| AMD EPYC 7763 | 23.3–24.4 | — | 93.3 | 70.9 | 1.313–1.326 | 초록 |
| Intel Xeon Platinum 8370C | 14.3–14.7 | — | — | — | 1.372–1.395 | 초록 |
| **Intel Xeon 6973P-C** | 19.5 | — | **119.6** | **58.1** | **2.060 / 2.145** | **빨강** |

대역폭이 14.3 → 45.7 GB/s 로 3배 변해도 넷은 1.27–1.40 에 모인다. 하나만 벗어나고, **그 하나에서 두 시간이 반대로 움직였다.** L3 열이 비어 있는 것은 진단이 이번에 처음 들어가기 때문이다 — 다음 실행부터 채워진다.

## 6. 미검증

- **Xeon 6973P-C 의 캐시 크기와 기준 커널 유효 전송률을 아직 모른다.** §3 의 진단이 그것을 가져온다. 캐시 가설은 **아직 가설이다.**
- 스레드 배치·NUMA·터보 거동은 재지 않았다(로컬에서 재현할 수단이 없다).
- 개발 PC 한 대에서만 빌드 변형을 쟀다. 다른 기계에서 AVX2 영향이 더 클 수 있다 — 다만 그렇다면 Xeon 에서 검출기가 느려지고 기준이 **같이** 느려졌어야 하는데 반대였다.
- 이 카드에서 단언·한계·커널을 바꾸지 않았으므로 반증은 수행하지 않았다.
