# QA-A-237c M1 — 고스트 느린 길의 최대 메모리를 실측했다

카드: QA-A-237c · Refs #245 · 기준 커밋 `9a63a16a`(237d: 판정을 float 로 고친 뒤). 제품 코드는 바꾸지 않았다(시험 하니스만).
단위: MiB(2^20 B), 괄호 안은 십진 MB. 200 MB = 190.7 MiB. 메모리는 모듈 몫(하네스 기준선 A 를 뺀 값), 3072² 고스트 포함, 출하 경로 `xpe_preprocess_pipeline_ex`.

## 0. 결론 먼저

1. **느린 길의 최대는 297.7 MiB(312.2 MB, 200 MB 의 156%)다.** 새 프로세스 3회가 DLL 구성과 훅 구성 모두에서 같은 값이다. QA-A-237b 가 계산한 297.3 MiB 와 0.4 MiB 차이다. 정상 길은 207.5 MiB(217.6 MB, 109%)로 그대로다.
2. **어떤 입력이 느린 길로 가는지는 코드로 정해진다**(§1): 판정 `frame_cannot_leave_float_range` 가 `false` 인 프레임. 단, **uint16 입력과 기본 설정으로는 일어나지 않는다**. 느린 길의 최대 297.7 은 비정상 입력(§3)에만 해당한다.
3. 느린 길 구간이 매우 좁다. 설정별로 프레임 크기를 키워 보면(§3 표) 정상 길에서 곧바로 "프레임이 실패함(`XPE_ERR_PROCESSING_FAILED`)"으로 넘어가는 구성이 많고, 느린 길에서 **성공하는** 크기 구간은 한 자릿수 안쪽이다. 느린 길의 메모리는 실패할 프레임에도 쓰인다(평면은 계산 전에 잡는다).
4. 그래서 결론은 둘로 나눈다(§4): **정상 데이터의 상한은 207.5 MiB(109%)**, **극단 입력의 일시 상한은 297.7 MiB(156%)**. 후보 (b)(M2)가 같은 −18.0 MiB 를 두 길에 모두 준다면 각각 189.5 MiB(99%), 279.7 MiB(146%)다.

## 1. 느린 길로 가는 조건 (코드)

`ghost_correct.cpp`, `xpe_ghost_correct`: 프레임을 읽은 뒤(입구의 NaN·Inf 거부와 미보정 핸들 통과 다음)

```cpp
const float maxAbs = max_abs_finite(px, n);
...
bool inPlace = frame_cannot_leave_float_range(*gh, maxAbs, coeffs, Tier3Mix{mixKeep, mixLocal});
if (inPlace) { /* 이력 평면에서 제자리 */ } else { /* next1, next2, backup 을 이 호출 안에서 잡는 느린 길 */ }
```

`frame_cannot_leave_float_range`(QA-A-237d)는 프레임의 최대 |값| M 과 핸들이 들고 있는 이력 상한(`histBound1/2`), 계수에서 tier 의 식을 같은 순서의 float 로 최악 입력에서 평가한다(`ew`, `sd`, `a1w`, `a2w`, `t1 = a1w × H1`, `t2 = a2w × H2`, `corr`, `n1w`, `n2w`, tier 3 은 `sum9`, `blend`). **그 값 중 하나라도 유한하지 않거나 1e37 을 넘으면** `false` 이고 느린 길이다. 그러므로 입력이 느린 길로 가는 길은 셋이다.

| 길 | 조건 | 출하 경로에서 일어나는가 |
|---|---|---|
| ① 큰 프레임 값 | M 이 커서 `corr`, `t1`, `n1w` 등이 1e37 을 넘음 | uint16 입력은 이득 뒤에도 약 6.5e5 이하(이득 ≥ 0.1)이므로 기본 설정에서는 **아니오**. float32 입력(우회 설정으로 호출자가 직접 float 를 넣을 때)에서만 가능 |
| ② 큰 계수 | tier 3 의 `nlcscBeta` 가 커서 `sd`, `a1w`, `t1` 이 한계에 가까움 | 기본값(0.1)에서는 **아니오**. 설정이 비정상으로 큰 값일 때(실측: 약 1e36)만 |
| ③ 극단 프레임의 잔여 | 큰 프레임 뒤 이력 상한 `histBound` 가 한동안 큼(τ2 = 20 에서 수십 프레임) | 극단 프레임이 먼저 있었을 때만 |

## 2. 측정 (`evidence/22`, `23`, `24`)

방법은 QA-A-236/237b 와 같다(새 프로세스마다 하네스 기준선 A 를 뺌, `GetProcessMemoryInfo`). 느린 길은 **tier 3 + `nlcscBeta = 1e36`** 으로 만들었다: 값이 한계(1e37)를 막 넘게 하면서 실제 계산은 float 범위 안에 머물러 프레임이 성공한다(출력은 0 으로 잘림). 첫 프레임은 이력이 0 이라 제자리, 이어지는 프레임은 느린 길이다(훅 구성의 카운터: 4프레임 중 제자리 1).

| 구성 | 실행 | 정상 상태 (C − A) | 최대 | 200 MB 대비 |
|---|---|---|---|---|
| 정상 길 (tier 3, 기본 beta) | DLL 3회 | 153.3 MiB | 207.5 MiB (217.6 MB) | 109% |
| **느린 길** (tier 3, beta 1e36, 4프레임) | **DLL 3회** | 153.3 ~ 153.4 | **297.7 MiB (312.2 MB)** | **156%** |
| **느린 길** (같음) | **훅 3회** | 153.3 ~ 153.4 | **297.7 MiB** | 156% |

### 단계별 (`evidence/25`, 훅, 느린 프레임)

프레임 1 의 단계 경계: `defect` 뒤 private 189.4, peak 207.5 → **`ghost` 뒤 peak 297.7**(+90.2). 297.7 = 189.4(그 시점 모듈 보유량: 정상 상태 153.3 + 작업 버퍼 36.0) + 108.3(느린 길의 평면 세 장). 프레임 2 도 같다. 최대가 나오는 단계는 정상 길이나 느린 길이나 ghost 다(정상 길은 gain 단계에서 207.5).

### 시간 (참고: **번갈아 잰 비교가 아님**)

프레임 시간 최솟값: 정상 길 299.2 ms, 느린 길 320.9 ms(DLL 구성, 프레임 1~3 각 9개). 느린 길이 약 +21.7 ms(+7%)다. 설정이 달라서(beta) 순수한 경로 차이가 아니고, 이 카드는 시간을 판정하지 않았다.

## 3. 어떤 크기의 입력이 느린 길로 가는가 (`evidence/30`)

`A237cRoute.DISABLED_WhichMagnitudesTakeTheScratchRoute`(훅 구성의 `DISABLED_` 탐침): 설정마다, 프레임 값을 `1e3 … 1e38`(자릿수별)로 올려 가며 같은 값의 프레임 150장을 먹이고(이력 상한이 가라앉을 만큼) **마지막 프레임**을 분류한다. 실제 판정을 쓴다(카운터). `.` 제자리, `S` 느린 길로 성공, `F` 프레임 실패. 8×8, 지연 `alpha1 0.1, tau1 1, alpha2 0.01, tau2 20`.

| 설정 | 제자리(`.`)가 끝나는 자릿수 | 느린 길 성공(`S`) | 실패(`F`) 시작 |
|---|---|---|---|
| tier 1 | 1e35 까지 | 1e36, 1e37 | 1e38 |
| tier 2 | 1e21 까지 | (자릿수 간격에서는 없음) | 1e22 |
| tier 3, 기본 beta 0.1 | 1e15 까지 | 1e16 | 1e17 |
| tier 3, beta 1e3 | 1e14 까지 | 1e15 | 1e16 |
| tier 3, beta 1e10 | 1e12 까지 | (없음) | 1e13 |
| tier 3, beta 1e20 | 1e8 까지 | 1e9 | 1e10 |
| tier 3, beta 1e30 | 1e5 까지 | 1e6 | 1e7 |
| tier 3, beta 1e35 | 1e3 | 1e4 | 1e5 |
| tier 3, beta 1e36 | (1e3 부터 이미 느린 길) | 1e3 | 1e4 |

읽는 법: 기본 설정에서 느린 길이 되려면 프레임 값이 tier 1 은 1e36, tier 2 는 거의 1e22, tier 3 은 1e16 급이어야 한다. uint16 입력(이득 뒤 최대 약 6.5e5)은 어느 쪽에도 닿지 않는다. `nlcscBeta` 가 1e35 이상이 되면 값이 1e3 대인 프레임도 느린 길이다. **느린 길로 가는 프레임은 대부분 곧 실패하는 프레임**이고(F 가 S 보다 훨씬 넓다), 실패하는 호출도 평면을 먼저 잡으므로 297.7 MiB 는 실패할 프레임의 일시 최대이기도 하다.

## 4. 결론 표 (200 MB = 190.7 MiB 대비)

| | 정상 길 | 느린 길 |
|---|---|---|
| 정상 상태(호출 전) | 153.3 MiB (160.7 MB) | 153.3 MiB |
| 최대(측정) | **207.5 MiB (217.6 MB) — 109%** | **297.7 MiB (312.2 MB) — 156%** |
| 어떤 입력인가 | uint16 입력 + 기본 설정 전부 | 큰 float 입력, 비정상으로 큰 `nlcscBeta`, 극단 프레임 뒤의 잔여 |
| (b) 로 −18.0 MiB 가 두 길에 모두 적용되면(예상) | 189.5 MiB (198.7 MB) — 99% | 279.7 MiB (293.3 MB) — 146% |

PERF-002 의 "최대 메모리" 에 답이 둘이다. 정상 데이터에 대해서는 207.5 MiB(109%)가 상한이고, 입력이 극단일 때는 297.7 MiB(156%)까지 올라가며 그 프레임은 대개 실패한다. 후보 (b)는 정상 길을 99%(여유 1.2 MiB)까지만 내리고 느린 길은 200 MB 를 넘는다. 느린 길까지 200 MB 아래로 내리려면 평면 세 장(108.0 MiB)을 잡지 않는 방법이 필요하고, 그것은 실패 시 원상 보존을 다른 방식으로 보장해야 하므로 별도 설계 결정이다(이 카드의 범위 밖).

## 5. 이 측정이 보지 않은 것

- 느린 길은 **tier 3 + 비정상 `nlcscBeta`** 한 경로로만 출하 파이프라인에서 쟀다. 큰 float32 입력(우회 설정)이나 극단 프레임 뒤의 잔여 경로는 같은 느린 길 코드를 타지만 따로 재지 않았다(메모리는 같은 평면 세 장이므로 같을 것으로 보이나 측정은 아님). tier 1·2 의 느린 길도 마찬가지다.
- 시간은 번갈아 재지 않았다(§2).
- §3 표는 동일한 값의 프레임 150장이다. 실제 노출의 분포가 아니라 판정이 제자리를 떠나는 자릿수를 보는 것이다. 8×8 한 크기, 지연 계수 한 쌍.
- 이 기계, MSVC 한 구성. 이 카드의 코드 변경이 없으므로 게이트(clang-tidy, doxygen)는 237d 의 결과가 유효하다(`modules/preprocess/src` 와 `include` 의 diff 가 없음).
- 하니스에 추가한 것: `XPE_A237C_BETA`(느린 길 구성), 제자리 프레임 수 출력(훅 구성), 위 자릿수 탐침. 모두 `DISABLED_` 이거나 환경 변수가 있을 때만 동작한다.
