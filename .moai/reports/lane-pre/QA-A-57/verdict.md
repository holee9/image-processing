## §2. Evidence — 증거

### 2-1. 게이트와 맥락 고정 (카드 1항)

```
[perf-gate] 3072x3072 single thread, warm, min of 3: 731.4 ms  (samples 741.3 / 740.2 / 731.4, spread 1.3%)
[perf-gate] regression gate 810 ms; SPEC improvement target 60 ms (AVX2, single thread) -- currently 12.2x the target
[perf-gate] 1024x1024 single thread, warm, min of 3: 87.0 ms
[  PASSED  ] 2 tests.
```

**맥락 고정 셋과 각각의 이유** (테스트 주석에 같은 내용이 있다):

1. **워밍업 1회, 버린다.** 첫 호출은 갓 할당한 37.75 MB 프레임·9.44 MB 맵의 페이지 폴트를
   물고 캐시도 비어 있다. 실재하는 비용이지만 게이트가 보려는 것이 아니다.
2. **3회 중 최솟값**(평균 아님, 단발 아님). 공유 데스크톱의 타이밍 잡음은 **한쪽으로만** 작용한다 —
   스케줄러·다른 프로세스·발열은 실행을 **느리게만** 만들 수 있다. 따라서 최솟값이 참값에
   가장 덜 오염된 추정이고, **17~23% 맥락 산포가 단언까지 도달하지 못하게 막는 장치**가 이것이다.
3. **단일 스레드.** SPEC 이 `92f8f1e` 로 이 전제를 명시했고 검출기는 스레드를 만들지 않는다 —
   게이트가 재는 것과 예산이 말하는 것이 같은 대상이다.

**고정이 작동한다는 증거**: A-55 는 같은 함수가 맥락에 따라 17% 갈리는 것을, A-56 은 같은
커널의 스프레드가 5.7% → 23.5% 로 벌어지는 것을 쟀다. 게이트 실행의 샘플 스프레드는
**1.3%(3072²)·0.4%(복원 후 재실행)** 다. 실패 메시지에 **샘플 세 개를 모두 인쇄**하므로,
실패가 진짜 느려진 것인지 한 샘플이 튄 것인지 로그만 보고 구분할 수 있다.

**810 의 근거**(내가 정한 것이 아니다): 사용자 결정 `92f8f1e` — 현재 732.1 ms + 약 10%,
맥락 산포를 고려해 느린 쪽에. 개선 목표 60 ms 는 **인쇄만 하고 단언하지 않는다** — 현재
12.2배이고, 도달하지 못한 목표를 게이트로 걸면 게이트가 상시 빨간 상태가 되어 회귀를 못 잡는다.

### 2-2. 커버리지 제외 — 기계적 확인 (카드 1항)

이름을 규칙에 맞췄다: `RuntimeDetectionPerformanceGateTest.Frame3072SquaredWithin810ms` 는
`cmake/XpeCoverage.cmake:29` 의 `XPE_COVERAGE_EXCLUDE_TESTS`
(`Performance|Within[0-9]+ms|PerformanceBudget|LargeImagePerformance`)에 **두 번** 걸린다.

주장으로 끝내지 않고 같은 정규식을 ctest 에 그대로 먹여 확인했다:

```
--- all gate tests:
  Test #615: RuntimeDetectionPerformanceGateTest.Frame3072SquaredWithin810ms
  Test #616: RuntimeDetectionPerformanceGateTest.Frame1024SquaredWithin120ms
--- with the coverage exclusion applied:
Total Tests: 0
```

계측 아래에서 타이밍을 단언하면 계측을 재게 된다 — 기존 규칙과 같은 이유다.

### 2-3. 게이트 민감도 반증 (카드 2항)

**조작**: `ComputeMedian` 의 8값 고속 경로(QA-A-54)를 우회해 모든 화소가 느린 경로를 타게 했다.

**빌드 결과** (`a57-falsify-build.log`): `BUILD_EXIT=0`,
`[13/13] Linking CXX executable bin\\xpe_preprocess_tests.exe` — 실제로 다시 빌드됐고
낡은 바이너리가 아니다.

```
[perf-gate] 3072x3072 single thread, warm, min of 3: 1201.2 ms  (samples 1201.2 / 1376.0 / 1454.9, spread 21.1%)
...(128): error: Expected: (best) <= (kRegressionGateMs), actual: 1201.2081 vs 810
...(186): error: Expected: (best) <= (kSmallGateMs), actual: 189.3907 vs 120
 2 FAILED TESTS
```

**게이트 2건 모두 실패한다.** 그리고 이 실행에서 스프레드가 **21.1%** 로 벌어진 것이
맥락 고정 설계를 다시 증명한다 — 샘플은 크게 흔들렸지만 **최솟값 1201.2 도 810 을 훨씬 넘어**
판정이 흔들리지 않았다.

**복원 확인**: `a57-restore-build.log` exit 0, 재실행 731.4 → **708.4 ms, 스프레드 0.4%, 2건 통과**.

### 2-4. 스레드 프로브 — 구현이 아니라 측정 (카드 3항)

```
[thread-probe] 3072x3072 per-pixel loop only; global sigma excluded
  hardware_concurrency reports 20
  NOTE: correctness of a threaded detector is NOT addressed here.

   threads       min ms    median ms   speed-up
         1        534.2        549.9      1.00x
         2        368.5        413.5      1.45x
         4        206.0        268.5      2.59x
         6        137.7        177.7      3.88x
         8        125.1        140.8      4.27x
        12         85.6         95.0      6.24x
        16         71.1         71.6      7.51x
        20         60.2         67.6      8.88x
```

프로브 설계에서 **일부러 유리하게 잡지 않은 것** 두 가지:
- **전역 σ 를 타이밍 밖에 뒀다.** 프레임 전체를 봐야 하므로 어떤 분할보다도 먼저 계산돼야
  하고, A-56 이 보인 대로 벡터화도 분할도 깔끔하지 않다. 그것을 속도 향상 수치에 섞으면
  숫자가 좋아 보이지만 거짓이 된다
- **행 구간 분할만.** 각 스레드가 같은 config 를 받아 자기 행만 돈다 — 실제 스레드 검출기가
  취할 모양이다

**교차 확인**: 1스레드 534.2 ms 는 A-55 가 실측한 픽셀 루프 532.0 ms 와 0.4% 차이다.
프로브가 같은 일을 재고 있다는 뜻이다.

**정확성은 이 카드에서 다루지 않았다**(카드 지시). 시간만 재고 맵은 버린다.

## §3. 스레드 정책 질문의 근거 (카드 3항 결론)

사용자에게 물을 때 필요한 숫자는 이것이다.

| | 현재(단일) | 12스레드 | 20스레드 |
|---|---|---|---|
| 픽셀 루프 | 534.2 ms | 85.6 ms | **60.2 ms** |
| 전역 σ (분할 안 됨) | 199.8 ms | 199.8 ms | 199.8 ms |
| **합계(추정)** | **734 ms** | **285 ms** | **260 ms** |
| SPEC 개선 목표 | 60 ms | 60 ms | 60 ms |

> **스레드만으로는 60 ms 에 닿지 않는다.** 픽셀 루프는 20스레드에서 60.2 ms 까지 내려가지만,
> **전역 σ 199.8 ms 가 분할되지 않은 채 그대로 남아 합계 약 260 ms** 가 된다. 목표의 4.3배다.
> 스레드를 허용하면 **병목이 픽셀 루프에서 전역 σ 로 완전히 넘어간다** — A-56 이 "전역 σ 는
> SIMD 로 줄어드는 종류의 비용이 아니다" 라고 한 그 단계가, 스레드 하에서는 **유일한 병목**이 된다.

부수적으로 읽히는 것:
- **12 → 20 스레드의 이득이 작다**(6.24 → 8.88배). i7-12700 은 P8+E4 이고 20은 논리 코어다.
  E-코어와 하이퍼스레드는 P-코어만큼 기여하지 않는다
- **8스레드에서 4.27배**로 이상적 8배에 못 미친다. 메모리·스케줄링 경합이 이미 보인다

## §5. Gaps — 관측하지 않은 것

1. **게이트를 이 기계에서만 검증했다.** CI 기계의 절대 성능은 다르고, **810 ms 가 거기서도
   적절한지 모른다.** CI 가 느리면 이 게이트는 상시 실패한다 — 첫 CI 실행 결과를 봐야 한다
2. **워밍업 1회가 충분한지 재지 않았다.** 2회·3회 워밍업에서 값이 더 내려가는지 확인하지 않았다
3. **§3 의 "합계(추정)" 는 덧셈이지 측정이 아니다.** 픽셀 루프와 전역 σ 를 따로 잰 값을
   더한 것이며, 실제로 스레드 검출기를 만들어 전체를 재지 않았다
4. **스레드 프로브의 정확성은 전혀 확인하지 않았다**(카드 지시). 맵 결과를 버렸으므로
   **이 수치는 "올바른 결과를 내는 데 걸리는 시간" 이 아니다.** 경계 행에서 이웃이 다른
   스레드 구간에 걸치는 문제는 읽기 전용이라 무해해 보이지만 **확인하지 않았다**
5. **전역 σ 를 분할할 수 있는지 조사하지 않았다.** §3 은 "분할 안 됨" 을 전제로 한 추정이고,
   차분 생성은 분할 가능하고 히스토그램은 스레드별 부분합 후 병합이 가능할 수도 있다 —
   **그렇다면 §3 의 결론이 바뀐다**
6. **E-코어/P-코어 배치를 고정하지 않았다.** 스케줄러가 정했다
7. 3072² 한 크기, 합성 프레임, 이 컴파일러 한 조합. 실프레임 미확인(#151)

## §6. Residual-risk — 남는 위험

1. **가장 큰 위험은 Gap 5 다.** "전역 σ 는 분할되지 않는다" 를 전제로 §3 의 260 ms 를 냈는데,
   **그 전제를 조사하지 않았다.** 차분 생성은 명백히 분할 가능하고, 기수 히스토그램도
   스레드별 테이블 후 병합이 원리상 가능하다. 분할된다면 스레드만으로 60 ms 에 훨씬 가까워지고
   **스레드 정책 질문의 답이 달라진다.** 사용자에게 올릴 때 이 불확실성을 함께 올려야 한다
2. **게이트가 CI 에서 처음 도는 순간이 진짜 시험이다.** 로컬 731 ms 와 CI 가 크게 다르면
   게이트를 옮겨야 하고, 그건 **측정 뒤에 할 일**이지 지금 추측으로 넉넉하게 잡을 일이 아니다
3. **최솟값 게이팅은 하향 잡음에는 무력하다.** 어떤 변경이 캐시 거동을 바꿔 *가끔* 빨라지면
   최솟값이 그것을 잡아 게이트를 통과시킬 수 있다. 잡음이 한쪽으로만 작용한다는 전제는
   이 기계·이 부하에서 관측된 것이고 보편 법칙이 아니다
4. **개선 목표 60 ms 를 단언하지 않는 선택은 의도적이지만 위험도 있다.** 목표가 게이트로
   걸려 있지 않으므로 **아무도 60 ms 로 다가가지 않아도 빨간불이 켜지지 않는다.**
   진행 추적은 게이트가 아니라 보고서가 해야 한다
5. **1024² 게이트 120 ms 는 여유가 크다**(현재 87.0). 작은 프레임은 L3 에 들어가 산포가
   달라서 넉넉히 잡았는데, 그만큼 **회귀를 늦게 잡는다**
