# QA-A-247 — 앱 경로와 같은 호출로 실데이터 전처리 단계별 시간 (마일스톤 3 U8 예산)

## 1. 결과

| 항목 | 값 (3 프로세스 × 5 회, 중앙값의 범위) |
|---|---|
| 앱이 한 프레임을 처리할 때 부르는 전처리 호출 합계 | **157.6 ~ 161.8 ms** (U8 예산 3000 ms 의 약 5 %) |
| 그중 맵 적재 3 회 (offset + gain + defect) | 100.6 ~ 104.0 ms |
| 그중 `xpe_preprocess_pipeline_out` | 49.8 ~ 52.9 ms |
| 그중 `init` / `shutdown` | 0.00 ms / 2.8 ~ 3.9 ms |
| 출력 | 15 회 모두 기준 영상 v2 (`d152e8eb…`)와 **바이트 동일** |

앱이 보는 전처리 몫은 프레임당 약 160 ms 이고, 이 중 적재가 약 65 %, 보정이 약 32 % 다. 앱 전체가 3000 ms 를 넘으면 전처리 호출이 원인일 가능성은 낮다(전처리 몫은 예산의 5 %). 나머지는 관리 코드 쪽 복사·변환·렌더링(§5)이고 gui 의 측정(GUI-C-236)이 가른다.

## 2. 앱이 전처리 DLL 을 부르는 순서와 인자

`gui/ImageProcTest/Services/Native/GuiPreprocessRunner.cs` (main `cff0ef79` 의 작업 트리에서 읽음; 함수 이름이 주소이고 줄 번호는 `grep -n` 값이라 고치면 밀린다):

1. `Run` — 보정 세 파일이 있는지 확인(`offset.xcal`, `gain.xcal`, `defect.xcal`; 없으면 "no calibration data" 로 건너뜀).
2. `XpePreprocessNative.xpe_preprocess_init(null)` (`:70` 부근).
3. 적재 세 번, 이 순서로: `xpe_calib_load_offset`, `xpe_calib_load_gain`, `xpe_calib_load_defect_map` (`:80-82`).
4. `RunPipelineOut` → `xpe_preprocess_pipeline_out(ref input, ref output, ref metadata, IntPtr.Zero, IntPtr.Zero, PipelineConfigJson)` (`:141`). 입력은 UInt16 버퍼(복사해 넣음), 출력은 Float32 버퍼, `calibState` 와 `ghostHandle` 은 둘 다 NULL, 설정은 `{"bypassTemp":true,"bypassNonlinearity":true,"bypassBinning":true}`, 메타데이터는 `XpeImageMetadataNative.Create(bodyPart, kVp, mAs 2.0, SID 1000 mm, pixelPitch)`.
5. 선택: `measureExposureIndex` 일 때만 노출 지수 측정 (일반 실행은 안 한다).
6. `finally` 에서 `xpe_preprocess_shutdown()` (`:105`).

**중요한 점**: 앱은 이 전체(init, 적재 3 회, 보정, shutdown)를 **프레임마다** 한다. `shutdown` 을 `finally` 에서 부르므로 맵이 프레임 사이에 유지되지 않는다. 그래서 프레임당 비용에 맵 적재 약 100 ms 가 매번 들어간다. (1단계의 B7 은 맵을 한 번 적재하고 40 프레임을 연속 처리한 값이라 이 적재를 포함하지 않는다.)

## 3. 측정

하니스 `A241Measure.DISABLED_A247_AppPathTiming` (`test_zz_a241_measure.cpp`, 소스 사본 `evidence/00_harness_a247.cpp.txt`): 위 호출을 같은 순서·같은 인자로, `calib-real-v2` 세트와 실영상 `wrist_lat_3072x3072.raw` 에 대해 한 프로세스 안에서 5 회, 호출마다 `steady_clock` 으로 잰다. 메타데이터는 bodyPart "WRIST", kVp 60, mAs 2, SID 1000 mm, pitch 0.15 (앱의 설정값이 아니라 대표값; 단계 함수가 메타데이터로 시간이 달라지지 않는다). 세 프로세스를 따로 돌렸다 (`evidence/20_app_path_timing.txt`).

DLL: `build/ci-preprocess/bin/xpe_preprocess.dll`, sha256 `c2524c57d80f3c9cb7ad72195355c11e855ba40c53132bf7f26154858fb94d32`, 1,022,976 B, 2026-10-08 10:48 빌드. **출처**: 이 기계에서 `cmake --build --preset ci-preprocess` (RelWithDebInfo)로 만든 로컬 빌드이고 CI 가 만든 산출물을 내려받은 것이 아니다. 소스는 `dev/preprocess` 의 `781283dd`(QA-A-246c) — main 의 전처리 코드에 246 의 `_out_ex`(앱이 쓰지 않는다)가 더해진 것이다. `HEAD`(`f10166a7`)는 그 위에 `.claude/settings.json` 훅 명령 변경 한 커밋만 있어 DLL 에 영향이 없다.

## 4. 1단계 B7·B9 와 나란히

| 항목 | 1단계 값 (QA-A-240) | 이번 (3 프로세스 중앙값 범위) | 같은 입력인가 |
|---|---|---|---|
| B7 프레임 처리 | 기본 설정에 `bypassTemp/Nonlinearity/Binning` 을 더한 설정, 40 프레임 연속, 중앙값 **52.1 ms** (`pipeline_ex`, 입력 덮어쓰기). 기본 설정 55.9 ms | `pipeline_out`, 같은 설정, 49.8 ~ 52.9 ms | 같은 영상·같은 `calib-real` 계열 맵이지만 맵이 다르다: B7 은 6장 평탄으로 만든 gain 과 `a240` 세트, 이번은 평탄 4·5·6 `calib-real-v2`. 호출이 다르다 (덮어쓰기 대 별도 출력 버퍼) |
| B9 맵 적재 | 세 파일 합계 중앙값 **97.9 ms** (94.7~100.3), 12 회 | 100.6 ~ 104.0 ms | 파일 크기 같음(offset 37,748,950 B, gain 37,749,092 B, defect 9,437,336 B), 내용은 gain 만 다름. `init` 을 매번 부르는 점은 B9 도 같음 |

- 프레임 처리: 이번 값이 B7 의 같은 설정 값(52.1 ms)과 같은 수준이다 (차 −2.3 ~ +0.8 ms). 별도 출력 버퍼가 시간을 늘리지 않았다.
- 적재: 이번이 B9 보다 2.7 ~ 6.1 ms 높다(3 ~ 6 %). B9 의 최대(100.3 ms)에 가깝거나 약간 넘는 값이다. 차이의 원인(gain 내용의 차이, 241 계열이 적재에 더한 검사들, 측정 시점의 기계 상태)은 분리하지 않았다. 둘 다 SRS 적재 한도 200 ms 의 절반 수준이다.

## 5. 이 측정이 보는 것과 못 보는 것

보는 것: 앱이 프레임마다 DLL 에 하는 호출의 네이티브 시간. 출력이 기준 영상 v2 와 같으니 시간을 잰 호출이 1단계 기준과 같은 일을 한 것이다.

못 보는 것 (앱 전체 시간 중 gui 가 재는 몫):
- 관리 코드 쪽 변환: `ushort[]` → `short[]` 복사, `Marshal.Copy`(입력 18.9 MB → 네이티브 버퍼), 출력 `ReadFloats`(37.7 MB), `ScaleToUInt16`(프레임 최대값 정규화), 화면 렌더링.
- 보정 세트 파일을 처음 읽는 **콜드 캐시** 적재 (이번에는 파일이 OS 캐시에 있다; 3 프로세스 모두 같은 파일을 방금 읽은 상태).
- `pipeline_out` 안의 단계별 시간 (카드의 요구는 앱이 부르는 호출 단위). 단계 안 시간은 따로 재지 않았다.
- 앱이 쓰는 실제 메타데이터 값(대표값으로 대신함).
- 앱의 실제 보정 디렉터리 위치가 느린 저장장치일 때.

참고 (카드 범위 밖의 관찰, 개선 제안이 아니다): 앱이 프레임마다 맵을 다시 적재하므로 프레임당 약 100 ms 가 적재다. 이 비용이 문제가 되면 `shutdown` 을 프레임마다 부르지 않는 쪽이 gui 의 선택지가 될 수 있다. 결정은 리더와 gui 의 몫이다.
