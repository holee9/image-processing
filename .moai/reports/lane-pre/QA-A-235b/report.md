# QA-A-235b — 보정 적재의 "나머지"(0 채움 + 전체 복사) 줄이기와 효과 측정

카드: QA-A-235b · Refs #245 · 제품 코드 변경(Codex 대상). 단언은 넣지 않았다(리더 결정).

## 1. 무엇을 바꿨나

`read_xcal_file` 에 선택 매개변수 `XCalPayloadSink`(`xcal_reader.hpp`)를 더했다. 비압축·비어 있지 않은 페이로드에서 reader 가 sink 의 `acquire(ctx, header, len)` 로 목적 버퍼를 한 번 받고, 1 MiB 조각을 **그 버퍼로 곧바로** 읽으면서 같은 조각을 해시에 넣는다. 해시 값과 검사 순서(헤더 검증 → 설정 블록 → 페이로드 읽기 → 해시 비교)는 그대로다.
- 이전: `payload.resize`(0 채움, 전체 크기) → 읽기 → 로더가 `memcpy` 로 맵 버퍼에 복사(전체 크기 한 번 더).
- 이후: 맵 버퍼(`new float[]` / `new uint8_t[]`, 값 초기화 없음)에 곧바로 읽는다.
- 적용: `xpe_calib_load_offset`, `xpe_calib_load_defect_map`, `xpe_calib_load_gain`(스칼라·다항식 둘 다). 보조 경로는 그대로 둔다 — 압축 파일, 길이 0, 로더가 받지 않는 형식·길이는 `acquire` 가 nullptr 로 **양보**하면 옛 경로(벡터에 읽고 복사)가 돌아서 이중으로 잘못된 파일이 받는 오류 코드의 우선순위가 변하지 않는다.
- 크기 계산은 `size_t` 로 먼저 한다(`static_cast<size_t>(h.width) * h.height`, 길이 비교는 `uint64_t`). 32비트 축소 없음.
- **실패 시 원래 맵 보존**: 목적 버퍼는 로더의 지역 변수이고(`StagedOffset`/`StagedDefect`/`map`), 파일 전체가 받아들여진 뒤 기존 커밋 코드가 공개한다. 읽기·해시·그 뒤의 어떤 실패에서도 전역 저장소에는 닿지 않는다.

## 2. 실패 경로의 버퍼 상태 — 시험 (`test_load_failure_keeps_store.cpp`, 5 케이스)

세 로더에 대해, 맵 A 를 적재해 탐침 프레임에 적용한 출력을 기록하고, 나쁜 파일 B 를 시도해 (1) 오류 코드, (2) 탐침 출력이 A 때와 같음, (3) 이어서 좋은 파일이 적재됨을 확인한다:

| 나쁜 파일 | 기대 코드 | 세 로더 |
|---|---|---|
| 페이로드 바이트 하나 뒤집음(해시 불일치) | `XPE_ERR_CONFIG_INVALID` | 통과 |
| 잘린 파일 | `XPE_ERR_IO_FAILED` | 통과 |
| 헤더가 잘못된 페이로드 길이를 선언 | `XPE_ERR_CONFIG_INVALID` | 통과 |
| 다른 종류의 파일(offset 로더에 defect, gain 로더에 offset) | `XPE_ERR_CONFIG_INVALID` | 통과 |
| (확인) 적재된 맵이 파일 페이로드 그대로 | 400 = 500 − 100 등 | 통과 |

**기대 코드가 옛 동작과 같은가**: 새 시험을 옛 경로에서도 돌려 확인했다 — 반증 팔 S1(sink 를 항상 양보 = 옛 벡터 경로)에서 5개 모두 **통과**한다(`evidence/30_arms.txt`). 그러니 위 코드와 저장소 보존은 옛 구현과 같은 결과다. 반증 S2(해시 비교 생략)는 `AFlippedPayloadByteIsRefused…` 가 빨강. 복원 뒤 초록.

## 3. 효과 — 바꾸기 전/후를 번갈아 (`evidence/10_ab_load_breakdown.txt`, `11_ab_summary.txt`)

같은 시험 소스(`A235LoadBreakdown`, 3072², 라운드 9회)를 **전/후 실행 파일로 번갈아** 세 번씩(B A B A B A) 돌렸다. 표는 세 번의 중앙값의 중앙값(ms, 로컬, 파일은 방금 쓴 것이라 OS 캐시에 있음):

| 단계 | 전 | 후 | 변화 |
|---|---|---|---|
| offset 읽기 (미변경 대조) | 21.7 | 21.6 | 0 |
| offset SHA-256 (미변경 대조) | 17.3 | 17.3 | 0 |
| **offset 전체 적재** | **53.5** | **44.5** | **−9.0** |
| gain 읽기 / SHA (대조) | 21.6 / 17.2 | 21.8 / 17.4 | 0 |
| **gain 전체 적재** | **59.6** | **49.9** | **−9.7** |
| defect 읽기 / SHA (대조) | 5.4 / 4.3 | 5.3 / 4.4 | 0 |
| **defect 전체 적재** | **13.3** | **10.9** | **−2.4** |
| 기준 SHA-256 64 MiB (기계 대조) | 30.9 | 30.8 | 0 |
| **세 파일 합계** | **126.4** | **105.3** | **−21.1 (−16.7%)** |

- 대조(읽기, SHA, 기준 해시)는 전후가 같고 세 번의 실행 사이 흩어짐도 ±0.5 ms 안이다 — 변한 것은 "나머지"뿐이다.
- **"나머지"**(전체 − 읽기 − SHA): 전 offset 14.5 · gain 20.8 · defect 3.6 = 38.9 ms → 후 5.6 · 10.7 · 1.2 = 17.5 ms (약 −55%). 남은 몫은 새 버퍼에 처음 쓸 때의 페이지 접근 비용과 gain 의 결함 분류 훑기 같은, 이번에 건드리지 않은 일이다.
- 전체 합계는 카드 가설의 "나머지 약 32%"를 모두 걷어내지 못하고 약 17% 를 걷어냈다(나머지의 절반 남짓).

**CI 환산**: "로컬 × 1.5" 는 QA-A-235 의 CI 네 번(합계 192~215 ms) 대 로컬 129 ms 에서 나온 **추정**이다. 그 비율을 그대로 쓰면 CI 평소 합계 약 192 → 약 160 ms 정도가 되지만, 이것은 로컬 변화량 −21 ms 에 1.5 를 곱한 값(약 −32 ms)을 뺀 것이지 CI 측정이 아니다. CI 실제 수치는 병합 뒤 리더가 로그에서 읽는다.

## 4. defect 143.8 ms 의 튐 — 시험 순서·파일 경로만 읽은 기록

`test_pipeline_performance_3072.cpp`: 픽스처가 `temp_directory_path()/qa_a_230_perf3072` 를 **SetUp 에서 지우고 새로 만들고 TearDown 에서 지운다**(83~95행). 세 파일(offset, gain, defect)을 이 디렉터리에 순서대로 모두 쓴 뒤 offset → gain → defect 순으로 적재한다(126~130행 근처). 즉 defect 파일은 **마지막에 쓰고 마지막에 읽는다**. 다른 시험이 같은 디렉터리 이름이나 같은 파일을 쓰는지는 이름 grep 으로 `test_integration.cpp` 에 `pipeline_perf` 문자열이 나오는 것만 확인했고, 그 시험이 같은 경로를 쓰는지는 열어 보지 않았다.
**원인은 정하지 못했다.** 이 읽기로 알 수 있는 것은 파일이 적재 직전에 같은 프로세스가 쓴 새 파일이라는 점뿐이다(offset·gain 도 마찬가지로 새 파일이고 그쪽은 튀지 않았다). seed 1 에서 이 시험 직전에 어떤 시험이 돌았는지는 읽지 않았다.

## 6. Gaps / Residual-risk

- 효과는 **로컬, OS 캐시가 있는 상태**의 측정이다. 콜드 읽기·CI 에서의 실제 크기는 모른다.
- 압축된 XCal(RLE)은 sink 를 쓰지 않는다. 그 경로의 효과는 없다(`test_xcal_compression.cpp` 와 oom 시험이 압축 파일을 적재하고 전체 1013 에 포함되어 통과했다. 그 경로의 시간은 따로 재지 않았다).
- 다른 로더(비선형 LUT, 다항식 생성기의 파일 읽기)는 바꾸지 않았다.
- gain 로더에서 sink 가 받은 맵을 이후 결함 분류가 바꾼다(`map[k] = 1.0f`) — 옛 경로와 같은 시점·같은 자리에서 일어나며, 이 변경 전후 gain 시험이 모두 통과했다.
- `AFileOfAnotherType…` 의 gain 쪽은 offset 파일을 주어 CONFIG_INVALID 를 확인했다. 다른 잘못된 형식 조합은 시험하지 않았다.
