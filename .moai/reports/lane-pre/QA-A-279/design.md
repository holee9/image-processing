# QA-A-279 — W15b 진단 계측 보강 설계 초안 (코드 변경 없음)

Refs #278. 이 문서는 설계 초안이다. 코드·시험·제품 파일은 바꾸지 않았고 아무것도 실행하지 않았다. 리더와 Reviewer(#267) 판정 뒤에 구현한다.

## 0. 불변 조건 (이 설계가 건드리지 않는 것)

- 사전조건 `proxyShift >= 0.8 * 1500` (1200 ms)와 그 단언 문구, 화면 단언 `screenShift >= 0.8 * 1500`, 주입량 1500 ms, 합격 기준은 그대로 둔다.
- 비교 대상은 proxy 중앙값 그대로이며 다른 구간(chain/display 등)으로 바꾸지 않는다.
- 게이트가 되는 측정은 지금과 같다: 무지연 앱 1개에서 3회 열기 → 종료 → 지연 앱 1개에서 3회 열기, 각 군의 정렬된 두 번째 값이 중앙값. 표본 수 3, 순서, 앱 시작 방식, 관측 알고리즘을 바꾸지 않는다.
- 새 계측은 **관찰 전용**이다. 새 단언을 넣지 않고(7절의 선택 사항 제외), 기존 단언의 입력 값도 바꾸지 않는다.
- 제품 동작은 바꾸지 않는다. 변경은 `XPE_TEST_FAULTS` 빌드에만 존재하는 코드로 한정한다(출하 빌드에는 이 형식이 없다 — `FaultInjectingBackend.cs` 첫 줄의 `#if XPE_TEST_FAULTS`).

## 1. 근거 (QA-W15B-1 에서 가져온 사실만)

- 실패 실행(CI 39602814368)의 chain/display 중앙값 차이는 +1479 ms 로 주입 1500 ms 가 거의 그대로 들어갔다. 그런데 proxy 중앙값 차이는 1006 ms 였다(1200 ms 에 194 ms 부족).
- 무지연 3회: proxy 2557 / 3855 / 2051 ms. 두 번째 열기의 prepare 가 1836 ms(다른 5회는 8~59 ms)였고 첫 열기가 더 무거웠다(pre 481·enhance 619·render 576). 정렬 두 번째 값이 첫 열기의 2557 ms 가 되어 기준 중앙값이 올라갔다.
- 직전 실행(39591918725)은 무지연 중앙값 2005 ms, 지연 3784 ms 로 shift 1779 ms 였다.
- 두 보존 로그에는 주입 sleep 의 실제 호출 횟수와 시간이 없다(`faultInjection=… calls=…` 상태 출력 없음). 따라서 "주입이 소실됐는가"와 "기준군이 흔들렸는가"를 로그만으로 가를 수 없다. 이 설계의 목적은 이 두 가지를 다음 실패 때 로그에서 갈라 읽을 수 있게 하는 것이다.
- 3개 표본과 고정 순서에서는 이상치 하나나 무거운 첫 열기가 중앙값을 바꾼다. 표본 수를 늘리는 안은 게이트의 정의(중앙값)를 바꾸므로 채택하지 않는다(4.3절).

## 2. (b) 주입 증거: sleep 마다 기록

### 2.1 무엇을 남기는가

`FaultInjectingBackend.DelayIfArmed()` 가 `Thread.Sleep` 을 부를 때마다 한 줄을 남긴다.

| 필드 | 값 | 이유 |
|---|---|---|
| `call` | 이 래퍼의 display pipeline 호출 번호(`_calls`, 1부터) | 시험의 open 번호와 짝짓는 열쇠 |
| `overload` | `chain` 또는 `displayInput` | 두 ApplyDisplayPipeline 중 어느 쪽인지 |
| `requestedMs` | 요청한 지연(예: 1500) | 설정과 실측 비교 |
| `startUtc`, `endUtc` | sleep 직전·직후 UTC 시각(ISO 8601, ms 정밀) | 시험이 기록하는 open 시간창과 대조 |
| `elapsedMs` | `Stopwatch` 로 잰 sleep 경과(소수 1자리) | 시스템 시계가 아니라 단조 시계를 쓴다 |
| `thread` | 관리 스레드 번호 | background task 에서 불렸는지 확인 |
| `pid` | 프로세스 번호 | 어느 앱 프로세스의 기록인지 |

지연 0 이하이면 sleep 을 부르지 않으므로 항목이 생기지 않는다. 대신 호출 수만 센다(2.3절).

### 2.2 어디에 남기는가

- 파일 하나에 한 줄씩 추가한다. 경로는 환경 변수 `XPE_TEST_FAULT_LOG` 가 있을 때만 쓴다. 변수가 없으면 아무것도 쓰지 않는다. 이 변수와 파일 쓰기는 `XPE_TEST_FAULTS` 빌드 안에만 둔다.
- `FaultInjectingBackend.Describe()` 의 출력 문자열은 **바꾸지 않는다.** 그 문자열은 `FailedRenderScenarios`(`faultInjection=display-pipeline-after:2 calls=1`)와 `ViewportTruthScenarios`(`faultInjection=off`)가 정확히 비교하는 계약이다.
- 자동화 트리에 새 항목을 추가하지 않는다. `MainWindowViewModel.cs`·`MainWindow.xaml.cs` 는 작업 트리 미커밋 변경 8개에 들어 있어 건드리지 않는다. 변경 대상은 두 파일뿐이다.
  - `gui/ImageProcTest/Services/FaultInjectingBackend.cs` (미커밋 변경 목록에 없음, 확인함)
  - `clients/ImageProcTest.E2ETests/Scenarios/Operator/QuickStartWalkthroughScenarios.cs` (미커밋 변경 목록에 없음, 확인함)
- 측정 구간을 건드리지 않는다. sleep 이 끝난 직후 파일을 쓰면 그 쓰기 시간이 chain/display 에 들어간다. 그래서 래퍼는 항목을 **메모리 목록에만** 넣고(잠금 하나, 비용 마이크로초), 별도 배경 스레드가 200 ms 마다 파일에 덧붙인다. `Shutdown()` 에서 남은 것을 비운다. 앱이 강제 종료돼도 마지막 200 ms 분량만 잃는데, 시험은 열기가 끝난 뒤 수 초 지나서 앱을 닫으므로 측정된 열기의 항목은 이미 파일에 있다.
- 시험 프로세스가 `XPE_TEST_FAULT_LOG` 를 앱 시작 전에 환경에 설정하면 자식 프로세스가 이어받는다. `GuiApp.Launch` 가 환경을 물려주는지는 구현 첫 단계에서 확인한다(미확인). 물려주지 않으면 이 설계는 환경 변수 대신 기존 `--automation-fault` 옆의 인수를 쓰는 안으로 바꿔야 하고, 그 경우 `AutomationArgs.cs` 변경이 늘어나므로 다시 검토를 받는다.

### 2.3 시험이 읽는 방식

- 시험은 지연 앱을 닫은 뒤(또는 읽기 전에 1초 기다린 뒤) 파일을 읽어 다음을 출력한다. 모두 `output.WriteLine` 이며 단언이 아니다.
  - 항목 수, 항목별 `elapsedMs`, 합계, 요청값 대비 최솟값·최댓값
  - 각 열기(open 1~3)에 속한 항목: 시험이 열기마다 기록한 UTC 시간창(파일 대화상자 확인 직전 → `FrameTimingText` 에 `open-to-2nd-tick (proxy) #i:` 가 나타난 시각) 안에 `startUtc` 가 있는 항목
  - 열기마다 `proxy` 와 `주입 sleep 합계` 와 `proxy − 주입 sleep 합계`(= 주입 외 시간)
- 이 마지막 줄이 핵심이다. 지연군의 "주입 외 시간"을 무지연군의 proxy 와 나란히 보면, 다음 실패에서 "주입이 거의 그대로 들어갔고 기준군이 늦었다"와 "주입 sleep 이 기록되지 않았다/짧았다"를 한눈에 가를 수 있다.
- 시간창에 속하지 않는 항목(예: 열기 뒤 비교 모드 참조 캡처에서 불린 display pipeline 호출)은 "창 밖"으로 따로 센다. 개수가 예상과 다르면 그대로 출력만 한다.
- 무지연 앱은 `Wrap` 이 내부 backend 를 그대로 돌려주므로(래퍼 없음) 기록이 없다. 무지연 군에 래퍼를 씌우면 측정 조건이 달라지므로 **씌우지 않는다.** 무지연 군의 호출 수가 필요하면 4.2절의 별도 팔에서 얻는다.

## 3. 반증: 주입을 끈(지연 0) 변이

계측이 "주입 없음"을 정말 보여주는지 두 층으로 확인한다.

### 3.1 단위 수준 (GUI 없음, 가장 싼 반증)

`clients/ImageProcTest.IntegrationTests` 쪽에서 `FaultInjectingBackend` 를 가짜 `IXpeBackend` 로 감싸고 `ApplyDisplayPipeline` 을 직접 부른다. 이 프로젝트는 이미 `FaultInjectingBackend.cs` 를 소스 링크로 쓰는 시험들이 있다(`FaultSeamCompiledOutTests`, `BackendLifecycleTests`, `AutomationArgsTests`). 새 시험 하나(예: `DelayLog_*`)로 다음을 단언한다.

| 입력 | 기대 기록 |
|---|---|
| 지연 50 ms, 호출 2회 | 항목 2건, 각 `elapsedMs` ≥ 50 − 허용 오차, `call` 1·2 |
| 지연 0 (`display-delay:0`), 호출 2회 | 항목 0건, 호출 수 2 — "주입 없음"이 기록으로 구별됨 |
| 지연 없음(`Wrap` 이 그대로 반환) | 래퍼 없음, 파일 없음 |

이것이 변이 반증이다: 시험 안에서 지연 값을 50 → 0 으로 바꾸면 "항목 ≥ 1" 단언이 실패해야 한다. 실행은 사용자 승인 뒤 비 GUI 시험 1개로만 하고, 승인 전에는 실행하지 않는다.

### 3.2 W15b 수준 (CI 에서만)

W15b 안에 관찰 전용 팔 하나를 추가한다(4.2절). 이 팔은 `display-delay:0` 으로 앱을 띄워 3회 열고, 같은 읽기 코드로 "항목 0건, 호출 N건, armed=true, delayMs=0" 이 출력되는지 본다. 이 출력은 단언이 아니라 CI 로그에서 사람이 읽는 증거다. GUI E2E 는 로컬에서 실행하지 않는다(전역 입력 위험). 실행 증거는 CI 에서만 얻는다.

## 4. (d) 표본: 번갈아·짝지은·워밍업 분리

### 4.1 게이트 팔은 그대로, 같은 자료로 짝지은 표를 출력한다

게이트 측정(무지연 3 → 지연 3)에서 얻은 열기별 값을 그대로 쓰고, 출력만 늘린다. 단언 입력(`proxyShift`)은 계산식 그대로다.

- 열기 번호별 짝: `delayed[i] − baseline[i]` (i = 1..3)와 chain/display, prepare, render 의 짝별 차이. 중앙값 차이 하나가 숨기는 "어느 열기가 흔들렸는가"를 보이기 위함이다. 이 짝은 서로 다른 앱 프로세스의 같은 번호 열기이므로 인과 비교가 아니라 나란히 놓는 표라고 표에 적는다.
- 첫 열기(워밍업)를 따로 적는다: 각 군의 열기 1을 "warm-up" 으로 표시하고, 열기 2·3 만의 평균과 차이(n=2, 참고용)를 함께 출력한다. 게이트 값(3개 중앙값)은 바꾸지 않는다. n=2 값은 판정에 쓰지 않는다고 출력 줄에 박아 둔다.
- 값은 이미 `FrameTimingText` 에서 읽는 항목(read, prepare, chain-and-display, pre, enhance, ui, render)이다. 새로 읽는 값은 없고, 현재 `OpenMeasurement(Proxy, ScreenMs, EarliestMs)` 에는 이 세부 항목이 없으므로 레코드를 확장한다(기존 필드·순서 유지).

### 4.2 번갈아 보는 추가 팔 (관찰 전용)

한 앱 프로세스 안에서는 지연이 켜져 있거나 꺼져 있으므로 한 앱 안에서 무지연·지연을 번갈아 돌릴 수 없다. 앱을 번갈아 띄우면 매 열기가 첫 열기(JIT·캐시 차가움)가 되어 게이트와 측정 조건이 달라진다. 그래서 게이트 팔은 그대로 두고, **게이트 측정 뒤**에 순서를 뒤집은 팔을 한 번 더 돈다.

- 순서: 게이트 팔(무지연 3 → 지연 3) 다음에 역순 팔(지연 3 → 무지연 3). ABBA 형태가 되어 시간 흐름에 따른 드리프트(러너 부하 증가·감소)를 서로 상쇄해서 볼 수 있다. 대신 앱 시작이 2회 늘고 GUI 열기가 6회 늘어난다.
- 영점 팔: 같은 뒤쪽에 `display-delay:0` 으로 3회(3.2절). 래퍼는 있고 sleep 은 없는 조건이다. 무지연 기준과의 차이는 "래퍼 존재 비용"의 상한 근사가 된다.
- 이 추가 팔의 결과는 게이트 판정에 쓰지 않는다. 출력에 `DISCLOSURE ONLY` 를 붙이고, 게이트 단언(`Assert.True(proxyShift …)`)은 **추가 팔을 돌리기 전에** 값을 계산해 두되 단언 실행 자체는 출력 뒤로 미룬다(실패해도 진단 출력은 남도록 순서만 바꾼다. 단언 식과 문구는 불변).
- 추가 팔에서 예외가 나면(앱 시작 실패 등) 게이트 판정을 바꾸지 않도록 잡아서 `DISCLOSURE ARM FAILED: <메시지>` 로 크게 출력한다. 이 try/catch 를 허용할지는 Reviewer 가 정한다(7절 결정 2).
- 비용: GUI 앱 시작 4회와 열기 9회가 늘어난다(앱 1개당 약 수십 초 규모는 CI 로그의 기존 실행 시간으로 확인해 구현 보고서에 적는다). 시간 길이를 지금 추정해서 적지 않는다.

### 4.3 표본 수를 바꾸지 않는 이유

게이트는 "각 군 3회의 중앙값"으로 정의돼 있다. 표본 수를 5로 늘리면 중앙값의 정의와 그 통계적 성질이 달라진다. 즉 합격 기준이 아닌 측정 정의를 바꾸는 일이라 이 카드의 불변 조건("비교 대상·기준 불변")에 닿는다. 3회 중앙값이 이상치 한 개에 흔들린다는 사실은 위 4.1~4.2의 출력으로 **드러내되 고치지 않는다.** 표본 수 변경이 필요하면 별도 카드와 Reviewer 판정이 필요하다.

## 6. 검증 계획 (구현 단계, 지금은 실행하지 않음)

1. 새 비 GUI 시험의 지연 50·0·없음 3행이 통과하고, 지연 값을 0 으로 바꾼 변이에서 "항목 ≥ 1" 이 실패하는지(원문 인용). 실행은 사용자 승인 후 시험 1개 단독으로만.

3. `FailedRenderScenarios`·`ViewportTruthScenarios` 가 읽는 `Describe()` 문자열이 바이트 단위로 같은지(문자열 비교 시험이 기존에 있다).
4. W15b 자체는 로컬에서 실행하지 않고 CI 의 `gui-e2e-native` 로그에서 확인한다: 새 출력이 나오는지, 게이트 단언이 이전과 같은 조건으로 판정하는지, 지연 앱의 sleep 항목이 열기마다 기록되는지, 영점 팔이 "항목 0건"을 보이는지.
5. 줄 끝 공백 검사(`tools/ci/Test-TrackedTextFiles.ps1`)를 커밋 전에 돌린다.

## 7. 리더·Reviewer 가 정할 것

1. 파일 로그(`XPE_TEST_FAULT_LOG` + 배경 기록)로 가는가, 아니면 자동화 트리 항목을 추가하는가. 이 설계는 파일 방식을 제안한다(미커밋 gui 변경 8개와 겹치지 않고 `Describe()` 계약을 건드리지 않기 때문). 트리 항목은 `MainWindowViewModel.cs` 변경이 필요해 현재 작업 트리와 충돌한다.
2. 4.2절의 역순 팔·영점 팔을 W15b 안에 넣는가, 아니면 게이트 팔 + 4.1절 출력(앱 시작 추가 없음)만 먼저 넣는가. 이 설계는 추가 팔까지 넣는 안을 제안하지만, 추가 팔의 예외를 잡는 try/catch 가 "관찰이 판정을 바꾸지 않는다"는 원칙에 맞는지는 Reviewer 판단이 필요하다. 가장 작은 안은 4.1절만이다.
3. 계측의 건전성(래퍼가 있는 지연 앱에서 기록 항목 ≥ 1)을 새 단언으로 올릴 것인가. 올리면 계측 소실이 즉시 실패로 드러나지만 새 실패 경로가 생긴다. 이 설계는 첫 단계에서는 올리지 않는다.
4. 3.1절의 비 GUI 시험 실행에 사용자 승인을 받는 절차(카드 단위 1회 승인 요청).

## 8. 이 설계가 하지 않는 것

- 임계값 1200 ms, 주입량 1500 ms, 단언 식·문구, 비교 대상 proxy, 표본 수 3 을 바꾸지 않는다.
- 실패 원인을 확정하지 않는다. 이 문서는 다음 실패에서 원인을 가를 수 있게 하는 계측 설계이며, 왜 1006 ms 가 나왔는지는 아직 입증되지 않았다.
- 로컬 GUI E2E, 빌드, 시험, push 를 하지 않았다. 작업 트리의 미커밋 gui 변경 8개는 그대로다.

## 9. 미검증

- `GuiApp.Launch` 가 시험 프로세스의 환경 변수를 앱에 물려주는지(2.2절).
- 배경 기록 스레드가 측정에 영향을 주지 않는다는 점은 설계 추론이다(구현 후 CI 의 열기 시간 분포를 직전 실행과 비교해야 한다).
- 열기 시간창에 sleep 항목을 짝짓는 방식이 모든 열기에서 정확히 1건씩 맞는지(열기 하나에서 display pipeline 이 몇 번 불리는지) 확인하지 않았다.
