## §2. 할 일 1 — 3072² 비트 파리티

### 2-1. 인덱스 산술 감사 (카드 요구: 안전한 *이유*를 적을 것)

읽은 것과 그 결과:

| 위치 | 계산 타입 | 3072² 최대값 | 타입 한계 | 판정 |
|---|---|---|---|---|
| `DetectFrame` 맵 쓰기 | `size_t`(64비트) | 9,437,183 | 1.8e19 | 안전 |
| `CollectNeighborValues` 화소 읽기 (350, 636행) | **`uint32_t`** | 9,437,183 | 4,294,967,295 | 안전 |
| `DetectDefectivePixel` 중심 화소 (689행) | **`uint32_t`** | 9,437,183 | 4,294,967,295 | 안전 |
| 행 분할 경계 | `uint64_t` → 좁힘 | — | — | 안전 |

**경계로 적는다**: 화소 인덱스는 `width * height - 1` 이 최대이고 `uint32_t` 로 계산되므로
**`width * height <= 2^32` 인 동안 정확**하다. 3072² = 9,437,184 대 4,294,967,296 — **455배 여유**.
정사각 프레임이면 **65536×65536 까지** 정확하다. 행 분할은 `uint64_t` 중간값을 거쳐 좁히므로
`height * threadIndex` 가 어떤 스레드 수에서도 감싸지 않는다.

**감사 중 내 A-61 가정 하나가 틀린 것을 찾았다.** A-61 보고서를 쓰며 나는 `dataSize` 를
`uint32_t` 로 생각하고 "float 프레임이 약 2^30 화소로 제한된다" 는 취지의 한계를 머릿속에
두고 있었다. 실제로는 `xpe_types.h:90` 에서 **`size_t dataSize`** 다 — 그 제한은 존재하지 않는다.
읽지 않고 적었으면 **없는 한계를 문서에 남길 뻔했다.** 이번에는 필드를 열어 확인했다.

### 2-2. 측정

`RealFrameSizeIsIdenticalAtEveryThreadCount` — 3072², 실제 이상치를 심어 all-zero 로 자명하게
통과하지 않게 하고, N∈{1,2,8,12,16} 에서 σ(비트)와 맵(화소 단위)을 1스레드와 대조.

```
[       OK ] ThreadParityTest.RealFrameSizeIsIdenticalAtEveryThreadCount
[==========] 6 tests from 1 test suite ran.
[  PASSED  ] 6 tests.
```

**이 시험은 오버플로를 찾을 것으로 기대하고 만든 것이 아니다**(§2-1 이 안전을 보인다).
§2-1 의 추론이 **코드에 대한 주장**이고, 그 주장을 실제 크기에서 확인하는 비용이 싸기 때문에 한다.
카드가 지적한 대로, 640×480 통과는 실제 크기 통과가 아니다 — A-60 이 기계 축에서 배운 것과
같은 형태이고 여기서는 축이 **크기**다.

## §3. 할 일 2 — 주석만 있던 계약

### 3-1. (a) 를 골랐다 — 함수가 채운다

```cpp
// QA-A-62: clear it here rather than trusting a comment. See the note above.
std::memset(map, 0, static_cast<size_t>(w) * static_cast<size_t>(h));
```

**측정 없이 기각하지 말라는 지시대로 쟀다.** `--decompose` 가 바로 이 memset 을 직접 잰다:

```
  TOTAL xpe_defect_detect_runtime  [measured]     688.1 ms   100.0%
    global sigma (Bm, shipped)     [measured]     179.7 ms    26.1%
    memset of the output map       [measured]       0.2 ms     0.0%
    per-pixel loop      [total - the two above]    508.2 ms    73.9%
```

**9.4 MB 쓰기 한 번 = 0.2 ms, 전체의 0.03%.** 게이트 비율도 **7.129** 로 정상 대역
(A-60 이 잰 7.125~7.375) 안이고 상한 10.00 에서 멀다 — **측정 가능한 영향이 없다.**

계약을 코드로 옮긴 이유는 카드가 적은 그대로다. 주석은 코드가 아니고, **이 계약은 조용히
틀린다** — 채워지지 않은 맵은 이전 내용을 갖고, 남아 있는 1은 검출과 구분되지 않는다.

### 3-2. `--regress diff` — 바뀌지 않았고, **그 이유가 중요하다**

```
diff a50-regress-bm.log  a62-regress-after.log
→ (차이 없음)  IDENTICAL to the QA-A-50 baseline (byte for byte)
```

카드는 "바뀌면 호출자가 안 채우고 있었다는 증거, 안 바뀌면 모두 채우고 있었다는 뜻" 이라고 했다.
**둘 다 아니다.** 확인해 보니 `--regress` 경로는 **`DetectFrame` 을 한 번도 부르지 않는다**
(`grep -c DetectFrame xpe_struct_frames.cpp` → **0**; 그 도구는 자체 `detect()` 에서
`DetectDefectivePixel` 을 직접 돌리고 맵을 `std::vector<uint8_t> map(kN, 0)` 으로 0 초기화한다).

그러므로 **diff 가 안 바뀐 것은 이 변경에 대해 아무것도 말해 주지 않는다.** 현재
`DetectFrame` 호출자는 파리티 테스트와 실험 도구뿐이고 둘 다 이미 0으로 채우고 있었다
(`grep` 으로 확인). "변화 없음" 을 "호출자들이 올바랐다" 로 읽으면 **관측하지 않은 것을
주장하는 것**이 된다.

### 3-3. 반증 — 단언이 옛 동작을 보는가

**조작**: `std::memset` 을 지우고 주석만 있던 상태로 되돌림.
빌드 `BUILD_EXIT=0`, `[15/15] Linking` 확인.

```
threads 1: a pre-dirtied map changed the result, so the function is not clearing it
[  FAILED  ] ThreadParityTest.DetectFrameClearsTheMapItself
```

단언은 맵을 **0xFF 로 미리 더럽혀** 넘기고 0으로 채운 맵의 결과와 같기를 요구한다.
플래그가 0개도 전부도 아님을 함께 단언해, 0xFF 가 우연히 일치하는 경우를 배제했다.

**복원 확인**: `FALSIFY` 0건, 빌드 exit 0, 6/6 통과.

## §4. Doxygen 2건 (리더 추가 요청)

A-61 에서 **내가 넣은** `RuntimeDetection_NormalizeThreads` 하나가 한 줄 주석만 갖고 있었다.
A-60 에서 채운 10개는 그대로 통과한다.

본문은 한 줄이다: `return (requested < 1) ? 1u : static_cast<uint32_t>(requested);`
**경계에서 무엇을 하는지**를 거기서 읽어 적었다:

- **0이나 음수 → 1로 클램프**. 오류가 아니다 — 이 함수에 오류 채널이 없고, "스레드 0개" 요청은
  단일 스레드 경로를 뜻한다
- **코어 수보다 크면 그대로 돌려준다.** 상한 클램프가 **없고**, 그것이 의도다 — 이 모듈은
  하드웨어 병렬도를 **읽지 않는다**(A-61 정책). 클램프할 기준 자체가 없다. 과다구독은 허용된다

`ComputeGlobalSigmaThreaded`·`DetectFrame` 은 A-61 에서 이미 `@param`/`@return` 을 갖췄다
(각각 3개·3개 확인).

**검증은 CI 가 한다.** 이 기계에 Doxygen 이 없고 설치는 되돌리기 어려운 환경 변경이라 하지
않았다(A-56/A-60 과 같은 판정). **"고쳤다" 는 주장이지 검증이 아니다.**

## §6. Gaps — 관측하지 않은 것

1. **Doxygen 을 로컬에서 돌리지 못했다.** CI 결과가 나와야 확인된다
2. **3072² 파리티를 한 프레임 한 종류로만 했다.** A-61 의 640×480 은 5종을 돌았지만
   3072² 는 잡음 프레임 하나다 — 크기를 우선한 대가이고, 카드가 "케이스를 줄이되 크기는
   줄이지 말라" 고 한 그대로다
3. **2^32 경계를 실제로 시험하지 않았다.** §2-1 은 타입 분석이지 측정이 아니다.
   65536² 프레임(17 GB)은 이 기계에서 만들 수 없다
4. **`DetectFrame` 이 지우는 범위는 `w*h` 바이트**다. 호출자가 그보다 작은 버퍼를 주면
   **넘어 쓴다** — 이전에도 같았지만, 이제는 함수가 쓰므로 책임 위치가 바뀌었다.
   길이 인자를 받지 않는 형태를 유지했고, 그 점을 여기 적는다
5. **memset 비용을 스레드 경로에서 따로 재지 않았다.** 0.2 ms 는 단일 스레드 분해값이다
6. 16 포화 원인·TSan·알고리즘 — 전부 카드 범위 밖

## §7. Residual-risk — 남는 위험

1. **Gap 4 가 새로 생긴 위험이다.** 계약을 함수로 옮기면서 "맵은 최소 `w*h` 바이트" 라는
   **새 전제**가 생겼다. 이전에는 호출자가 채우므로 크기를 호출자가 알았고, 이제는 함수가
   호출자가 준 크기를 **모른 채** 쓴다. 공개 진입점은 `dataSize` 를 검증하지만 `DetectFrame` 은
   내부 함수라 그 검증을 거치지 않는다 — **길이 인자를 받는 형태가 더 안전하고, 그건 서명
   변경이라 이 카드에서 하지 않았다**
2. **`--regress diff` 가 이 변경을 전혀 시험하지 않는다**(§3-2). 지금 계약을 지키는 증거는
   신규 단언 하나뿐이고, 그 단언은 640×480 에서만 돈다
3. **3072² 파리티 통과가 "모든 크기에서 안전" 을 뜻하지 않는다.** 타입 경계는 계산했지만,
   그 사이 크기(예: 8192×8192)는 재지 않았다
4. **Doxygen 이 또 깨질 수 있다.** 새 함수를 넣을 때마다 같은 일이 반복됐다(A-60 에서 10건,
   A-61 에서 2건 — 둘 다 내가 넣은 것). **헤더에 함수를 추가하면 `@param`/`@return` 을 같이
   쓴다**는 규칙이 코드로 강제되지 않는다
5. 20배 초과 그대로 — 이 카드는 정확성 작업이고 성능을 바꾸지 않았다(0.2 ms 추가는 0.03%)
