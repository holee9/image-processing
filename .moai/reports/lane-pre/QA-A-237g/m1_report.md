# QA-A-237g M1 — 실제 보정 맵 세 개 전부로 다시 잰 최대 메모리

이슈: #245 (SRS-CALIB-PERF-002, 최대 메모리 ≤ 200 MB, 고스트 포함). 경로: 출하 `xpe_preprocess_pipeline_ex`, 3072², tier 1·3, 정상 길.
기준 커밋: 6940a44d (237f). 코드 변경 없음, 측정 하니스(`test_zz_a237b_mem.cpp`)만 확장.

## 1. 결론

| 입력 | 정상 상태 | 최대 | 200 MB(= 190.73 MiB) 대비 |
|---|---|---|---|
| 합성 맵 (237b~237e 의 측정 조건) | 153.3 MiB | 189.5 MiB | 충족 (이 조건이 거짓이었다) |
| 실제 결함 맵 + 합성 offset·gain (237f) | 153.3 MiB | 189.9 MiB (199.1 MB) | 충족, 여유 0.9 MB |
| **실제 맵 세 개 전부 (offset·gain·BPM), 스칼라 gain, tier 1** | **153.8 MiB** | **199.6 MiB (209.3 MB)** | **9.3 MB 초과, 미충족** |
| 실제 맵 세 개 전부, tier 3 | 153.8 MiB | 199.4 MiB (209.1 MB) | 9.1 MB 초과, 미충족 |
| 실제 평탄 영상 6장으로 만든 다항 gain (degree 2), tier 1 (하니스가 준 선량, 아래 §2.3) | **225.4 MiB** | **316.3 MiB (331.7 MB)** | 131.7 MB 초과 |

- 실제 맵 세 개로 `union_mask` 경로가 **실제로 탄다**: 이득 맵 생성기가 만든 gain 에서 [0.1, 10.0] 밖의 화소 42,026개(0.445 %)가 결함으로 분류되고, 결함 맵(BPMap) 23,505개와 합쳐진다.
- 최대는 결함 단계의 일시 증가 +9.5 MiB 가 만든다 (189.9 → 199.4). 내역은 `union_mask` 복사 9.0 MiB + 237f 의 순번 표 약 0.5 MiB 다. 이 9.0 MiB 는 이득 보정이 결함으로 분류한 화소가 하나라도 있으면 항상 더해진다.
- 합성 맵 조건(237b~237e)에서 정상 길 최대가 맞았던 것은 하니스가 그 분기들을 한 번도 타지 않았기 때문이다 (§3).
- 고스트는 실제 입력에서 3프레임 모두 제자리 경로였다 (`ghost frames processed in place: 3 of 3`, tier 1·3 모두). 느린 길(scratch)은 이 입력에서 타지 않았다.
- 다항 gain 은 정상 상태만 225.4 MiB 라 최대 메모리 요구를 어떤 변경 없이도 넘는다: 계수 평면이 화소당 3개(degree 2)로 108 MiB, 파일 크기 113.2 MB. 이 경로를 200 MB 에 맞추는 것은 별도 설계 사안이다.

## 2. 입력과 단계별 최대

### 2.1 실제 맵 세 개의 출처

| 맵 | 출처 | 크기 | 만든 방법 |
|---|---|---|---|
| offset | `tests/test_data/CalData_6/dark.raw` (uint16 3072², 18,874,368 B, 전체 평균 2503.13) | 생성 파일 37,748,950 B (float32 평면) | 제품의 `xpe_calib_generate_offset` (프레임 1장, 100 ms, 25 °C) |
| gain | 같은 폴더 `bright01~06.raw` 6장 (각 18,874,368 B, 이미 offset 보정된 값이라 dark 참조 없음) | 생성 파일 37,749,092 B (float32 평면) | 제품의 `xpe_calib_generate_gain` (6장, 화소별 평균을 전체 평균으로 정규화) |
| BPM | 같은 폴더 `BPMap.map` (uint8 3072², 9,437,184 B, README: 0 = 정상) | 23,505개 결함 (0.249 %) | 파일 그대로 (0 아닌 값을 1 로) |
| 입력 프레임 | `dark.raw` + `bright0k.raw` (uint16 포화 합) | 3072² uint16 | 하니스가 64 KiB 조각으로 읽어 합침 (통째로 읽으면 하니스가 최대를 가린다) |

저장소에는 `CalData_6` 외에 3072² offset·gain 맵 파일이 없다 (`calibration_cases/` 아래 각 폴더와 클라이언트 빌드 산출물의 `.xcal` 은 픽스처 미리보기용). 그래서 gain 은 저장소의 실제 평탄 영상에서 제품 생성기로 만들었다. 이 gain 이 실제 장비의 운영 gain 과 같은지는 확인할 수 없다. 만드는 과정의 일시 메모리가 측정 최대에 섞이지 않도록 생성은 별도 프로세스(`A237gMaps.DISABLED_GenerateRealMaps`)로 하고 측정 프로세스는 만들어진 `.xcal` 을 읽는다.

### 2.2 단계 경계의 최대 (실제 맵 세 개, 스칼라 gain, tier 1, 프레임 0, 증거 `21_g2_stage_table_frame0.txt`)

| 지점 | 비공개 사용 (MiB) | 최대 커밋 (MiB) | 직전 대비 상승 |
|---|---|---|---|
| 프레임 전 | 153.8 | 153.8 | |
| 읽기 직후 | 153.8 | 153.8 | 0.0 |
| 온도 직후 (작업 버퍼 생성) | 189.9 | 189.9 | +36.1 |
| offset, 비선형, 이득, 빈닝 직후 | 189.9 | 189.9 | 0.0 |
| **결함 직후** | 189.8 | **199.4** | **+9.5** (union_mask 9.0 + 순번 표) |
| 고스트, 최종 복사 직후 | 189.8 | 199.4 | 0.0 |

같은 실행에서 프레임 1 은 결함 직후 최대가 199.6 (+0.2) 까지 올랐다. 그 이유는 확인하지 않았다.

### 2.3 다항 gain 경로 (참고: 선량이 데이터셋에 없다)

README 가 말하듯 데이터셋에는 선량이 없다. 그래서 다항 맵의 선량은 1000~6000 으로 하니스가 정했다. 이 값은 적합을 정할 뿐 이 경로가 쓰는 메모리의 크기를 바꾸지 않는다. 측정은 정상 상태 225.4 MiB, 온도 +18.0, offset +18.1, 이득 +54.7 (다항 이득 계산용 `evaluated` 평면 36 MiB 가 포함), 최대 316.3 MiB 다. 이 경로는 출하 설정이 쓰는지 확인하지 못했다.

## 3. 합성 하니스가 한 번도 타지 않은 분기

각 단계의 큰 할당 × 생기는 조건 × 하니스가 그 조건을 만드는가. 크기는 3072². "237b~237f 하니스" 는 합성 offset(상수)·gain(상수)·결함 16화소, uint16 입력, 고스트 핸들 있음, 설정 기본값.

| 단계 | 큰 할당 | 크기 | 생기는 조건 | 237b~237f 하니스 | 이번 측정 |
|---|---|---|---|---|---|
| 맵 읽기 (정상 상태) | offset 평면 | 36 MiB | 항상 | 만든다 | 만든다 |
| 맵 읽기 | gain 평면 | 36 MiB | 스칼라 gain | 만든다 | 만든다 |
| 맵 읽기 | gain 다항 계수 평면 | 화소당 (차수+1)×4 B: degree 2 에서 108 MiB | 다항 gain 이 읽혀 있을 때 | **만들지 않는다** | 별도 측정 (§2.3) |
| 맵 읽기 | 결함 맵 | 9 MiB | 항상 | 만든다 | 만든다 |
| 맵 읽기 | gain 이 분류한 화소 목록 | 화소당 4 B | gain 에 [0.1, 10.0] 밖의 화소 | **0개** | 42,026개 |
| 파이프라인 | 고스트 이력 평면 2장 | 72 MiB | 고스트 핸들을 줄 때 | 만든다 | 만든다 |
| 온도~이득 | 작업 버퍼 (float 크기) | 36 MiB | 스칼라 gain + uint16 입력 | 만든다 | 만든다 |
| 온도~이득 | uint16 단계 버퍼 3개 + float 평면 | 18+18+18+36 MiB | 다항 gain, 또는 float32 입력, 또는 이득 우회 | **만들지 않는다** | 다항 경로만 측정 |
| 이득 | 다항 gain 평가 평면 `evaluated` | 36 MiB | 다항 gain | **만들지 않는다** | 다항 경로만 측정 |
| 빈닝 | float 복사 | 36 MiB | `binningMode > 1` | **만들지 않는다** (기본 설정) | 만들지 않는다 |
| 결함 | **`union_mask` 복사** | **9 MiB** | gain 이 분류한 화소가 있거나 프레임별 분류 목록(다항 gain)이 있을 때 | **만들지 않는다** (분류 0개) | **탄다 (+9.0)** |
| 결함 | 거리 표 (237f 후: 결함 수에 비례) | 237f 전 9 MiB, 후 결함 23,505개에서 0.1 MiB 안팎 (계산한 추정, 따로 재지 않음) | 3×3 이웃이 전부 결함인 화소가 있을 때 | 237f 전까지 **만들지 않았다** (고립 화소) | 탄다 |
| 결함 | 군집 표시 | 1.125 MiB → 237f 후 0.1 MiB 안팎 (같은 추정) | 결함 화소가 하나라도 있을 때 | 만든다 | 만든다 |
| 결함 | float 복사 (호출자 float32 버퍼) | 36 MiB | 호출자가 float32 입력을 줄 때 | **만들지 않는다** (uint16 입력) | 만들지 않는다 |
| 고스트 | scratch 평면 3장 | 108 MiB | 제자리 안전 판정이 float 범위를 증명하지 못할 때 (nlcscBeta 가 매우 클 때 등) | 기본은 **타지 않는다**, 237c 에서 `XPE_A237C_BETA` 로만 강제 | 타지 않았다 (3프레임 모두 제자리) |
| 고스트 | 행 2줄 (tier 3) | 화소 폭 × 8 B (24 KB) | tier 3 | 237c 에서 tier 3 를 측정했다 | tier 3 를 측정했다 |
| 고스트 | 호출자 float32 버퍼일 때의 사본 | 36 MiB | 호출자가 float32 입력을 줄 때 | **만들지 않는다** | 만들지 않는다 |
| 최종 복사 | 없음 | 0 | | | |

하니스가 만들지 않는 조건이 **출하 설정에서 실제로 일어나는지**는 이 표로 알 수 없다. 표가 말하는 것은 어느 분기를 측정하지 않았다는 것까지다. 예를 들어 다항 gain, 빈닝, 호출자 float32 입력, 고스트 scratch 경로가 출하 호출에서 쓰이는지는 확인하지 않았다.

## 4. 흔들림과 시간

- 이번 측정은 일반적인 번갈아 측정이 아니라 단일 실행 단계 표다 (프레임 3장). 237f 에서 잰 같은 빌드의 새 프로세스 24회 퍼짐은 0.1 MiB 였다. 이번 입력에서의 퍼짐은 반복해서 재지 않았다.
- 프레임 시간은 실제 맵에서 113 ms (tier 1), 307~312 ms (tier 3) 로 합성 맵의 85 ms, 280 ms 보다 길다. 결함 군집과 `union_mask` 때문이다 (원인 분해는 하지 않았다).

## 5. M2 필요성

실제 맵 세 개에서 정상 길 최대 199.6 MiB (209.3 MB) 가 200 MB 를 9.3 MB 넘는다. `union_mask` 복사 9.0 MiB 를 없애면 나머지 +0.2~0.5 MiB 만 남아 최대가 약 190 MiB (199.3 MB 근방)가 될 것으로 보인다 (측정 전 추정). 그 경우 여유는 약 0.7 MB 다 (237f 와 같은 바닥: 이득 단계 직후 189.9 MiB). 이 바닥 아래는 이번 카드 범위가 아니다 (offset 정수화, 느린 길).

## 6. 미검증 · 잔여 위험

- gain 은 저장소의 실제 평탄 영상으로 만들었으나 장비의 운영 gain 이 아니다. 분류 화소 수(42,026)가 운영 gain 에서도 비슷한지 알 수 없다.
- 다항 gain 의 선량은 하니스가 정한 값이고, 출하 설정이 다항 gain 을 쓰는지 확인하지 않았다.
- 입력 프레임 `dark + bright` 는 합성한 raw 다 (README 상 `bright` 는 offset 보정된 값이라 합이 raw 에 가깝다고 보았을 뿐 확인하지 않았다).
- 단일 실행이라 이번 입력에서의 퍼짐은 모른다.
