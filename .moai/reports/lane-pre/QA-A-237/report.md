# QA-A-237 M1 — 최대 메모리 200 MB(SRS-CALIB-PERF-002)를 줄일 후보 조사

카드: QA-A-237 · Refs #245 · 기준 커밋 `a03d2c69` · **코드 변경 없음**(보고서와 증거 스크립트만). 어느 후보를 할지는 리더가 정한다.
단위: 3072² 평면은 float32 36.0 MiB(= 37.7 MB), uint16 18.0 MiB(= 18.9 MB), uint8 9.0 MiB(= 9.4 MB). 표의 MiB 옆 MB 는 십진 환산(1 MiB = 1.048576 MB)이고, 200 MB 는 190.7 MiB 다.
코드 인용은 줄 번호 대신 파일과 심볼 이름으로 적었다(편집에 밀리지 않도록). 모두 `a03d2c69` 에서 읽었다.

## 0. 결론 먼저

1. **프레임 1 의 일시 +36.1 MiB 의 출처**는 gain 단계의 `std::vector<float> reciprocal(n)` (`gain_correct.cpp`, `xpe_gain_correct_in`)로 보인다. gain 호출마다 float 평면 하나를 새로 잡았다가 돌려준다. 코드로 읽고 QA-A-236 의 측정값 세 개와 맞춰 본 **추정**이며, 단계별 Peak 계수를 직접 재지는 않았다(§1.3).
2. **새로 찾은 것(미측정)**: QA-A-236 이 잰 경로는 시험이 stage 함수를 하나씩 이어 부른 경로다. 출하 진입점(`xpe_preprocess_pipeline_ex` → `pipeline_core`)은 모듈 안에서 단계별 `std::vector` 6개를 함수가 끝날 때까지 쥔다. 코드로 계산하면 **그 경로의 최대는 423.6 MiB(444.2 MB)로, 측정한 297.7 MiB(312.2 MB)보다 크다**. 리더가 RTM 에 312 MB 를 쓰기 전에 알아야 할 사실이라 카드 범위 밖이지만 적는다(§2.B).
3. **고스트를 포함해 200 MB 아래로 들어가려면 맵 쪽 후보만으로는 안 된다.** 손으로 이은 경로 기준으로 맵 쪽 후보를 전부 해도(reciprocal 제거 + offset 정수화) 243.6 MiB(255.4 MB)다. 고스트 평면 5장 중 next·backup 3장(108.0 MiB)을 없애는 후보가 있어야 들어간다(§2.A).
4. **출력이 바이트 단위로 같은 후보**는 reciprocal 제거, 고스트 평면 제거(검사 후 제자리 갱신), 단계 버퍼 수명 단축이다. **같지 않을 수 있는 후보**는 offset 정수화(§1.1)와 고스트 정밀도 낮추기(§1.2)이고, 정밀도 낮추기는 기각을 권한다(§3).

## 1. 항목별 후보

### 1.1 offset 맵 float32 (36.0 MiB, SRS 가정은 uint16 18.0 MiB)

**왜 float32 인가.**
- 파일 형식이 float 다: `xcal_validator.cpp` 가 OFFSET 형식이 `XCAL_FMT_FLOAT32` 가 아니면 거부하고, `xpe_calib_load_offset.cpp` 의 `acquire` 가 `len == pixels * sizeof(float)` 가 아니면 거부한다. 생성기(`xpe_calib_generate_offset.cpp`)도 FLOAT32 로 쓴다(암실 프레임 평균이라 소수부가 있다).
- 적용은 `offset_correct.cpp` 의 `offset_correct_float_avx2` 에서 `raw − offset` 을 float32 로 빼고 0~65535 로 자른 뒤 `+0.5` 를 더해 버린다.

**소수부가 출력에 영향을 주는가.** 정확한 산술로는 거의 주지 않는다. raw 는 정수이므로 `floor(raw − o + 0.5) = raw − ceil(o − 0.5)` 이고, 출력은 offset 값 `o` 를 정수 `K(o) = ceil(o − 0.5)`(반올림, 0.5 는 내림)로만 본다. 소수부는 `+0.5` 반올림에서 이미 버려진다. 그래서 uint16 에 소수 비트를 넣는 방식(Q12.4 등)은 의미가 없고, 담을 값은 K 다. 아래는 이 추론을 float32 경로 모사로 확인한 결과다(`evidence/10_offset_k_equivalence.txt`).

| 방식 | 줄어드는 양 | 현행 float32 경로와의 차이(합성 표본) | 바꿔야 할 범위 | 위험 |
|---|---|---|---|---|
| **K 를 uint16 으로**(`ceil(o−0.5)`, 맵당 2 B) | **−18.0 MiB**(18.9 MB) | 정수 offset·정확히 .5 인 offset 에서 불일치 **0**. 무작위 소수 offset 에서는 **raw ≥ 4096 인 화소에서만** 1 DN 차이: 모든 (raw, offset) 쌍 대비 0.072%(균등 0~4000)·0.263%(정규 1500±30). raw < 4096 구간은 0 | 적재 시 변환, `offset_correct_float_avx2` 와 그 스칼라 비교대상 `xpe_offset_apply_scalar_reference`, 스냅샷 타입(`CalibSnapshot::offset_map`), `xpe_calib_save`·`calibration_cache` 의 맵 복사 | ① 차이의 원인은 K 가 틀려서가 아니라 **현행 float32 뺄셈의 반올림**(큰 raw 에서 ulp 가 커짐)이다. 하지만 현행 출력이 기준이라 "바이트 동일"은 아니다. ② 음수·NaN·±Inf offset 은 uint16 K 에 안 들어가므로 float 맵 유지 폴백이 필요하다. ③ `xpe_calib_save` 가 메모리 맵을 그대로 파일로 쓰므로, 적재 후 저장하면 소수부가 사라진 파일이 나온다(`test_calibration_roundtrip.cpp` 가 바이트를 비교하는지는 확인하지 않았다) |
| uint16 Q12.4 (소수 4비트) | −18.0 MiB | **불일치 약 2.5%**(정규·균등 모두). 원인: 격자가 반정수 경계를 포함해, 소수부가 0.5 ~ 0.5+1/32 인 offset 이 경계로 반올림되어 K 가 바뀐다(해석상 1/32 = 3.1%, 표본 2.7%: `evidence/11_q4_flip_rate_check.txt`) | K 안과 같음 | K 안이 같은 크기에 더 정확하므로 **채택할 이유가 없다** |
| float16 / bfloat16 | −18.0 MiB | float16 은 가수가 11비트라 offset 이 1024 이상이면 값 간격이 1 이 되어 소수부를 못 담는다. 출력이 달라진다 | — | 기각 |

한계: 표본은 **합성** offset(균등·정규)이고, 위 비율은 raw 를 0..65535 에 균등하게 가중해 센 값이라 실영상의 raw 분포에 따라 달라진다. 실제 생성기가 낸 맵의 값 분포와 실영상 raw 로는 재지 않았다. 확인 방법: 실제 offset 맵의 서로 다른 값 몇 만 개에 대해 raw 0..65535 전수로 두 경로를 비교한다(스크립트는 `10_offset_k_equivalence.py.txt`).

### 1.2 고스트 핸들의 float 평면 5장 (180.4 MiB, SRS 150 MB ≈ 4장)

SRS 의 150 MB 는 float 평면 4장(4 × 37.7 = 151 MB)과 산술상 맞는다(SRS 가 평면 수를 적지는 않았으니 일치일 수도 있다). 평면이 5장이 된 경위는 헤더 주석에 있다: `next1`·`next2` 는 QA-A-202c 가 "핸들 메모리를 2배로"(2장 → 4장) 만들었고, `backup` 은 QA-A-217 이 "다섯 번째 float 평면"으로 더했다(`xpe_preprocess_internal.h`, `GhostCorrectorHandle`).

| 평면 | 하는 일 | 프레임 사이에 필요한가 | 호출 안에서 필요한 이유 |
|---|---|---|---|
| `hist1`, `hist2` (72.0 MiB) | IRF 누산기(상태) | **필요** | 다음 프레임의 입력 |
| `next1`, `next2` (72.0 MiB) | 새 이력을 쓰는 곳. 프레임이 끝까지 성공하면 `swap` | 불필요(호출 안에서만 쓰고 읽음) | 중간에 실패한 프레임이 이력을 건드리지 않게 하려고(QA-A-202c) |
| `backup` (36.0 MiB) | 들어온 프레임의 복사본 | 불필요 | ① 실패 시 `px` 를 되돌림(QA-A-217, REQ-P1A-032) ② tier 3 의 3×3 평균이 읽는 원본(QA-A-218b) |

세 평면(next1, next2, backup)은 `xpe_ghost_create` 에서 한 번 잡고 `xpe_ghost_destroy` 까지 상주한다. 사용 구간은 `xpe_ghost_correct` 호출 안뿐이다.

| 후보 | 줄어드는 양 | 출력 | 바꿔야 할 범위 | 위험 |
|---|---|---|---|---|
| **G0** next·backup 을 호출마다 잡고 돌려줌 | 호출 사이 상주 −108.0 MiB, **최대는 그대로** | 바이트 동일 | `ghost_correct.cpp` | ghost 단계가 마지막이라 최대가 그 호출 안에서 나온다. 손으로 이은 경로의 ghost 단계 최대는 261.6 MiB 그대로다. 프레임마다 108 MiB 를 잡으므로 페이지 폴트 비용이 생기고, 파이프라인 중간의 `bad_alloc` 위험도 생긴다("핸들과 함께 한 번 할당"은 의도된 선택이었다). **최대를 줄이지 못하므로 요구 충족 후보가 아니다** |

G1·G2 의 설계: 지금은 한 번의 순회에서 `n1`·`n2`·`px` 를 쓰고, 도중에 유한성 검사에 걸리면 `backup` 으로 `px` 를 되돌리고 `next` 를 버린다. 대안은 **순회 A**(검사만: `px`·`hist` 를 쓰지 않고 `corrected`·`n1`·`n2` 가 유한한지만 본다)를 먼저 돌리고, 통과하면 **순회 B**(`hist1`·`hist2`·`px` 를 같은 인덱스에서 읽고 같은 인덱스에 쓴다. 원소별 연산이라 제자리가 안전하다)를 도는 것이다. 순회 B 는 순회 A 와 같은 식을 쓰므로 실패하지 않는다.

공통 위험(G1·G2):
- **바이트 동일은 구성이 아니라 시험으로 보여야 한다.** 같은 식이 두 번 인라인되면 컴파일러가 두 곳을 다르게 컴파일할 수 있다(빌드 플래그는 `/arch:AVX2` 뿐이고 `/fp:fast` 는 없다. FMA 결합 여부는 미확인). 하나의 인라인 함수로 묶고, 프레임 수십 장 처리 뒤의 출력과 `hist` 를 비트 단위로 비교해야 한다. 실패 경로(`test_ghost_failed_frame.cpp`)도 같은 결과여야 한다.
- **시간**: 순회가 한 번 더 늘어난다(`hist1`·`hist2`·`px` 읽기 108 MiB). ghost 단계 예산(시험 출력의 `ghost … [140]` ms)에 영향이 있는지 **재지 않았다**.
- 대안 G3(입구에서 |값| 상한을 두어 실패를 불가능하게 만들고 순회 한 번으로 처리)은 순회 비용이 없지만, 상한을 넘는 유한 입력의 오류 코드가 바뀌어 `test_ghost_failed_frame.cpp` 가 고정한 동작이 달라진다. 바이트 동일 후보가 아니다.

### 1.3 프레임 1 의 일시 +36.1 MiB 의 출처

**추정: `gain_correct.cpp` 의 `std::vector<float> reciprocal(n)`.** `xpe_gain_correct_in` 이 gain 호출마다 n 개 float(36.0 MiB)를 새로 잡고 `1/gain` 을 채운 뒤 `apply_gain_avx2` 에 넘기고 함수가 끝나면 돌려준다. 맵이 스칼라일 때도 매번 그렇다.

왜 프레임 0 에서는 안 보이고 프레임 1 에서만 보였는가: 시험 하네스의 `beforeGhost = gainOut`(`test_pipeline_performance_3072.cpp`)이 프레임 0 에서 36.1 MiB 를 할당하고(`D − C2 = 36.1`), 프레임 1 에서는 같은 크기라 용량을 재사용한다. 그래서 프레임 0 의 gain 단계 최대는 하네스 복사본이 아직 없을 때 나오고, 프레임 1 에서는 복사본이 있는 상태에서 `reciprocal` 이 더해진다.

예측과 측정(`evidence/20_budget_table.txt` §C):

| | 예측 | QA-A-236 측정(PeakPagefile) |
|---|---|---|
| 프레임 0 gain 단계 | C2 335.6 + 36.0 = 371.6 MiB | D: 371.7 ~ 371.8 |
| 프레임 1 gain 단계 | C2 335.6 + 36.1 + 36.0 = 407.7 MiB | E: 407.8 |

다른 후보를 코드로 배제한 범위: `temp_compensate.cpp`·`nonlinearity_correct.cpp`·`readout_validate.cpp`·`binning_correct.cpp` 에는 `vector<`·`new T[]`·`make_unique<`·`malloc` 이 없다(같은 검색이 binning 에서 `xpe_find_nonfinite` 이름을 잡아 파일을 읽었다는 대조가 됨). 고스트 호출 안에는 프레임마다의 할당이 없다. defect 단계는 `std::vector<bool>` 두 개(각 n 비트 = 1.1 MiB)뿐이다(`union_mask` 는 이득 분류 화소가 있을 때만, `FillDistance` 는 주변에 정상 화소가 없는 군집 화소가 있을 때만 생긴다).

**확인하지 않은 것**: 단계별 Peak 계수. 확인 방법은 프레임 1 에서 `xpe_gain_correct` 호출 직전·직후의 `PeakPagefileUsage` 를 임시 계측으로 읽는 것이다(QA-A-236 과 같은 방식, 읽고 되돌림). 이 추정이 틀리면 §2 의 R 열이 달라진다.

**후보 R: reciprocal 제거.** 평면을 만들지 않고 작은 조각(예: 행 몇 줄)씩 `1.0f / gain` 을 계산해 곧바로 적용한다.
- 줄어드는 양: 최대 −36.0 MiB(정상 상태는 그대로).
- 출력: 같은 `1.0f / g` 값을 같은 `x * recip` 곱에 넣으므로 바이트 동일. 다만 지금은 **유효성 검사를 전부 마친 뒤에 적용**해서 실패한 호출이 `dst` 를 건드리지 않는다. 조각 처리로 바꿔도 이 성질을 지키려면 `is_valid_gain` 만 도는 읽기 전용 순회를 먼저 두어야 한다(평면 할당 없이 읽기 한 번 추가).
- 바꿔야 할 범위: `xpe_gain_correct_in` 안. 다항 이득 경로는 별도(§4).

### 1.4 gain 맵(36.0 MiB)·defect 맵(9.0 MiB)

SRS 가정(gain 37.7 MB, BPM 9.4 MB)과 구현이 같고(실측 합 81.2 MiB), 파일 형식이 float·uint8 이다. **후보에서 빼도 된다.** gain 맵 자리에 reciprocal 맵을 상주시키는 안은 gain 값이 저장·내보내기에 쓰이고 `1/(1/g) ≠ g` 라서 바이트 동일이 아니며, 상주량도 줄지 않는다. 같은 효과는 R 이 낸다.

## 2. 조합별 예상 최대 (고스트 포함)

| B + N (R 없이) | 153.6 MiB (161.1 MB) | 189.7 MiB (198.9 MB) | 99%, **여유 1.0 MiB** |
| R + B + N | 153.6 MiB (161.1 MB) | 153.6 MiB (161.1 MB) | 81% 충족 |
| O + B + N (R 없이) | 135.6 MiB (142.2 MB) | 171.7 MiB (180.0 MB) | 90% 충족 |
| R + O + B + N | 135.6 MiB (142.2 MB) | 135.6 MiB (142.2 MB) | 71% 충족 |

읽는 법: 이 경로에서는 **고스트 평면 제거(B+N)가 필수**이고, R 과 O 는 여유를 만든다. B+N 만으로는 최대가 190.7 MiB 에 1.0 MiB 차로 붙어 있어, 측정 오차 안이다. 맵 쪽 후보(R, O)만으로는 어떻게 합쳐도 충족하지 못한다.

### B. 출하 진입점 `xpe_preprocess_pipeline_ex` → `pipeline_core` (코드 계산, **미측정**)

`pipeline_core` 는 `stage1Data`(uint16)·`stage2Data`·`stage3Data`·`stage4Data`(float)·`stage6Data`·`stage7Data` 를 함수 지역 `std::vector` 로 잡고 **함수가 끝날 때까지** 쥔다(기본 설정에서 binning 모드 1 이라 `stage5Data` 는 없음). 호출자 버퍼는 손으로 이은 경로의 하네스 버퍼와 마찬가지로 뺐다.

| 조합 | 단계 버퍼 최대 | 합계(맵 81.2 + 고스트 180.4 포함) | 200 MB 대비 |
|---|---|---|---|
| P0 출하 그대로(ghost 단계에서 18×3 + 36×3) | 162.0 MiB | 423.6 MiB (444.2 MB) | 222% 초과 |
| P1 마지막 사용 뒤 해제 + ghost 를 `stage6` 에서 제자리 처리(`stage7` 복사 제거) | 90.0 MiB (gain 단계: stage3 + stage4 + reciprocal) | 351.6 MiB (368.7 MB) | 184% 초과 |
| P2 = P1 + R | 74.4 MiB (defect 단계) | 336.0 MiB (352.3 MB) | 176% 초과 |
| P3 = P2 + defect 를 `stage4` 에서 제자리 처리 | 54.0 MiB | 315.6 MiB (330.9 MB) | 165% 초과 |
| P3 + G2 (고스트 72.4 MiB) | 54.0 MiB | 207.6 MiB (217.7 MB) | 109% 초과 |
| P3 + G2 + O | 54.0 MiB | 189.6 MiB (198.8 MB) | 99% **여유 1.1 MiB** |

P1~P3 은 모두 **수명만 바꾸는 변경**이라 바이트 동일이다. ghost 를 제자리로 돌려도 되는 근거: 실패 시 `xpe_ghost_correct` 가 자기 `backup` 으로 되돌리고 파이프라인은 오류를 반환하며 호출자 버퍼에 쓰지 않는다(`stage7` 복사는 `QA-A-104` 의 "자기 복사본을 준다"는 주석에서 온 것이고 복구에는 쓰이지 않는다). defect 를 제자리로 돌려도 되는 근거: `defect_correct.cpp` 의 `QA-A-146` 주석과 `InPlaceMatchesOutOfPlace` 시험이 제자리 호출을 보증한다.

읽는 법: 출하 경로 기준으로는 **후보 전부를 합쳐야 겨우 200 MB 에 닿고 여유가 1 MiB 대**다. 이 경로를 기준으로 삼는다면 더 쓸 수 있는 후보(예: offset 단계를 uint16 버퍼 하나로 제자리 처리)를 이 조사에서 분석하지 않았다.

## 4. 이 조사가 보지 않은 것 (Gaps) / 잔여 위험

- **재지 않았다**: 모든 후보의 실제 MiB·시간·출력. 이 보고서의 줄어드는 양은 평면 크기 산술이고, 최대 열은 QA-A-236 의 측정값(맵 81.2 + 고스트 180.4 + 일시 36.1 MiB)에서 뺀 값이다.
- **일시 +36.1 MiB 의 출처는 추정**이다(§1.3). 단계별 Peak 계수를 읽는 임시 계측이 확인 방법이다.
- **출하 경로(§2.B)는 코드 계산이고 측정하지 않았다.** 이 경로를 `PeakPagefileUsage` 로 재는 것이 R·P 열을 판정하는 가장 직접적인 다음 단계다. P1~P3 의 제자리 처리가 `bypass*` 설정 조합에 따라 달라지는 별칭 관계(예: gain 우회 시 `stage4` 가 `stage3` 나 호출자 버퍼를 가리킴)에서도 안전한지는 따져 보지 않았다.
- offset K 의 표본은 **합성**이고, 음수·NaN·±Inf offset 에서 현행 AVX2 경로가 내는 값과 K 규칙이 같은지 코드로만 읽었다(실행 안 함).
- G1·G2 의 시간 비용, 두 순회가 같은 비트를 내는지는 미확인.
- **다항 이득 경로**는 후보·측정 밖이다. `evaluated`(36.0 MiB) + `reciprocal`(36.0 MiB) + 계수 평면(설정의 계수 개수 × 36.0 MiB)이 상주·일시로 더 쌓인다. 출하 설정이 다항이면 §2 의 기준이 달라진다.
- **보정 캐시 경로**(`calibration_cache.cpp` 의 offset 적재)는 맵을 `staging`(36.0 MiB)으로 복사해 캐시에 게시한다. 캐시 API 를 쓰는 호출자는 맵 복사본을 하나 더 쥘 수 있다. 측정하지 않았다.
- MSVC 2022 한 구성만 가정했다.
- SRS 문장의 해석과 어느 후보를 할지는 리더·사용자 몫이다. 이 보고서는 선을 제안하지 않는다.
