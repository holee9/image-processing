## 2. 증거 (Evidence)

### C1 — 원인: 한 기계 안의 두 마이크로아키텍처가 그 분기를 재현한다

**두 번째 기계는 이 기계 안에 있었다.** i7-12700 은 P(Golden Cove)와 E(Gracemont) 두 코어를 갖는다. 같은 작업을 각각에 핀으로 묶으면 컴퓨터 한 대로 두 마이크로아키텍처를 잰다. 새 모드 `xpe_detect_experiment --gate-probe` 가 그것이다.

```
[gate-probe] 3072x3072, single thread, min of 5
  P-core   detect 166.7  sigma 138.8  rows 16.25 | reference  96.9 | ratio 1.720
  E-core   detect 237.2  sigma 195.6  rows 38.82 | reference 181.4 | ratio 1.308
  CI                                                              | ratio 1.323
```

**E-코어가 CI 비율을 1.2% 안에서 재현한다.** 즉 CI 값은 설명해 없앨 이상치가 아니고, **정상 대역이 지금 이만큼 넓다.**

P→E 로 갈 때의 배수가 이유를 말한다:

| | P | E | 배수 |
|---|---|---|---|
| detect (전체) | 166.7 | 237.2 | **1.42** |
| sigma | 138.8 | 195.6 | 1.41 |
| rows (AVX2) | 16.25 | 38.82 | **2.40** |
| 기준 커널 | 96.9 | 181.4 | **1.87** |

기준은 1.87배 느려지는데 검출기는 1.42배만 느려진다 → 비율이 내려간다. 그리고 검출기가 1.42인 이유는 **A-65 이후 시간의 90%가 sigma(1.41)이고 AVX2 루프(2.40)는 10%뿐**이기 때문이다. A-65 이전에는 검출기가 대부분 스칼라 화소 루프여서 기준과 같이 움직였고, 그래서 그때는 5.4% 안에서 맞았다.

**비율이 재는 것이 바뀌었다** — "이 기계가 얼마나 빠른가"에서 "이 기계의 메모리형 작업 대 스칼라 연산의 비"로.

### C2 — 후보 5종을 재고, 전부 기각했다

제약을 지켰다: **어느 후보도 검출기 코드를 한 줄도 부르지 않는다.** 전부 도구 TU 안에 독립적으로 작성했다.

| 후보 | 성격 | P→E 배수 |
|---|---|---|
| A (현행 게이트 커널) | 스트리밍 min/max + float 연산 | 1.87 |
| B | 16 MB 히스토그램, 정수 scatter | 1.78 |
| C | 36 MB 스트리밍 차분 + 히스토그램 | 1.89 |
| D | A + C | 1.86 |
| E | 4중 누산 스트리밍 합 (대역폭) | 1.75 |
| **검출기** | | **1.42** |

**테스트 TU 안에서 쓸 수 있는 것은 전부 1.75~1.89 에 모인다.** 검출기는 1.42다. 이유는 둘로 보인다 — 검출기는 `/arch:AVX2` 로 컴파일되고 테스트 TU 는 아니며, 검출기의 지배 단계가 이 후보들이 재현하지 못하는 메모리 형태다.

**그래서 결론은 "더 좋은 커널을 찾자"가 아니다.** 정상 대역이 약 1.30~1.72 로 넓다는 것이 사실이고, 상한은 그 위에 놓아야 한다. 기존 커널은 **그대로 두었다**(frozen 이라고 적혀 있고, 그 표시가 이번에 지켜진 것이다). 기각한 후보는 코드로 남기지 않고 측정값만 게이트 파일 주석에 기록했다.

### C3 — 상한 유도 (A-60 과 같은 방식)

**정상 대역** (AVX2 정상, fresh build 확인):

```
P-core  1.636 / 1.660 / 1.695 / 1.720   (4회)
E-core  1.298 / 1.301 / 1.303 / 1.308   (4회)
CI      1.323                            (A-65 이후 실행, 리더가 읽음)
```

**회귀 대역** — `XPE_DETECT_HAS_AVX2` 를 0 으로 강제(= 벡터 경로를 조용히 잃는 변경이 만들 모습). `BUILD_EXIT=0` 확인, detect 165.3 → 719.8 ms 로 실제 재빌드임이 보인다:

```
P-core  ratio 7.060   (detect  719.8 / ref 102.0)
E-core  ratio 7.154   (detect 1302.5 / ref 182.1)
```

회귀 대역에서는 **두 코어가 1.3% 안에서 일치한다** — AVX2 가 사라지면 검출기가 다시 스칼라가 되어 스칼라 기준을 다시 따라가기 때문이다. 이것이 C1 의 설명을 한 번 더 확인해 준다.

**상한 2.20**: 두 마이크로아키텍처를 통틀어 최악 정상값(1.720)보다 **27.9% 위**(A-60 이 쓴 29.6% 와 같은 성격), 최선 회귀값(7.060)보다 **69% 아래**. P-코어에서 1.28배, E-코어·CI 에서 1.69배 회귀를 잡는다. 종전 10.00 은 **6배 회귀까지 통과**시켰다.

더 조이지 않은 이유: 1.720 은 측정값이지 상한이 아니고, CI 러너 하드웨어는 이미 한 번 바뀌었다(기준 커널 172.3 → 158.1 ms). 관측된 기계 간 폭보다 좁은 여유는 민감도를 거짓 실패로 사는 것이다.

게이트 실행:

```
[perf-gate-ratio] 3072 ratio=1.612 limit=2.200
[       OK ] RuntimeDetectionPerformanceGateTest.Frame3072SquaredWithinMachineRatio
```

### C4 — 피연산자 순서를 구조로

네 개의 선택 각각에 **스칼라 삼항식이 곧 이름인 함수**를 만들고, 호출부는 자연스러운 `(a, b)` 순서로만 부른다. 뒤집는 일은 두 줄짜리 본문 안에서만 일어난다.

```cpp
/** @brief Exactly `(b < a) ? b : a` -- the `lo` of MedianSortCE. */
inline __m256 SelectCeLower(__m256 a, __m256 b) { return _mm256_min_ps(b, a); }
/** @brief Exactly `(b < a) ? a : b` -- the `hi` of MedianSortCE. NOT max(b, a). */
inline __m256 SelectCeUpper(__m256 a, __m256 b) { return _mm256_max_ps(a, b); }
inline __m256 SelectGreaterOf(__m256 x, __m256 y) { return _mm256_max_ps(x, y); }
inline __m256 SelectLesserOf(__m256 x, __m256 y) { return _mm256_min_ps(x, y); }
```

헤더 전체에서 `_mm256_min_ps`/`_mm256_max_ps` 를 부르는 곳은 이 네 줄뿐이다(확인: `grep` 결과 나머지는 전부 주석). 새 선택이 필요하면 여기에 이름 있는 래퍼를 추가하도록 `[HARD]` 로 적었다.

**테스트도 한 단계 내려갔다.** `NamedSelectionsMatchTheirScalarTernaries` 가 네 함수를 직접, 6×6 조합(±0 포함)으로 비트 비교한다. 중앙값에서 유추하게 하지 않고 함수 이름을 그대로 가리킨다.

**반증** — `SelectCeUpper` 안에서 피연산자를 뒤집었다. `BUILD_EXIT=0`:

```
SelectCeUpper(0, -0): scalar 0x80000000 vector 0x0
SelectCeUpper(-0, 0): scalar 0x0 vector 0x80000000
[  FAILED  ] Avx2ParityTest.NamedSelectionsMatchTheirScalarTernaries
[  FAILED  ] Avx2ParityTest.SignedZeroOrderingMatchesTheScalarNetwork
[  FAILED  ] Avx2ParityTest.PerLaneInputsAgreeBitForBit
[       OK ] Avx2ParityTest.FrameMapsAreIdenticalPixelForPixel        <-- 여전히 통과
```

카드 지시대로 `SignedZeroOrdering` 은 **지우지 않았다**. 프레임 테스트가 여전히 통과한다는 사실이 왜 그것이 필요한지를 그대로 보여준다.

### C5 — A-65 의 미검증 항목이 실제 결함이었다

A-65 보고서 Gaps 에 이렇게 적었다: *"비-MSVC 컴파일러 … 스칼라로 떨어진다 — 그 경로를 빌드해 보지 않았다."*

회귀 대역을 재려고 `XPE_DETECT_HAS_AVX2` 를 0 으로 만들자 **빌드가 깨졌다**:

```
runtime_detection.h(967): warning C4127: 조건식이 상수입니다  -> C2220 (에러)
runtime_detection.h(947): warning C4189: 'h': 참조되지 않음   -> C2220 (에러)
```

`const bool useVector = false;` 를 두고 `if (!useVector || ...)` 로 쓴 형태가 `/W4 /WX` 에서 상수 조건식이고, `h` 는 벡터 분기에서만 쓰였다. **AVX2 가 없는 어떤 환경에서도 이 헤더는 컴파일되지 않았다.** 벡터 분기를 `#if` 로 완전히 걷어내고 `h` 를 그 블록 안으로 옮겨 고쳤다.

**이 결함은 회귀 대역을 재려고 시도했기 때문에 나왔다.** 재지 않았으면 미검증 항목으로 남아 있었을 것이고, 미검증 항목은 결함이 아닌 것처럼 보인다.

그리고 처음 두 번의 측정은 **낡은 바이너리에서 나왔다** — 빌드가 C2220 으로 실패했는데 프로브가 이전 exe 로 돌아 직전과 똑같은 숫자를 찍었다. `BUILD_EXIT` 을 읽는 절차가 세 번째로 구제했다.

## 3. baseline 귀속 (Baseline-attribution)

- P/E 수치, 후보 5종, 회귀 대역 전부 **이 워크트리, 이 기계, 이번 세션**에서 잰 것이다. 각 셀 min of 5, 워밍업 1회 버림.
- CI 비율 **1.323** 은 리더가 읽어 전달한 값이며 **내가 재지 않았다**. 상한 유도에는 정상 대역의 한 점으로만 썼고, 그 점은 E-코어(1.298~1.308) 안쪽이라 상한을 좌우하지 않는다.
- A-60 의 7.125~7.715, A-65 의 692.7 ms 등은 인용이며 재측정하지 않았다.
- 게이트 커널은 한 글자도 바꾸지 않았다.

## 4. 미검증 (Gaps)

- **새 상한 2.20 을 CI 에서 확인하지 않았다.** A-60 과 같은 순서다 — 리더가 푸시 후 CI 비율을 읽어야 확정된다. CI 의 마지막 관측값 1.323 은 상한 아래이지만, **그 값은 이전 커밋의 것**이다.
- **세 번째 마이크로아키텍처.** P/E 는 둘 다 Intel 12세대다. CI 러너가 AMD 나 다른 세대라면 배수가 또 다를 수 있다. 정상 대역을 두 점(그리고 CI 한 점)으로 잡았을 뿐 경계를 증명하지 않았다.
- **비-MSVC 빌드는 여전히 안 해 봤다.** C5 에서 고친 것은 `XPE_DETECT_HAS_AVX2 == 0` 경로가 **MSVC 에서** 컴파일된다는 것이다. GCC/Clang 자체는 이 레인에 없다.
- **sigma 가 왜 1.41 인지** 재지 않았다. 메모리 형태라고 적었지만 분해하지 않았다 — 다음 카드의 주제다.
- **P-코어 핀 고정이 SMT 를 고려하지 않는다.** 논리 0번에 묶었고 그 물리 코어의 다른 스레드가 놀고 있다고 가정했다. 확인하지 않았다.
- **Doxygen 로컬 확인 불가** — 여전히(#159).

## 5. 잔여 위험 (Residual-risk)

- **2.20 은 P-코어 기준으로는 넉넉하고 E-코어 기준으로는 헐겁다.** 같은 상한이 두 코어에서 다른 민감도를 갖는다(1.28배 대 1.69배). CI 가 E 성격이면 실질 민감도는 1.69배다. 이보다 잘하려면 기준이 검출기를 따라가야 하는데, C2 가 그 길이 막혀 있음을 측정으로 보였다.
- **대역이 또 움직일 것이다.** σ 를 고치면 검출기의 구성이 다시 바뀌고, 구성이 바뀌면 비율이 재는 것이 또 바뀐다. **이번 카드가 두 번째로 겪은 일이고, 다음에도 겪을 것이다.** 게이트 상한은 큰 성능 변경마다 다시 유도해야 하는 값으로 취급하는 것이 맞다.
- **구조가 우회 가능하다.** 네 래퍼를 쓰라는 것은 주석의 `[HARD]` 이고 컴파일러가 강제하지 않는다. 누가 `_mm256_max_ps` 를 직접 쓰면 막히지 않는다 — 다만 그때도 `SignedZeroOrdering` 이 남는다. 기계적 강제(예: 헤더를 훑는 테스트)는 하지 않았다.
- **`--gate-probe` 는 이 기계의 코어 번호를 가정한다** (논리 0 = P, 16 = E). 다른 기계에서는 두 줄이 같은 코어를 잴 수 있고, 그러면 조용히 같은 숫자를 낸다.
