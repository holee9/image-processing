## 2. 무엇을 바꿨나

- **A1** — 세 로더를 "단계(stage)" 와 "확정(commit)" 으로 갈랐다(`xpe_preprocess_internal.h` 에 `StagedOffset/Gain/Defect`, `xpe_calib_stage_*`, `xpe_calib_commit_*_locked`, `xpe_calib_after_gain_commit`). 단계 함수는 읽기·체크섬·검증·할당·파싱을 전부 하고 전역을 건드리지 않으며 예외를 던지지 않는다. 확정 함수는 `g_calib` 에 옮기기만 하고 실패하지 않는다. 개별 로더 `xpe_calib_load_offset/gain/defect_map` 은 단계+확정을 차례로 부를 뿐이라 호출자에게는 그대로다(전체 시험이 같은 결과). 게인 로더가 확정 뒤에 하던 일(품질 메타데이터 반영, 다항식 범위 경고)은 `xpe_calib_after_gain_commit` 으로 옮겼고, 파이프라인은 세트가 모두 확정된 뒤에만 부른다. 파이프라인의 두 곳(단일·배치)에 복사되어 있던 읽기 블록은 `load_calibration_set` 하나로 합쳤다.
- **A2** — 핸들에 두 번째 이력 평면 쌍(`next1/next2`)을 만들 때 한 번 할당해 두고, 프레임은 `hist` 를 읽고 `next` 에 쓰며, 성공했을 때만 두 쌍을 `swap` 한다. 마지막 프레임 시각과 노출 추정도 같은 지점에서 확정한다. 단계 함수는 노출 통계를 핸들에 직접 쓰지 않고 `FrameStats` 로 돌려준다.
- **B1** — `xpe_logging.cpp`: 새 로거(싱크·로거·수준)를 지역에 완성 → `spdlog::set_default_logger` 로 설치 → 그 뒤에 이전 로거를 놓는다(이름이 다를 때만 `drop`). 설치 단계가 던지면 이전 로거가 그대로 기본이다.
- 공개 헤더: 파이프라인의 교정 세트 계약, 고스트의 실패 계약·메모리 2배, `xpe_log_set_file` 의 실패 계약을 적었다.
- 시험: `test_ghost_failed_frame.cpp`(2), `test_oom_injection.cpp` 의 `OomPipeline` 셋(세트 구별 통제 / 파일 오류 5종 × 두 진입점 / 할당 실패 스윕 × 두 진입점), `test_common_oom_injection.cpp` 의 A→B 전환 스윕.

## 3. 교정 세트 계약 — 최종 문장 (api-spec 용 한 단락)

> **교정 세트의 적재.** 파이프라인 진입점(`xpe_preprocess_pipeline`, `xpe_preprocess_pipeline_batch`)에 교정 디렉터리를 주면 `offset.xcal`, `gain.xcal`, `defect.xcal` 은 하나의 세트로 읽힌다. 세 파일이 모두 읽히고 검증되고(체크섬·형식·만료·게인 품질 필드) 메모리에 올라온 뒤에야 저장된 맵·치수·시각·세션 id·품질 메타데이터가 한꺼번에 교체된다. 그 전에 어떤 오류(파일 없음·손상·만료·형식 불일치·품질 필드 불량·메모리 부족)가 나도 교정 저장소와 품질 메타데이터는 호출 전 그대로이고, 호출은 해당 오류 코드를 돌려주며 영상과 메타데이터는 건드려지지 않는다. 세트가 일단 교체된 뒤에는, 이어지는 프레임 처리가 실패(예: 메모리 부족)하더라도 교체된 세트가 유지된다 — 개별 적재 함수 뒤에 보정 함수를 부르는 것과 같은 의미다. 개별 적재 함수(`xpe_calib_load_*`)와 `xpe_calib_state_load` 의 동작은 이 계약의 영향을 받지 않는다.

**QA-A-202b 보고서 정정.** 202b 의 1절은 "OOM 이면 … 교정 저장소가 호출 전과 같다" 고 적었다. 맞는 것은 "세트를 읽는 동안의 실패는 저장소를 바꾸지 않는다" 이고, 세트가 교체된 뒤 프레임 처리에서 실패하면 새 세트가 남는다. 202b 의 시험이 이를 못 본 이유: 저장소에 미리 넣은 세트와 파이프라인이 읽는 파일이 같은 값이어서 반쯤 교체된 저장소가 원래 것과 구별되지 않았다. 이번 시험은 값이 다른 세트 B 를 쓰고, 두 세트가 다이제스트로 구별됨을 통제로 먼저 단언한다(`SetsAAndBDiffer...`).

## 4. 고스트: 단독 API 의 계약 변화와 영향

- **변화**: `xpe_ghost_correct` 가 `XPE_ERR_PROCESSING_FAILED` 로 끝나면 핸들의 `hist1/hist2`, `lastAcqTimeSec`, `lastFrameMean`, `exposureWeight` 가 호출 전 그대로다. 전에는 처리된 화소까지의 이력이 이미 갱신되고, 마지막 프레임 시각은 처음부터 갱신되었다. 성공하는 호출의 결과는 달라지지 않는다(전체 시험 통과, 고스트 시험 47개 포함).
- **영향**: ① 실패한 프레임 뒤에 이어지는 호출은 "실패한 프레임이 없었던 것처럼" 처리된다(시간 간격도 마지막 **성공** 프레임에서 잰다). ② 호출자의 `img` 의 이미 보정된 화소는 되돌리지 않는다(헤더에 적음). ③ **메모리가 2배**: 핸들이 평면 둘이 아니라 넷을 든다(3072² 에서 약 75.5 MB → 151 MB).
- **시간** (3072², 12 프레임 중앙값, 같은 기계·같은 회차 교대 4회, `06_perf_ghost.txt`):

## 5. 이번 작업에서 시험이 잡아 준 설계 오류 (기록)

처음 만든 단계/확정 분리에서 `StagedOffset::map` 을 `unique_ptr` 로 두었더니, 확정 함수 안의 `g_calib.offset_map = std::move(staged.map)` 가 **제어 블록을 할당**했다(`offset_map`·`defect_map` 은 QA-A-202 이후 `shared_ptr` 이므로 `unique_ptr` → `shared_ptr` 변환은 할당한다). "확정은 실패하지 않는다" 는 전제가 깨져, 할당 실패 스윕에서 `noexcept` 함수 밖으로 예외가 나가 프로세스가 `terminate` 했다(종료 코드 3). 스택 추적(DbgHelp, 임시, 이미 제거)이 `xpe_calib_commit_offset_locked` 를 가리켰다. 단계 객체가 `shared_ptr` 를 들게 바꿔(제어 블록은 단계에서 할당) 해결했다. 게인의 두 맵(`unique_ptr`)은 이동만 하므로 할당이 없다.

## 8. 미검증 (Gaps)

- **`xpe_calib_state_load` 는 바꾸지 않았다.** 이 함수도 세 파일을 개별 로더로 차례로 적재하며 각각의 성공 여부를 상태에 적는다(리더 범위: "파이프라인의 3종 적재만"). 같은 반쯤 교체 문제가 이 경로에는 남아 있다.
- 캐시 로더(`xpe_calib_load_*_cached`)는 세트 개념이 없고 바꾸지 않았다.
- 고스트: 호출자의 `img` 에서 이미 보정된 화소는 되돌리지 않는다. 노출 통계는 tier 2·3 만 갱신하므로 tier 1 에서는 `lastFrameMean`·`exposureWeight` 가 원래도 바뀌지 않는다.
- B1: **같은 경로로 다시 지정**하면 새 싱크가 파일을 잘라내므로(`truncate=true`), 그 뒤의 실패에서는 이전 로거는 남지만 파일 내용은 이미 잘려 있다. 이 이중 실패(같은 경로 + 할당 실패)는 시험하지 않았다. 헤더는 "append 모드" 라고 적었으나 코드는 잘라내기로 연다 — 이번에 고치지 않았다(기존 불일치).
- 실패 시험 대상 파일 오류는 5종(없음·손상·품질 필드 불량 / 결함 없음·만료)이다. 게인 만료·오프셋 오류의 조합은 시험하지 않았다(단계 순서상 같은 코드 경로).
- `ci-preprocess` 구성 하나, Windows/MSVC 에서만 돌렸다.

## 9. 잔여 위험

- 고스트 핸들 메모리가 2배가 되어, 큰 프레임에서 `xpe_ghost_create` 가 이전보다 쉽게 `XPE_ERR_OUT_OF_MEMORY` 를 낼 수 있다(생성 실패는 이미 처리된다).
- 세트 확정 뒤 프레임 처리가 실패하면 새 세트가 남는다는 의미는 3절에 한 문장으로 적었다. 호출자가 "실패한 호출은 아무것도 바꾸지 않는다" 를 기대하면 어긋난다.
