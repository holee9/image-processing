# QA-A-172 (`#230`) — 경로는 **있고**, 그것은 타일 선택이 아니라 **검출 패스의 스칼라 폴백**입니다

카드가 물은 것은 두 가지였습니다 — 측정 능력(§2)과 `1.23x` 가 나올 경로(§3). 답이 카드의 가정과 **둘 다 다른 자리**에 있어서, 결론보다 먼저 정정 셋을 적습니다.

**모든 절대 ms 의 조건**: 3072×3072 FLOAT32, AVX2, 단일 스레드, `i7-12700`, RelWithDebInfo, 워밍업 1회 폐기 후 **번갈아 12라운드의 최솟값**(같은 라운드 안에서 비교 대상끼리 교대 — 이 기계의 이중 모드가 양쪽에 같이 걸리게). 관측 산포는 각 표에 함께 적었습니다.

---

## 0. 정정 셋

### (a) 카드가 말한 벽은 **이 함수의 벽이 아닙니다**

`xpe_interpolate_pixel`·`median_filter_cluster` 는 `defect_correct.cpp`(**`REQ-P1A-012`**, `QA-A-144`·`QA-A-169`)의 커널입니다. `#230` 의 성능 미달은 **`REQ-P1A-013` 런타임 검출**이고, 그 지배 항인 타일 선택은 `runtime_detection.h` 의 **`inline` 함수**입니다.

| 함수 | 위치 | 시험에서 부를 수 있나 |
|---|---|---|
| `SelectKthSmallest`, `ComputeTileSigmas`, `BuildFrameConfig`, `DetectRowRange`, `DetectEightPixelsAvx2` | `runtime_detection.h` (`inline`) | **예** — 헤더를 포함하면 됩니다. DLL 경계가 없어 `LNK2019` 가 날 수 없습니다 |
| `xpe_interpolate_pixel` | `helpers.cpp` (외부 링크, DLL 미노출) | 아니오 → **아래 §2 에서 풀었습니다** |
| `median_filter_cluster` | `defect_correct.cpp:78-112` **익명 네임스페이스** | 아니오 (내부 링크) |

즉 이 카드의 전반부("지배 항을 격리 못 한다")는 전제가 성립하지 않았습니다. 지배 항은 **`QA-A-165`·`QA-A-166` 이 이미 격리해 쟀습니다**(`차분 5.28`, `선택 63`, 검출 망 `7.71`).

### (b) "타일 선택이 하한의 90~93%" 는 두 수의 혼합입니다

| 무엇의 몇 % | 값 | 근거 |
|---|---|---|
| 선택 ÷ **타일 σ 단계** | 92% (63 / 68.3) | `QA-A-165` 의 90 / 92 / 93% |
| (차분 + 선택) ÷ **하한 76 ms** | 90% (68.3 / 76) | 위 표의 항 합 |
| 선택 ÷ **하한 76 ms** | 83% (63 / 76) | |

셋 다 사실이지만 **어느 것도 "출하와 하한의 격차가 어디에 있는가" 를 말해 주지 않습니다.** 그 이유가 (c) 입니다.

### (c) 하한 `76 ms` 의 선택 항은 **독립 하한이 아니라 출하 코드의 in-situ 실측**입니다

`QA-A-166` 표: `선택 63 ms (in-situ)` = `QA-A-165` 의 스테이지 68 − 차분 5. 하한이 **출하가 실제로 쓰는 값**을 그대로 넣었으므로, **`출하 ÷ 하한` 비는 선택 항을 구조적으로 1.0 으로 만들고** 나머지 항의 초과분만 잰 것입니다. 그래서 1.59배 전체가 선택이 아닌 곳에 있어야 했고, 실제로 그렇습니다(§1).

## 1. 분해 — 합이 전체와 맞습니다 (카드 §4)

같은 라운드 안에서 출하 진입점(`xpe_defect_detect_runtime`)과 그것이 하는 세 가지를 교대로 쟀습니다(`evidence/1_stage_sum_vs_whole.txt`).

| 타일 σ (`BuildFrameConfig`) | **63.1 ms** | 53% | 68.3 (차분 5.28 + 선택 63) — **같음** (§0c) |
| 지도 초기화 (`memset`) | 0.47 ms | 0.4% | 메모리 2.46 |
| **행 순회 (`DetectRowRange`)** | **53.7 ms** | **46%** | **7.71** (중앙값 망만) |
| 단계별 최솟값의 합 | 117.3 ms | | |
| **출하 전체 (최솟값)** | **117.9 ms** | | 하한 76 |
| 전체 − 합 | **0.6 ms** | | |

라운드별 어긋남도 `−15.3 … +2.1 ms` 이고 첫 라운드(−15.3)를 뺀 나머지는 `±5 ms` 이내입니다 — `QA-A-169` 의 `4.93 ms` 같은 **설명 못 한 몫이 없습니다.**

**출하–하한 격차는 행 순회의 초과분에서 나옵니다.** 항별로 맞추면:

| | 출하 | 하한 | 차 |
|---|---|---|---|
| 행 순회 vs 검출 망 | 53.7 | 7.71 | **+46.0** |
| 타일 σ | 63.1 | 68.3 | −5.2 |
| `memset` (하한에서는 메모리 항이 `max` 안에 들어가 더해지지 않음) | 0.47 | — | +0.5 |
| **합** | 117.3 | 76.0 | **+41.3** |

행 순회의 초과 `46 ms` 가 격차 전부이고 타일 단계는 오히려 하한보다 5 ms 작습니다.

> **제 오독 하나를 적습니다.** 분석 중 `QA-A-165` 반증표의 `AVX2 출하 13.5 ms` 를 3072² 검출 패스로 읽고 "`122 = 72 + 13.5 + 36 ms 어디에도 없음`" 이라 생각했습니다. `13.5 ms` 는 **1024² 프레임**의 전체 경로 값입니다(`test_zz_a161_probe.cpp:40` `kW = kH = 1024`, 그 시험의 목적이 *"타일 표가 전부를 스칼라로 밀었는가"* 였습니다). 측정이 이 착각을 바로잡았습니다.

## 2. §2 — 어느 칸입니까

**이 카드의 경로에서는 해당 없음** — 벽이 없는 자리를 벽이라 적었습니다(§0a). 다만 벽이 **실재하는** 함수(`defect_correct`)에 대해 네 갈래를 답해 둡니다. 카드 가정 중 가장 단정적이던 것이 **한 곳 틀렸기** 때문입니다.

| 갈래 | 판정 | 증거 |
|---|---|---|
| **내보내기** | **불필요.** 제품 ABI 에 추가되는 것 없음 | 아래 "내부 링크" 가 풀림 |
| **내부 링크** | **가능 — 같은 시험 타깃에 선례가 이미 있고, 실제로 풀었습니다** | ↓ |
| 계측 | 시도하지 않음 (필요 없었음) | |
| 불가 | **`median_filter_cluster` 만 해당** — 익명 네임스페이스라 링크로는 닿지 않음 | `defect_correct.cpp:78-112` |

### 내부 링크 — 선례와 대조군

`xpe_preprocess_tests` 는 제품 `src/*.cpp` 를 **6개 직접 컴파일해 넣고 있습니다**(`CMakeLists.txt`): `rle_codec`, `xpe_calib_generate_offset_methods`, `xcal_writer`, `xcal_reader`, `xpe_sha256_backend`, `xcal_validator`. 그중 `xpe_sha256_backend.cpp` 의 주석이 **바로 이 사유**입니다 — *"Sha256Stream is not exported from the DLL"*.

대조: 시험 타깃 블록을 파싱해 모듈별로 센 결과(`evidence/6_test_targets_compiling_src.txt`) — `preprocess` 6, `gsvg` 3, `ai` 2. **범위**: 타깃 이름에 `tests` 가 들어간 `add_executable` 블록만 봤고 그 정규식에 걸린 모듈은 4개입니다(`enhance_basic` 은 블록이 0개 `.cpp` 로 나와 목록 변수 방식으로 보이고, `enhance_advanced`·`display`·`dicom`·`common` 은 **걸리지 않아 판정하지 않았습니다**). 그러므로 "이 저장소 전반의 관행" 이 아니라 "**확인한 세 모듈에 선례가 있다**" 입니다.

**실제로 풀었습니다.** `helpers.cpp`(외부 링크 함수 `xpe_interpolate_pixel`) 를 시험 타깃 소스에 **한 줄** 더하고 격리 프로브를 붙였습니다 → `BUILD_EXIT=0`, 중복 심볼 없음, `LNK2019` 소멸.

| | 결과 |
|---|---|
| `xpe_interpolate_pixel` 격리 | **5.9 ns/호출**, 고립 결함 9,216곳(프레임의 0.098%) 한 번 훑는 데 **0.054 ms** |
| 조건 | 같은 위치 목록을 200회 반복해 최솟값 — **이웃 화소가 캐시에 있는 더운 값**이라 커널 비용의 **하한**에 가깝고, 실제 경로의 몫이 아닙니다 |

이 수는 `QA-A-169` 의 설명 못 한 `4.93 ms` 에 대한 답이 **아닙니다** — 그 격차는 커널이 아니라 커널 밖(복사·맵 훑기·할당의 차가운 값)에 있다는 방향만 보여 줍니다(`0.054 ms` 는 `9.91 ms` 의 0.5%).

`median_filter_cluster` 는 **다른 결정**이 필요합니다: (i) 시험 번역 단위에서 `.cpp` 를 `#include` 하거나 (ii) 익명 네임스페이스 밖으로 꺼내는 제품 소스 수정. (ii) 는 ABI 를 바꾸지 않지만(내보내지 않음) 제품 소스를 건드리므로 **선택하지 않았고 보고만** 합니다. (i) 는 시도하지 않았습니다.

## 3. §3 — 검출 패스의 **타일 경계 스칼라 폴백**

`DetectRowRange` 는 8칸 묶음의 여덟 칸이 **한 타일에 속할 때만** 벡터 경로(`DetectEightPixelsAvx2`)를 탑니다(참조 σ 를 방송하기 때문). 걸치는 묶음은 `scalarSpan` → **화소마다 `DetectDefectivePixel`** 로 빠집니다.

### 산술 (측정으로 확인됨)

타일 128, 묶음은 `x = 1, 9, 17, …` 에서 시작하므로 경계 `128k` 마다 `[128k−7, 128k]` 한 묶음이 걸칩니다. 행마다 경계 23곳 → **행당 184 화소**.

| | 값 |
|---|---|
| 스칼라로 가는 화소 / 행 | **184 / 3072 (5.99%)** |
| 프레임 전체 | 564,880 / 9,437,184 (**5.99%**) |

### 시간 — **독립된 두 추정이 맞습니다** (`evidence/2_straddle_fallback_cost.txt`)

| 추정 | 방법 | 값 |
|---|---|---|
| ① 시간 차 | 출하 행 순회 **53.0** − 걸침이 없는 구성(타일 한 장 = 한 행; 수치는 다르고 **시간만** 씀) **18.5** | **34.4 ms** |
| ② 직접 비용 | 그 564,880 화소를 스칼라로 직접(**62.6 ns/화소**) **35.4** − 같은 묶음을 벡터로 **3.4** | **31.9 ms** |
| 두 추정의 차 | | **2.5 ms** (7%) |

**화소의 6.0% 가 행 순회의 약 2/3 를 씁니다.** `QA-A-164` 가 이 헤더에 적은 *"at most one run in sixteen"* 은 **횟수는 맞고 비용을 재지 않은 문장**이었습니다(그 카드는 제가 했습니다). 화소당 비용이 다릅니다:

| | 화소당 | 근거 |
|---|---|---|
| 스칼라 폴백 | **62.6 ns** | 위 ② |
| 벡터, 촘촘한 전체 순회 | **1.96 ns** | 걸침 없는 구성 18.5 ms ÷ 9,437,184 화소 (가장자리 2화소/행 포함) |
| 벡터, 걸침 묶음만 따로 훑은 값 | 6.0 ns | 위 ② 의 3.4 ms ÷ 564,880 — 6% 씩 띄엄띄엄 접근해 캐시 효율이 낮은 측정이라 촘촘한 값보다 큽니다 |

스칼라 대 촘촘한 벡터는 **32배**이고, 6% × 32 ≈ 1.9 대 94% × 1 이므로 폴백 몫이 `1.9 / (1.9 + 0.94) ≈ 67%` — 측정한 `34.4 / 53.0 = 65%` 와 맞습니다. (② 가 뺀 벡터 값 3.4 ms 는 위 6.0 ns 측정이라 **폴백 비용을 약간 작게 잡는 쪽**입니다. 촘촘한 벡터 몫 `564,880 × 1.96 ns ≈ 1.1 ms` 를 빼면 `35.4 − 1.1 = 34.3 ms` 로 ① 과 0.1 ms 차입니다.) 같은 헤더의 `QA-A-69` 주석이 이미 *"스칼라 경계가 화소의 0.33% 인데 화소 루프의 16%"* 라고 적은 것과 **같은 형태**이고, 그때 이 걸침 묶음은 아직 없었습니다.

## 4. 대체안 — **무엇으로 바꾸는지**, 계산이 아니라 측정으로

**대체**: 참조 σ 를 **방송이 아니라 레인별 벡터**로 둡니다. 걸치는 묶음은 왼쪽 타일 참조와 오른쪽 타일 참조를 `_mm256_blendv_ps` 로 가릅니다(첫 `cut` 레인은 왼쪽, 나머지는 오른쪽). 걸치지 않는 묶음은 `cut ≤ 0` 이라 전 레인이 같은 값을 받아 방송과 동일합니다. **`DetectRowRange` 의 `oneTile` 분기가 없어집니다.**

프로브 안의 **복사본**(`DetectEightPixelsPerLane`)으로 구현했습니다 — 바뀐 곳은 참조 σ 한 군데뿐이고 나머지는 출하 줄 그대로입니다. 복사본이므로 **출하 진입점과 화소 단위로 비교**했습니다.

### 등가 (`evidence/3_per_lane_equivalence_and_rows.txt`)

| 프레임 | 표지 | 걸침 묶음 안의 표지 | **불일치** | 참조를 뒤바꾼 반증 팔의 불일치 |
|---|---|---|---|---|
| 균일 잡음 | 50 | 3 | **0** | 1 |
| 단계(σ 10→40) + 경계 옆 이상치 | 18,381 | 18,333 | **0** | **1,101** |

- **공허하지 않음**: 단계 프레임의 표지 18,381 중 **18,333 이 걸침 묶음 안**입니다 — 바뀐 경로가 실제로 판정을 내린 화소입니다
- **반증 팔이 터짐**: 좌우 참조를 뒤바꾸면(런타임 `volatile` 스위치) 단계 프레임에서 **1,101건이 갈라집니다.** 같은 뒤바꿈이 **균일 잡음 프레임에서는 1건뿐**이라 그 프레임만으로는 검사가 약했을 것입니다 — 단계 프레임이 판별력을 줍니다
- 구성상으로도 비트 동일이어야 합니다: 레인마다 `(1−w)·ref·ref` 를 출하와 **같은 순서**로 계산한 값을 받습니다

### 시간

| | 행 순회만 | 전체 경로 |
|---|---|---|
| 출하 | 53.7 ms | **117.4 ms** |
| 레인별 참조 | **23.0 ms** | **86.1 ms** |
| 차 | −30.7 | **−31.3** |
| 관측 산포 (12회) | 출하 53.7–60.0 / 대체 23.0–24.3 | 출하 117.4–139.9 / 대체 86.1–95.8 |

**전체 경로는 별도로 쟀습니다**(`evidence/4_whole_path_per_lane.txt`): `BuildFrameConfig + memset + 레인별 행 순회`를 출하 진입점과 **같은 라운드에서 교대로**, 지도는 측정 전후 모두 **불일치 0**. 부분 측정의 합으로 낸 예상(`117.9 − 30.7 = 87.2`)과 실측 `86.1` 이 `1.1 ms` 안에서 맞습니다 — `QA-A-167` 의 *"계산이었고 실제 구현은 20% 더 느렸다"* 를 피하려고 계산에 머물지 않았습니다.

### 하한·목표와의 관계 — **사실만**

```
하한                          76 ms    (QA-A-167 확정, 같은 기준)
출하 (오늘, 최솟값)          117.4 ms  →  1.54배   (QA-A-168: 121.2 ms, 1.59배)
레인별 참조 (오늘, 최솟값)     86.1 ms  →  1.13배
현행 목표 (하한 대비)                      ≤ 1.3배  →  98.8 ms
```

프로브 파이프라인은 현행 목표선 **아래 12.7 ms** 입니다. **목표 숫자는 제안하지 않습니다.**

## 5. 그러면 무엇이 남는가 — 구조상 남는 것

대체 뒤의 분해(`86.1 ms`): 타일 σ **63.1**(73%) + 행 순회 **23.0**(27%) + `memset` 0.5.

| 항 | 남는 이유 | 더 줄일 측정된 경로 |
|---|---|---|
| **타일 σ 63.1** | 576 타일 × 2회 정확 선택(`SelectKthSmallest`) | **없음.** 고정비를 없애는 구현이 20% **느렸고**(`QA-A-166`), `std::nth_element` 는 3.5배 느렸습니다. 다른 정확 선택 알고리즘은 **이 카드에서 재지 않았습니다** |
| 행 순회 23.0 | 망 7.71 외 적재·편차·σ·비교·저장 15.3 ms | 이 카드에서 더 나누지 않음. 스칼라 가장자리 2화소/행은 0.4 ms |

## 6. 구현 시 걸리는 조건 — **읽기로 본 것이고 측정하지 않았습니다**

프로브 복사본은 **출하 구성**(타일 128, `blendWeight > 0`)만 다룹니다. 출하 코드에 옮기려면 다음을 지켜야 합니다:

1. **타일이 8 미만이면 한 묶음이 세 타일에 걸칠 수 있습니다** — 레인별 참조 둘로는 부족합니다. 출하 상수는 128 이지만 `config.tileSize` 는 시험에서 바꿀 수 있으므로, 이 경우 스칼라 폴백을 **남겨야** 합니다
2. **`tileSize == 0`(타일 표 없음)** 이면 프로브의 `cut` 계산이 0 으로 나눕니다. 출하는 `tile == 0` 을 `oneTile` 이 이미 처리하므로 같은 처리가 필요합니다
3. **`blendWeight == 0`(옛 규칙)** 은 복사본이 다루지 않습니다 — 출하의 `else` 가지를 그대로 둬야 합니다
4. 스레드 경로(`DetectFrame` 의 작업자)도 `DetectRowRange` 를 쓰므로 **같은 변경을 받습니다.** 기존 병렬 등가 시험이 그 경로를 덮는지는 이 카드에서 확인하지 않았습니다

**변경 범위(측정이 아니라 읽기)**: `runtime_detection.h` 안 `inline` 함수 둘의 수정이고, **내보낸 심볼·구조체·시그니처는 변하지 않습니다** — 제품 ABI 변경이 아닙니다.

## 10. 미검증 / 잔여 위험

- **대체안은 프로브 복사본**이고 출하 코드에서 돌려 본 것이 아닙니다. §4 의 등가는 프레임 둘(균일, 단계+이상치)에서 확인했고, **구성상 비트 동일**이라는 논거가 나머지를 받칩니다. 임의 프레임에서의 등가를 전수로 보인 것은 아닙니다
- **`1.13배` 의 분모 76 ms 는 이 세션에서 다시 재지 않았습니다**(`QA-A-167` 확정값). 다만 오늘 타일 단계 최솟값이 `63.1` 로 하한이 쓴 `63` 과 같아 **분모의 기준이 오늘과 같다**는 것은 확인했습니다

- **`xpe_interpolate_pixel` 5.9 ns 는 반복 측정의 더운 값**이라 실제 경로에서의 몫이 아닙니다(§2)
