# QA-A-157 (#219) — 측정 불가를 합격으로 읽지 않게 했습니다

카드 §2 를 먼저 했고, **두 질문 모두 "맞추려는 대상이 옳다"** 로 답했습니다. 그래서 §1 (a) 를 그대로 수행했습니다.

## §2-1 — `:315` 의 `false` 는 **우연이 아니라 설계**입니다

`git blame` 으로 두 갈래의 출생 시각을 나란히 놓았습니다.

| 자리 | 커밋 | 시각 | 제목 |
|---|---|---|---|
| gain 경로 `overall_pass = false` (유효 화소 0) | `b6c19b8` | 2026-04-26 **21:35** | `feat(calibration): 7건 결함 수정 + FUNC-026/022~025/검증메트릭 구현` |
| offset 경로 `overall_pass = true` (균일 raw) | `86d2894` | 2026-04-26 **22:10** | `fix(calibration): 테스트-구현 불일치 4건 수정` |

`false` 는 **기능과 함께 들어왔습니다** — 그 함수를 처음 쓴 사람이 "잴 수 없으면 합격이 아니다" 로 정한 값입니다.

`true` 는 **35분 뒤**에 들어왔고, 그 커밋의 자기 요약 줄이 `- xpe_verify_metrics.cpp: uniform 이미지 처리 개선` 입니다. diff 는 `has_variation` 블록을 **신설**하면서 그 안에 `overall_pass = true` 를 넣습니다. 즉 **균일 이미지 시험이 빨간 것을 초록으로 만들려고 쓴 값**이지, 제품 판단으로 고른 값이 아닙니다.

**→ 맞추려는 대상(gain 의 `false`)이 옳습니다.** (#196 형태의 "가드가 감싸던 것보다 오래 산다" 와 같은 모양이지만, 여기서는 반대로 **나중에 들어온 쪽**이 근거가 약합니다.)

## §2-2 — 다른 두 함수에는 같은 분기가 **없습니다**

`xpe_verify_defect`·`xpe_verify_pipeline` 의 조기 반환을 전수로 읽었습니다.

| 함수 | 조기 반환 전수 | 측정 불가 → 합격 분기 |
|---|---|---|
| `xpe_verify_defect` | `XPE_ERR_INVALID_INPUT`, `XPE_ERR_BUFFER_TOO_SMALL`, `XPE_ERR_UNSUPPORTED_FORMAT`, 정상 끝(`:529`) | **없음** |
| `xpe_verify_pipeline` | 같은 오류 셋 + 정상 끝(`:616`) | **없음** |

둘 다 "잴 수 없다" 를 오류 코드로 내보내지, `XPE_OK` + 합격으로 내보내는 자리가 없습니다. 검색 범위는 `modules/preprocess/src/xpe_verify_metrics.cpp` 의 두 함수 본문 전체이고, 대조군은 같은 파일의 offset·gain 두 갈래(둘 다 잡힘)입니다.

**→ 둘 다 "없다/우연" 이 아니므로 §1 을 되돌릴 이유가 없습니다.**

## §1 구현 — (a) gain 경로와 맞췄습니다

`xpe_verify_metrics.cpp` 의 균일-raw 분기:

```cpp
metrics->dark_bias = 0.0;
metrics->dsnu = 0.0;
metrics->residual_noise = 0.0;
metrics->overall_pass = false;   // was true
return XPE_OK;
```

주석에 세 가지를 남겼습니다.

1. **왜 `false` 인가** — 두 오류가 대칭이 아닙니다. 거짓 합격을 믿은 호출자는 검증 안 된 프레임을 내보내고, 거짓 불합격을 믿은 호출자는 멀쩡한 프레임을 한 번 더 봅니다. **조용한 쪽은 앞의 하나뿐입니다.**
2. **어느 쪽이 설계였는가** — 위 §2-1 의 blame 증거를 주석 안에 적었습니다.
3. **한계, 그리고 그것은 실재합니다** — `overall_pass` 는 bool 하나인데 상태는 셋(합격 / 불합격 / 잴 수 없음)입니다. (a) 는 셋째를 둘째에 접습니다. 안전한 방향의 접기지만, **호출자는 여전히 둘을 구분하지 못합니다.** 진짜 해법은 별도 상태 필드이고 요구가 먼저라 여기서 만들지 않았습니다.

## §3 — 카드의 첫 갈래가 맞았습니다: **기존 시험 하나가 이 결함을 고정하고 있었습니다**

바꾸고 빌드하니 정확히 하나가 깨졌습니다.

```
[  FAILED  ] VerifyMetricsTest.VerifyOffset_PerfectCorrection
```

**그 시험의 픽스처는 자기 이름이 약속한 것을 한 번도 실행한 적이 없습니다.** 균일한 `raw` 를 넘겼으므로 어두운 영역이 없고, 호출은 측정 없이 조기 반환으로 빠져 `dark_bias = 0`·`dsnu = 0`·`overall_pass = true` 를 **분기가 채워 준 값**으로 받았습니다. 단언 셋은 전부 그 채워진 값 위에서 초록이었습니다.

그리고 그 분기가 생긴 이유가 바로 이 시험입니다 — `86d2894` 가 "uniform 이미지 처리 개선" 으로 신설한 것.

### 픽스처를 고치면서 **또 하나 알게 된 것**

첫 수정 두 판이 연달아 빨갰고, 둘 다 같은 원인이었습니다. 어두운 ROI 는 `raw` 의 **10 분위 미만**(`:291`~`:300`)인데:

- **판1** — 어두운 화소를 절반, 값 하나(`500`)로 뒀더니 10 분위 값이 `500` 이라 `< 500` 이 **0개**. 그러면 코드가 조용히 **전 화면**으로 대체합니다(`dark_corrected.empty()` 갈래). `dark_bias = 1000` (= 전 화면 평균).
- **판2** — 지터를 `i % 10` 으로 줬는데 밝기 주기가 `i % 5` 라 어두운 화소가 `i % 10 ∈ {0,5}` 두 값만 갖게 됐습니다. 같은 이유로 또 전 화면. `dark_bias = 1599.6`.

최종 픽스처는 **어두운 화소를 소수(20%)로 두고 지터 주기를 밝기 주기와 분리**했습니다(`(i / 5) % 10`). 이제 ROI 가 실제로 잡히고, 보정 프레임에서 그 화소들이 정확히 0 이라 `dark_bias = 0`·`dsnu = 0` 으로 **계산되어** 합격합니다. 사유를 시험 안에 적었습니다.

> 이 빈 ROI 대체 갈래는 **조용합니다** — 아무 신호 없이 측정 대상을 바꿉니다. 이 카드의 범위 밖이라 손대지 않았지만, `dark_bias` 를 믿는 모든 판정에 걸리는 자리입니다.

## 새 시험 — 그 입력을 고정합니다

```cpp
TEST_F(VerifyMetricsTest, VerifyOffset_UnmeasurableFrameDoesNotPass)
```

균일 `raw`(1500)·균일 `corrected`(1500). `XPE_OK` 는 그대로 받고(측정 불가는 오류가 아님), `overall_pass == false` 를 고정합니다. `dark_bias`·`dsnu` 가 0 인 것도 단언했는데, **측정값이 아니라 분기의 자리표시자**임을 다음 읽는 사람이 오해하지 않게 하려는 것입니다(주석에도 적음).

## 미검증 / 잔여 위험

- `overall_pass` 를 읽는 **제품 소비자**는 없습니다(선언 + 시험 11곳). 카드가 준 사실을 제가 다시 세지는 않았습니다 — 카드 판단을 그대로 씀.
- 이 변경은 **균일 프레임에 대한 판정을 뒤집습니다**. 균일 프레임을 검증에 넣던 외부 사용처가 있다면 이제 불합격으로 읽습니다. 저장소 안에서는 위 시험 하나가 유일한 그런 호출처였습니다.
- `xpe_verify_defect`·`xpe_verify_pipeline` 의 "분기 없음" 은 두 함수 **본문 전수 읽기**로 확인한 것이고, 같은 결함이 다른 파일에 있는지는 보지 않았습니다.
- 새 시험이 고정하는 것은 `false` 라는 **값**이지, "측정 불가" 라는 **상태**가 아닙니다. 상태 필드가 생기면 이 시험도 함께 바뀌어야 합니다.
