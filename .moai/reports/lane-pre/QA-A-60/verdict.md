## §2. Evidence — 증거

### 2-1. 왜 절대값이 아닌가

A-59 가 미검증으로 적은 "CI 기계는 아직 한 번도 안 쟀습니다" 에 다음 CI 런이 답했다.

| | 로컬 | CI | 비 |
|---|---|---|---|
| 3072² | 702.3 ms | **1340.9 ms** | 1.91배 |
| 1024² | 82.8 ms | **148.2 ms** | 1.79배 |

CI 샘플 1360.9 / 1363.3 / 1340.9, 스프레드 1.7% — **잡음이 아니라 기계**다.
1400 으로 올리면 개발 기계에서 2배 회귀가 통과한다(카드 지시대로 하지 않았다).

### 2-2. 기준 작업 선택 — 카드의 제안을 측정으로 기각했다

카드는 "작은 프레임의 같은 검출 경로" 를 자연스러운 후보로 들었다. **이미 가지고 있던
로그로 검증할 수 있었고, 검증해 보니 쓸 수 없었다.**

| 3072/1024 비율 | 값 |
|---|---|
| 정상(로컬) | 702.3 / 82.8 = **8.48** |
| 같은 코드, CI | 1340.9 / 148.2 = **9.05** |
| **실제 코드 회귀**(A-57: 중앙값 고속 경로 우회) | 1201.2 / 189.4 = **6.34** |

기계는 잘 흡수한다(8.48 → 9.05). 그런데 **진짜 회귀는 비율을 내린다** — 1024 프레임은 L3 에
들어가서 연산이 늘 때 상대적으로 더 손해를 보기 때문이다. `비율 <= R` 게이트는 그 회귀를
**통과시킨다.** 감시 대상과 기준이 같은 코드를 공유하면 감시할 것이 상쇄된다.

그래서 기준은 **이 테스트 파일에 고정된 커널**이다 — 메모리를 훑고 float 산술과 min/max 를
하지만 검출기 코드를 한 줄도 부르지 않는다. 기계가 느려지면 둘 다 커지고 비율은 그대로,
코드가 느려지면 검출기만 커져 비율이 오른다.

### 2-3. 기준 커널을 두 번 고쳤다 — 둘 다 측정이 시켰다

**첫 판(3 sweeps)은 쓸 수 없었다.** 기준값이 실행마다 24.8~46.6 ms 로 **2배 가까이** 흔들렸고,
그 결과 비율이 절대값보다 더 시끄러웠다 — 안정시키려던 것이 더 불안정해진 것이다.
12 sweeps + 5회 최솟값으로 늘리자 기준값이 99~113 ms 로 안정됐다.

**검출 반복도 3 → 5회로 늘렸다.** 1024 비율이 3회에서 0.739~1.123(52%)로 흔들렸는데,
그 폭이 정상과 회귀의 간격보다 넓었다 — **게이트가 자기 잡음 안에 살 수는 없다.**

### 2-4. 최종 측정 (모두 **빌드 exit 0 을 확인한 뒤**)

```
정상 5회:  3072 ratio 7.266 / 7.146 / 7.125 / 7.375 / 7.174   (스프레드 3.5%)
           1024 ratio 0.755 / 0.969 / 0.629 / 0.928 / 0.728   (스프레드 54%)

회귀 3회:  3072 ratio 12.711 / 12.466 / 12.190
           1024 ratio  1.153 /  1.140 /  1.359
```

| | 정상 최악 | 회귀 최선 | 분리 | 판정 |
|---|---|---|---|---|
| 3072 | 7.375 | 12.190 | **1.65배** | 게이트 가능 → **상한 10.00** |
| 1024 | 0.969 | 1.140 | **1.18배** | **게이트 불가** |

**1024 는 게이트로 만들지 않았다.** 정상 스프레드가 54%인데 정상 최악과 회귀 최선이 1.18배
떨어져 있다 — 어떤 상한도 정상 대역 안에 들어간다. 건강한 코드에서 터지거나, 영영 안 터지거나
둘 중 하나다. **자기 잡음 안에 있는 게이트는 없는 것보다 나쁘다** — 통과할 때까지 다시 돌리는
습관을 만들고, 그게 진짜 회귀가 통과하는 경로다. 숫자는 **찍되 단언하지 않는다**(CI 로그에
남아 추세는 읽힌다).

최종 실행(게이트 통과):
```
[perf-gate] 3072x3072 single thread, warm, min of 5: 692.9 ms  (samples 692.9 / 704.5 / 889.0 / 829.0 / 1005.6)
[perf-gate] reference kernel: 97.4 ms
[perf-gate-ratio] 3072 ratio=7.113 limit=10.000
[perf-gate-ratio] 1024 ratio=0.795 limit=none (diagnostic only, ...)
[  PASSED  ] 2 tests.
```

### 2-5. 실패 메시지 (카드 3항)

옛 문구 "셋 다 넘으면 진짜 느려진 것" 은 **이번 CI 상황에서 정확히 틀린 답**을 준다 —
느린 기계에서는 셋 다 높고 서로 붙어 있다. 새 메시지는 절대값·기준값·비율을 모두 찍고,
읽는 법을 적고, **그 옛 결론을 실제 CI 숫자와 함께 명시적으로 부정한다**:

```
  HOW TO READ THIS: the ratio is detection / reference, so a slow machine raises
  BOTH and leaves the ratio alone. A raised ratio means the DETECTOR got slower
  relative to this machine -- that is a code regression, and re-running will not
  clear it. If instead the absolutes look high but the ratio is near its usual
  value, the machine is slow and the code is fine.
  (Do NOT read three high samples as proof of a regression: on a slow machine all
  three are high and consistent -- QA-A-59's CI run showed exactly that,
  1360.9 / 1363.3 / 1340.9 with 1.7% spread.)
```

### 2-6. 반증 (카드 반증 절)

카드가 요구한 반증은 "기준 작업을 느리게 만들어 **비율이 안 움직이는지**" 다.
**그 형태로는 성립하지 않는다**: 기준만 느리게 하면 비율은 정의상 반드시 움직인다.
카드의 전제("기계가 균일하게 느려질 때 비율은 그대로")를 시험하려면 **둘 다** 느려져야 하고,
그건 (a) 다른 기계 또는 (b) 배경 부하다. **(b)는 이 레인 규약이 금지한다**(배경 부하 생성 금지).
그래서 (a) = CI 가 그 시험이고, §4 가 그것을 다룬다.

대신 게이트의 **목적**에 해당하는 절반을 반증했다 — 진짜 코드 회귀에서 비율이 오르는가:
- 조작: `ComputeMedian` 의 8값 고속 경로 우회(A-57 이 쓴 그 회귀)
- 빌드: `BUILD_EXIT=0`, `[14/14] Linking CXX executable bin\xpe_preprocess_tests.exe`
- 결과: 3072 비율 **7.1~7.4 → 12.2~12.7**, 상한 10.00 을 넘어 **게이트 발동**

**빌드 결과를 읽어서 두 번 구제받았다.** 이번 카드에서 `BUILD_EXIT=1` 인 채로 낡은 바이너리가
"정상" 비율을 찍은 일이 두 번 있었다(포맷 문자열 인자 불일치 C4474, 그 전엔 C2220).
그 값들은 **버렸다.** 위 표의 숫자는 전부 exit 0 을 확인한 뒤의 것이다.

### 2-7. Doxygen (카드 추가 절)

10개 함수의 `@param`/`@return` 을 채웠다. **코드를 읽고 썼고, 이름에서 추론하지 않았다.**
리더가 특히 짚은 둘:

- **`SelectKthSmallest` 의 `k` 는 0-기반**이다. 본문 `if (seen + hist[b] > k)` 에서 k=0 이면
  누적이 0을 넘는 첫 버킷 = 가장 작은 값이 나온다. 그리고 **`if (k >= n) k = n - 1u;` 로
  잘라낸다** — 범위를 벗어난 k 가 오류가 아니라 클램프라는 사실도 적었다
- **`MedianOfEight` 는 완전 정렬 후 `(v[3] + v[4]) * 0.5f`**, 즉 **4번째와 5번째로 작은 값의
  평균**이다. 짝수 개 중앙값 규약이 이 파일 전체에서 같다는 것도 함께 적었다

그 밖에 코드에서 확인해 적은 것: `ComputeMedian` 은 **입력을 재배열할 수 있다**(generic 경로는
제자리 분할, 8값 경로는 건드리지 않음 — 그래서 "재배열 여부를 가정하지 말라" 로 적었다),
`ComputeGlobalSigma` 의 조기 반환은 `w < 2 && h < 2`(**AND**)라 **1×N 프레임은 한 방향으로
계속 측정된다**, `DetectDefectivePixel` 은 이웃이 `RUNTIME_DETECTION_MIN_NEIGHBORS` 미만이면
false(SPEC 의 "판단하지 말고 건너뛴다" 규칙).

## §3. 판정

> **비율 설계는 로컬에서 작동한다** — 정상 7.125~7.375(스프레드 3.5%)와 회귀 12.190~12.711 이
> 1.65배 갈라지고, 상한 10.00 이 그 사이에 여유 있게 놓인다. **1024 는 같은 처리를 받았으나
> 분리되지 않아 게이트로 만들지 않았다**(1.18배 대 54% 스프레드). **다만 전제의 절반 —
> "비율이 기계에 대해 불변인가" — 는 CI 값 없이는 확인 불가이고, 상한 10.00 은 그때까지
> 잠정이다.**

## §4. 막힌 것 — push 가 필요하고 나는 push 할 수 없다

카드와 리더 메시지 모두 **"브랜치 push 후 CI 런 로그에서 비율을 읽고 상한을 확정하라"** 고 한다.
**이 레인은 push 가 금지되어 있다** — `CLAUDE.local.md`: "`push` 금지 — 커밋이 미푸시 유일본이다",
그리고 사용자 확인 대상에 push 가 명시되어 있다. 동료 세션의 요청이 그 금지를 풀지 못한다.

그래서 **읽을 수 있게 만들어 두고 넘긴다**:

1. 매 실행이 grep 한 줄을 찍는다 — `[perf-gate-ratio] 3072 ratio=<x> limit=<y>`
2. 상한 10.00 은 **소스 주석에 잠정으로 표시**했고, 확정 절차도 거기 적혀 있다
3. **리더가 해야 할 일**: 병합·push 후 CI 런 로그에서 `perf-gate-ratio` 줄을 읽고
   - CI 3072 비율이 **7~8 근처**면 → 전제 성립, 상한 10.00 유지(또는 max(로컬, CI)×1.3 으로 조정)
   - CI 비율이 **10 을 넘거나 5 아래**면 → **기준 커널이 기계를 대표하지 못한다는 뜻**이고,
     비율 설계를 버리고 **환경별 상수**로 가야 한다(카드가 둔 대안). 그 판단의 근거 숫자가
     바로 그 한 줄이다

게이트가 CI 에서 통과할지는 **모른다.** 현재 CI 절대값(1340.9 ms)이 로컬의 1.91배이므로,
기준 커널도 비슷하게 느려지면 비율은 7 근처를 유지해 통과한다. **그 가정이 이 카드의
유일한 미검증 핵심이다.**

## §5. Baseline-attribution — 무엇에 대고 쟀나

- **CI 절대값**: 리더가 전달한 CI 런 수치(1340.9 / 148.2, 샘플 3개 포함). 내가 재지 않았다
- **로컬 비율**: 이번 턴 5회 실행의 원값. 매번 **빌드 exit 0 을 확인한 뒤**의 값만 썼다
- **회귀 비율**: 같은 바이너리 형상에서 A-57 의 회귀를 재현해 3회
- **8.48 / 9.05 / 6.34 대조표**: A-57·A-59 로그 파일의 절대값에서 계산. 새로 재지 않았다
- **Doxygen 오류 목록**: 리더가 전달한 CI 런 34673059911 의 목록
- **테스트 수**: 이번 트리 ctest 전체

## §6. Gaps — 관측하지 않은 것

1. **CI 비율을 못 읽었다**(§4). 상한 10.00 은 잠정이고, 게이트가 CI 에서 통과할지 **모른다**
2. **Doxygen 을 로컬에서 돌리지 못했다** — 이 기계에 설치돼 있지 않고, 설치는 되돌리기 어려운
   환경 변경이라 하지 않았다(A-56 의 vcpkg 판정과 같은 이유). **"고쳤다" 는 주장이지
   검증이 아니다** — 카드가 요구한 확인은 CI 런 결과이고, 그것도 push 뒤에야 나온다
3. **카드가 요구한 형태의 반증을 하지 못했다**(§2-6). 기계 균일 감속을 재현할 수단이 없다
4. **기준 커널이 다른 CPU 에서 검출기와 같은 비율로 스케일하는지 모른다.** 캐시 크기·메모리
   채널이 다르면 비율이 달라진다 — 그게 §4 의 판정 기준이다
5. **1024 진단값의 추세를 누가 읽는지 정하지 않았다.** 단언이 없으므로 아무도 안 볼 수 있다
6. **3072 게이트의 정상 샘플 스프레드가 커졌다**(최종 실행 692.9~1005.6, 45%). 최솟값을
   쓰므로 판정은 흔들리지 않았지만, 그 폭이 왜 커졌는지 보지 않았다

## §7. Residual-risk — 남는 위험

1. **가장 큰 위험은 §4 다.** 이 카드는 CI 가 확인해야 끝나는데 나는 그 단계를 밟을 수 없다.
   리더가 push 하고 `perf-gate-ratio` 를 읽기 전까지 **게이트는 초록일 수도 빨간불일 수도 있다**
2. **Doxygen 은 검증되지 않았다.** 18건을 겨냥해 고쳤지만 **로컬 확인 수단이 없다.**
   문법 오류나 `@p` 오타가 남아 있으면 여전히 실패한다 — 이건 A-59 가 "로컬 통과는 게이트
   통과의 증거가 아니다" 를 배운 것과 **같은 형태의 미검증**이다
3. **주석을 채우는 일 자체가 이 저장소의 반복 실패 지점**이다(이름·주석이 코드에 대해 주장하고
   아무도 재검증하지 않는 형태). 코드를 읽고 썼다고 적었지만, **읽었다는 것 자체는 증명할 수
   없다** — 검증 가능한 형태로 남긴 것은 `k` 0-기반·클램프·짝수 규약처럼 **코드 라인을 인용한
   부분뿐**이다
4. **1024 를 진단으로 내린 것이 신호를 잃는 대가**를 치른다. 작은 프레임에서만 나타나는 회귀는
   이제 아무 단언에도 걸리지 않는다
5. 여전히 20배 초과이고 이 카드는 성능을 1 ms 도 개선하지 않았다 — 게이트를 고쳤을 뿐이다
