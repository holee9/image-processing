# QA-A-64 — 조용한 거절을 디버그에서 시끄럽게, 그리고 남은 1.7배가 어디 있는지

**카드**: `.moai/lanes/pre/inbox/QA-A-64.md` · **브랜치**: `dev/preprocess` · **기계**: Intel Core i7-12700 (P8+E4, 20 threads)

---

## 1. 주장 (Claim)

| # | 주장 |
|---|---|
| C1 | `DetectFrame` 에 디버그 단언을 넣었다. 릴리스 동작은 바뀌지 않는다 — `NDEBUG` 에서 `assert` 는 사라지고 조용한 `return` 만 남는다 |
| C2 | 반증: 짧은 길이로 부르면 단언이 **터진다**(abort, exit 3). 정확한 길이에서는 **안 터진다** |
| C3 | 3072² 단계 분해를 1/8/16 스레드에서 측정했고, **분해값의 합과 전체의 간극을 별도 행으로** 적었다 |
| C4 | 화소 루프 내부를 gather / median / copy+MAD / 나머지로 나눠 측정했고, 기존 `--decompose` 의 화소 루프 분할이 **측정 하네스 결함으로 무효**임을 확인했다 |
| C5 | 메모리는 여전히 병목이 아니다 — 프레임 스트리밍 읽기가 16스레드 전체 시간의 1.3% |
| C6 | 전체 스위트 628/69 통과, 경고 0 |

**측정만 했고 아무것도 고치지 않았다.** 아래 §6 에 판단을 근거와 함께 올린다.

## 2. 증거 (Evidence)

### C1 — 디버그 단언

`modules/preprocess/include/runtime_detection.h:1012` 부근:

```cpp
    const size_t needed = static_cast<size_t>(w) * static_cast<size_t>(h);
    // QA-A-64: the rejection is silent, and a silent rejection looks exactly
    // like "nothing was defective" (#148 was that shape). ...
    assert(mapCount >= needed && "DetectFrame: map is shorter than width * height");
    if (mapCount < needed) return;
```

단언이 `return` **앞**에 온다. 두 줄이 같은 조건을 말하고, `NDEBUG` 에서는 `assert` 만 사라지므로 릴리스 코드는 A-63 과 바이트 단위로 같다.

### C2 — 반증 (단언이 실제로 터지는지)

저장소의 테스트 프리셋은 `RelWithDebInfo` = `NDEBUG` 정의 → **일반 스위트에서는 이 단언을 실행할 수 없다.** 그래서 `NDEBUG` 없이(`/MDd /Od`) 컴파일한 독립 TU 로 확인했다. 스크래치패드의 `a64_assert_probe.cpp`, 컴파일 `COMPILE_EXIT=0`:

```
--- exact:
PROBE mode=exact mapCount=4096 needed=4096
PROBE returned normally (assertion did NOT fire)
EXACT_EXIT=0
--- short:
PROBE mode=short mapCount=4095 needed=4096
Assertion failed: mapCount >= needed && "DetectFrame: map is shorter than width * height",
  file D:\workspace-github\xpe-pre\modules\preprocess\include\runtime_detection.h, line 1019
SHORT_EXIT=3
```

한 요소만 짧아도 터진다. 정확한 길이에서는 조용하고 정상 반환한다. 프로브는 `_CrtSetReportMode` 로 단언을 모달 대화상자 대신 stderr 로 보낸다 — 안 그러면 자동 실행이 멈춘다.

**릴리스에서 동작이 안 바뀐다는 증거**: `RelWithDebInfo` 빌드로 628/69 전부 통과(§C6). 특히 A-63 의 `MapLengthTest.ShortMapIsRejected*` 2건이 그대로 통과한다 — 릴리스에서는 여전히 조용히 거절한다는 뜻이다.

### C3 — 단계 분해와 **간극**

새 모드 `xpe_detect_experiment --decompose-threads`. `DetectFrame` 을 직접 재고, 같은 스레드 수로 σ·memset·행 루프를 따로 잰 다음, **합과 전체의 차이를 GAP% 로 출력**한다.

```
[decompose-threads] 3072x3072 (9437184 pixels), best of 3 per cell
  threads       TOTAL      sigma     memset      rows*       SUM*     GAP%   rows_situ  repl/x
  1             665.5      139.9        0.2      598.5      738.5   -11.0%       525.5   1.14x
  8             176.3       39.1        0.4      130.1      169.6     3.8%       136.9   0.95x
  16            108.2       33.3        0.4       61.5       95.2    12.0%        74.5   0.83x
```

- `rows*` 는 이 TU 에서 컴파일한 **복제** 루프다. DLL 안의 것과 코드 생성이 다르므로 절대값이 배송 루프의 시간이 **아니다** — `repl/x` 가 그 비율(0.83~1.14배)이다.
- `rows_situ = TOTAL - sigma - memset` 은 구성상 전체를 정확히 채운다. 단계별 몫은 이쪽으로 읽어야 한다.

**구성상 채우는 분해 (rows_situ 기준)**:

| threads | TOTAL | sigma | 몫 | memset | 화소 루프 | 몫 |
|---|---|---|---|---|---|---|
| 1 | 665.5 | 139.9 | 21.0% | 0.2 | 525.5 | 79.0% |
| 8 | 176.3 | 39.1 | 22.2% | 0.4 | 136.9 | 77.7% |
| 16 | 108.2 | 33.3 | **30.8%** | 0.4 | 74.5 | 68.9% |

**스레드 확장 배수**: σ 는 139.9 → 33.3 = **4.2배**, 화소 루프는 525.5 → 74.5 = **7.1배**. 전체는 6.15배.

**GAP% 에 대해**: 복제 루프를 쓴 합은 전체와 -11.0% ~ +12.0% 어긋난다. A-58 이 86.5 ms 를 보고하고 배송 경로가 18% 느렸던 그 간극과 같은 크기다. 이번에는 그것을 숨기지 않고 별도 열로 찍는다. 원인을 하나로 특정하지 않는다 — 복제 루프의 코드 생성 차이, 스레드 생성·join, 워커별 scratch 벡터, 맵 첫 접근 페이지 폴트가 모두 이 안에 들어 있고, 이 측정으로는 분리되지 않는다.

### C4 — 화소 루프 내부

```
[pixel-stages] 3072x3072 (9437184 pixels), single thread, best of 3
  cumulative stage                          ms     delta   share
  gather neighbours                      104.6     104.6   13.9%
  + median (19-CE network)               366.1     261.5   34.8%
  + copy + MAD                           644.8     278.7   37.1%
  = full DetectDefectivePixel            750.4     105.6   14.1%
```

네 단계가 누적이고 단조 증가한다. **두 선택(median + MAD) 이 합쳐서 540.2 ms = 루프의 71.9%.**

**A-56 하한과의 대조** (A-56 기록: 19-CE 네트워크만 스칼라 260.3 ms, AVX2 15.97 ms):

- 이번 측정의 median 단계 **261.5 ms** 는 A-56 의 스칼라 하한 **260.3 ms** 와 사실상 같다. 즉 **median 은 이미 스칼라 하한에 붙어 있다.** 스칼라로 더 짤 여지가 거의 없다는 뜻이고, 남은 여유는 A-56 이 잰 AVX2 쪽(16.3배)에 있다.
- copy+MAD 278.7 ms 는 8개 복사 + 편차의 중앙값이므로 선택 한 번을 더 하는 것과 같다. median 과 같은 크기로 나온 것이 그 해석과 일치한다.

**기존 `--decompose` 의 화소 루프 분할은 무효다.** 같은 실행에서 이렇게 찍혔다:

```
    copy + MAD  (delta)                        434.6 ms    71.5%
    threshold + map write  (delta)            -130.1 ms   -21.4%
```

**음수 델타**. 원인은 코드가 아니라 하네스다 — 그 모드는 중간 변형에서 화소마다 `volatile float` 에 누적하는데(9,437,184번의 직렬화 저장), 전체 루프 변형은 플래그된 화소에만 맵을 쓴다. 중간 변형만 부풀려진다. `DetectDefectivePixel` 은 MAD 앞에서 단락하지 않으므로(이웃 5개 이상이면 전부 계산) "실제 루프가 MAD 를 건너뛴다"는 해석은 **틀렸다** — 코드를 읽어 확인했다(`runtime_detection.h:669`).

새 모드는 모든 단계가 평범한 지역 변수에 누적하고 루프가 끝난 뒤 한 번만 escape 한다. **부분의 합이 전체를 넘으면 그것은 하네스가 틀렸다는 신호**이고, 그 문장을 코드 주석에 남겼다.

### C5 — 메모리인지 연산인지

```
[memory-floor] streaming read of 9437184 float32 (36.0 MB)
   1 threads:    4.16 ms  ->   9.1 GB/s
   8 threads:    1.75 ms  ->  21.5 GB/s
  16 threads:    1.40 ms  ->  27.0 GB/s
```

16스레드에서 프레임 전체 읽기가 1.40 ms, 같은 조건의 전체 시간 108.2 ms 의 **1.3%**. 1스레드에서도 4.16 / 665.5 = 0.6%. **A-56 의 "연산 병목" 결론은 스레드가 붙은 뒤에도 유지된다.**

A-56 은 같은 성격의 읽기를 1.16 ms(≈40.7 GB/s)로 쟀고 이번엔 1.40 ms(27.0 GB/s)다. 차이는 측정 방식이다 — 이번 것은 스칼라 `double` 누적 루프라 대역폭 상한이 아니라 누적 의존 사슬에 걸린다. **그래서 이 숫자는 "달성 가능한 최대 대역폭"이 아니라 "이 형태로 읽으면 이만큼"이다.** 어느 쪽 숫자를 쓰든 결론(1~4 ms 대 108~665 ms)은 같아서 더 정밀하게 재지 않았다.

## 3. baseline 귀속 (Baseline-attribution)

- 모든 시간은 이 워크트리, 이 실행, 이 기계(i7-12700)에서 나왔다. 셀마다 best-of-3.
- A-56 의 260.3 ms / 15.97 ms / 40.7 GB/s 는 **이번에 다시 재지 않은 물려받은 값**이며, 위에서 대조용으로만 인용했다. median 단계는 이번 실측(261.5)이 그 값과 일치하는 것을 확인한 것이고, AVX2 15.97 은 확인하지 않았다.
- A-58 의 "18% 낙관적" 은 인용이며 이번 GAP%(-11.0~+12.0%)와 같은 성격이라고만 말한다. 같은 원인이라고 주장하지 않는다.
- 테스트 수 628/69 는 A-63 과 같다 — 이번 카드는 테스트를 추가하지 않았다(단언은 릴리스 스위트에서 실행 불가, §C2).

## 4. 미검증 (Gaps)

- **디버그 단언이 저장소 스위트에서 실행되지 않는다.** 모든 프리셋이 `RelWithDebInfo`/`Release`/Debug 커버리지뿐이고, 커버리지 프리셋(Debug)은 preprocess 를 포함하지 않는다. 확인은 수동 프로브로만 했고, **회귀로 잠기지 않았다** — 누가 단언을 지워도 CI 는 조용하다. Debug 프리셋에서 preprocess 테스트를 도는 구성을 만들 가치가 있는지는 판단을 올린다(§6).
- **GAP% 의 원인 분해 안 함.** 스레드 생성·join, scratch 벡터 할당, 페이지 폴트 중 무엇이 얼마인지 재지 않았다. 카드가 "간극의 크기를 적으라"고 했고 그것만 했다.
- **AVX2 하한 재측정 안 함.** A-56 의 15.97 ms 를 그대로 인용했다.
- **1스레드 복제 루프가 배송 루프보다 1.14배 느린 이유** 미조사. DLL 경계·인라인 차이로 보이지만 측정하지 않았다.
- **다른 프레임 크기·종류** 안 쟀다. 3072² 균일 잡음 + 주입 이상치 한 종류다. #148 의 교훈대로, 구조 있는 실제 영상에서 분해가 달라질 수 있다 — 특히 플래그 비율이 바뀌면 마지막 단계(맵 쓰기)가 달라진다.
- **Doxygen 로컬 확인 불가** — 여전히. `78670bc` CI 결과는 리더가 읽는다(#159).

## 5. 잔여 위험 (Residual-risk)

- **best-of-3 은 이 기계의 상태에 취약하다.** A-63 실행에서 3072² 표본이 692.7~1126.3 으로 벌어진 적이 있다. 이번 수치들도 같은 조건에서 나왔고, 비율(σ 대 루프, 단계 몫)은 안정적이지만 절대값은 ±10% 정도 움직인다고 보는 것이 맞다.
- **복제 루프 기반 결론의 취약성.** 화소 루프 내부 분해는 전부 복제 루프에서 나온 것이다(배송 루프 안을 계측하려면 코드를 바꿔야 하는데 이 카드는 측정만 한다). 복제/배송 비율이 1.43배(750.4 대 525.5)이므로 **단계 몫(%)은 믿을 만하지만 단계 ms 절대값은 배송 경로의 것이 아니다.**
- **`--decompose` 는 그대로 두었다.** 화소 루프 분할이 무효라는 것을 새 모드의 주석에 적었지만, 옛 모드 자체는 손대지 않았다(측정만 하라는 카드 범위). 누가 `--decompose` 출력을 그대로 인용하면 음수 델타를 인용하게 된다.

## 6. 판단 — 어디를 고쳐야 하는가 (근거 포함)

카드가 "판단이 서면 근거와 함께 올리라"고 했다. 세 가지를 올린다.

**(1) 가장 큰 단일 항목은 두 선택(median + MAD)이고, 스칼라로는 이미 하한이다.**
근거: median 단계 실측 261.5 ms 가 A-56 의 스칼라 하한 260.3 ms 와 일치한다. 두 선택이 루프의 71.9%. 그러므로 **스칼라 최적화로 남은 1.7배를 메우는 경로는 없다** — 여기서 더 줄이려면 SIMD 다. A-56 이 잰 AVX2 15.97 ms 가 그 여유의 크기를 말한다.

**(2) 16스레드에서는 전역 σ 가 두 번째 항목이 아니라 병목의 3분의 1이다.**
근거: σ 는 4.2배만 확장하는데 화소 루프는 7.1배 확장한다. 그래서 몫이 21.0% → 30.8% 로 커진다. **화소 루프만 SIMD 로 반으로 줄이면 σ 가 곧바로 절반 가까이를 차지한다.** A-61 이 잰 σ 의 포화(워커당 256 KB 테이블 할당)가 그 원인 후보이지만 이번에 재지 않았다 — 순서를 정한다면 화소 루프가 먼저이고, σ 는 그 다음에 다시 재야 한다.

**(3) 메모리는 아니다.** 1.3%. 이 축은 닫아도 된다.

**도구가 있어야만 답이 나오는 지점** (카드가 적어 올리라고 한 것):

- **GAP% 의 내부 분해** — 스레드 생성/join, scratch 할당, 페이지 폴트의 비중. 코드 안 타이머로는 서로를 가린다. 샘플링 프로파일러나 ETW 가 있어야 갈라진다. 다만 GAP 자체가 전체의 12% 이하라 **지금 우선순위는 아니라고 봅니다.**
- **배송 루프(DLL 내부)의 단계별 시간** — 복제가 아니라 진짜. 계측 코드를 넣으면 그 코드가 측정을 바꾼다(위 volatile 사례가 바로 그 형태). 샘플링 프로파일러면 코드를 안 건드리고 답이 나옵니다.

둘 다 **지금 필요하다고 주장하지 않습니다.** (1)의 결론 — 스칼라 하한에 붙었으니 다음 수는 SIMD — 은 프로파일러 없이도 섰습니다.
