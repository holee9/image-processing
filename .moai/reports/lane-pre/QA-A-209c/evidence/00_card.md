## 1 (높음) 옛 writer 의 정상 산출물을 새 reader 가 거부

옛 `build_config_json` 은 압축 파일 + 비어 있지 않은 호출자 설정에서 닫는 `}` 를 하나 더 붙였다: `{"mode":"production","xcal_compression":1,"xcal_raw_payload_len":4096}}`. 빈 객체 `"{}"` 는 `{,"xcal_compression":...}}` 가 됐다. 옛 reader 는 문자열 검색이라 허용했고, 새 reader 는 해시 검증 전에 `CONFIG_INVALID`. 교정 파일은 현장에서 만들어 보관하는 것이라, 거부하면 재생성 전까지 그 장비의 교정이 막힌다.

**리더 결정: 좁은 레거시 수용.** 느슨한 JSON 으로 되돌리지 않는다(#49 의 중복·중첩 방어를 잃는다).
- 엄격 파싱이 실패한 경우에만, 블록이 **옛 writer 가 만들 수 있었던 두 모양 그대로**일 때 결정적으로 고쳐 쓴 뒤(끝의 `}` 하나 제거 / `{,` → `{`) **다시 엄격 파싱**한다. 고친 결과도 중복·중첩·두 압축 키 규칙을 그대로 통과해야 한다. 두 모양 외의 깨짐은 지금처럼 거부
- 이 경로를 탔다는 사실을 경고 알림으로 남긴다(파일을 새 writer 로 다시 만들라는 안내 포함). 알림 문구는 레인 간 계약 — 보고서에 적을 것
- 옛 writer 가 그 모양을 만든 조건(압축이 실제로 적용된 경우 + 호출자 설정 유무)을 코드로 확인해 계약에 정확히 적는다. 해시가 설정 블록을 덮는지도 확인해 적을 것(덮지 않는다면 이 수용이 변조 탐지를 약하게 하는지 판단)
- 시험: `90c1b6b1` 의 옛 writer 식을 시험 안에 재현해 만든 두 모양의 파일(비어 있지 않은 설정, `"{}"`) → 새 reader 가 적재 + 경고, 같은 맵. 두 모양을 **조금만 벗어난** 블록(끝 `}` 둘, `{,` 뒤 중복 키, 고친 뒤 중첩 키)은 거부. 반증: 레거시 경로를 지우면 수용 시험 빨강, 모양 판정을 느슨하게 하면 거부 시험 빨강
