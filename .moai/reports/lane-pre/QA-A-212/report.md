# QA-A-212 — ConfigStrictParse 의 `write_xcal_file` 간헐 −9: 원인은 시험이 아니라 "목적지 파일을 잠깐 열고 있는 다른 프로세스", 제품 쪽 노출이 있어 고치기 전에 보고 (Refs #233)

기준: dev/preprocess `56a05cc5`. **코드 변경 없음**(진단용 수정은 되돌렸고 `git status` 에 modules/ 변경 0건). 증거: `evidence/`.

## 결론

1. 실패한 호출은 `write_xcal_file` 의 **마지막 단계, 임시 파일을 목적지로 바꾸는 `MoveFileExA(REPLACE_EXISTING|WRITE_THROUGH)`** 이고 OS 오류는 항상 `ERROR_ACCESS_DENIED(5)` 다(실패 22/22 런, 진단 출력 `20_…txt`). 파일 열기·쓰기 단계는 한 번도 실패하지 않았다.
2. 그 순간 **목적지는 잠긴 것이 아니다**: 실패 직후 목적지를 `DELETE`·`READ` 로 열면 둘 다 성공했고(속성 정상), **1 ms 뒤 같은 호출이 성공**했다(13/13). 즉 다른 누군가가 목적지를 1 ms 안쪽으로 열고 있었다.
3. 원인은 우리 코드도 시험의 경로 공유도 아니다: 제품 코드 없는 20줄짜리 프로그램(`12_race.cpp`: 파일을 쓰고 같은 이름으로 바꾸기를 반복)이 **같은 폴더에서 같은 시기에 같은 방식으로 실패**했다(아래 §2). 같은 프로그램이 다른 시기에는 0 건이다.
4. 메커니즘은 재현된다: 목적지를 `FILE_SHARE_DELETE` 없이 잠깐씩 열기만 하는 프로그램(`13_scanner.cpp`)을 곁에 돌리면 `MoveFileEx` 가 **GLE=5 로 3000 번 중 1565 번 실패**한다(없을 때 0). 임시 파일 쪽을 열면 GLE=32 로 실패 — 현장 서명은 5 이므로 열려 있던 것은 **목적지**다.
5. **제품 쪽 노출이 있다**: `replace_file` 은 재시도가 없어, 백신·색인기·동기화 도구가 목적지를 잠깐 열고 있으면 `xpe_calib_save`, 모든 생성기가 `XPE_ERR_IO_FAILED` 로 실패하고 옛 파일을 남긴다. 카드 규칙대로 **고치기 전에 보고하고 대기**한다(§4 제안).

**전체 스위트·셔플은 실패 횟수를 정량화하지 못했다**: 실패가 시기에 따라 달라져서(같은 코드가 같은 날 22/40 → 0/40), 전체·셔플 실행은 실패가 나던 시기에 돌리지 못했다. 격리 실행의 실패 시험이 전부 같은 파일을 루프로 쓰는 시험이라는 사실만 확인했다.

## 2. 원인 가설과 반증 시도 ("원인인가 증상인가")

**가설**: 목적지를 쓰기 직후에 열어 보는 외부 프로세스(백신 실시간 검사, 색인기, 파일 감시자)가 있어, 같은 이름으로 바꾸는 `MoveFileEx` 가 그 순간 거부된다.

시도한 반증과 결과:

| 반증 시도 | 결과 |
|---|---|
| 제품의 읽기 핸들이 안 닫혀서? (읽기가 원인이면 읽기 없는 시험은 안 터진다) | 읽기 없이도 터짐 → 기각 |
| 시험 간 같은 경로 공유·순서 의존? | 제품·시험 없는 `race.exe` 가 같은 시기에 터짐 → 기각 |
| 실패가 `ofstream` 이나 `WRITE_THROUGH` 때문? | 변형 4개 모두 터지고, 같은 조건이 다른 시기엔 0 건 → 기각 |
| 실행 파일의 신선도(막 빌드한 서명 없는 exe)? | 8분 뒤 같은 exe 가 같은 비율 → 기각 |
| 폴더 때문? | `modules/preprocess` 에서 터지던 `race.exe` 가 나중에 같은 폴더에서 0 건 → 폴더 고정 요인 아님, **시간에 따라 변하는 외부 활동** |
| 목적지를 짧게 여는 프로그램이 정말 같은 증상을 만드는가 | 만든다(§결론 4): GLE=5, 목적지 열기 가능, 재시도로 복구 — 서명 일치 |

**한계(이 가설이 확인하지 못한 것)**: 열고 있던 프로세스가 **무엇인지**(Defender, 검색 색인, git fsmonitor, 다른 레인의 도구 …) 특정하지 못했다. 시기에 따라 사라지는 것은 외부 활동의 존재를 시사하지만, 그 정체는 증명하지 않았다. 흉내 낸 scanner 는 초당 약 6.8만 번 열어 실제보다 훨씬 거칠다 — 메커니즘의 증명이지 빈도의 증명이 아니다.

## 3. 시험 쪽 고침은 하지 않았다

시험이 쓰는 경로(`csp_gx.xcal`, 현재 작업 디렉터리)를 바꾸거나 고유 경로로 만들어도 **같은 외부 프로세스가 같은 방식으로 새 목적지도 열 수 있고**, 고유 경로는 "덮어쓰기" 자체를 없애 이 시험이 하던 일(같은 파일을 새 내용으로 바꾸고 읽기)을 바꾼다. 위 기각 목록이 말하듯 원인이 시험의 경로 선택이 아니므로, 시험만 고치면 증상을 가릴 뿐이다. 카드 4번("원인을 되살리면 실패가 다시 나는지")은 §결론 4 의 scanner 로 증명되어 있다 — 고친 코드 쪽이 없으므로 "고친 뒤 0 건" 은 아직 없다.

## 4. 제품 쪽 제안 (리더 결정 대기)

`xcal_writer.cpp` `replace_file`: Windows 에서 `ERROR_ACCESS_DENIED`·`ERROR_SHARING_VIOLATION` 이면 **짧은 간격으로 제한된 횟수만 재시도**(예: 1 ms 부터 시작해 합계 약 100 ms 이내, 그 뒤에도 실패하면 지금처럼 `XPE_ERR_IO_FAILED` 와 임시 파일 삭제). 근거: 관찰된 모든 사건이 1 ms 안에 복구됐고, 재시도하지 않아도 되는 경로(다른 오류, POSIX `rename`)는 바뀌지 않으며 형식·공개 함수·성공 경로는 불변이다. 시험은 다음을 넣는다: (a) 목적지를 계속 여는 scanner 를 시험 안에서 돌리는 상태에서 쓰기가 성공하는 것(현재 코드는 실패), (b) scanner 가 영구히 잡고 있으면 제한 시간 뒤 `XPE_ERR_IO_FAILED` 가 나고 옛 파일이 그대로인 것, (c) 재시도 코드를 빼면 (a) 가 다시 빨갛게 되는 것. 리더가 승인하면 구현한다. 승인 전에는 아무것도 바꾸지 않았다.

## 미검증 (Gaps)

- 목적지를 열던 프로세스의 정체.
- 전체·셔플 실행의 실패율(§1 한계).
- 재시도 구현이 실제 환경에서 효과가 있는지(제안일 뿐 구현하지 않음).
- 다른 파일 쓰기 경로(`xpe_calib_save` 등 `write_xcal_file` 를 거치지 않는 것이 있는지)는 보지 않았다.

## 잔여 위험

CI 러너(깨끗한 환경)에서는 낮겠지만 개발자 기기·현장 기기(백신 상주)에서는 `xpe_calib_save` 와 생성기가 가끔 `XPE_ERR_IO_FAILED` 를 낼 수 있고, 지금은 호출자가 이유를 알 수 없다(알림도 없음).
