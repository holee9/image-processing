# GUI-C-156 — 행 15·16 재귀 설계 (보고만, 구현 없음)

**결론 먼저: 제가 걱정하던 재귀는 지금 구조에 없습니다.** 그러나 **만들기는 쉽고**, 한 가지 선택(어느 러너를 부르는가)이 그것을 가릅니다.

구현하지 않았습니다. 이 문서는 카드가 요구한 **설계 보고**입니다.

---

## 1. 먼저 — 두 러너가 실제로 무엇인가

| | `gui/ImageProcTest.SelfCheck` | `gui/ImageProcTest.E2E` |
|---|---|---|
| 형태 | **콘솔 `Exe`**(`OutputType=Exe`) | **콘솔 `Exe`** |
| 앱 참조 | `ProjectReference` → `gui/ImageProcTest` | 같음 |
| 앱 exe 를 띄우는가 | **아니오** | **아니오** |
| 무엇을 하는가 | 앱의 타입을 인프로세스로 써서 목 백엔드 결과를 단언 | ① `SelfCheck.exe` 를 **자식 프로세스로** 실행(`Program.cs:25`) ② **자기 프로세스 안에서** `new MainWindow()` 를 띄워 STA 스레드로 구동(`:74`) |

**둘 다 `ImageProcTest.exe` 를 실행하지 않습니다.** 따라서

```
앱 → E2E.exe → (SelfCheck.exe 자식) + (E2E.exe 안의 MainWindow)
```

로 끝나고 **앱 exe 가 다시 뜨지 않습니다.** 무한 재귀가 아닙니다.

## 2. 그럼 재귀는 어디서 생기는가 — **다른 러너를 부르면**

`clients/ImageProcTest.E2ETests` 는 다릅니다. 그 픽스처는 **앱 exe 를 실제로 띄웁니다**
(`ApplicationFixture.cs:132` `ProcessStartInfo(exePath)`).

그래서 "Run GUI E2E" 가 **`dotnet test clients/ImageProcTest.E2ETests`** 를 부르면:

```
CI 가 스위트 실행 → 앱 exe 기동 → (시나리오가 메뉴를 누름) → 앱이 스위트 실행
   → 앱 exe 또 기동 → …
```

**이쪽이 진짜 순환**이고, CI 의 `gui-e2e-native` 가 정확히 그 첫 줄입니다(`ci.yml:615`).

### 2.1 그래서 설계 선택 1 — **어느 러너를 부를 것인가**

| 선택 | 순환 | 비고 |
|---|---|---|
| **A. `gui/ImageProcTest.E2E.exe` 를 부른다** | **없음** | 콘솔 러너. 자기 안에 창을 만들므로 앱 창이 둘이 되지만 프로세스가 분리돼 있고 끝나면 종료 |
| B. `dotnet test clients/ImageProcTest.E2ETests` 를 부른다 | **있음** | 픽스처가 앱 exe 를 띄움 |

**A 를 제안합니다.** 툴팁이 말하는 *"현재 테스트 러너"* 도 이쪽이고(행 15 는 `SelfCheck`, 행 16 은 `E2E`), 순환이 구조적으로 생기지 않습니다.

## 3. 그래도 표식이 필요합니다 — **선택 A 에서도**

A 를 택해도 한 가지가 남습니다: **하네스가 띄운 앱에서 이 명령이 눌리는 경우.**

`clients` 의 E2E 시나리오가 실수로(또는 미래의 누군가가) 이 메뉴를 누르면
`스위트 → 앱 → E2E.exe → 그 안의 또 다른 MainWindow` 가 되어, **한 번뿐이지만 측정이 오염**됩니다.
제가 이번 주에 겪은 것과 같은 종류입니다 — 측정 중에 다른 것이 끼어드는 형태.

### 3.1 설계 선택 2 — **표식: 새로 만들지 않고 이미 있는 것을 씁니다**

| 후보 | 지금 보이는가 | 판정 |
|---|---|---|
| `App.IsAutomationMode` | `RawPath` **와** `ReportPath` 가 둘 다 있을 때만 참(`App.xaml.cs:42`). **E2E 픽스처는 `--automation-report` 를 주지 않으므로 거짓** | **부족** — 하네스가 띄운 앱을 못 잡음 |
| **`App.AutomationBackendMode` 가 비어 있지 않음** | 픽스처가 **항상** `--automation-backend` 를 넘김(`ApplicationFixture.cs:137-138`). 자동화 보고 모드도 넘김 | **충분** — 두 경우 다 잡힘 |
| 새 환경변수(`XPE_GUI_NO_RUNNER` 류) | 없음. 픽스처와 CI 양쪽을 고쳐야 함 | **불필요** — 위가 이미 있음 |

**제안: `App.AutomationBackendMode` 가 설정돼 있으면 두 명령은 러너를 띄우지 않고 그 이유를 상태줄에 적습니다.**

- 사람이 직접 연 앱: 그 값이 비어 있음 → **정상 동작**
- 하네스가 띄운 앱(E2E 픽스처·자동화 보고 모드): 값이 있음 → **거부 + 사유**

**환경변수가 아니라 인자**를 쓰는 이유: 환경변수는 자식 프로세스로 상속돼 **의도하지 않은 곳까지 번집니다.**
인자는 그 프로세스 하나에만 붙고, 이미 픽스처가 **예외 없이** 넘기고 있습니다.

### 3.2 거부는 비활성이 아니라 **말하는 것**입니다

`IsEnabled=false` 로 만들면 자동 집계(`DisabledFutureCommandCount`)가 **하네스 실행에서만 하나 더 세어**,
같은 빌드가 실행 방식에 따라 다른 수를 보고합니다. 그건 `#165` 가 고친 문제를 반대 방향으로 되살리는 것입니다.

**메뉴는 켜 두고, 눌렀을 때 상태줄에 사유를 적습니다** — 행 11 의 "비어 있을 때" 와 같은 형태입니다.

## 4. 확인했지만 **설계 밖**인 사실 하나 — 두 러너가 CI 에 없습니다

`.github/workflows/` 전체에서 `ImageProcTest.E2E` 와 `ImageProcTest.SelfCheck` 를 실행하는 곳이 **0건**입니다
(솔루션 `gui/ImageProcTest.slnx` 에는 등재돼 있습니다).

즉 **행 15·16 이 부르려는 러너 자체가 지금 아무 CI 잡에서도 안 돕니다.** `#205` 형태입니다.
이 카드의 범위가 아니라 **보고만** 합니다 — 다만 "메뉴에서 부를 수 있게 한다" 가
"이제 CI 가 그것을 돌린다" 를 뜻하지 않는다는 점은 구현 전에 정해져야 합니다.

## 5. 남은 미확인 — **이것들 때문에 아직 "설계 완료" 가 아닙니다**

카드가 *"확인 전에는 설계가 아니다"* 라고 한 기준을 제 자신에게 적용합니다.

| 미확인 | 왜 필요한가 |
|---|---|
| `E2E.exe` 가 **다른 앱 인스턴스가 떠 있는 동안** 도는가 | 자기 `MainWindow` 를 만드는데, 앱이 이미 STA 창을 가진 상태에서 자식으로 띄웠을 때의 동작을 **실행해 보지 않았습니다** |
| 러너가 **얼마나 걸리는가** | 앱이 UI 스레드에서 기다리면 멈춘 것처럼 보입니다. 비동기로 띄우고 결과를 받는 형태가 필요한데 **시간을 재지 않았습니다** |
| **실패를 실패로 보고하는가** | 카드 §2 의 요구입니다. `E2E.exe` 는 `Assert` 실패 시 예외로 죽는 것으로 보이나 **종료 코드를 실행으로 확인하지 않았습니다** |
| 러너 exe 의 **경로 해석** | `E2E.exe` 는 `FindRepoRoot` 로 저장소를 거슬러 올라가 `SelfCheck.exe` 를 찾습니다. 배포본에서는 그 경로가 없을 수 있습니다 |

**다음 단계 제안**: 위 넷을 실행으로 확인(러너를 손으로 한 번 돌려 시간·종료 코드·동시 실행을 재는 것)한 뒤
구현 카드를 받는 것입니다. 지금 구현하면 그 넷이 전부 가정이 됩니다.

## 6. 요약 — 제안하는 설계

1. **행 15** → `gui/ImageProcTest.SelfCheck.exe` 를, **행 16** → `gui/ImageProcTest.E2E.exe` 를 **자식 프로세스로** 실행
   (`clients` 스위트는 부르지 않습니다 — 그쪽이 앱 exe 를 띄워 순환을 만듭니다)
2. **하네스가 띄운 앱에서는 거부**합니다 — 판정은 `App.AutomationBackendMode` 가 비어 있지 않은지
3. 거부는 **비활성이 아니라 상태줄 문구**로 — 집계가 실행 방식에 따라 달라지지 않게
4. 결과는 **종료 코드와 stdout 마지막 줄**을 상태줄·로그에 싣고, 실패는 실패로 적습니다
5. 단언은 `gui-e2e-native` 에서 — 다만 **§5 의 넷을 먼저 실행으로 확인**해야 합니다
