# GUI-C-93 보고 — 앱 창 활성화 시각과 첫 UIA 조회 시각 (#170, 마지막 원인 조사)

커밋(dev/gui, 미푸시): 9980e62 — 기록 전용 픽스처 변경, 기본 꺼짐.

## 1. 기록 방법 (`LaunchTimingRecorder`)

- **켜는 법**: `XPE_C93_TIMING=1` 일 때만 켜진다. 기동마다 `XPE-C93-TIMING` 한 줄을 남긴다.
- **기록하는 시각** (모두 UTC):

| 항목 | 출처 | 해상도 |
|---|---|---|
| 프로세스 시작 | `Process.StartTime` (OS 기록) | 100 ns 단위 값 |
| `GetMainWindow` 반환 | 반환 직후 `DateTime.UtcNow` | 시스템 정밀 시계 |
| 첫 `AutomationId` 조회와 결과 | 탐침의 `launched` 조회 직전 `DateTime.UtcNow` | 같음 |
| 앱 창 첫 포그라운드 | `SetWinEventHook(EVENT_SYSTEM_FOREGROUND, WINEVENT_OUTOFCONTEXT)`. 전용 스레드의 메시지 루프가 콜백 안에서 `DateTime.UtcNow` 를 찍는다 | 이벤트 전달 지연만큼 |

- **포그라운드를 폴링하지 않은 이유**: 처음에는 폴링으로 시험했다(`smoke/` 첫 실행, 본 표본에서 제외). `Thread.Sleep(1)` 로 돌린 폴링은 **중앙값 15.5 ms 간격**이었다. 타이머 해상도를 올리면(`timeBeginPeriod`) 앱을 포함한 모든 프로세스의 타이밍이 바뀌므로 이벤트 훅으로 바꿨다.
- **꺼진 상태에서 달라진 것**:
  - 탐침의 `launched` 조회를 문자열 조립 안에서 하던 것을, 같은 순서 위치에서 변수에 담아 한 번 하도록 바꿨다. 조회 순서와 횟수는 그대로다.
  - 켠 상태에서만 `SafeFramework(launched)` 읽기가 다른 요소 두 개의 조회보다 앞으로 온다.

## 6. 한계

- **결함 표본**: 이번 70 기동의 Win32 는 3건(4.3%)으로, C-91·C-92 보다 적다. 결함 쪽 분포는 사실상 점 세 개다.
- **이벤트 시각**: 콜백 안에서 찍은 시각이라 실제 전환 시각보다 늦을 수 있다(out-of-context 전달 지연, 측정하지 않음). 모든 기동에 같은 방향으로 작용한다.
- **측정한 시각의 범위**: "첫 조회" 는 탐침의 조회다. 결함이 사는 요소는 `GetMainWindow` 가 만든 것이며, 그 **생성 시각**은 반환 시각으로만 알 수 있다.
- **변수 켠 상태의 영향**: 켠 상태에서는 앞에 적은 읽기 순서 하나가 달라진다. 이것이 결함률에 영향을 주는지는 측정하지 않았다.
