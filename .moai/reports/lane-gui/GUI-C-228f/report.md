# GUI-C-228f — PDB 문서 해시로 "컴파일된 그 내용"을 확인 (Codex #129)

앱 코드는 고치지 않았다. 바뀐 것은 `Safety/MockBlockingStaticTests.cs` 뿐이다.

## 무엇을 바꿨나

- 문서마다 PDB 의 해시 알고리즘 id 와 해시를 읽고, 해석한 파일 **바이트**의 해시와 비교한다(`ResolveByHash`). 다음은 모두 빨강이다.
  - PDB 에 해시가 없다.
  - 알고리즘 id 가 컴파일러가 쓰는 두 가지(SHA-256, SHA-1)가 아니다.
  - 해시가 같은 파일이 없다(빌드 뒤 소스가 바뀌었거나 빌드한 체크아웃이 아니다).
  - 같은 문서의 후보 파일이 둘 이상이다(PDB 가 적은 경로와 저장소 루트 아래 경로 꼬리들을 합쳐 서로 다른 파일이 둘 이상이면, 내용이 같든 다르든 모호함으로 실패. 리더 지시의 "같은 꼬리 후보 둘 이상" 해석: 내용이 다른 가짜 후보도 걸러야 해서 해시 필터 뒤가 아니라 앞에서 센다).
- 저장소 밖 경로(NuGet 캐시의 테스트 SDK 소스)도 해시가 같을 때만 인정한다.
- 스캔은 해시를 비교한 **그 바이트**를 디코딩해서 읽는다(`CompiledSource.Text`). 비교한 뒤 파일을 다시 읽지 않으므로 그 사이의 바꿔치기가 없다.
- 지금 트리에서 167개 문서가 모두 해시가 일치한다(통합 시험이 통과하는 것이 그 증거).

## 통제

`TheHashCheck_AcceptsOnlyAFileWithThePdbHash_AndRefusesEveryOtherCase`: 임시 저장소 루트의 작은 파일로, 해시가 같은 꼬리 파일은 수용(SHA-256·SHA-1 모두, 경로가 루트 밖이어도 해시가 같으면 수용), 내용이 바뀐 파일·해시 없음·미지원 알고리즘·파일 없음·같은 꼬리의 둘째 파일(내용이 같든 다르든)·루트 밖 파일의 해시 불일치는 각각 거절.

## 줄바꿈(autocrlf)

- 해시는 빌드 때 디스크에 있던 바이트에 대한 것이다. 이 시험도 시험 때 디스크의 바이트를 읽는다. 둘 사이에 파일이 바뀌지 않으면 같다.
- `core.autocrlf` 는 체크아웃·커밋 때 변환을 하는 설정이라(여기는 `input`: 커밋 때 CRLF→LF) 빌드와 시험 사이에는 개입하지 않는다. 로컬에서 측정한 것: 작업 트리의 파일 바이트로 빌드한 PDB 해시가 167개 모두 시험 때 일치한다(통합 시험 전체 통과).
- CI: `ci.yml` 의 "Run C# integration tests" 단계가 `dotnet test`(빌드 포함)를 한 번에 돌린다고 읽었다(그 단계가 `--no-build` 없이 시험 프로젝트를 호출). 같은 잡·같은 디스크 바이트라 일치한다고 읽었으나 CI 로그로 직접 확인하지는 않았다.
- 빌드 뒤에 `git checkout` 이나 에디터 저장으로 줄바꿈이 바뀌면 해시가 달라져 빨강이 되는데, 이 시험이 막으려는 사례와 구별되지 않는다(가용성 한계로 문서에 적었다).

## 미검증 / 잔여 위험

- CI 에서 실제로 일치하는지는 보지 않았다(위 줄바꿈 항 참조).
- 해시 알고리즘은 SHA-256 과 SHA-1 두 가지만 지원한다. PDB 가 다른 알고리즘을 쓰면(현재 컴파일러에는 없음) 빨강이다.
- 이 규칙은 "후보가 둘이면 내용이 달라도 빨강"이라 저장소 루트 아래에 문서와 같은 꼬리의 무관한 파일이 있으면 오탐이 날 수 있다. 현재 167개 문서에서는 발생하지 않았고, 생기면 파일 이름을 바꾸거나 허용 목록 대신 이 규칙을 다시 논의해야 한다.
- 이전 팔 중 PDB 와 무관한 것(F, C, G, H, JSON 손상)은 이번에 다시 돌리지 않았다. 바뀐 코드는 해시·후보 해석뿐이고 그 팔들이 건드린 경로가 아니라고 읽었다.
- DLL 없는 구성과 Release 구성은 이번에도 돌리지 않았다.
