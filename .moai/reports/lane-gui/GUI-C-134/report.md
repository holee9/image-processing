# GUI-C-134 — main 빨강: 원인은 `#156` 이다 (**측정으로 확정**), 골든 정정

## 1. 결론

`P10` 의 골든 해시가 움직인 원인은 **`efd14c1`(`#156`, VOI LINEAR 식)** 이다. 추정이
아니라 **양방향 측정**이다. 골든을 `f2a5640e9bd1a7fc` 로 정정했고, **왜 바뀌었는지를
상수 옆에 남겼다**.

## 2. `§3` 양방향 측정 — 원인 고정

같은 시나리오·같은 시험 바이너리에, **`xpe_display.dll` 만 갈아** 돌렸다.

```
새 DLL (efd14c1 이후, run 36233436427 / 9b7f378)
  P10 hash=f2a5640e9bd1a7fc mean=85.206

옛 DLL (efd14c1 이전, run 36230905807 / 3fda16a)
  P10 hash=36fc547e253b07f1 mean=85.205      ← 골든이 돌아왔다
```

**옛 DLL 에서 골든이 복귀했으므로 원인은 `#156` 이다.** 카드가 경고한 경우(옛 DLL 에서도
`f2a5…` 가 나오는 것)는 일어나지 않았다.

### 산출물 귀속 — 문자열이 아니라 커밋 조상 관계로

```
git merge-base --is-ancestor efd14c1 3fda16a  → NO    (초록 쪽에 없다)
git merge-base --is-ancestor efd14c1 9b7f378  → yes   (빨강 쪽에 있다)
```

**md5 는 판별자가 아니다** — 두 실행의 DLL 11개가 전부 다르다(매 실행 재빌드). 그래서
"어느 DLL 이 바뀌었나" 로는 원인을 좁힐 수 없고, 조상 관계가 유일한 귀속 수단이다.
(`GUI-C-131` 에서 문자열 프로브로 실패한 뒤 세운 방식이다.)

## 3. 변화의 **크기** — 0.001 카운트

```
mean  85.205 → 85.206      (Δ 0.001, 0..255 스케일)
```

`P10` 은 **기본 창**으로 돈다 — `AppSettings.cs:38-39` 의 `c=32768`, `w=65535`
(시나리오는 GSVG 파라미터만 만지고 VOI 는 건드리지 않는다). 그 창에서 두 식의 차이는
최대 `0.5/(w−1)` ≈ **0.0039 카운트**이고, 프레임 평균으로는 그보다 작다 — 실측 0.001 이
그 안에 든다.

**post 가 계산으로 넘긴 두 경우 중 "넓은 창" 쪽이 맞았다.** 좁은 창(`c=100, w=200`)
쪽이면 1024 인덱스에서 511.5 → 514.07 로 **눈에 보이는** 차이가 났을 텐데, 여기서는
아니다. post 의 수치는 계산이었고 이 측정이 어느 쪽인지 갈랐다.

### 그래서 이 단언이 무엇을 재고 무엇을 못 재는가

해시는 **비트 동일성**을 묻는다. 이 시험의 이름은 `KeptTheDrawnPixels` 인데,
**0.001 카운트의 반올림 이동과 렌더가 깨진 것을 구별하지 못한다** — 화면으로는 같은
영상인데 해시는 완전히 바뀐다.

지금 고치지 않는다(카드 범위 밖). 기록만 남긴다: 골든 해시는 **회귀 감지기로는
과민하고, 표시 품질 측정기로는 쓸 수 없다.** 크기를 말해 주는 것은 평균이고, 그래서
평균을 상수 주석에 같이 적었다.

## 4. 골든 정정 — 숫자만 바꾸지 않았다

`GsvgLargeFrameScenarios.cs:630`. 상수 옆 주석에 남긴 것:

- 옛 값 `36fc547e253b07f1` → 새 값 `f2a5640e9bd1a7fc`
- **옛 골든은 틀린 식으로 찍힌 값**이다. `efd14c1` 이 `XPE_VOI_LINEAR` 을 DICOM PS3.3
  C.11.2.1.2.1 창 배치(`center-0.5`/`width-1`)로 바꿨다. **회귀가 아니라 정정이다**
- 양방향 측정 원문(두 해시 + 두 평균)
- 변화 크기 0.001/255 와 그것이 뜻하는 것
- **다시 갱신해야 할 때는 표시 파이프라인 식이 또 바뀐 것**이므로 그 변경을 먼저 찾아
  인용하라. 그런 변경 없이 움직인 해시는 회귀다

### 정정 뒤 양방향 재확인 (`G1`·`G2`)

```
새 DLL -> 통과!  - 실패: 0, 통과: 1, 건너뜀: 0, 전체: 1
옛 DLL -> 실패!  - 실패: 1, 통과: 0, 건너뜀: 0, 전체: 1
```

**`G2` 가 실제로 성립한다** — 원인을 되돌리면 실패가 다시 나타난다. 골든만 바꾸고
끝냈다면 이 대조가 없었을 것이다.

## 5. `§5` 같은 원인의 다른 골든 — **움직인 것 1, 안 움직인 것과 그 이유**

전수로 찾았다. 시험 트리에 **절대 해시 골든은 하나뿐**이다.

```
grep -rnE "\"[0-9a-f]{16}\"" clients/ gui/ --include=*.cs
  → GsvgLargeFrameScenarios.cs:630  PreviewBaselineHash   (유일)
```

| 단언 종류 | 파일 | LINEAR 변경에 움직였나 | 이유 |
|---|---|---|---|
| **절대 골든** | `GsvgLargeFrameScenarios.cs:592` | **움직였다** | 상수와 비교하므로 식이 바뀌면 깨진다 |
| 상대 해시 (before → after, 같은 실행) | `TwoLaneWorkbenchScenarios.cs` (L-01·02·04·06) | **안 움직였다** | 양변이 같은 DLL 로 찍히므로 식이 바뀌어도 **같이** 움직인다 |
| 상대 해시 (lane A vs lane B) | `LaneDenoiseScenarios.cs` (L-05) | **안 움직였다** | 같은 이유 |
| 절대 평균·화소 수치 | — | 해당 없음 | 그런 단언이 없다 (`Assert.Equal(<실수>` 0건) |

**안 움직인 것이 정보다**: lane 시나리오들은 **상대 비교**라 표시 식 변경에 면역이다.
바꿔 말하면 **표시 식이 틀리게 바뀌어도 그 시험들은 초록**이다 — `#156` 같은 변경을
잡아낸 것은 오늘도 `P10` 하나뿐이었고, 그 민감함이 §3 의 과민함과 같은 성질이다.

## 6. 빌드·시험

```
BUILD_EXIT=0
Native P10          : 새 DLL 통과 1 / 옛 DLL 실패 1  (§4 대조)
Native E2E 전체     : 통과 150, 건너뜀 0, 실패 0  (12m 5s, 새 DLL + 정정된 골든)
```

**전체 150건이 초록이므로 `#156` 으로 움직인 것은 `P10` 하나다** — §5 의 정적 census 가
예측한 대로이고, 이것이 그 예측의 실측 확인이다. 건너뜀 0 이라 "재지 않고 지나간 것"
도 없다.

## 7. 미검증 (Gaps)

- ~~Native E2E 전체 결과가 없다~~ → **150 통과 / 0 건너뜀 / 0 실패로 확인했다** (§6).
- **IntegrationTests 를 이 카드에서 다시 돌리지 않았다.** 표시 식은 E2E 경로이고 통합
  시험은 DLL 을 직접 부르지만, LINEAR 를 타는 통합 단언이 있는지 전수로 보지 않았다.
- **`modules/display` 의 새 식이 옳은지는 판정하지 않았다** — post 소유이고, 카드 범위
  밖이다. 이 보고는 "gui 의 골든이 그 변경으로 움직였다" 까지다.
- **좁은 창에서 재지 않았다.** 0.001 은 기본 창(`w=65535`)의 값이다. 좁은 창을 쓰는
  임상 프리셋에서는 차이가 커지는데(post 계산: `c=100,w=200` 에서 1024 인덱스 2.5),
  그것을 측정한 시험은 없다.
- 실행은 각 팔 1회다. 해시는 결정적이라 반복이 필요 없다고 판단했지만 **재지는 않았다.**
