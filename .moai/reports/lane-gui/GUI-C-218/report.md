# GUI-C-218 — 레거시 E2E 의 UIA 타임아웃과 `dotnet test` 가 멈추는 원인 (#249)

## 결론 (한 문단)

**두 현상은 서로 다른 원인의 연쇄다.** (1) UIA 타임아웃의 원인은 **212b 가 도입한 자식 프로세스 오라클이 앱 시작 때 UI 스레드에서 세 번 동기로 실행되는 것**이다: UI 스레드가 시작 직후 중앙값 약 1 초(최대 4.4 초) 응답하지 않고, FlaUI 의 UIA 연결 제한 시간이 2 초라서 그 사이에 걸린 UIA 호출이 `Operation timed out` 으로 실패한다. 자식 프로세스 도입 전 커밋은 같은 시험이 **0/32 실패**, 도입 후는 **7/32 실패**(Fisher 정확검정 p = 0.011). (2) `dotnet test` 가 멈추는 것은 **시험 정리 결함**이다: 시작 도중 UIA 타임아웃이 `LaunchOrSkip` 안에서 터지면 `LegacyApp` 객체가 만들어지기 전이라 시험의 `using` 이 닫을 것이 없고, 남은 앱이 시험 호스트의 출력 파이프를 쥔 채 살아 있어서 파이프를 읽는 쪽이 끝나지 않는다. 이 정리 결함은 **고쳤다**(수정 뒤 실패 22건에 남은 앱 0개). 앱 쪽 원인은 제안만 한다.

## 1. 재현과 A/B (`ab_runs_*.txt`)

A = 자식 프로세스 도입 전(214, `0ac0db5a` 를 `git archive` 로 풀어 따로 빌드), B = 도입 후(HEAD `d90bd2ce`). 같은 시험·같은 네이티브 폴더, **A·B 를 번갈아**(ABBA) 실행했고 `dotnet test` 출력은 파이프가 아니라 **파일**로 받았다(파이프로 받으면 아래 3 절 때문에 측정이 멈춘다). 매 실행 뒤 남은 `ImageProcTest.exe`·`xpe_oracle_*` 폴더·`xpe_not_a_directory_*` 파일을 기록하고 앱은 강제 종료했다.

| `ab_runs_1_all_legacy` | 레거시 9건 전체 12회씩 | 0/12 | **2/12** (R01·R02) | 실패 2건 → **앱 2개** |

- 실패는 전부 같은 모양이다: `UIA Timeout`/`COMException: Operation timed out (0x80131505)`, 위치는 시험 본문이 아니라 **`LaunchOrSkip` 안의 `GetMainWindow`**(`LegacyPreprocessReadinessScenarios.cs:93`, 스택은 `runs1/r01_B.txt`).
- **실패한 모든 B 실행(수정 전 7건)이 앱을 정확히 하나씩 남겼고, 성공한 실행은 남기지 않았다.** A 는 실패도 남은 앱도 0.
- 표 3 은 같은 시간에 다른 무거운 명령(디스크 스캔)이 돌던 때라 B 실패율이 65%까지 올랐다 — **부하에 민감하다는 것이 UI 정지 가설과 맞는 관측**이지만 A/B 비교에는 쓰지 않는다. 표 4 가 깨끗한 기계에서의 비교다. B 의 실패율은 22%~45%로 기계 상태에 따라 움직인다.

## 2. 원인 1 — UI 스레드가 시작 때 막힌다 (UIA 타임아웃)

**FlaUI 의 기본 UIA 연결 제한 시간은 2 초**다(`flaui_default_timeouts.txt`: `ConnectionTimeout = 00:00:02`, `TransactionTimeout = 00:00:20`; 시험과 같은 어셈블리에서 읽음). 대상 앱의 UI 스레드가 2 초 넘게 메시지를 처리하지 못할 때 걸린 UIA 호출이 위 예외로 실패한다.

앱 시작(`MainWindow.Window_Loaded`)은 `RefreshNativeHealth()`(→ 오라클 1회) → 그 안의 `RefreshModuleReadiness()`(→ 2회) → `RefreshModuleReadiness()`(→ 3회)로, 오라클을 **UI 스레드에서 동기로 세 번** 돌린다(코드 읽기로 확인한 호출 경로, 실제 자식 수는 아래 측정으로 확인). 212b 이전에는 같은 호출이 프로세스 안에서 몇 ms 였지만 지금은 호출마다 자식 프로세스(WPF 앱 한 벌)를 띄운다.

측정:
- **자식 수**(`oracle_children_at_startup.txt`, 앱을 12번 띄워 4 ms 간격으로 프로세스 목록을 봄): B 는 매번 **자식 3개**(각 150~260 ms, 합 530~710 ms), A 는 0개.
- **UI 정지**(`ui_stall_*`, 메인 창에 `WM_NULL` 을 3 ms 간격으로 보내 응답 못 한 가장 긴 구간):

| 변이 | 시작 | 중앙값 | p90 | 최대 | >1 s | >2 s |
|---|---|---|---|---|---|---|
| A 프로세스 안 오라클 | 30회 | **224 ms** | 245 | 327 | 0 | 0 |
| C 자식 오라클 3개(현재) | 30회 | **963 ms** | 1781 | **2947** | 13 | **3** |
| D 실험: 판정 캐시, 자식 1개 | 30회 | 438 ms | 1036 | 2109 | 5 | 1 |

(A·C·D 를 번갈아 6회씩 5라운드. 앞선 별도 측정에서는 C 의 최대가 4.4 s. D 는 `$TEMP` 에 만든 **버려질 사본**이고 저장소에는 없다.)

2 초를 넘는 정지가 C 에서 30회 중 3번(10%), 1 초 이상은 13번이다. 시험이 UIA 로 창을 잡는 순간이 그 구간에 걸리면 실패한다. 시험은 UIA 호출을 여러 번 하므로 정지가 2 초 미만이어도 호출 하나가 더 막힐 수 있어, 22~45% 라는 실패율이 10% 라는 2 초 초과 정지율보다 큰 것과 모순되지 않는다고 추정하지만 **이 추정은 검증하지 않았다**. **인과를 직접 증명한 것은 아니다**: A/B 로 "자식 프로세스 도입이 실패를 만든다"(p=0.011)와 "도입이 UI 정지를 만든다"(위 표)를 각각 보였을 뿐, 실패한 바로 그 실행의 UI 정지를 잰 것은 아니다.

## 3. 원인 2 — 남은 앱이 파이프를 쥔다 (`dotnet test` 멈춤)

`LaunchOrSkip` 은 `Application.Launch(info)` 다음 `GetMainWindow` 를 아무 보호 없이 불렀다. 거기서 UIA 타임아웃이 터지면 예외가 `LegacyApp` 생성자에 닿기 전에 밖으로 나간다 → 시험의 `using var app = LegacyApp.LaunchOrSkip(...)` 는 대입이 일어나지 않아 `Dispose` 할 것이 없다 → 앱 프로세스, `UIA3Automation`, R02 의 오류 유도용 파일이 샌다.

샌 앱이 왜 `dotnet test` 를 붙잡는가(`leak_holds_the_pipe.txt`, 같은 방식으로 앱을 띄우고 끝내 닫지 않는 작은 부모 프로그램으로 실험): 앱은 `UseShellExecute=false` 에 아무것도 리다이렉트하지 않아 **부모의 표준 핸들을 상속**한다.
- 부모의 표준 출력이 **파이프**일 때: 부모가 끝난 뒤에도 읽는 쪽이 **20초 넘게 안 끝났다**(앱을 죽이자 즉시 반환).
- 같은 부모의 표준 출력이 **파일**일 때: 0.5초에 반환(앱은 계속 실행 중). 파이프가 없으니 기다릴 것이 없다.

즉 CI 처럼 출력이 파이프인 환경에서 샌 앱은 `dotnet test` 를 끝나지 않게 만든다. 이번 조사 중에도 내 도구 호출이 같은 이유로 여러 번 멈췄다(남은 앱을 죽이면 풀림). 핸들 덤프(`handle.exe`)는 쓰지 않았다 — 위 행위 실험이 같은 사실을 보이고, 실제 어떤 핸들 번호인지는 확인하지 않았다. (실험 파일의 1번 줄 끝 `app running=False` 는 20초 대기 뒤 내가 앱을 죽인 다음에 확인한 값이라 무시해도 된다.)

## 4. 처분

### 고쳤음 (시험 정리 코드, 원인이 명확)
`LegacyPreprocessReadinessScenarios.LegacyApp.LaunchOrSkip`: 앱이 시작된 뒤의 모든 경로를 `try/catch` 로 감싸 실패하면 **앱을 프로세스 트리째 종료하고, 자동화 객체를 닫고, 유도용 파일을 지운 뒤 다시 던진다.** `Dispose()` 의 종료도 트리 종료로 바꿨다(자식 오라클이 살아 있을 수 있어서). 시험 한 건을 더했다: `ALaunchThatFailsAfterTheAppStarted_LeavesNoAppAndNoFaultFileBehind` — 창 제한 시간을 1 ms 로 줘서 시작 후 실패를 **확실히** 만들고, **시스템에서** 새 앱 프로세스와 유도 파일이 없는지 본다(수정이 만든 자신의 장부가 아니라).
- 반증(`fix_arms.txt`): 앱을 죽이지 않게 하면 "a failed launch left 1 app instance(s) running" 으로 빨강, 유도 파일을 안 지우면 파일 개수 단언이 빨강.
- 효과: 수정 뒤 표 3·4 에서 실패 22건에 **남은 앱 0개**(수정 전 7건 모두 1개씩).

### 제안 (앱 쪽 원인 — 적용하지 않음, 리더 결정)
우선순위 순:
1. **시작 때 UI 스레드에서 동기로 돌리지 않는다**(오라클을 비동기·배경으로, 결과가 오면 화면 갱신). UI 정지 자체를 없애는 가장 직접적인 방법이다. 캐시만으로는(D) 중앙값은 438 ms 로 줄지만 1 초 넘는 정지가 5/30, 2 초 넘는 정지가 1/30 남는다 — 자식 한 개의 시작 비용이 변동한다.
2. **3번 → 1번**: 같은 DLL(경로+수정 시각)의 오라클 판정을 프로세스 수명 동안 캐시하거나 중복 새로고침을 없앤다(D 실험: 자식 1개, 합 216 ms). 1 번과 함께 쓰면 비용이 3분의 1.
3. 시험 쪽 임시 완화는 **권하지 않는다**: `ConnectionTimeout` 을 늘리면 실패는 줄지만 UI 가 실제로 1~4 초 막히는 사실을 가린다(앱은 진단용이지만 응답 없는 시작은 결함이다).

## 5. CI 의 `gui-e2e-native` 가 같은 위험에 있는가 — 판단

**그렇다.** (`origin/main` 의 `ci.yml` 읽기, 실행은 아님)
- 잡은 E2E 프로젝트 **전체**를 `dotnet test … --logger "console;verbosity=detailed"` 한 번으로 돌린다(pwsh, 실행 사이에 프로세스를 정리하는 단계 없음). 리더가 병합한 패치로 레거시 앱도 빌드되어 R01·R02 가 이 잡에서 돈다.
- 출력이 러너의 파이프이므로 샌 앱은 이 단계를 `timeout-minutes: 45`(잡 제한)까지 멈추게 한다 — **수정 전**에는. 수정 뒤 레거시 시작 실패는 앱을 남기지 않는다.
- **R01·R02 의 UIA 타임아웃 자체는 CI 에서도 날 가능성이 높다**: 이 기계에서 B 실패율이 22%~45% 였고, 호스팅 러너는 보통 더 느리다고 알려져 있어 자식 프로세스 시작과 UI 정지가 길어질 것으로 예상한다(CI 에서 재 보지는 않았다). 앱 쪽 제안 1·2 가 없으면 그 시험은 간헐적으로 빨강일 것이다.
- **gui 앱용 `ApplicationFixture` 도 같은 모양의 노출이 있다**: 생성자가 `Application.Launch` 뒤 `GetMainWindow` 등을 보호 없이 부르고, 생성자가 던지면 `Dispose` 가 불리지 않는다. 다음 픽스처의 시작 전 정리(`KillLeftovers`)가 그 앱을 죽이므로 **마지막** 픽스처가 실패할 때만 샌다. 이번에 그런 실패를 관측하지는 못했고, 고치지 않았다.
- 잡 쪽 안전망 제안: `dotnet test` 단계 뒤에 `if: always()` 로 `Get-Process ImageProcTest -ErrorAction SilentlyContinue | Stop-Process -Force` 를 둔다(남은 앱이 있으면 단계가 끝난 뒤 정리, 파이프 대기 자체는 못 막으므로 `--blame-hang-timeout` 병행).

## 한계

- B 실패율(22%~45%)은 기계 상태에 따라 움직인다. 표본은 표 1+2: B 7/32, 표 4: 9/20 이다.
- D(캐시)는 **한 번 만든 실험 사본**의 측정이다. 비동기 방안은 구현해 보지 않았다(효과는 "UI 스레드에서 안 도는 것은 정지를 만들 수 없다"는 구조에 기댄 추정이다).
- 핸들 덤프는 하지 않았고, 파이프 점유는 행위 실험으로 보였다.
- 실행별 로그(`runs*/`)는 디스크에만 있고 커밋하지 않았다(표가 요약이다).
