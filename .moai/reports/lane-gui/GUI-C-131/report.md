# GUI-C-131 — GSDF 광도 배열을 **끝점 둘**로 줄인다 (#155)

> **소급 기록이다.** 변경과 커밋(`bff8001`, main `a05e343`)은 2026-09-19 에 끝났고
> 보고서가 없었다. 수치는 세션 트랜스크립트에서 **원문을 복원**했고, 원천에 없는 것은
> 적지 않았다 — 역산·추정은 넣지 않았다.

## 1. 무엇을 바꿨나 — 한 줄

`gui/ImageProcTest/Services/RealXpeBackend.cs`:

```csharp
var luminanceValues = new[] { 0.05f, 400.0f };
```

이전에는 로그 격자 `(0.05, 1, 10, 100, 400)` 다섯 값이었다.

## 2. 왜 — 배열의 뜻이 바뀌었다

`REQ-DISP-029` 가 이 배열에 **원래 없던 뜻**을 줬다: 원소 `i` 는 구동 준위
`DDL_i = i/(count-1) × 65535` 에서 **측정한** 광도이고, 따라서 **값의 간격 자체가
디스플레이 특성곡선**이다.

- **옛 계약**(헤더가 최소·최대만 읽는다고 적혀 있던 때) 아래에서 로그 격자는 **옳았다.**
- **새 계약** 아래에서 같은 배열은 **지어낸 곡선**이다 — 1·10·100 cd/m² 는 각각 구동
  준위 25%·50%·75% 에서 측정된 값이라고 주장하는 셈인데, **측정한 패널이 없다.**

**끝점 둘이 정직한 입력이다.** `count == 2` 는 "구동 준위 0 과 전체 스케일의 광도,
그 사이는 선형" 이라는 가정을 **명시**하고, 그것은 옛 호출이 이미 암묵적으로 깔고
있던 가정과 **같다.** 중간값을 지어내는 대신 가정을 드러냈다.

측정한 곡선을 넣는 것은 패널 측정이 필요하고, 그것은 `#151` 로 **보류**다.

## 3. 시험 — `GsdfCalibrationInputTests.cs` 세 건

| # | 단언 | 성격 |
|---|---|---|
| 1 | 호출이 끝점 둘을 넘기고 `0` 을 돌려주며 `gsdfEnabled == 1` | 호출이 성립한다 |
| 2 | **최대를 바꾸면 LUT 이 바뀐다** (400 → 200) | **값이 곡선에 닿는가** |
| 3 | 소스 가드 — 호출부가 정확히 그 둘이고 중간값을 지어내지 않았다 | 런타임으로는 못 보는 축 |

**두 번째가 이 카드의 핵심이다.** 1·3 은 배열이 *있다*는 것까지만 본다. 값이
**실제로 LUT 에 도달하는지**는 바꿔서 결과가 달라지는 것으로만 알 수 있다.

**세 번째가 필요한 이유**: 1·2 는 다섯 값을 넘기는 호출에서도 똑같이 통과한다 —
`count` 가 시험 대상이고, 그것을 말해 주는 것은 호출부뿐이다.

## 4. 측정한 것 — 그리고 **2/1024 라는 수치**

당시 스테이징된 `xpe_display.dll` 기준:

```
LUT entries differing between max=400 and max=200: 2 of 1024
   at index 512: 32800 vs 32800
```

**단언은 통과했지만(`differences > 0`) 차이가 1024 중 2개뿐이고, 중앙(index 512)은
완전히 같다.** 이것은 **옛 min/max-only 계약과 일치하는 모습**이다.

그 DLL 은 `2026-09-19 16:46` 빌드였고, `#155` 2단계 커밋보다 앞선다.

### 정정 — 당시 쓴 문자열 프로브는 **판별할 수 없는 프로브였다**

당시 이렇게 적었다: "`REQ-DISP-029` 문자열 없음 = `#155` 2단계 이전, 대조군 `gsdf`
FOUND". **이 추론은 성립하지 않는다.**

```
grep -rn "REQ-DISP-029" modules/display/src/ modules/display/include/
  → presentation_lut.cpp:84, :91  (주석)
  → display_api.h:324, :327       (주석)
```

**`REQ-DISP-029` 는 소스에서 주석에만 있다** — 어떤 빌드에도 문자열 리터럴로 들어가지
않는다. 따라서 그 프로브는 2단계 전이든 후든 **항상 0** 이고, 전후를 가릴 수 없다.
대조군 `gsdf` 가 잡힌 것은 "grep 이 파일을 읽는다" 만 증명했다 — **대상이 애초에
들어갈 수 없는 문자열이면 대조군은 프로브를 구해 주지 못한다.**

신선한 빌드에서 확인했다: `REQ-DISP-029 → 0` (여전히 없다), `gsdf → 1`.

**결론은 살아남았지만 근거가 하나 빠진다.** 당시 유효했던 근거는 **날짜**뿐이다
(DLL 16:46 < 2단계 커밋). 이름·주석은 코드가 아니다.

### 직접 측정으로 확인 (2026-09-26, 신선한 산출물)

`build/ci-fresh` (CI run `35435692495`, head `7d32053`) 를 스테이징하고 같은 시험을
다시 돌렸다:

```
LUT entries differing between max=400 and max=200: 1021 of 1024
   at index 512: 5356 vs 6759
gui passes [0.05, 400] (count 2)
xpe_gsdf_calibrate -> 0, gsdfEnabled=1
```

**2 → 1021 / 1024, 그리고 중앙이 32800 동일에서 5356 vs 6759 로 갈렸다.**
`#155` 2단계가 들어오면서 **곡선이 실제로 LUT 에 닿는다.** 당시의 "2/1024 는
스테이징 상태의 보고" 라는 진단이 그대로 확인됐다 — 시험은 고치지 않고 그대로
두었고, 스테이징이 갱신되자 같은 시험이 신호가 됐다.

## 6. 미검증 (Gaps)

- **측정한 패널 곡선으로는 재지 않았다.** 끝점 둘은 선형 디스플레이 가정이고, 그
  가정이 실제 패널에서 맞는지는 이 카드에서 확인할 수단이 없다(`#151` 보류).
- ~~`#155` 2단계 이후의 수치를 모른다~~ → **2026-09-26 에 쟀다: 1021/1024** (§4).
- **중간 구동 준위에서의 정확도를 주장하지 않는다.** 끝점 둘은 사이를 선형으로
  두는 것이고, 실제 패널이 선형이 아니면 중간이 틀린다. 그 오차 크기는 재지 않았다.
- Native E2E 는 `Gsdf·W13` 만 돌렸다. 전체 E2E 는 이 카드에서 돌리지 않았다.

## 7. 잔여 위험

- 단언이 `> 0` 인 것은 여전히 느슨하다 — 1021/1024 도, 2/1024 도 통과한다. **지금
  조이면 옛 DLL 에서 빨개져 무엇이 틀렸는지 구별되지 않으므로** 이 카드에서는 고치지
  않았고, 조이는 것은 후속 카드다.
- 문자열 프로브를 신선도 판별에 쓴 것이 이 보고의 실수였다. **주석에만 있는 식별자는
  바이너리 프로브의 대상이 될 수 없고, 대조군은 그 결함을 잡아 주지 못한다.**
- 이 보고서는 소급 기록이다. 명령의 verbatim 출력은 트랜스크립트에서 복원한 것이고,
  당시의 증거 파일이 따로 남아 있지는 않다.
