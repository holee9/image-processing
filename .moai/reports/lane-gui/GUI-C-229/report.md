# GUI-C-229 — R02 실제 키 입력이 글자를 잃음 (CI gui-e2e-native, main 714f3477)

## 결론 먼저

**원인은 가르지 못했다.** CI 로그에는 키마다의 값이나 전경 창 기록이 없고, 이 데스크톱에서 실제 키 입력으로 반복하는 것은 위험해서 하지 않았다(아래). 대신 (1) 지금까지 확인된 사실을 적고, (2) 다음 실패 때 (a)(b)(c) 를 가를 기록을 시험에 넣었다. 단언은 그대로 엄격하다.

## 확인된 사실

| 사실 | 근거 |
|------|------|
| 직전 main 실행에서 R02 는 통과했고, 실패한 실행의 코드는 앱·E2E·모듈·워크플로 변경이 없다 | `git diff --stat fbb6edc0 714f3477 -- gui clients/ImageProcTest clients/ImageProcTest.E2ETests .github modules CMakeLists.txt CMakePresets.json` 가 빈 출력. 같은 범위의 통합 시험 프로젝트 쪽은 6개 파일이 나와(대조군) 명령이 변경을 볼 수 있음을 보인다. 이 범위의 경로 분류: `.moai/reports` 72 + `clients/ImageProcTest.IntegrationTests` 6 |
| R02 는 최근 14개 실행 중 13번 통과, 1번 실패 | `ci_history_real_input.txt` (실행 37087424320 ~ 37157733109, 한 실행은 잡이 건너뜀) |
| 통과한 R02 는 모두 `box='4321'` + 낡음 표시를 남겼다 | 같은 파일 |
| R02 의 시간은 이번 실패도 평소 범위다 | 통과 4.9~10.1 s, 실패 6.4 s. 같은 실행의 R01 은 2.9 s(통과한 실행들의 범위 1.4~2.9 s 안) — 기계가 유난히 느렸다는 신호는 없다 |
| 실행 순서가 매번 같다 | R02 바로 앞은 모든 실행에서 `L02_ACandidateSetting_MovesOnlyTheCandidate`, 바로 뒤는 `R01` |
| 실패 메시지는 상자 값 한 가지뿐이다 | `Expected "4321"`, `Actual "43"` (RealInputScenarios 154행). 키마다의 값, 전경 창, 재읽기는 기록돼 있지 않다 |

즉 같은 코드·같은 순서·평소 시간에서 약 14분의 1 로 일어난 간헐 실패이고, 코드 변경은 원인이 아니다. 간헐이라는 것은 관찰이고, 왜 그런지는 아직 모른다.

## 왜 로컬에서 N회 반복하지 않았나

이 시험은 실제 키 입력(전역 입력)을 쓰고 `XPE_E2E_ALLOW_GLOBAL_INPUT=1` 일 때만 돈다. 시험 파일 머리말과 GUI-C-171 이 이유를 적고 있다: 키는 앱이 아니라 **전경 창**으로 가고, 공유 데스크톱에서 ESC 가 다른 세션의 터미널로 가 세션을 중단시킨 적이 있다. 이번 작업 중에 그 위험이 눈앞에서 확인됐다. 입력 없이 만든 메시지의 전경 창 항목이 이 데스크톱의 전경으로 **Windows 보안 팝업(PickerHost 프로세스, 제목 "Windows 보안")** 을 보고했다(`r02d_message_from_real_window.txt`). 그 상태에서 실제 키를 보냈다면 숫자와 Tab 이 그 팝업으로 갔을 것이다. 그래서 시험은 이 환경에서 돌리지 않았다(게이트 그대로, 건너뜀 확인). 이 팝업이 무엇인지(자격 증명·패스키 요청 등)는 내가 열어 보지 않았다. 사용자가 확인할 일일 수 있다.

반증이 아니라 관찰이다: 이 팝업은 "Windows 에서 앱 말고 다른 창이 전경을 가져가는 일이 실제로 있다"는 예일 뿐 CI 실패의 원인이라는 증거가 아니다.

## 시험에 넣은 것 (단언은 그대로 엄격)

변경: `RealInputScenarios.cs`, `Fixtures/KeyLossDiagnosis.cs`(새), `Scenarios/Workflows/KeyLossDiagnosisTests.cs`(새). 앱 코드는 안 고쳤다.

1. **키마다 전경 확인**: `GlobalInput.Type(typed)` 한 번 대신 `TypeKeyByKey` 가 글자마다 보내기 직전에 앱이 전경인지 확인하고 기록(경과 ms 포함)한다. 앱이 전경이 아니면 그 키와 이후 키는 **보내지 않는다**(다른 창으로 가지 않는다). 키 사이에 앱 UI 를 읽지 않으므로 타이밍은 한 번에 치는 것과 같다.
2. **같은 엄격한 단언**: 글자 4개 전부, 마지막 키 600 ms 뒤. 어긋나면 `Assert.Fail` 인데, 메시지에 다음이 들어간다: 600 ms 뒤 값과 **1.5초 뒤 재읽기** 값, **Width 상자**(탭 순서의 다음 상자) 값, 지금 키보드 포커스, 전경 창 설명, 키마다 기록, 그리고 어느 설명이 맞는지(`KeyLossDiagnosis.Classify`).
3. **가르는 법**:
   - (a) 전경 이탈 → 기록에 "app in front: NO, NOT sent", 또는 빠진 글자가 Width 상자에 있음, 또는 값이 그대로이고 포커스가 상자 밖
   - (c) 너무 일찍 읽음 → 1.5초 뒤에 상자가 "4321"
   - (b) 앱이 덮어씀 → 값이 그대로이고 포커스는 상자 안(키는 상자가 포커스를 가졌을 때 보냈음)
   - 어디에도 안 맞으면 "맞는 설명이 없음"이라고 말한다.
4. 통과한 실행에도 `R02 key trace:` 한 줄이 남아 정상 실행의 키 간격이 쌓인다.
5. 이 읽기 도우미는 판정하지 않는다. 시험은 읽기 결과와 무관하게 실패한다.

## 확인 (입력 없이 가능한 것)

| 항목 | 결과 |
|------|------|
| `KeyLossDiagnosisTests` 8건(분류 6가지·추적 형식) | 통과 8/8 (E2E 프로젝트, 앱 없이) |
| `R02d_TheLostKeysMessage_IsBuiltFromTheRealWindow_WithoutSendingAKey` — 실제 창에서 메시지를 만듦, 키는 보내지 않음 | 통과 (UIA 만 사용). 메시지에 600 ms·1.5 s 값, Width 상자 값, 포커스, 전경 창, 키 추적, "Reading: (a) …" 가 모두 들어 있음 |
| `R02` 자체 | 이 환경에서는 게이트로 건너뜀(건너뜀 확인). 새 R02 경로(`TypeKeyByKey`, `DescribeLostKeys` 의 실패 경로)는 **컴파일만** 되고 실제 키 입력으로는 실행해 보지 않았다 |

## 미검증 / 잔여 위험

- 실패 원인(a)(b)(c) 는 모름. 재현율도 못 쟀다(전역 입력을 돌리지 않음).
- 새 R02 경로가 CI 에서 실제로 도는 것은 다음 CI 실행에서 처음 관찰된다. 키마다 `GetForegroundWindow` 호출이 추가되는 것 말고는 입력 순서·간격이 같다고 읽었으나 CI 에서 측정하지는 않았다.
- 키마다 전경 확인은 "확인과 전송 사이"의 틈을 없애지 못한다. 틈은 마이크로초 단위로 좁아졌을 뿐이다.
- 이 환경의 Windows 보안 팝업은 R02d 가 우연히 드러낸 것이고 내가 만든 것이 아니다.
- 리더가 알려 준 `061f5a66` 의 CI 결과는 보지 않았다(그 실행에는 `gui-e2e-native` 잡이 아직 없었다). 그 결과를 받으면 `R02 key trace:` 줄이 새 코드로 나오지 않으므로(그 실행에는 이 변경이 없다) 새 기록은 이 커밋 이후의 실행부터 생긴다.
