## 1. 주장

1. **SelfCheck 를 한도 아래로 되돌렸다.** 17.5–17.7 초 → **1.8–2.4 초(12회, 평균 1.9 초)**. 앱의 대기는 15 초(250 ms × 60)이고 올리지 않았다. 목표는 "한도의 절반(7.5 초) 이하"였고, 실측 최대 2.4 초는 한도의 약 1/6 이다.
2. **어떻게**: (a) 시나리오를 3072² 픽스처가 아니라 **256² 생성 이미지**로 돌린다(시나리오는 순서를 단언하지 픽셀을 단언하지 않는다; 3072² 는 시나리오마다 로드·렌더만 약 1 초), (b) 고정 `Task.Delay`(9곳)를 전부 **사건 대기**로 바꿨다(체인 호출 수·로그 줄·화면 이미지 참조의 변화) + UI 큐 비우기(`Dispatcher.Yield(ApplicationIdle)`)로 "이미 올라온 연속 동작이 끝났는지" 를 기다린다. 남은 `Task.Delay` 는 폴링 간격 20 ms 하나다.
3. **시험이 증명하던 것은 약해지지 않았다**: 반증 5팔이 이전과 **같은 시나리오 집합**을 빨갛게 한다(§2-3).
4. **건너뜀 문구를 원인별로 나눴다**: 실행 파일 없음 / 시작했으나 한도 안에 안 끝남 / 시작 못 함 / 원인 불명, 그리고 실행했고 실패(별도 단언 문구). 시험이 갈래별 문구와, 분류의 열쇠인 문구가 앱의 실제 상태줄과 같은지를 고정한다.
5. **시나리오 3 의 간헐 실패(dev/gui CI, `[3 stale failing Lane B] a stale lane failure erased or replaced the new lanes`)의 원인을 찾아 고쳤다**: 300 ms 고정 대기로 "새 백엔드의 레인이 그려졌다"를 가정했다. 느린 환경에서는 그 전에 스냅샷을 떠서, 나중에 그려진 새 레인이 "옛 실패가 레인을 덮었다"로 읽혔다. 이제 새 Lane B 가 그려진 사건(화면의 Lane B 이미지 객체가 첫 렌더의 것과 달라짐)을 기다린다.
6. f1028a83 보고서 4-2 의 "원인 미확인"을 **정정 표시**로 고쳤다(`.moai/reports/lane-gui/GUI-C-190/report.md`).

## 4. 미검증

1. **건너뜀 분류를 앱의 실제 상태줄 전부로 검증하지는 않았다.** 분류의 열쇠 문구 4개(`runner is not built`, `needs the repository`, `Running …`, `did not run:`)는 앱 소스에 있는 것을 시험이 대조한다(소스 읽기). 실제 앱을 각 상태로 만들어 문구를 읽지는 않았다.
2. **건너뜀의 성격은 문구만 바꿨다.** "한도 안에 안 끝남"도 여전히 **건너뜀**이다(요청이 문구였다). 느려진 러너가 다시 건너뜀으로 숨는 것은 막지 못한다 — 다만 문구가 "NOT A MISSING EXECUTABLE - DID NOT FINISH IN TIME" 으로 시작해 오인하지 않는다. 실패로 올릴지는 리더 결정 사항이다.
3. 작은 이미지(256²)로 시나리오를 돌리는 것이 3072² 에서만 나타나는 타이밍 결함을 놓치는지는 보지 않았다. 시나리오가 단언하는 것은 순서·화면 객체 참조이고 반증은 같은 집합을 잡았다.
4. 부하 재현은 이 기계의 CPU 경합이다. CI 러너에서 같은 확률로 걸렸다는 뜻은 아니다. "연속 10회 이상 0 실패" 기준은 12회(무부하) + 24병렬 72회로 충족했다.
5. Native E2E 는 로컬에서 못 돌린다(#98).

### 4-3. 폐기한 첫 부하 측정

처음 8 병렬 × 3회를 **하나의 출력 디렉터리를 공유**한 채 돌렸다. 새 코드도 24회 중 4–5회 실패했는데 전부 `appsettings.selfcheck.json` 을 두 프로세스가 동시에 쓰다 난 `IOException` 이었다(러너의 앞부분이 그 파일을 옆에 쓴다) — 시나리오 실패가 아니라 측정 장치의 충돌이라 그 숫자는 버리고, 프로세스마다 출력 디렉터리를 따로 둔 위 표로 다시 쟀다.
