## 2. 증거

### C1 — 기본값 정렬

`git show origin/main:modules/gsvg/src/virtual_grid.h` →
`pyramidLevels = 4` / `pyramidGain = 1.3` / `denoiseK = 2.0`. GUI 도 같은 값으로 맞췄습니다.

잡음 k 는 설정이 없던 값이라 새로 노출했습니다(`GsvgDenoiseK`, 범위 0–10, 기본 2.0, 화면 `GsvgDenoiseKInput`). 세 키는 **함께 보내거나 함께 생략**합니다 — 모듈이 단수 0 인데 이득이 1.0 이 아니거나 k 가 0 이 아니면 설정을 거부하기 때문입니다(`virtual_grid.cpp:691`).

`#182` 바인딩 개수 35 → 36.

### C2 — 이득 1.3 의 효과 (P-09)

```
P09 levels=0          : hash=36fc547e253b07f1 mean=85.205 stage=28 ms
P09 levels=4 gain=1.0 : hash=36fc547e253b07f1 mean=85.205 stage=48 ms
P09 levels=4 gain=1.3 : hash=a1bc70c62a9e60fa mean=82.796 stage=49 ms
```

| | 이득 1.0 | 이득 1.3 | 변화 |
|---|---|---|---|
| 그려진 픽셀 해시 | `36fc547e253b07f1` | `a1bc70c62a9e60fa` | 다름 |
| 평균 밝기(65535 척도) | 85.205 | 82.796 | **−2.409** |

비교용으로, C-102 에서 잰 다른 기본값들의 영향은 Δ0.279(선밀도)·Δ0.534(공기 신호)였습니다. **이득 1.3 의 영향은 그보다 4~9 배 큽니다.** 기본값 변경이 화면에 보이는 수준의 변화라는 뜻이므로, 기존 사용자가 보던 그림이 달라집니다.

P-09·P-10 은 이제 의존하는 피라미드 값을 **매 단계 명시**합니다. 기본값이 또 바뀌어도 비교 대상이 소리 없이 달라지지 않습니다.

### C3 — 게이트 기준 재측정

잡음 단계가 더해져 작업량이 늘었습니다. 3회 × 7적용 = 21 표본:

```
median=62.0 p95=69.0 max=70.0 ms [57, 59, 61, 62, 67, 69, 70]
median=62.0 p95=65.0 max=76.0 ms [58, 60, 62, 62, 63, 65, 76]
median=62.0 p95=63.0 max=65.0 ms [53, 59, 61, 62, 63, 63, 65]
```

중앙값 62 ms(3회 동일), 최악 76 → 퍼짐 1.23배 → 문턱 = 62 × 1.23 × 1.36 = 104 → **105 ms**. 유도 방식(1.36)은 C-104 과 같게 두어 세 값이 비교 가능합니다.

상수 주석에 **세 번의 이동을 모두** 남겼습니다: 27 ms(피라미드 키 미전송) → 50 ms(단수 4) → 62 ms(이득·잡음까지 모듈과 정렬). 매번 작업량이 바뀌어 기준을 다시 잰 것이고, 빨간 실행을 통과시키려 문턱을 넓힌 적은 없습니다. **이력이 안 보이는 게이트는 조용히 완화된 게이트와 구별되지 않습니다.**

### C4 — 게이트는 CI 에서 돕니다 (제 지적의 정정)

C-104 에서 "이 게이트는 Native 전용이라 CI(Mock)에서 안 돈다" 고 적었습니다. **절반만 맞았습니다.** `ci.yml` 의 `gui-e2e-native` 잡을 읽으니:

```yaml
      - name: Run FlaUI E2E smoke (Native)
        env:
          XPE_E2E_BACKEND: Native
          XPE_NATIVE_DIR: ${{ github.workspace }}/build/e2e-native-dlls
          XPE_NATIVE_DIR_EXCLUSIVE: "1"
        run: >
          dotnet test clients/ImageProcTest.E2ETests/ImageProcTest.E2ETests.csproj
          -c Debug
          --logger "trx;..."
```

**`--filter` 가 없습니다** — 프로젝트 전체를 Native 로 돌립니다. 따라서 P-08 은 이미 그 잡에서 실행됩니다. 제가 "Mock 이라서 안 돈다" 고 쓴 것은 `gui-automation`(Mock) 잡만 보고 `gui-e2e-native` 잡을 확인하지 않은 탓입니다.

### C5 — 문턱이 CI 기계에서 설지 (예상: 서지 않는다)

| | 개발 PC | CI 러너 |
|---|---|---|
| CPU | i7-12700 | Xeon 6973P-C |
| 논리 코어 | (다수) | **4** |
| 메모리 대역 | 25.5 GB/s | **19.4 GB/s** |

출처: pre 레인 QA-A-115 의 `[perf-gate-machine]` 관측.

GSVG 가상 그리드는 스레드 자동(`threads=0`)이고, post 레인이 QA-B-105 에서 스레드 수별로 재어 **메모리 대역에 묶인다**고 기록했습니다(스레드 8 이후 이득 없음). 코어가 4 개뿐이고 대역이 0.76 배인 기계에서는 단계 시간이 상당히 늘 것으로 봅니다. **105 ms 문턱이 설 가능성은 낮습니다.**

**측정됐습니다 — 예상이 맞았습니다.** CI 실행 `35294573612`(head `3f520f8`, C-104 코드 상태)의 `gui-e2e-native` 로그:

```
P08 gsvg stage over 7 runs: median=84.0 p95=88.0 max=92.0 ms [82, 83, 84, 84, 85, 88, 92]
The GSVG stage's median rose to 84 ms against a 80 ms gate (baseline 50 ms, measured spread 1.10x).
```

같은 코드에서 **개발 기기 50 ms · CI 84 ms → 1.68 배**입니다. 퍼짐 자체는 CI 가 오히려 좁습니다(1.10 vs 1.22) — 러너가 조용한 기계라는 뜻이고, 느린 것은 변동이 아니라 **수준**입니다.

C-105 기본값(잡음 단계 추가)에서는 개발 기기가 65 ms 이므로 CI 는 65 × 1.68 ≈ 109 ms 로 예상됩니다. **현재 문턱 105 ms 는 CI 에서 서지 못할 가능성이 높습니다** — 이것은 다시 추정입니다. 다음 CI 실행이 실측값을 줍니다.

### C6 — CI 가 드러낸 결함: "끔" 이 모듈 기본값으로 켜지고 있었다

같은 CI 실행에서 P-09·P-10 이 해시 불일치로 실패했습니다. CI 로그:

```
P09 levels=0          : hash=0fe341c9b0ebebe1 mean=83.290 stage=83 ms
P09 levels=4 gain=1.0 : hash=5895cf2c7dd11845 mean=78.106 stage=91 ms
P09 levels=4 gain=1.3 : hash=0fe341c9b0ebebe1 mean=83.290 stage=87 ms
```

`levels=0` 과 `gain=1.3` 이 **완전히 같고** `gain=1.0` 만 다릅니다 — 제 로컬 측정과 정반대입니다. 기계 차이로 보였지만, **추측하지 않고 바이너리를 맞췄습니다**: 이번 CI 산출물로 스테이징을 갈아 끼우고(아래 C7) 로컬에서 같은 시험을 돌리자 CI 결과가 **그대로 재현**됐습니다.

```
(새 DLL, 수정 전)  levels=0 : hash=0fe341c9b0ebebe1 mean=83.290
                   gain=1.0 : hash=36fc547e253b07f1 mean=85.205   ← 옛 DLL 의 levels=0 출력
                   gain=1.3 : hash=a1bc70c62a9e60fa mean=82.796
```

원인이 드러났습니다. **GUI 는 "끔" 을 키 생략으로 표현하고 있었는데, 생략은 끔이 아니라 모듈 기본값입니다.** 모듈 기본값이 0 에서 4/1.3/2 로 바뀌자 GUI 의 "끔" 이 조용히 "모듈 기본 설정으로 켜짐" 이 됐습니다. 그래서 새 DLL 에서 `levels=0` 의 출력이 `gain=1.3` 과 같았던 것입니다 — 둘 다 같은 설정으로 돌았으니까요.

고친 방식: **세 키를 항상 함께 보냅니다.** 끔은 단수 0 에 모듈이 그 경우에 요구하는 값(이득 1.0, k 0)을 같이 보내는 것으로 표현합니다. 모듈은 `levels==0` 인데 이득이 1.0 이 아니거나 k 가 0 이 아니면 설정을 거부하므로(`virtual_grid.cpp:691`), 생략도 0 단독 전송도 답이 아닙니다.

수정 후(같은 새 DLL):

```
P09 levels=0          : hash=36fc547e253b07f1 mean=85.205 stage=53 ms
P09 levels=4 gain=1.0 : hash=36fc547e253b07f1 mean=85.205 stage=69 ms
P09 levels=4 gain=1.3 : hash=a1bc70c62a9e60fa mean=82.796 stage=58 ms
```

끔과 이득 1.0 이 같고(피라미드가 항등), 이득 1.3 만 다릅니다 — 의미가 맞습니다.

**이 결함은 로컬에서는 드러날 수 없었습니다.** 로컬 DLL 의 모듈 기본값이 0 이라 "생략 = 끔" 이 우연히 성립했기 때문입니다. CI 가 새 모듈로 돌면서 전제가 깨진 것을 보여 줬습니다.

### C7 — 스테이징 재생성과 `-17`

CI 실행 `35294573612` 의 `xpe-ci-{common,preprocess,post}-binaries` 를 내려받아 `build/ci-3f520f8/bin` 에 놓고 제품 표를 옆에 복사했습니다. `gsvg.dll` 이 실제로 바뀌었습니다:

```
7c993cfbf5d41773831a71ad8c1905ea  build/ci-3f520f8/bin/gsvg.dll   (새)
6202b44cb7dacf1431db0ac89a7f4555  build/ci-c72f0e8/bin/gsvg.dll   (옛)
```

같은 산출물을 통합시험 경로(`build/ci-common/bin`)에도 복사하고 전체를 돌렸습니다:

```
IntegrationTests : 총 241, 통과 240, 건너뜀 1, 실패 0
```

**C-103 부터 남아 있던 `xpe_error_string(-17)` 실패가 사라졌습니다.** 원인이 코드가 아니라 낡은 바이너리였다는 판단이 이번에 확인됐습니다 — 그때는 "확인하지 못했다" 고 적었던 항목입니다.

주의: 통합시험을 돌릴 때 `XPE_NATIVE_DIR` 을 쓰면 안 됩니다. `NativeSearchPolicyTests` 3건이 "기본 탐색은 빌드 디렉터리를 제시하지 않는다" 를 단언하는데, 환경 변수가 바로 그 전제를 바꿔 실패합니다(측정: 실패 4건 중 3건). DLL 을 경로에 놓는 방식이어야 합니다.

### 구조 제안 (결정은 리더)

문턱을 기계별로 나눠야 한다면, pre 레인이 QA-A-115 에서 배운 것과 같은 함정을 피해야 합니다 — **기준이 측정 대상과 같은 병목에 묶여 있지 않으면 비율이 기계를 상쇄하지 못합니다.**

세 가지를 제안만 합니다.

1. **같은 병목의 기준값으로 비율 게이트.** 같은 실행 안에서 GSVG 단계와 함께, 같은 프레임을 한 번 훑는 메모리 묶인 작업(예: 디스플레이 파이프라인의 입력 마샬링)을 재고 비율로 판정. 장점은 기계를 상쇄한다는 것, 위험은 두 작업의 병렬성이 달라 비율이 코어 수에 반응할 수 있다는 것입니다.
2. **기계별 문턱을 명시적으로 둘로.** 개발 기기용·CI 러너용 두 상수를 두고 환경 변수로 고름. 단순하지만 러너가 바뀌면 다시 재야 합니다.
3. **CI 에서는 게이트를 끄고 값만 기록.** 회귀 감시는 개발 기기에서만, CI 는 추세 기록만. 가장 안전하지만 CI 에서 회귀를 못 잡습니다.

어느 쪽이든 **CI 에서 실제 값을 먼저 재고** 정해야 합니다. 이전에 810 ms 문턱이 CI 에서 1.91 배로 나온 사례가 있습니다.

## 3. 기준 귀속

- C1~C3 의 초기 수치는 `build/ci-c72f0e8/bin` (CI run 35275125717) 로, C5~C7 과 최종 기준(65 ms)은 `build/ci-3f520f8/bin` (CI run 35294573612) 로 측정했습니다. 두 DLL 은 실제로 다릅니다(md5 대조 §C7).
- CI 수치(84 ms, P-09 해시)는 제가 실행한 것이 아니라 CI 로그에서 읽은 것입니다.
- 기계 제원(19.4 / 25.5 GB/s)은 pre 레인 QA-A-115 의 CI 관측을 인용한 것이며, 제가 재지 않았습니다.
- 모듈 기본값은 `origin/main` 의 `virtual_grid.h` 에서 직접 읽었습니다.

## 4. 미검증

- **C-105 코드에서 CI 의 P-08 값** — 1.68 배로 환산해 109 ms 를 예상했을 뿐, 재지 않았습니다. 다음 CI 실행이 실측값을 줍니다.
- **가상 그리드 E2E 가 CI 의 표 스테이징으로 통과하는지** — 이번 실행은 P-08/P-09/P-10 이 실패해 끝났고, "표를 못 찾아 실패" 는 더 이상 보이지 않았지만 전체가 초록인 실행을 보지는 못했습니다.
- **끔 결함이 언제부터 있었는지** — 모듈 기본값이 바뀐 시점부터로 보지만, 그 사이 배포본에서 실제로 어떤 영향이 있었는지는 조사하지 않았습니다.
- 이득 1.3 이 진단상 옳은지 — 연결과 크기만 쟀고 화질 판단은 하지 않았습니다.
- CI 러너에서 GSVG 단계가 얼마나 느려지는지의 **배수** — 제원에서 추정만 했습니다.

## 5. 잔여 위험

- 기본 출력이 바뀌었습니다(Δ밝기 2.409). 이전 화면과 다른 그림이 나오는 것은 의도된 변경이지만, 그 사실이 사용자에게 알려지는 경로는 없습니다.
- **`gsvg.dll` 은 CI 의 두 검사 어디에도 걸리지 않습니다.** 이름이 `xpe_` 로 시작하지 않기 때문입니다:
  - 스테이징 존재 검증은 `xpe_common`·`xpe_preprocess`·`xpe_display` 세 개만 확인합니다 — `gsvg.dll` 이 빠져도 통과합니다(가상 그리드 시험이 실패로 드러나긴 하지만 원인이 스테이징임을 바로 알기 어렵습니다).
  - 앱 폴더 누수 검사는 `-Filter xpe_*.dll` 입니다 — 앱 폴더에 `gsvg.dll` 이 있어도 잡지 못하므로, 그 경우 로케이터가 아니라 OS 로더로 통과한 것을 초록으로 읽게 됩니다. 이 잡의 전제("여기서 통과하면 로케이터 경로가 증명된다")가 GSVG 에 대해서는 성립하지 않습니다.
  - 확인: 제 로컬 앱 폴더에는 `gsvg.dll` 도 `xpe_*.dll` 도 없습니다(`ls gui/ImageProcTest/bin/Debug/net8.0-windows` → 해당 없음). 즉 제 Native 측정은 로케이터 경로로 돈 것이 맞습니다.
  - 두 검사 모두에 `gsvg.dll` 추가를 제안합니다. `ci.yml` 은 lead 소유라 바꾸지 않았습니다.
