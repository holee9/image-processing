# GUI-C-130 — #163 의 원인을 **바꿔서 사라지고 되돌려서 돌아오는 것**으로 확인했다

## 1. 결과 — 원인 확정

`View → Compare Mode` 하위 메뉴를 **클릭으로 여는 것**이 `#163` 실패의 원인이다.
클릭은 하위 메뉴 헤더를 **토글**하므로, 마우스가 올라간 것만으로 이미 열린 경우
클릭이 **열지 않고 닫는다**.

| 팔 | 코드 | 결과 (20회) |
|---|---|---|
| A — 기준선 | `ExpandCollapse.Expand()` (GUI-C-108 에서 넣은 실험 경로) | 통과 20 / **실패 0** |
| B — 한 축만 바꿈 | `compare!.AsMenuItem().Click()` | 통과 15 / **실패 5 (25%)** |
| A2 — 되돌림 | A 와 동일 파일로 복원 | 통과 20 / **실패 0** |

**양방향이다.** 바꿔서 실패가 나왔고(0 → 5), 되돌려서 사라졌다(5 → 0). 한 방향만이면
"운이 좋았다" 와 구별되지 않는다는 지적이 이 설계를 만들었다.

원자료: `measured.txt` (명령·팔별 집계·실패한 회차 번호).

## 2. (a) 표본 수와 근거

**n = 20, 세 팔 모두 동일.** 팔 A 를 먼저 20회 돌린 뒤 팔 B 로 바꿨으므로 수는
측정 전에 고정됐다.

근거 — 이 이슈에서 관측된 실패율에서 나온다. 팔 B 의 실측 실패율은 25%(5/20)이다.
실패율 p 에서 n회 전부 통과할 확률은 `(1-p)^n` 이므로:

| n | p = 0.25 일 때 우연히 무실패 | p = 0.67(옛 4/6) 일 때 |
|---|---|---|
| 6 | 18 % — **무시 못 한다** | 0.14 % |
| 20 | **0.32 %** | 사실상 0 |

**6회로는 부족하다는 판정이 맞았다.** p=0.25 에서 6회 무실패는 다섯 번에 한 번쯤
그냥 일어난다 — 이 이슈에서 표본 때문에 두 번 틀린 것이 정확히 이 구간이었다.
n=20 이면 팔 A·A2 의 "실패 0" 이 우연일 확률이 0.32% 로 내려간다.

**"사라졌다" 의 정의**: 20회에서 실패 0. 팔 A·A2 가 둘 다 이것을 만족했다.

## 3. (b) 바꾼 축 — 하나뿐

바꾼 것은 `ComparisonEntryPointScenarios.cs` 의 **한 블록**이다.

```csharp
// 팔 A (기준선 = 현재 코드)
if (compare!.Patterns.ExpandCollapse.TryGetPattern(out var expand)) { expand.Expand(); }
else { compare.AsMenuItem().Click(); }

// 팔 B (측정용, 지금은 없음)
compare!.AsMenuItem().Click();   // ARM B (#163, GUI-C-130): the one axis under test.
```

대기 시간·탐색 방식·백엔드·프레임은 **건드리지 않았다.** QA-B-136 에서 화소 크기를
바꾸려다 장면까지 움직여 첫 실행이 무효가 된 사례가 이 제약의 근거다.

**제품 코드는 손대지 않았다** — 바뀐 것은 E2E 시험 파일 하나이고, 그것도 측정 뒤
원복했다. 주입과 원복을 둘 다 확인하고 나서 재었다:

```
arm B injected
0                      ← 빌드 오류 수
224:        compare!.AsMenuItem().Click();   // ARM B (#163, GUI-C-130)
```
```
0                      ← 원복 후 grep -c "ARM B"
0                      ← 빌드 오류 수
```

주입이 조용히 안 먹은 채로 초록을 읽는 함정(CRLF/LF 혼재)은 이 확인으로 막았다.

## 4. (c) 되돌림

팔 A2 는 백업(`CEP130.keep.cs`)에서 **바이트 단위로 복원**한 파일로 돌렸다. 실패 5건이

## 7. 미검증 (Gaps)

- **Native 백엔드에서 재지 않았다.** 60회 모두 Mock 이다(`unset XPE_E2E_BACKEND`).
  메뉴 상호작용은 백엔드와 무관하다고 보지만 **재지는 않았다.**
- **`#163` 의 옛 실패(4/6)가 같은 원인인지는 단언하지 않는다.** 그 측정은 다른 시점의
  다른 코드에서 나왔고, 이번 팔 B 의 25% 와 실패율이 다르다. 같은 메커니즘으로
  **보이지만** 같다고 입증하지는 않았다.
- **왜 25%인지는 모른다.** 클릭 시점에 하위 메뉴가 이미 열려 있느냐가 마우스 이동
  타이밍에 달렸다는 설명은 **가설**이고, 열린 상태를 직접 관측해 확인하지 않았다.
- **표본 수 근거를 재기 전에 글로 남기지는 않았다.** n=20 은 측정 전에 고정됐지만,
  위 §2 의 산수는 사후에 적은 것이다.
- 다른 메뉴 경로(`PipelineMenu` 등)에 같은 토글 함정이 있는지 보지 않았다.

## 8. 잔여 위험

- 팔 A 의 코드는 `TryGetPattern` 이 실패하면 **클릭으로 내려간다** — 그 분기에 들어가면
  원인이 되살아난다. 60회 중 그 분기가 몇 번 쓰였는지는 계측하지 않았다.
- 25% 는 이 기계·이 부하에서 나온 값이다. CI 에서 같은 비율이 나온다는 근거는 없다
  (게이트를 잘못된 기계에서 잡은 사례가 이미 있다).
