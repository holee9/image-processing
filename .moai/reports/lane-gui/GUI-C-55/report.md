## 0. 먼저 — 시험 대상이 복사본이 아니게 했다

지표 코드를 `ComparisonRenderHarness` 로 추출하고 C-54 의 측정과 이 카드의 반증이 **같은 코드**를
쓰게 했다. 복사본을 시험하면 **이미 보고한 수치에 대해 아무것도 증명하지 못한다.**

추출 후 C-54 수치가 변하지 않음을 확인했다(Δ255 40.3/251.2, Δ8 5.3/4.2/바닥 3.3/1.61x).

## 2. (4) 부호 — 지표가 아니라 렌더러가 부호를 싣는다

**이것은 부호 규약을 고르는 것이 아니다.** #149 는 부호 규약을 정하지 않았고, 이 측정이 묻는
것은 **지표가 부호에 반응하는가** 하나다. 규약을 고르는 것과 규약 의존성을 재는 것은 다르다.

귀속을 가르기 위해 **두 경로로 나눠** 쟀다:

```
(4) reference path: +64 -> 60.2/255,  -64 -> 60.2/255   (gap 0.0)
(4) heatmap path:   +64 -> 22.3/255,  -64 -> -15.7/255  (gap 38.0)
```

참조 경로의 입력은 `|source − processed|` 라 **부호에 무관하게 같은 영상**이다. 거기서 간격이
**0.0** 이므로 **지표는 부호에 무관하다.** 남은 38.0 은 전부 **렌더러의 것**이다.

**이유는 렌더러 구조에서 바로 읽힌다**: 히트맵은 processed 를 source 위에 합성하므로 밝아진
변화는 밝게, 어두워진 변화는 어둡게 나온다. **절댓값 차분은 그럴 수 없다** — 절댓값은 부호를
잃기 때문이다.

### C-54 수치 정정

**C-54 의 모든 패치는 배경보다 밝았다.** 따라서 그 수치는 **한쪽 부호만** 기술한다.

| 입력 | C-54 보고(밝은 패치) | **어두운 패치 같은 크기** |
|---|---|---|
| Δ64 히트맵 분리도 | 22.3 | **−15.7**(크기 15.7) |
| 참 차분 분리도 | 60.2 | 60.2 (동일) |
| 비율 | 37 % | **26 %** |

**결론은 약해지지 않는다.** "히트맵이 분리도를 압축한다" 는 양쪽 부호에서 성립하고(37 %·26 %
모두 100 % 에 못 미친다), 오히려 **절댓값 차분이 가질 수 없는 성질(부호 의존)이 하나 더** 나왔다.
정정된 것은 주장이 아니라 **주장의 적용 범위**다 — C-54 의 테스트 파일 상단에 그 범위를 적었다.

## 4. 부수 발견 — 실제 재획득이 처음으로 관측됐다

재실측 중 Native 스위트가 1건 실패했고, C-49 의 스크립트로 이름을 잡았다:

```
run 2  FAIL: WindowReacquireTests.ReadableWindow_IsKept_AndLeavesNoNote
run 3  FAIL: 같은 것                         (3회 중 2회)

Assert.Equal() Failure: Strings differ
Expected: ""
Actual:   "The launched window did not support Autom"…
```

**C-50·C-51 이 "모사된 방아쇠만 밟았다" 고 남긴 자리가 이것으로 닫힌다** — 실제 결함이 실제
실행에서 일어났고, C-51 이 만든 노트가 그것을 **기록했다.** 진단 값이 쓸모를 증명한 셈이다.

**그런데 그 실패는 결함이 아니다.** `ReadableWindow_IsKept_AndLeavesNoNote` 는 **건강한 획득**에서
무슨 일이 일어나는지 묻는 시나리오이고, 그 실행은 건강하지 않았다. **측정 불가이지 실패가
아니다.** 노트를 사유로 `Skip` 하게 바꿨다 — C-37 의 규칙(측정 안 된 것을 통과로 세지 않는다)을
그대로 적용했고, 통과로 세지도 않는다.

수정 후 Native 3회 0 실패. Mock 실행에서 건너뜀이 1~2 로 변하는데, **그 변동 자체가 실제
결함의 발생 여부**다.

**빈도가 이전 추정과 다르다**: C-50 은 Mock 프로브 60회에서 3회(5 %)를 봤는데, 여기서는 Native
3회 중 2회다. 표본이 작아 비율로 말하지 않는다 — 다만 **Native 에서 더 자주 보인다는 신호**는
있고, 원인(왜 Win32 공급자를 받는가)은 여전히 미결이다.

## 5. 미검증 (Gaps)

- **(4)의 결론은 Δ64 한 크기에서 왔다.** 다른 Δ 에서 부호 간격이 어떻게 변하는지 재지 않았다.
- **부호 규약을 고르지 않았고, 부호 기준 측정도 하지 않았다**(카드 지시).
- **Native 에서의 재획득 빈도를 재지 않았다**(§4). 3회는 비율을 말할 표본이 아니다.
- **왜 Native 에서 더 자주 보이는지 모른다** — 관측만 있고 원인은 없다.
- **하네스 추출이 값을 바꾸지 않았다는 확인은 C-54 의 두 수치로만** 했다(Δ255·Δ8). 나머지
  행은 재확인하지 않았다.
- 실제 해부 구조 영상은 이 카드가 아니다(#151 자리).

## 6. 잔여 위험 (Residual risk)

- **`ReadableWindow_IsKept_AndLeavesNoNote` 가 이제 환경에 따라 건너뛴다.** 항상 건너뛰는
  상태가 되면 그 시나리오는 아무것도 지키지 않는데, **건너뜀 수가 그 신호**다(0이 아니면
  실제 결함이 일어난 실행이 있다는 뜻).
- **지표가 건강하다는 결론은 네 가지 주입에 한한다.** 재지 않은 성질(예: 패치가 배경보다
  넓을 때, 패치 내부가 균일하지 않을 때)은 여전히 모른다.
- **부호 의존은 렌더러의 성질로 확정됐지만, 그것이 결함인지는 이 카드가 말하지 않는다** —
  #149 의 부호 규약이 미결이기 때문이다.
