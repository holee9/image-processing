# GUI-C-145 (#214) — `ScrollIntoView` 로 고쳤다. 그리고 `C-143` §7 을 다시 정정한다

상태: **고침 완료·반증 완료·CI 수치 제출.** 그리고 **`C-143` §7 의 절반이 제 계측 착시였다** — §5.

---

## 1. 무엇을 고쳤나 — 한 줄

`gui/ImageProcTest/Views/AnalysisPanel.xaml.cs` 의 `OnLogSelectionChanged`:

```csharp
if (LogList.SelectedItem is { } selected)
{
    LogList.ScrollIntoView(selected);
}
```

`AnalysisPanel.xaml` 의 로그 `ListBox` 에 `x:Name="LogList"` 와 `SelectionChanged` 를 붙인 것이 전부다.

**View 에 둔 이유**: 스크롤은 View 관심사다. 뷰모델은 이 목록의 참조를 갖지 않고, 가져서도 안 된다.
대안(선택 해제)은 `C-142` 에서 기각된 쪽 — 복사를 막지만 **왜 안 되는지가 안 보인다**.

**범위가 측정된 결함보다 넓다는 것을 적어 둔다**: 이 처리기는 모든 선택 변경에 반응한다. 사용자가
방금 클릭한 행에는 무동작(이미 보인다)이고, 추가되는 것은 **프로그램이 바꾼 선택도 스크롤된다**는
것이다. 그래서 새 시험만이 아니라 **E2E 전체를 다시 돌렸다**(§4).

## 2. 검증 — 카드 §2 표 세 행

계측은 `C-143` 의 A3·A2 를 그대로 쓴다(조건을 새로 만들지 않았다).

| 행 | 고치기 전 | **고친 뒤** |
|---|---|---|
| A3 맨 위 (재실행 34, 필터 후 27행, `viewSize` 71.4%) | **`visible=True`** — 결함이 아니었다 (§5) | `visible=True` |
| A3 맨 아래 (같은 조건) | **`offscreen=True`, 클리핑 `0x0`** → `visible=False` | **`visible=True`** (`y=…`, 클리핑 `338x23`, `verticallyInside=True`) |
| A2 (재실행 12, 필터 후 `viewSize` 100%) | 네 조건 `visible=True` | 네 조건 **`visible=True`** (악화 없음) |

`viewSize < 99.5%` 단정 유지 — 고친 뒤에도 조건이 성립함을 데이터가 보인다(71.4%).

## 3. 반증 — 고침을 끄면 빨개진다

카드 §3 이 요구한 것. 처리기를 런타임 거짓 조건으로 조기 반환시키고 같은 A3 를 돌렸다.

| 팔 | A3 맨 아래 | A3 맨 위 |
|---|---|---|
| 고침 **끔** | **`offscreen=True`** → NOT VISIBLE | `visible=True` |
| 고침 **켬** | `verticallyInside=True` → **VISIBLE** | `visible=True` |

**맨 아래 조건이 고침을 본다.** 맨 위 조건은 양쪽 다 초록이라 이 고침의 증거가 되지 못한다 —
그것을 §5 에서 정정한다.

### 가상화와의 만남 (카드 §3 둘째 요구)

`ScrollIntoView` 는 **실체화까지 한다** — 이것이 이 API 를 고른 이유이기도 하다. 측정: 필터 켠 뒤
선택 행의 `offscreen` 이 `True` → `False` 로 바뀌고 클리핑 폭이 `0` → `338` 이 된다. 실체화되지
않은 항목을 대상으로 불러도 아무 일도 안 일어나는 경우는 **관측되지 않았다**.

단, `A3` 는 알림 27건이라 **필터 후 전부 실체화될 수 있는 규모**다. 수백 건에서 같은지는 재지 않았다.

### 최소 고침을 찾느라 세 가지를 넣었다 붙였다 뺐다

| 팔 | A3 맨 아래 | 결론 |
|---|---|---|
| 즉시 호출만 | **VISIBLE** | **이것으로 충분하다** |
| 지연(`Dispatcher.BeginInvoke`) | VISIBLE | 불필요 |
| 지연 + 컨테이너 `BringIntoView` | VISIBLE | 불필요 |
| + `VirtualizingPanel.ScrollUnit="Item"` | VISIBLE | 불필요 |

세 가지는 **12픽셀 잔차를 쫓다** 들어간 것이고, 그 잔차는 앱이 아니라 **계측**이었다(§5).
계측을 고친 뒤 즉시 호출만으로 충분해서 **셋 다 제거했다** — 효과가 귀속되지 않는 코드를 남기지
않는다.

## 4. CI 수치 (카드 §4 — 판단은 리더)

| 값 | 실측 |
|---|---|
| `gui-e2e-native` 현재 소요 | **17분 03초** (main 런 `36319608397`, `12:48:25Z` → `13:05:28Z`) |
| A3 단독 | **1분 27초** |
| A3 를 넣으면 | 약 **+8.5%** (87초 / 1023초) |
| 34회를 27회로 줄이면 | **1분 26초** — **1초 차이.** 재실행 횟수는 비용 요인이 아니다 |
| 27행을 더 싸게 만드는 경로 | **없다.** `MockXpeBackend` 는 알림 고정 3건, 픽스처 이음매는 창 읽기 프로브, Native 는 실행당 약 1건 |

**재실행을 줄여도 시간이 줄지 않는다.** 비용은 앱 기동(약 13초)과 조건별 필터 토글·스크롤·측정
주기에 있다. 그래서 34회를 유지했다 — 27회는 필터 후 `viewSize` 89.3% 로 99.5% 한계에 가깝고,
34회는 71.4% 로 여유가 크며 **비용이 같다**.

줄이려면 조건 수를 줄이는 쪽이다(맨 아래만 남기면 약 절반). 맨 위 조건은 §5 대로 이 고침의 증거가
아니므로 **뺄 수 있다** — 다만 "다른 스크롤 위치에서 악화 없음" 을 보이는 값은 있다. **어느 쪽이든
넣을지 말지는 리더 판단**이다.

### 회귀 — 처리기 범위가 넓으므로 전체를 돌렸다

| 스위트 | 결과 |
|---|---|
| E2E 전체 (Native) | **162 통과 / 건너뜀 0 / 실패 0** (14분 10초) |
| IntegrationTests | **265 통과 / 1 건너뜀 / 실패 0** |
| E2E 전체 (Mock) | **133 통과 / 29 건너뜀 / 실패 0** (8분 27초) |

**Mock 전체에서 한 번 빨개졌고, 그것이 제 새 시험이었다.** A3 의 조건 단정이 Mock 에서 터졌다 —
`MockXpeBackend` 는 알림을 **고정 3건** 추가하고 반복문도 조절 수단도 없어서, 재실행을 34번 해도
필터 후 목록이 3행·`viewSize` 100% 다(실측). 즉 **이 백엔드에서는 조건을 만들 수 없다.**

고친 방향을 적어 둔다: **조건 단정을 느슨하게 하지 않았다.** 그러면 Native 에서 알림이 쌓이지 않는
회귀가 조용히 지나간다. 대신 백엔드로 갈라 **구조적 사유를 적고 건너뛴다**(`Skip.If(BackendMode ==
"Mock")`). 결과가 정확히 갈린다 — Mock 1건 건너뜀 / Native 3건 실행·통과.

§1 에 적은 대로 이 처리기는 **모든 선택 변경**에 반응하므로, 새 시험만 보는 것으로는 범위를 덮지
못한다. 그래서 전체를 다시 돌렸다.

## 5. `C-143` §7 정정 — 절반이 제 계측 착시였다

`C-143` §7 은 A3 **두 조건 모두** `visible=False` 로 적었다. **맨 위 조건은 틀렸다.**

### 무엇이 틀렸나

`Visibility()` 가 비교 대상 목록 사각형을 **케이스 시작 시점에 한 번 잡아** 재사용했다. 목록은 측정
사이에 움직인다 — 기하 프로브로 확인: 측정 시점 목록 `976,308`, 선택 행 `977,309` (연속, 온전히
안쪽)인데, 케이스 초반에 잡은 사각형은 `y=295` 였다. **13픽셀 차이가 "23줄 중 11줄만 걸침" 으로
읽혔다.**

`offscreen=True` 는 UIA 속성이라 내 사각형과 무관하다 — **맨 아래 조건의 결함은 실재한다.**
맨 위 조건의 "11/23" 만 착시였다.

### 고친 방법

`Visibility()` 와 `IsRowVisible()` 이 **호출 시점에** 목록 사각형을 읽는다. 매개변수로 넘기지 않는다.

### 정정 범위

| 문서 | 이전 기술 | 정정 |
|---|---|---|
| `C-143` §7 | A3 **두 조건** 모두 화면 밖 | **맨 아래만.** 맨 위는 계측 착시 |
| `#214` | 필터가 선택을 화면 밖으로 옮긴다 | **목록이 아래로 스크롤돼 있을 때** 그렇다 |

`#214` 자체는 유지된다 — 결함이 있고, 이 카드가 고쳤고, 반증으로 귀속됐다. **좁아진 것은 조건**이다.

### 왜 이걸 먼저 못 봤나

`C-142` 에서 `Visibility()` 를 만들 때는 한 케이스에서 한 번만 측정했고, 사각형이 낡을 시간이
없었다. `C-143`·`C-145` 에서 **한 케이스 안에서 여러 번** 재기 시작하면서 낡았다. 계측을 재사용하며
조건만 늘린 것이 카드 지시였고 맞았지만, **재사용한 계측의 전제(사각형이 안 움직인다)를 다시
확인하지 않았다.**

## 6. 미검증 / 잔여 위험

- 알림 **수백 건** 규모에서 `ScrollIntoView` 와 가상화의 만남을 재지 않았다 (§3)
- Mock 경로는 알림 고정 3건이라 이 조건을 만들 수 없다 — **Native 전용 검증**이다 (카드 §5)
- 처리기가 **모든 선택 변경**에 반응한다. 프로그램이 바꾼 다른 선택에서 원치 않는 스크롤이 생기는
  경우를 열거하지 않았다 — E2E 전체 초록이 그 범위의 관측이다
- `ScrollIntoView` 가 **바깥 `ScrollViewer`** 까지 처리하는지는 미확정. 이 측정에서는 필요하지
  않았다(행이 온전히 안쪽으로 들어왔다). `BringIntoView` 는 효과가 귀속되지 않아 제거했다
- 26~27 경계 지점 측정은 **범위 밖**(카드 §5)
- **CI 에서 아직 안 돌았다** (이 커밋 미푸시)
