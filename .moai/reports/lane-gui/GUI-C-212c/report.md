## 1. 오라클 결과를 믿는 조건

Codex 의 재현 그대로: 자식이 `{"Passed":true}` 를 찍고 비정상 종료해도, 로그에 JSON 모양 줄이 끼어도 통과였다.

- **프로토콜 줄**: 자식은 `XPE-ORACLE-RESULT: <json>` 한 줄을 쓴다. 접두사 없는 줄(네이티브 DLL 의 로그 포함)은 결과가 아니다. 접두사 줄이 0개면 "gave no result", 2개 이상이면 "ambiguous".
- **종료 코드**: 0 이 아니면 결과 줄이 있어도 실패("Oracle process failed", 종료 코드와 stderr 포함).
- **필수 필드**: 결과 레코드의 생성자 매개변수 중 기본값이 없는 것(리플렉션으로 읽으므로 필드를 더하면 자동으로 필수가 된다)이 JSON 에 없거나 null 이면 이름을 나열한 실패. JSON 객체가 아니면(`[1]`, `"x"`, `null`, 깨진 JSON) 실패.
- **성공 불변식**(`Validate`, `Passed: true` 일 때): 실행됨, 상태 "Synthetic oracle pass", 단계가 정확히 `offset, gain, defect` 순서이고 각각 코드 `OK`·통과·유한한 측정, 입력 보존, 입력 해시 전후 동일(64자리 16진), 출력 해시, 비유한 값 0개, 두 실행 동일(RMSE 0, 유한), 출력이 유한한 범위를 가짐(최대 > 최소), 지연이 유한한 비음수. 정직한 실패 결과("Calibration setup failed" 등)는 상태만 있으면 그대로 전달한다.

시험(`PreprocessSyntheticOracleProtocolTests`, 순수 파서 + 실제 자식 프로세스 대역):
- **대조군**: 완전하고 일관된 결과 + 종료 코드 0(로그 줄이 앞뒤에 끼어도)은 통과 — 전부 거부하는 검사기는 아무것도 증명하지 못한다. 실제 `cmd.exe` 자식이 좋은 줄을 찍고 0 으로 끝나는 경우도 통과.
- 좋은 줄 + 종료 코드 1(파서와 실제 자식 둘 다), 결과 줄 둘, 접두사 없는 JSON, `{"Passed":true}` 만 있는 줄, JSON 이 아닌 4종.
- 불변식을 하나씩만 깨고 `Passed: true` 를 유지한 17건(미실행, 다른 상태, 실패한 단계, 오류 코드가 있는 단계, 단계 순서·누락·없음, 입력 미보존, 해시 변경·공란, 출력 해시 공란, 비유한 값, 실행 간 차이, NaN, 범위 없음, 무한대, NaN 측정). 각 시험은 먼저 "이 깨진 결과도 여전히 통과를 주장한다"를 단언한다.

## 2. 작업 객체

`KillOnCloseJob`(kernel32 `CreateJobObjectW` / `SetInformationJobObject` / `AssignProcessToJobObject`): 마지막 핸들이 닫히면 — 부모가 닫든 부모 프로세스가 어떻게 끝나든 — 시스템이 작업 안 모든 프로세스를 종료한다. 호스트는 자식을 시작하자마자 작업에 넣고, 작업 생성이나 배정이 실패하면 자식을 (시작 전이면 시작하지 않고, 시작했으면 죽이고) 실패로 보고한다. 시간 초과·예외·훅 예외 경로는 모두 종료를 시도하고 "was killed" 또는 "could not be confirmed killed" 를 결과에 쓴다.

시험:
- 작업에 넣은 자식은 핸들을 닫으면 15초 안에 종료, **같은 방식으로 띄웠으나 작업에 넣지 않은 자식은 영향 없음**(대조군).
- 호스트 자신의 배선: 시험 이음새 훅이 호스트가 만든 작업을 닫으면 60초 제한을 기다리지 않고 자식이 사라지고(PID 조회 실패), 닫지 않으면 같은 자식이 제한 시간까지 돈다.
- 훅이 예외를 던져도 자식은 종료되고 상태에 "was killed".

## 3. 서명 대조기 (`ModuleSignatureParity.cs`)

- **(a)** `const char*` 에 `[MarshalAs]` 없이 `CharSet.Auto` 를 허용하던 줄을 거부로 바꿨다("marshalled with CharSet.Auto (UTF-16 on Windows)"). 통제: 같은 바인딩을 `CharSet.Ansi` 로 쓰면 깨끗하다(양쪽 모두 확인).
- **(b)** 고정 배열(`char name[16]`, `uint16_t table[4]` 형)을 총 바이트가 아니라 세 가지로 비교한다: 형태(`ByValArray`, 또는 char 배열이면 `ByValTStr`), 원소 종류(`ushort[]` ↔ `uint16_t`; char 배열은 `byte[]` 도 허용), 원소 수(`SizeConst`). 통제 시험: **Codex 의 예(`uint16_t[4]` 를 8 원소 `byte[]` 로) 거부**, 같은 크기의 `short[]`(부호 다름) 거부, 원소 수 다름, 속성 없음, 문자열이 아닌 배열에 `ByValTStr`, 배열이 아닌 것에 `ByValArray`, char 배열의 `ByValTStr` 길이 다름. 허용 대안(char 배열을 `ByValArray` `byte[]` 로) 은 깨끗해야 한다 — 과잉 거부 방지.
- 실제 소스는 새 규칙에서도 **지적 0건**이다(기존 27건 통과 그대로). 실제 바인딩에서 이 오용이 발견되지는 않았다는 Codex 의 설명과 일치한다.

## 반증 (`falsification_arms.txt`, 25건 모두 빨강, 매번 바이트 단위 복원)

1: 종료 코드 무시(2건 빨강), 결과 줄 둘 허용, 필수 필드 미검사, 불변식 전체 미검사(17건), 불변식 12개 각각 제거(1e~1p, 각 1~3건) / 2: 작업에 안 넣음, 킬온클로즈 해제, 종료 무동작 / 3: Auto 허용, 배열 전체 미검사(7건), 원소 종류·원소 수·형태·ByValTStr-비문자 각각 미검사.

## 한계

- 작업 객체는 자식이 시작된 **직후**에 배정한다. 그 짧은 틈에 자식이 손자 프로세스를 만들면 손자는 작업 밖이다. 오라클은 만들지 않지만 일반 보장은 아니다(일시 중단 상태로 시작해 배정하는 방식은 택하지 않았다).
- "부모 프로세스가 비정상 종료해도 자식이 남지 않는다"는 OS 의 작업 객체 계약에 기댄다. 시험은 **핸들을 닫는 것**(부모 종료 때 OS 가 하는 일)으로 대신했고, 실제로 부모 프로세스를 죽이는 시험은 만들지 않았다.
- 불변식은 필드 값의 일관성을 보는 것이지 해시가 실제 데이터의 해시임을 재계산하지는 않는다(자식이 거짓 해시를 일관되게 쓰면 통과한다). 자식은 같은 앱 exe 라는 신뢰 경계 안에 있다.
- 대조기 (b) 는 헤더에 선언된 **구조체 필드의 고정 배열**을 본다. 함수 매개변수 `T[N]` 형은 C 에서 포인터로 소멸하므로 기존 포인터 규칙이 담당한다.
