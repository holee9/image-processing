측정만 했습니다. 앱·러너 **무변경**(`git status` 로 확인).

**가장 큰 결과: `ImageProcTest.E2E.exe` 는 지금 저장소 안에서도 실패합니다.** 재귀와 무관한 이유로,
`#175`(2026-09-17)가 창 제목을 바꾼 뒤 러너의 상수가 따라오지 않았습니다.

## 2. ① 동시 실행 — 반만 답했습니다

| 실행 | 앱이 떠 있을 때 | 앱 없이 |
|---|---|---|

| `E2E.exe` | **exit ≠ 0**, 1613 ms | exit ≠ 0, 1744 ms |

`SelfCheck` 는 **앱이 떠 있어도 정상**입니다 — 창을 만들지 않으니 예상대로입니다.

`E2E` 는 **동시성을 판정할 수 없습니다.** 앱이 있든 없든 **같은 첫 단언에서 죽기 때문**입니다.
창을 두 개 띄웠을 때 무슨 일이 생기는지는 **여전히 미확인**이고, §3 을 고치기 전에는 잴 수 없습니다.

## 4. ④ 배포본 경로 — **두 러너 모두** 저장소에 묶여 있습니다

`E2E.exe` 만 그런 줄 알았는데 아닙니다.

| 러너 | 어디서 저장소를 찾나 | 밖에서 실행하면 |
|---|---|---|
| `E2E.exe` | `Program.cs:412-426` `FindRepoRoot` — `docs/project/sprint-plan.md` 를 찾아 부모로 거슬러 올라감 | `InvalidOperationException: Repository root not found.` (152 ms) |
| `SelfCheck.exe` | `GuiFixtureManifestService.FindRepositoryRoot` — **`Program.cs:5`, 첫 문장** | `InvalidOperationException: Repository root could not be located.` (155 ms) |

측정 방법: 각 러너의 출력 폴더를 저장소 **밖**(`%TEMP%` 아래)으로 통째로 복사해 실행.
그 위치에서 부모 방향으로 `docs/project/sprint-plan.md` 가 **없음을 먼저 확인**했습니다(진짜 저장소 밖).

**실패 방식**: 조용하지 않습니다. 둘 다 **명시적 예외 + 비영 종료 코드**로 죽습니다 — 이건 좋은 쪽입니다.
다만 **배포본에서는 두 명령 다 동작하지 않습니다.**

## 5. ③ 종료 코드 — 제 계측이 한 번 틀릴 뻔했습니다

처음엔 bash 에서 `$?` 로 읽어 **`127`** 이 나왔습니다. 그 수를 그대로 적었으면 틀린 보고였습니다 —
PowerShell 로 프로세스의 실제 코드를 읽으니 **`-532462766`** (`0xE0434352`, .NET 미처리 예외의 표준 코드)입니다.
`127` 은 bash 가 매핑한 값입니다.

| | 종료 코드 (실제) |
|---|---|
| 성공 (`SelfCheck`, 저장소 안) | **0** |
| 실패 (`E2E`, 제목 불일치) | **-532462766** |
| 실패 (둘 다, 저장소 밖) | **-532462766** |

**실패를 실패로 냅니다** — 0 이 아니므로 메뉴가 초록을 위장할 일은 없습니다.
다만 **예외로 죽는 것이라 0/1 같은 약속된 코드가 아닙니다**: 호출하는 쪽은 `== 0` 으로만 판정해야 하고,
`== 1` 을 기대하면 틀립니다.

## 6. ② 소요 시간 — 비동기가 필요한 규모는 아닙니다

| | 시간 |
|---|---|
| `SelfCheck` 성공 | **1.05 s** (앱이 떠 있을 때 0.78 s) |
| `E2E` 실패까지 | **1.6–1.7 s** |
| 저장소 밖 즉시 실패 | 0.15 s |

**1초대**입니다. UI 스레드를 그 시간 막으면 사용자에게는 멈춘 것으로 보이므로 그래도 **비동기로 띄우고
진행 표시를 두는 편**이 맞지만, "몇 분" 급이라 별도 설계가 필요한 규모는 아닙니다.

**단, `E2E` 의 시간은 실패까지의 시간입니다.** 끝까지 도는 시간은 §3 을 고쳐야 알 수 있습니다 —
창을 만들고 메뉴를 열고 도움말 창까지 여는 시나리오라 **더 길 것으로 보이지만, 재지 않았습니다.**

## 7. 그래서 구현이 어떻게 바뀌는가 (카드 §2 의 마지막 문장)

| # | 답 | 구현에 미치는 영향 |
|---|---|---|
| ① | 반만 답함 | `E2E` 동시성은 §3 뒤에 다시 재야 합니다 |
| ② | 1초대 | 비동기 + 진행 표시. 별도 설계 불필요 |
| ③ | 0 / 예외 코드 | 호출부는 **`== 0` 으로만** 판정. `1` 을 기대하면 틀립니다 |
| ④ | **두 러너 다 저장소 의존** | **행 15·16 은 개발 기계 전용 명령입니다** |

**넷 중 셋이 구현을 바꿉니다.** 그리고 §3 이 그 위에 하나 더 얹습니다:

1. **행 16 은 지금 구현하면 안 됩니다** — 부를 러너가 깨져 있습니다. 러너의 제목 단언을 먼저 고쳐야 하고,
   그것은 `gui/ImageProcTest.E2E/` 수정이라 이 카드 범위 밖입니다
2. **행 15 는 구현 가능합니다** — `SelfCheck` 는 저장소 안에서 돌고, 앱이 떠 있어도 돌고, 1초 남짓입니다
3. **두 명령 다 "저장소가 있을 때만" 입니다** — 배포본에서 무엇을 보여 줄지 정해야 합니다.
   제 제안: 러너 exe 가 없거나 저장소 밖이면 **비활성이 아니라 상태줄 문구**(`C-156` §3.2 와 같은 이유)

## 8. 미검증 / 잔여 위험

- **`E2E` 가 끝까지 도는 시간·동시 실행 동작** — §3 때문에 못 쟀습니다. 이 카드의 가장 큰 공백입니다
- 측정은 **제 기계 한 대**입니다. CI 러너에서는 다릅니다 — **로컬 실측, CI 상한 추정**
- 배포본 모사는 **출력 폴더 복사**입니다. 실제 설치본의 구조(단일 파일·자체 포함 등)는 다를 수 있습니다
- `SelfCheck` 가 저장소 안에서 **일부러 실패**했을 때의 코드는 재지 않았습니다 — 저장소 밖 실패로 대신했고,
  둘 다 같은 `.NET 미처리 예외` 경로라 같은 코드일 것으로 **보이지만 관측은 아닙니다**
- `#227`(두 러너가 CI 에 없음)은 카드 §4 대로 **다루지 않았습니다.** 다만 §3 의 결함이 그 공백 때문에
  드러나지 않았다는 점은 기록해 둡니다
