## 2. 증거

### C1~C2 — 성능 회귀 시험 (P-08)

읽는 값은 **모두 앱 안에서 잰 것**입니다(연쇄의 단계별 `Stopwatch`). C-103 에서 확인한 대로 바깥 측정은 UI 자동화가 2 초를 먹어 앱의 변화를 볼 수 없으므로, 문턱에 자동화 비용이 섞이지 않게 했습니다.

**첫 기준(피라미드 키 미전송 상태), 3회 × 7적용 = 21 표본:**

```
median=27.0 p95=28.0 max=32.0 ms [26, 27, 27, 27, 28, 28, 32]
median=27.0 p95=28.0 max=33.0 ms [27, 27, 27, 27, 28, 28, 33]
median=27.0 p95=28.0 max=33.0 ms [27, 27, 27, 27, 27, 28, 33]
```

퍼짐 33/27 = 1.22배. 문턱 = 27 × 1.22 × 1.36 = **45 ms**(관측 최악값의 1.36배). 1.36 은 "조용한 실행에서 못 본 기기 부하" 몫이며, 코드에 대한 안전 여유가 아닙니다.

**그리고 이 문턱이 제 변경에서 빨간불을 켰습니다:**

```
The GSVG stage's median rose to 51 ms against a 45 ms gate (baseline 27 ms, measured spread 1.18x).
```

원인은 명확합니다 — 같은 카드에서 피라미드 단수 기본값을 4 로 두면서, 가상 그리드 실행마다 라플라시안 피라미드가 다시 돌게 됐습니다. **의도한 변경**입니다. 그래서 문턱을 올린 것이 아니라 **새 기본값에서 기준을 다시 쟀습니다**(3회 × 7적용):

```
median=50.0 p95=57.0 max=59.0 ms [48, 49, 50, 50, 50, 57, 59]
median=49.0 p95=50.0 max=54.0 ms [48, 48, 49, 49, 49, 50, 54]
median=50.0 p95=51.0 max=56.0 ms [49, 49, 49, 50, 50, 51, 56]
```

퍼짐 59/50 = 1.18배 → 문턱 = 50 × 1.18 × 1.36 = **80 ms**. 유도 방식(1.36)은 첫 번째와 같게 두어 두 값이 비교 가능합니다. 이 경위를 상수 주석에 그대로 적었습니다 — "기준을 다시 재는 것" 과 "문턱을 완화하는 것" 은 다른 행위이고, 구분이 남아 있어야 다음 사람이 속지 않습니다.

**한계(적어 둡니다):** 이 시험은 Native 전용이고, CI 의 gui-automation 은 Mock 으로 돌립니다. 따라서 **CI 에서는 이 회귀를 잡지 못합니다.** 여기서만 잡습니다.

### C3~C5 — 피라미드 설정 (P-09)

```
P09 levels=0          : hash=36fc547e253b07f1 mean=85.205 stage=41 ms
P09 levels=4 gain=1.0 : hash=36fc547e253b07f1 mean=85.205 stage=51 ms
P09 levels=4 gain=1.3 : hash=a1bc70c62a9e60fa mean=82.796 stage=51 ms (Δ평균 vs off=2.409)
```

**단수만으로는 픽셀이 바뀌지 않습니다.** 코드가 그 이유를 말합니다 — `virtual_grid.cpp` 의 `PyramidContrast` 는 각 상세 대역을 빼고(`lap = fine - up`) 되돌릴 때 `up += gain * band` 로 더합니다. `gain == 1.0` 이면 정확히 원래 영상으로 복원됩니다. 필드 주석도 `double pyramidGain = 1.0;   // detail gain (1 = unchanged)` 입니다.

즉 단수만 노출하면 사용자에게 **시간만 10 ms 더 쓰고 아무것도 바꾸지 않는 설정**을 주게 됩니다. 카드가 요구한 "값을 바꾸면 해시가 달라지는지" 의 답이 "아니오" 였고, 원인이 이득이었으므로 **이득도 함께 노출했습니다.** 카드 범위를 한 항목 넘은 결정이므로 여기 적습니다. 기본값은 1.0 으로 두어 오늘의 출력은 움직이지 않습니다.

모듈 기본값에 기대지 않고 GUI 가 키를 **명시적으로** 보냅니다(`vg_pyramid_levels`, `vg_pyramid_gain`). 0(끔)일 때는 두 키를 모두 보내지 않습니다 — 모듈이 `levels==0` 인데 이득이 1.0 이 아니면 거부하기 때문입니다.

노출 범위: 단수 0(끔)·4–8, 기본 4. 이득 0.1–4.0, 기본 1.0. 범위 밖 값은 기본으로 되돌립니다.

### C6 — 미리보기 비트맵 (P-10)

바꾼 것: `CreatePreview` 의 매개변수를 `IReadOnlyList<ushort>` 에서 `ReadOnlySpan<ushort>` 로. 두 반복문이 픽셀마다 인덱싱하는데(3072² = 9.4 M회 × 2), 인터페이스를 거치면 매번 가상 호출이 됩니다. **산술은 한 글자도 바꾸지 않았습니다.**

같은 빌드·같은 도구로 전후를 쟀습니다(변경을 임시로 되돌려 3회, 복원 후 3회):

| | 1회 | 2회 | 3회 |
|---|---|---|---|
| 전(인터페이스) | 14 ms | 16 ms | 16 ms |
| 후(스팬) | 8 ms | 8 ms | 8 ms |

앱의 배경 작업 전체도 21/201/22 ms → 14/15/14 ms 로 내려갔습니다(201 은 §4 의 흔들림).

**출력 불변 확인:** P-10 이 그려진 해시를 **변경 전에 기록된 값**(`36fc547e253b07f1`, C-102 P-03 기준)과 비교합니다. 같은 빌드를 자기 자신과 비교하면 "일관되게 틀린 것" 도 통과하므로, 독립적으로 얻은 값에 고정했습니다.

### C7 — 순서

`git show origin/main:modules/gsvg/src/virtual_grid.h` → `int pyramidLevels = 0;` (여전히 0). post 의 기본값 4 변경은 아직 main 에 없습니다. **순서가 어긋났습니다.** 다만 GUI 가 키를 명시적으로 보내므로 지금 상태에서도 정상 동작하며, post 가 4 로 바꿔도 GUI 동작은 달라지지 않습니다.

## 3. 기준 귀속

- 모든 수치는 이번 실행에서 `build/ci-c72f0e8/bin` (CI run 35275125717) 의 DLL 로 측정했습니다.
- 미리보기 전/후 비교는 **같은 세션·같은 시험·같은 DLL** 에서, 코드만 되돌려 쟀습니다.
- P-10 이 고정한 해시는 GUI-C-102 에서 기록된 값입니다(이번 실행에서 다시 만든 값이 아닙니다).

## 4. 미검증

- **`work` 가 이따금 200 ms 로 튀는 이유.** 전 측정에서도 1회(201 ms) 나왔습니다. 후 측정 3회에서는 안 나왔지만 없어졌다고 말할 표본이 아닙니다.
- **피라미드 단수를 4 가 아닌 값(5–8)으로 올렸을 때의 비용·출력.** 4 와 0 만 쟀습니다.
- **이득 1.3 이 진단상 옳은 값인지.** 연결 확인용으로 쓴 값이며 화질 판단은 하지 않았습니다.
- **미리보기 개선이 다른 크기 영상에서도 같은 비율로 빨라지는지.** 3072² 한 크기만 쟀습니다.
- **`-17` 이 새 DLL 로 통과하는지**(여전히 막힘).
- 이 성능 게이트가 **다른 기기에서 적절한지.** 개발 기기 1대입니다.

## 5. 잔여 위험

- **게이트가 CI 에서 돌지 않습니다.** Native 전용이고 CI 는 Mock 입니다. 누군가 여기를 안 돌리면 회귀가 통과합니다.
- 이득 기본값 1.0 은 출력을 바꾸지 않지만, 피라미드가 켜진 채 **비용만 10 ms** 들어갑니다. 기본을 0(끔)으로 둘지 4 로 둘지는 리더 결정 사항으로 남깁니다 — 저는 카드 지시대로 4 로 두었습니다.
- 편집 중 literal backspace(0x08)가 다시 3건 들어갔습니다. 커밋 전에 전수 검사로 잡았고(`control-char files: none`), HEAD 는 깨끗했습니다. 매 편집 뒤 검사를 돌리는 습관을 유지합니다.
