## 1. §3 의 답 — 질문 자체가 측정으로 갈렸습니다

카드가 *"두 관례 중 어느 쪽을 따를지 고르고 이유를 적으라"* 고 했는데, 먼저 확인한 사실이 질문을 바꿉니다:

> 그 메뉴 항목은 **`IsCheckable` 이 없습니다.** 머리말이 `Open Pipeline _Diagnostics` 이고, **명령**입니다 — 행 7·8 같은 **두 상태 토글이 아닙니다.**

그래도 패널의 **가시성**은 어디든 살아야 하므로, 두 관례를 놓고 골랐습니다:

| 기존 관례 | 실제 상태 |
|---|---|
| `ShowCalibrationPanel` (뷰모델 속성) | 읽는 곳이 **자기 메뉴의 `IsChecked` 하나** — 패널이 없습니다 |
| `Settings.ShowDisplayPanel` (영속 + 보고) | 영속되고 자동화가 `DisplayPanelVisible` 로 읽는데 **역시 패널이 없습니다** |

**둘 다 결함입니다.** 그래서 **세션 전용 뷰모델 속성**(`ShowPipelineDiagnostics`)을 골랐고, 근거 셋을 코드에 적었습니다:

1. **실행 선택이 아니라 화면 선호**입니다 — `#136` 이 그 둘을 가른 이유가 *"영속된 값이 이전 실행의 잔재로 검사 결과를 정하는 것"* 이었습니다
2. 자동화는 **데이터를 직접** 봅니다(`stages`·`displayInput` 이 이미 보고서에 있음) — 가시성 필드를 영속해도 **사는 것이 없습니다**
3. **결정적인 것**: 플래그에 **읽는 이가 생깁니다**(패널의 `Visibility`). 두 기존 관례가 정확히 그것을 못 가졌으니, 어느 쪽을 따라도 **패턴이 아니라 결함을 복제**하게 됩니다

## 2. 무엇을 읽어 만들었나 — **새 측정 상태 0개**

| 상태 | 이미 있던 것 |
|---|---|
| 한 번도 렌더 안 함 | `LastChain is null` |
| 단계가 꺼져 있었음 | `StageOutcome.Status == NotRequested` |
| 단계가 돌았음 | `Status` + `ElapsedMs` |
| 지금 것인가 | `IsPreviewStale` · `PreviewStaleReason` |

새로 만든 것은 **가시성 플래그 하나**와 **파생 `HasPipelineDiagnostics`**(`LastChain is not null`)뿐입니다. 파생은 저장하지 않으므로 낡을 수 없고, `LastChain` 이 바뀔 때 알림을 함께 냅니다 — 그러지 않으면 첫 렌더 뒤에도 패널이 *"아무것도 안 돌았다"* 고 말합니다.

### 2.1 거짓말은 **이미 있었습니다**

`StageOutcome.ElapsedMs` 의 XML 주석이 직접 적고 있습니다 — *"Zero for a stage that was not requested"*. 그리고 `ChainResult.Timings` 가 그 0을 **`preprocess=0 ms`** 로 이미 찍습니다.

상태 바에서는 옆에 상태가 붙어 있어 읽을 수 있습니다. **시간만 나열하는 패널에서는 그 0이 홀로 섭니다** — 카드가 지목한 바로 그 형태입니다. 그래서 변환기를 만들었고, 그 변환기는 **억제만 하고 만들어 내지 않습니다**: 출력이 모델의 숫자이거나 `—` 둘뿐이고, **없는 값에 기본값을 주는 분기가 없습니다.**

## 3. 화면에서 읽습니다 — 모델에서 다시 만들지 않습니다

자동화 보고서의 단계 줄은 **렌더된 패널의 `TextBlock`** 에서 읽습니다. 모델에서 재조립하면 *"데이터가 맞다"* 는 확인이 되지만, **이 행이 틀릴 수 있는 단 하나**(꺼진 단계가 `0 ms` 로 찍히는 것)는 렌더 단계에 있으므로 관측 밖이 됩니다. §5 의 팔 B 가 그것을 실제로 보여 줍니다.

**읽는 범위를 패널로 좁혔습니다.** 처음엔 `FindDescendant<ItemsControl>(this)` 였는데 그것은 창의 **첫 `ItemsControl`(메뉴)** 을 잡습니다 — 엉뚱한 컨트롤의 글자를 진단 줄로 보고했을 자리입니다.

## 4. 세 구별 — 실측 (카드 §4)

| 상태 | 관측 |
|---|---|
| **한 번도 렌더 안 함** | `HadMeasurementAtStartup = False`(렌더 전에 읽음), 렌더 뒤 `HasMeasurement = True` |
| **꺼진 단계** | `preprocess · NotRequested · — switched off` — **`0 ms` 가 없습니다** |
| **지금 것인가** | null → *"display parameters changed…"* → null (§4.1) |

### 4.1 세 번째의 첫 측정이 **다른 것을 재고 있었습니다**

처음엔 패널 옆에서 `PreviewStaleReason` 을 읽었더니 이렇게 나왔습니다:

> *"STALE — the display pipeline failed; …"*

**그건 매개변수 경로가 아닙니다.** 같은 스크립트의 **행 11 정지 시험**이 먼저 `StalePipelineFailed` 를 남기고, 그 사유는 **설계상 뒤의 매개변수 편집으로 덮이지 않습니다**. 즉 필드는 **주입과 무관한 이유로** 비어 있지 않았습니다 — 참이지만 검사하려던 것이 아닙니다.

**첫 성공 렌더 직후로 옮기고 삼중으로** 바꿨습니다:

| | |
|---|---|
| 편집 전 | **null** |
| 편집 후 | *"STALE — display parameters changed since this image was rendered…"* |
| 되돌린 후 | **null** |

**전/후/복원 셋이 귀속을 만듭니다.** 그리고 복원 팔이 *"stale 이 떼어지지 않는 라벨"* 이 아님도 같이 보입니다.

### 4.2 Native 에서 **한 화면에 두 종류가 다르게** 찍혔습니다

Mock 에서는 두 단계가 모두 `NotRequested` 라 "숫자를 찍는 쪽" 을 볼 수 없었습니다. Native 로 돌렸더니:

```
preprocess · RequestedNotApplied · 1 ms   Preprocessing skipped: calibration file(s) not found — …
gsvg · NotRequested · —                   switched off
```

**시도된 단계는 실측 `1 ms` 와 사유를 달고, 꺼진 단계는 숫자가 없습니다.** 이것이 이 구별의 가장 강한 형태입니다 — *"실행마다 숫자가 있거나 없거나"* 가 아니라 **한 화면에서 단계별로** 갈립니다.

## 5. 반증

| 팔 | 주입 | 결과 |
|---|---|---|
| **A** | 변환기가 그 0을 시간으로 찍게 | **A-10 FAIL** |
| **B** | 보고서가 패널이 아니라 **모델에서** 줄을 재조립하게 | **A-10 FAIL** |

**팔 B 가 이 카드의 반증입니다** — 화면에서 읽는 것이 판별력을 만든다는 것을 보여 줍니다. 모델을 읽는 판이었다면 **두 팔 다 통과**했을 것입니다.

원복 확인: 변환기 `git diff --stat` 빈 출력, A-10 초록.

## 6. 회귀 — **첫 실행의 실패 2건은 제 오염이었습니다**

| 실행 | 전체 | 통과 | 건너뜀 | 실패 |
|---|---|---|---|---|
| 1차 | 174 | 141 | 31 | **2** |
| 2차(아무것도 같이 안 돌림) | **174** | **143** | 31 | **0** |

**원인은 제가 만들었습니다.** 1차가 도는 동안 §4.2 의 Native 관측을 하려고 **앱 인스턴스를 하나 더 띄웠습니다**(`ImageProcTest.exe --automation-backend Native`). `ApplicationFixture` 는 남은 인스턴스를 정리하고 창을 붙잡는데, 낯선 앱이 같은 시각에 뜨면 그 자리가 흔들립니다. 2차는 동시 실행 없이 돌려 **실패 0**입니다.

시험 수는 173 → **174**(A-10), 통과는 142 → **143** — 더한 만큼 정확히 올랐습니다.

**제 방법의 결함 둘을 같이 적습니다:**
1. **측정 중에 같은 앱을 또 띄웠습니다.** 저장소에 *"측정 중에 소스를 고치지 않는다"* 를 적어 뒀는데, **인스턴스를 더 띄우는 것**도 같은 종류입니다 — 이번엔 소스가 아니라 **프로세스**로 같은 실수를 했습니다
2. **1차 실행에 로거를 안 붙여 실패 이름을 잃었습니다.** 그래서 무엇이 깨졌는지 **끝까지 확인하지 못했습니다** — 재현되지 않았다는 것만 말할 수 있습니다. 앞으로 전체 스위트는 `--logger trx` 로 돌립니다
