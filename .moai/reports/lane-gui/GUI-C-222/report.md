# GUI-C-222 — C11 을 워커 없는 사설 앱 픽스처로 옮겨 실제로 돌게 하기 (GUI-C-221 선택지 A, #254)

Refs #254 #249. 시험 코드만 바꿨다(`clients/ImageProcTest.E2ETests`). **ci.yml 의 허용 목록 `'254'` 행은 삭제 가능**: C11 의 `XPE-SKIP-ALLOWED:254` 건너뜀을 지웠다(`grep XPE-SKIP-ALLOWED ProcessingChainScenarios.cs` 0건).

## 변경

1. **C11 을 `AiWorkerAbsentScenarios`(워커 없는 사설 앱)로 옮기고 둘로 나눴다** — 도우미 `RestoreAiSession` 의 두 분기를 각각 실제로 실행한다.
   - `C11a`: 표시가 있는 상태(워커가 꺼짐) → Restart AI 분기. 앱에서 3번 실패시켜 표시를 만든다(전제: `worker=Disabled; failures=3; ceiling=3` 와 표시 문구 `after 3 of 3 failures` 를 **단언**, 건너뛰지 않는다) → 도우미 → 표시 없음 + 센 실패 없음.
   - `C11b`: 센 실패만 있고 표시가 없는 상태 → 종료 후 재초기화 분기. 1회와 2회 두 번 돌린다(전제: `worker=Active; failures=N; ceiling=3` 와 표시 없음을 단언) → 도우미 → 센 실패 없음. 그다음 **한 번 더 호출해 `failures=1`** 임을 확인한다: 읽은 값만이 아니라 "다음에 일어나는 일"로 센 실패가 0 으로 돌아갔음을 증명한다(남아 있었다면 1 회 뒤엔 2, 2 회 뒤엔 표시가 뜬다).
   - 이 픽스처에서 건너뛰는 것은 C09 와 같은 두 경우뿐이다: 앱이 안 떠 있음/네이티브 DLL 이 없어 사설 폴더를 만들 수 없음(`!app.Prepared`), 네이티브 백엔드가 아님. 둘 다 CI 건너뜀 게이트가 토큰 없는 건너뜀으로 잡는다(아래 4번). 전제 상태가 안 서면 **실패**다.
2. **순서 의존 없음**: 각 시나리오가 시작 상태를 스스로 만든다. 도우미를 쓰지 않고 백엔드 메뉴(종료·초기화)만으로 깨끗한 세션을 만들고(깨끗함 = 꺼지지 않았고 센 실패가 없음; 새로 시작한 세션은 호출 전까지 `worker=Unknown` 으로 읽힌다 — 처음 시도에서 이 정의가 틀려 실패했고 실행 출력으로 고쳤다), 끝에서 앱을 처음 상태로 되돌린다(`finally`, 단계마다 보호). C09 는 시작할 때 표시가 없음을 단언하므로 뒤에 오는 시나리오가 표시를 남기면 빨개지는데, 이 끝 정리가 그것을 막는다. 같은 클래스 안 `C11b(2)` 가 앞 라운드가 남긴 `failures=1` 에서 시작해도 통과하는 것이 10회 모두에서 관측됨(`consecutive_10_runs.txt` 의 `c11b2_start`).
3. **`XPE-SKIP-ALLOWED:254` 건너뜀 삭제.** 옛 `C11`(공유 앱) 메서드를 지우고 자리에 이동 사유 주석을 남겼다. `RestoreAiSession` 은 `internal static`(출력 도우미를 인자로)으로 바꿔 C10 과 새 시나리오가 함께 쓴다.
4. **DLL 없는 로컬 구성에서 C10 이 실패하던 것**: 판단 — **건너뜀이 맞다**. 근거: 이 시나리오는 "모듈에 물어봤을 때"를 관찰하는데 `xpe_ai.dll` 이 없으면 메뉴가 꺼져 모듈에 물을 수 없다; 그것은 구성의 사실이지 앱의 결함이 아니다. `C10` 은 이제 메뉴가 꺼져 있으면 사유를 적고 건너뛴다(앞서 `InvokeAiMenuItem(requireEnabled: true)` 가 단정으로 실패). (C11 은 옮겨졌고 C09 형 건너뜀이 같은 구성을 처리한다.)
   **CI 구성에서 이 건너뜀이 절대 발동하지 않음의 근거 두 가지**(읽은 것): (a) ci.yml Native E2E 준비 단계가 `xpe_ai.dll`·`xpe_ai_worker.exe` 를 포함한 목록에서 하나라도 `build/e2e-native-dlls` 에 없으면 `Write-Error "missing …"` + `exit 1` 로 잡을 실패시킨다(`ci.yml` 1040~1042행 부근); (b) 설령 건너뛰어도 토큰이 없어 건너뜀 게이트가 "NOT RUN (unexplained)" 로 잡을 실패시킨다. 로컬 실측: DLL 없는 디렉터리 → `건너뜀`(사유 문장 그대로 출력), DLL 있는 디렉터리 → `통과`.

## 반증

| 팔 | 방법 | 결과 |
|---|---|---|
| 1 | 도우미의 표시 분기 조건을 끔(`if (false && banner)`) | **C11a 는 빨개지지 않았다.** 이유: 표시 분기가 꺼지면 다음 `else if (counted)` 분기(센 실패가 3)가 같은 일을 하는 종료·재초기화로 표시도 지운다 — 두 분기의 겹침이다. 이 팔은 분기를 무력화한 것이 아니라 다른 분기로 우회시킨 것이라 반증으로 세지 않는다 |
| 1b | 표시 분기의 **Restart AI 누르기 줄**만 제거 | C11a 빨강: `C11a: the worker-off mark is still shown 10 s after Restart AI.` |
| 2 | 도우미의 종료·재초기화 분기를 끔(`else if (false && counted)`) | C11b 빨강, C11a 는 통과(예상대로: 표시가 있으면 표시 분기가 처리) |

복원 후 `cmp` 로 원본과 동일함을 확인했다.

## 연속 실행

`AiWorkerAbsentScenarios`(C09, C11a, C11b) 10회 연속, 현재 트리에서 빌드한 `xpe_ai`(`$TEMP/c215_native`, QA-B-195 -4 동작) 로: 모든 회차 `exit=0 passed=3 failed=0 skipped=0`, 회차당 135~144 초(`consecutive_10_runs.txt`). 시간 흔들림: 최소 135 s, 최대 144 s.

## 한계 / 미검증

- 10회 모두 같은 순서(클래스 안 시험 순서)로 돌았다. 순서를 뒤집은 실행은 하지 않았다 — 순서 의존이 없다는 근거는 각 시나리오가 시작 상태를 스스로 만들고 확인한다는 구조와 `C11b(2)` 가 더러운 상태에서 시작해도 통과한 관측뿐이다.
- 첫 실행(초록 전)에서 `Unknown` 정의가 틀려 두 시나리오가 실패했고 그것을 고친 뒤의 결과만 위 표에 있다.
- CI 에서의 결과는 아직 없다. 로컬 모듈은 현재 트리에서 빌드한 것이고 CI 가 만든 DLL 이 아니다.
- C10 의 마지막 정리 `RestoreAiSession(window, "C10", output)` 은 그대로 둔다(모듈이 다시 세게 되면 필요하다).
