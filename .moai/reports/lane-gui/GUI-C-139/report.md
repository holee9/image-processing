# GUI-C-139 (#206) — "구별이 안 된다" 를 먼저 잰다

상태: **§1 전제 확인 완료, §2 판정 기준 확정. 측정값은 아직 없다.**

이 커밋에는 **측정값이 들어 있지 않다.** 카드 §6 이 "판정 기준을 측정값보다 먼저" 를 요구하므로,
기준을 먼저 적어 커밋하고 그다음 커밋에서 측정한다. **커밋 순서가 그 증거다** — 기준을 측정
뒤에 고쳤는지 나중에 확인할 수 있어야 한다.

## 1. 전제 확인 — 3번이 거짓이다

| # | 전제 | 확인한 것 | 아직 참인가 |
|---|---|---|---|
| 1 | 심각도가 **글자**뿐이고 색·아이콘·필터가 없다 | `AnalysisPanel.xaml:513-517` 의 `DataTemplate` 은 `{Binding}` 을 그리는 `TextBlock` 하나뿐이고 `Foreground="#b0b6c0"` 가 **고정**이다. 심각도에 따라 달라지는 것이 없다 | **참** |
| 2 | 알림이 일반 로그와 **같은 목록**에 섞인다 | `RaiseAlert`(`MainWindowViewModel.cs:1971`)가 `Alerts.Insert(0, alert)` 와 `Log($"ALERT {sev} {code}: {msg}")` 를 둘 다 한다. 후자가 `Logs` — `LogListBox` 가 그리는 그 목록이다 | **참, 그리고 더 강하다** (아래) |
| 3 | `C-123` 이 그 `DataTemplate` 을 **의도적으로** 안 건드렸다 | **거짓** (아래) | **거짓** |

### 전제 2 는 생각보다 강하다 — 로그 목록이 유일한 표면이다

`Alerts` 컬렉션을 **그리는 XAML 이 없다.** gui 의 `*.xaml` 전체에서 `ItemsSource="{Binding Alerts…`
는 **0건**이다. `#165`(GUI-C-65)가 Alerts Panel 을 없앤 결과다 — `MainWindow.xaml:161` 에 그
경위가 적혀 있고, 남은 것은 `Clear Alerts` 명령(메뉴·버튼)뿐이다.

부재 주장이라 대조군을 짝지었다. 같은 검색이 잡은 **존재하는** 바인딩 4개:
`BodyPartOptions`, `Logs`, `Studies`, `VoiLutModeOptions`. 검색은 XAML 을 읽고 있다.

따라서 **알림이 화면에 나타나는 곳은 로그 목록 하나**다. "같은 목록에 섞인다" 가 아니라 "섞인
목록이 유일한 표면이다" — `#206` 의 비용 계산에 들어가는 것은 이쪽이다.

### 전제 3 — 결정이 기록에 없다

카드는 *"왜 그대로 뒀는지가 이 카드의 비용에 들어간다"* 고 했다. 답은 **아무도 결정하지 않았다**다.

| 확인 | 관측 |
|---|---|
| 템플릿을 쓴 커밋 | `54a3ae7` (2026-05-09) — `feat(workbench): evaluation workbench UI 전체 구현 (slice 1-12) (#78)` |
| C-123 의 커밋 | `2849903` — 같은 파일을 만졌으나(16줄 추가) `DataTemplate`·`Foreground="#b0b6c0"` 에 닿은 줄 **0건** |
| C-123 보고서 | 제목이 *"아무것도 안 고르고 Copy 를 눌렀을 때"*. `DataTemplate` 언급 0회. `로그 목록` 은 1회 나오는데 **Copy 버튼의 발견 가능성** 논거일 뿐이다 |

즉 템플릿은 심각도 개념이 지금 형태로 생기기 **전에** 쓰인 것이고, C-123 의 범위는 Copy 버튼이었다.
**결정의 부재를 결정으로 읽으면 안 된다** — "이미 검토해서 그대로 둔 것" 이라는 비용 논거는 쓸 수 없다.

## 2. 판정 기준 — **측정 전에 적는다**

카드 제안은 *"알림 N건이 섞인 로그에서 특정 알림을 찾는 데 몇 줄을 훑어야 하는가"* 다. 그 방향을
쓰되, **문턱을 내 직관이 아니라 UI 에서 가져온다.**

### 왜 비율이 기준이 아닌가

`GUI-C-132` 의 `44줄 중 6줄`(13.6%)은 **찾는 비용을 말해 주지 않는다.** 같은 13.6% 라도 알림 6건이
맨 위에 붙어 있으면 한눈에 보이고, 44줄에 고르게 퍼져 있으면 전부 읽어야 한다. 비율은 **위치를
버린 통계**이고, 위치를 버린 통계는 배치를 보지 못한다.

### 기준 — 한 화면에 들어오는가

문턱은 **로그 목록이 한 번에 보여 주는 줄 수**다. 한 페이지 안이면 읽는 사람은 한 화면을 훑어
찾고, 페이지를 넘어가면 **스크롤하며 기억해야 하는** 질적으로 다른 작업이 된다. 이 값은
**측정한다** — `MaxHeight="600"`, `FontSize="11"` 에서 추정하지 않는다.

| 지표 | 정의 | 왜 |
|---|---|---|
| **C1 — 페이지 크기** | 로그 목록이 스크롤 없이 보여 주는 줄 수 (실측) | 문턱의 출처 |
| **C2 — 최신 알림까지 깊이** | 목록 맨 위에서 첫 `ALERT` 줄까지의 줄 수 | "알림이 있나?" 작업의 비용 |
| **C3 — 전수 확인 깊이** | 맨 위에서 **가장 오래된** `ALERT` 줄까지의 줄 수 | "알림을 다 봤나?" 작업의 비용 — 이쪽이 실제 부담이다 |
| **C4 — 비알림 최대 연속** | 알림 사이에 끼인 비알림 줄의 최대 연속 길이 | 눈이 건너야 하는 구간 |
| (참고) 비율 | 알림 줄 / 전체 줄 | **기준이 아니다.** C-132 와 비교하기 위한 문맥 |

### 판정 규칙 (측정 전 확정)

- **설계로 본다**: 모든 조건에서 **C3 ≤ C1** 이고, 실행이 길어져도 C3 가 **C1 안에 머문다**
  → 찾는 비용이 한 화면으로 **유계**다. 색·아이콘이 없어도 작업이 성립한다.
- **결함으로 본다**: 어느 현실적 조건에서 **C3 > C1** 이거나, C3 가 실행 길이에 따라 **계속 자란다**
  → 비용이 사용량에 비례해 커진다. 시각 채널 없이는 "알림을 다 봤나" 를 답할 수 없다.
- **판정 불가**: 조건을 한 개만 재게 되는 경우. 표본 하나로는 어느 쪽도 주장하지 않는다
  (`C-132` 의 44/6 이 지금 그 상태다).

유계인지 자라는지를 보는 것이 핵심이라, **절대 문턱 하나로 자르지 않는다.** "10줄" 같은 숫자를
내가 정하면 그 숫자가 판정을 만든다 — C-138 에서 모델 문턱이 정당한 보정을 터뜨렸던 것과 같은
형태다.

### 재는 조건 (최소 3개)

| 조건 | 왜 |
|---|---|
| 알림이 **드문** 실행 | 정상 경로. C-132 가 이쪽 표본이다 |
| 알림이 **잦은** 실행 — 프레임당 1건 | `#199`: 이 호스트는 매 실행 종료 함수를 불러 억제가 걸리지 않는다. **실재하는 경로**다 |
| 알림 **0건** 실행 | 대조군. 0건에서 C2·C3 가 정의되지 않아야 하고, 그것이 측정이 도구를 타고 있다는 확인이 된다 |

### 이 기준이 못 보는 것 (미리 적는다)

- **읽는 사람의 실제 시선**을 재지 않는다. 줄 수는 대리 지표다. 사람이 `ALERT` 토큰을 패턴으로
  인지해 건너뛸 수 있으므로, 실제 비용은 C3 보다 **작을 수 있다** — 이 기준은 상한이다.
- **색·아이콘이 얼마나 개선하는지**는 재지 않는다. 이 카드는 현 상태의 비용만 잰다.
- 스크롤 위치·선택 상태처럼 사용자가 만든 상태는 무시한다.

## 3. 2a 가 만든 새 성질 — 확인 항목

`#201`(a)/GUI-C-136 이후 로그에 **사라질 수 있는 줄**이 생겼다: `Clear Alerts` 가 `_alertLogLines`
에 있는 줄만 `Logs` 에서 제거한다. 이전에는 로그가 **추가만** 되는 목록이었다.

색·아이콘·필터를 넣으면 그 `DataTemplate` 이 **제거될 수 있는 항목**을 그린다. 가상화된 `ListBox`
에서 항목 제거와 템플릿/컨테이너 상태가 엇갈리는 경우가 있는지 확인 항목으로 둔다 —
**지금 문제가 있다는 주장이 아니다.**

확인할 것: `VirtualizingStackPanel` 재활용 모드, 제거 직후의 컨테이너-항목 대응, `Clear Alerts`
직후의 선택 상태(`SelectedLog` 가 사라진 줄을 가리키는 경우).
