# GUI-C-212d — Codex #100 보류 4건 (212c) (#249)

## 결론

| # | 지적 | 처리 | 확인 |
|---|---|---|---|
| 1 높음 | 부모 성공 불변식에 단계별 효과·단계 필드 필수가 빠짐 | 세 단계 모두 `MaxAbsError > 0`(유한)을 요구, 단계 레코드의 필드(`Stage`·`ErrorCode`·`LatencyMs`·`MaxAbsError`·`Passed`)를 JSON 에서 직접 확인(`Stages[1].MaxAbsError` 식 이름으로 보고), 단계가 객체가 아니거나 `Stages` 가 배열이 아니어도 실패 | 시험 + 반증 2건 |
| 2 보통 | 작업 객체 배정 전에 자식이 실행됨 | 자식을 `CREATE_SUSPENDED` 로 만들고 → job 에 배정 → 재개. `Process.Start` 로는 불가해 `CreateProcessW` P/Invoke(표준 핸들 3개만 상속하도록 `PROC_THREAD_ATTRIBUTE_HANDLE_LIST`) | 일시정지 관측 + 배정 직후 job 을 닫으면 자식이 한 번도 안 돎 + 반증 2건 |
| 3 보통 | 자식 출력을 제한 없이 메모리에 읽음 | 스트리밍으로 읽고 결과 줄 64 KiB·표준 출력 합계 1 MiB·표준 오류 256 KiB 상한, 초과 시 자식 종료 + 명시적 실패. 프로토콜 UTF-8 고정(양끝), 잘못된 UTF-8 은 실패 | 시험 + 반증 6건 |
| 4 낮음 | `ByValTStr` 문자 폭 | 구조체 `StructLayout(CharSet=…)` 을 읽어 폭 계산(Ansi 1바이트, Unicode·Auto 2바이트), 네이티브 `char[]` 에는 Ansi 만 허용 | 통제 시험 + 반증 2건 |

최종 빌드: IntegrationTests **817/817** 통과. 레거시 E2E **9/9**(실제 exe 로 오라클을 돌리는 격리 시나리오 포함) — 아래 "관측된 불안정" 참고. 반증 **12건 전부 빨강**(`falsification_arms.txt`).

## 1. 단계별 효과

`Validate` 가 단계마다 `MaxAbsError` 가 유한할 뿐 아니라 **0 보다 큰지**를 본다(212b 에서 gain 에 도입한 "효과 없는 보정은 통과 아님"이 부모 경계에서 다시 열려 있었다). 지연이 음수이거나 비유한이어도 실패. `MissingFields` 는 최상위 이름만 보던 것을 `JsonNode` 로 바꿔 단계 객체 안까지 본다 — 단계에서 `MaxAbsError` 가 빠지면 역직렬화가 0 을 채워 "측정 없음"이 "효과 0"으로만 읽히던 경로가 있었다.

시험(`PreprocessSyntheticOracleProtocolTests`): 기존 17건 불변식 표에 5건 추가(세 단계 각각 효과 0, 음수 효과, 음수 지연), 단계 필드 5종을 하나씩 JSON 에서 삭제(필드 이름이 지적문에 나오는지까지), 단계가 문자열이거나 `Stages` 가 문자열인 경우, 그리고 **수정하지 않은 문서는 통과**하는 대조군.

## 2. 일시정지로 만들고, job 에 넣은 뒤, 재개

`SuspendedChild` 가 pipe 두 쌍과 NUL 표준 입력을 만들고 `CreateProcessW(CREATE_SUSPENDED | CREATE_NO_WINDOW | EXTENDED_STARTUPINFO_PRESENT)` 로 자식을 만든다. 상속 핸들은 `PROC_THREAD_ATTRIBUTE_HANDLE_LIST` 로 표준 핸들 세 개뿐이라 이 프로세스의 다른 핸들이 자식으로 새지 않는다. 그 다음 `AssignProcessToJobObject`, 그 다음 `ResumeThread`. 어느 단계에서든 실패하면 자식을 죽이고 시작 실패로 보고한다. 종료 대기·강제 종료·종료 코드는 프로세스 핸들로 직접 하고, 강제 종료는 job 전체(`TerminateJobObject`)와 프로세스에 건다.

시험(`PreprocessSyntheticOracleHostTests`, 호스트의 시험 이음새 `HostSeams` 로 경계마다 관측):
- 생성 직후와 배정 직후의 자식은 **모든 스레드가 일시정지(Wait/Suspended)**이고, 재개 뒤에는 같은 관측이 "실행 중"이다(관측 도구가 둘을 가른다는 대조).
- **배정 직후 재개 전에 job 을 닫으면** 자식은 한 번도 실행되지 않는다: 자식이 첫 명령으로 쓰는 표지 파일이 생기지 않는다. 대조군: 닫지 않은 같은 자식은 표지를 쓴다.
- 인용 시험: 공백·따옴표·끝 역슬래시·빈 인자·한글 인자가 시스템 자신의 파서(`CommandLineToArgvW`)로 정확히 되읽힌다.
- 시작 도중 훅이 예외를 던지면 자식이 종료되고(PID 조회 실패) "did not start" 로 보고된다.

## 3. 출력 한도 — 값과 근거

실제 오라클 자식을 재 보니(`real_oracle_output_sizes.txt`) **표준 출력 909 바이트(결과 줄 하나 908 바이트), 표준 오류 0 바이트**였다.

| 한도 | 값 | 정상의 몇 배 | 근거 |
|---|---|---|---|
| 결과 줄 | 64 KiB | 약 72배 | 단계가 늘어도 JSON 은 수 KB. 이 줄만 메모리에 모은다 |
| 표준 출력 합계 | 1 MiB | 약 1150배 | 접두사 없는 줄(네이티브 로그)은 모으지 않고 지나가며 세기만 한다 |
| 표준 오류 | 256 KiB | — | 진단 문자열로 보관하는 유일한 텍스트 |

읽기는 8 KiB 버퍼로 바이트를 지나가며, 줄의 앞 19바이트가 접두사와 같을 때만 모은다(그 밖의 줄은 줄바꿈이 올 때까지 버린다). 한도를 넘으면 자식을 종료하고 어느 한도인지 쓴 실패("output too large")를 낸다. 결과 줄은 **UTF-8 예외 던짐 디코더**로 읽고(잘못된 바이트는 실패), 자식 쪽 쓰기도 `CreateWorkerWriter` 로 BOM 없는 UTF-8·LF·줄마다 flush 로 고정했다(콘솔 코드 페이지 무관).

시험:
- 줄바꿈 없는 5 MiB 출력 → 표준 출력 한도. 줄바꿈 없는 32 MiB **결과 줄** → 줄 한도로 멈추고, 그동안 **부모 프로세스 할당 총량 24 MiB 미만**(전부 버퍼링하면 100 MiB 이상). 표준 오류 600 KiB → 표준 오류 한도.
- 같은 출력이 더 큰 한도 안에서는 정상 통과하고 작은 한도에서는 실패(한도가 실제로 판정을 가름).
- 한글이 날 그대로(`\u` 이스케이프 아님) 들어간 결과가 UTF-8 로 정확히 읽힘. 잘못된 UTF-8 은 "result invalid".

## 4. `ByValTStr` 문자 폭

`CsStruct` 에 `CharSet`(속성이 없으면 .NET 기본값 Ansi)을 읽어 넣고, `ByValTStr` 한 글자의 바이트 수를 거기서 정한다. 네이티브 `char[N]` 에는 Ansi 만 허용하고 Unicode·Auto 는 "2-byte characters … the struct needs CharSet.Ansi" 로 지적한다(총 크기 불일치도 함께 나온다). 통제: 명시적 `CharSet.Ansi`와 속성 없음은 둘 다 깨끗, Unicode·Auto 는 각각 지적. 실제 소스는 새 규칙에서도 지적 0건(기존 파서 시험 통과).

## 반증 (`falsification_arms.txt`, 12건 모두 빨강, 바이트 단위 복원)

1a 효과 없는 단계 허용 / 1b 단계 필드 미검사 / 2a 일시정지 없이 생성 / 2b job 에 배정 안 함 / 3a 표준 출력 합계 무제한 / 3b 결과 줄 무제한 / 3c 표준 오류 무제한 / 3d 한도 초과 시 자식을 죽이지 않음 / 3e Latin-1 로 디코딩 / 3f 잘못된 바이트 허용 / 4a 한 글자를 항상 1바이트로 / 4b 구조체 CharSet 을 읽지 않음.

2a(일시정지 없이 생성)는 **1건만** 빨강이다(일시정지 관측 시험). "job 을 닫으면 자식이 안 돎" 시험은 이 변이에서도 통과할 수 있다: 일시정지가 아니어도 배정과 재개 사이 틈이 사실상 0 이라 표지가 쓰이기 전에 종료될 수 있기 때문이다. 즉 그 시험은 **틈이 있을 때 잡는다고** 주장하지 못하고, 일시정지 자체는 관측 시험이 지킨다.

## 관측된 불안정 (고치지 않음, 원인 미확정)

레거시 E2E 를 연달아 돌리던 중 **두 번 `UIA Timeout`**(첫 번째는 R01, 두 번째는 R02)이 났다. 둘 다 앞선 실행이 남긴 `ImageProcTest.exe` 인스턴스가 살아 있거나 직전에 IntegrationTests 가 돈 직후였다. 정리한 상태에서는 4회 연속 9/9(그 이전 첫 실행도 9/9; `e2e_legacy_clean_run.txt` 는 그중 하나, 11 s ~ 25 s). 남은 앱이 있는 상태에서는 `dotnet test` 가 표준 출력 pipe 가 닫히기를 기다려 **5분 이상 멈춘 것처럼 보이는** 현상도 있었다(앱이 테스트 호스트의 출력 핸들을 물고 있음).

- 앱 단독 실행에서는 16초 동안 계속 응답(`Responding=True`)했고, TEMP 를 파일로 깨뜨린 오라클 자식은 0.2 초에 실패 결과를 낸다 — 새 호스트가 UI 를 막는다는 증거는 못 찾았다.
- 그러나 "남은 인스턴스가 원인"이라는 것도 **입증하지 못했다**. 통과 5회·실패 2회의 차이로만 말할 수 있다.

## 한계

- `CreateProcessW` 직접 호출이라 `Process` 객체가 없다. 종료·대기·종료 코드를 핸들로 직접 다루는 코드가 늘었다(시험은 시간 초과·종료 확인·예외 경로를 덮는다).
- 재개 전 단계는 시험 이음새로만 관측한다. 부모가 **실제로 죽는** 시험은 이번에도 만들지 않았다(핸들 닫기로 대신).
- 한도 값은 실측 정상의 70배 이상으로 정한 것이며, 오라클이 더 많은 로그를 쓰게 되면 다시 정해야 한다.
