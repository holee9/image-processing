## 1. 왜 바꿨나 (측정)

옛 구현은 타일마다 **자기** 최소·최대를 눈금으로 쓰고 화소를 자기 타일의 표 하나로만 변환했다. 이웃 타일의 표가 서로 다른 값 눈금을 설명하니 출력이 모든 경계에서 계단졌다. 옛 코드에는 "보간을 일부러 피했다"는 주석과 `@MX:ANCHOR … bilinear` 가 서로 모순되게 같이 있었는데, 새 코드는 `contrast_enhance.cpp` 머리 주석 한 곳에 알고리즘을 적고 모순을 없앴다.
측정 전에 "옛" DLL 이 정말 옛 코드인지 독립 옛 알고리즘 기준과 대조했다(3케이스 ≤1.1e-7, `clahe_ab_out.txt`). QA-B-204 의 "33배" 는 다른 입력의 값이어서 인용하지 않고 이번 입력의 수치(1022배)를 적는다.

## 2. 구현 요점 (`contrast_enhance.cpp`)
- 눈금: 전역 최소·최대로 4096 구간. 타일 표: 그 눈금 위 히스토그램을 `clip × 면적 / 4096`(최소 1)에서 자르고 초과분을 고르게 분배.
- **나머지 분배 결함을 반증이 아니라 측정으로 찾았다.** 처음에는 나누어떨어지지 않는 나머지를 앞쪽 구간에 몰아줬다. 작은 타일(면적 < 4096)에서는 나머지가 초과분 대부분이라, 표가 타일이 눈금 어디에 있느냐에 따라 달라져 AC-04 의 옛 램프가 표준편차 1.02 → 0.0066 으로 붕괴했다. 독립 기준도 같은 가정을 공유해 둘이 일치했으므로 일치만으로는 못 잡았다. 표준(Zuiderveld, OpenCV 의 residualStep)대로 나머지를 일정 간격으로 눈금 전체에 분배하도록 구현·기준 둘 다 고쳤다.
- 보간: 타일 중심(`(시작+끝−1)/2`) 기준, 가장자리 화소는 타일 2개, 모서리는 1개. 화소가 없는 타일(ceil 나눗셈이 만드는 가장자리 타일)은 제외.
- 결과는 별도 버퍼에 만들고 끝에 복사(실패 시 이미지 불변, 기존 계약). 입력 검증·오류 코드는 그대로.

## 3. 시험이 바뀐 곳 (리더가 요청한 목록)
CLAHE 값을 단언하던 시험은 `enhance_basic` 의 두 개뿐이다(clients/gui 의 시험은 `ContrastEnhance` 를 0 을 돌려주는 모의로 대체해 값을 보지 않는다; e2e 파이프라인은 4단계로 호출만 하고 값은 단언하지 않으며 통과).
1. `LowContrastRegion_ContrastImproves`(AC-04): 옛 시험은 이미지 전체가 램프 495..505 인 장면이었고 "중심 표준편차 +20%"를 요구했다 — 타일별 늘리기 덕에만 통과(×1.385). 이미 고르게 펼쳐진 램프는 범위를 유지하는 평형화로 더 얻을 것이 없다(새 ×1.001). AC-04 문구("**저대비 영역**의 지역 대비 +20%")대로 넓은 범위 이미지 속 저대비 영역 장면으로 바꿨다. 옛 램프는 `AlreadyEvenlySpreadImage_IsLeftNearlyAsItIs`(×0.9~1.1)로 남겨 표준 동작을 기록.
2. `ExceptionGuard…KeepsItsImagePropertiesOnEveryTileShape` 의 "타일 안에서는 밝은 입력이 어두운 출력이 되지 않는다": 옛 설계에서만 성립(화소가 자기 타일 표 하나로 변환). 위치마다 보간 가중치가 달라 더는 성립하지 않아 삭제하고 주석으로 사유를 남겼다. 더 강한 `MatchesAnIndependentReference` 로 대체.
3. 새: `ClipLimit_BoundsTheContrastGain`(이득 ×9.6, 18.3, 27.2, 68.7, 무제한 188 — 단조 증가), `SmoothRamp_HasNoStepAtTileBoundaries`, `MatchesAnIndependentReference`(C++ 독립 구현, 9케이스, 최솟값이 0 이 아닌 케이스 포함).
4. `Performance_3072x3072_Within50ms`: 값이 하나뿐인 이미지(즉시 반환 → 9 ms, 아무것도 재지 않음, QA-B-204 E2)를 벤치마크 데이터로 교체.

## 4. 소비처
gui `EnhanceBasicStage`(→ `GuiEnhanceNative`), clients 의 `NativeEnhanceBasicPreviewService`(미리보기), `XpeEnhanceBasicReadinessProbe`(export 존재만 확인), e2e 파이프라인 4단계. 모두 같은 `xpe_contrast_enhance` 를 부르며 시그니처·오류 계약은 불변. **눈에 보이는 변화**: 출력 영상의 국소 대비와 타일 경계 모양(계단 소멸). 문서 쪽(리더 소유): `docs/enhance-basic` 에는 알고리즘 세부를 단정한 문장이 없어 충돌은 못 찾았고, `api-spec.md:965` 의 "CLAHE or similar technique" 에 표준 정의·"입력 범위 유지"·클립 하한 1 을 한 줄 보탤 수 있다(헤더 `enhance_basic_api.h` 에는 적었다).

## 6. Gap / 잔여 위험
Gap
- 속도는 이 개발 머신 한 대, 번갈아 6회다. REQ-ENH-017(50 ms)은 여유 ~11 ms(새 중앙값 39 ms) 이고 CI 공유 러너에서는 재지 않는다(Performance 시험은 CI 제외).
- 실제 X-ray 영상으로는 보지 않았다. 합성 장면(그라디언트·블록·노이즈)과 독립 기준 대조뿐이다. "임상적으로 보기 좋은가"는 판단 밖.
- 독립 기준 구현 둘(파이썬·C++)은 같은 정의(Zuiderveld)에서 썼다. 정의 자체가 맞는지는 OpenCV 의 residualStep·클립 하한 1 규약과 대조한 설명 수준이고 OpenCV 실행 결과와 직접 비교하지는 않았다.
- 클립 한계가 타일 면적이 작을 때 모두 같게 동작한다(`clip × 면적 / 4096 < 1` 이면 하한 1). 256² 이미지 8×8 타일에서 클립 1~5 가 동일. 표준 규약이고 헤더에 적었지만 앱의 기본값(3072², 8×8 → 면적 147k, 하한 아님)에서는 해당 없음.
- 중간 3회 빌드가 변형 소스로 남았다가 복원 후 다시 빌드했다 — 이 보고서의 수치는 복원한 최종 트리(병합 `2e296737` 위)의 재빌드에서 나온 것.

잔여 위험
- 출력 영상이 눈에 띄게 달라진다(계단 소멸, 국소 대비 변화). 하류 단계(USM, GSVG, 디스플레이 LUT)의 임상 튜닝값은 이 변화를 반영하지 않았다.
- 소비처의 기대 영상(gui 시각 회귀 기준 이미지)이 있다면 갱신이 필요할 수 있다 — 존재 여부는 확인하지 못했다.
