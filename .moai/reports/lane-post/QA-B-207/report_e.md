# QA-B-207e — CLAHE 느린 길의 속도 절벽: 화소 단위 오차 필터 (+ Codex #145 의 64비트 정수 경로)

기준: `dev/postprocess` e783531f 위. Refs #251. 증거 접미 `e_`.

## 결과 한 줄
화소 하나(0.0123)가 영상 전체를 15배 느리게 하던 절벽이 사라졌다. 같은 3072² 영상에서 207d 566~724 ms → 207e 51~56 ms(빠른 쌍둥이 45~47 ms). 정수값 영상에 화소 하나(0.001)가 섞인 경계 화소 영상(Codex #145 형)도 (필터만 있던 중간 빌드) 628~744 ms → 73 ms. 정확성 시험은 207d 의 것 전부 그대로 통과.

## 구조 (clahe_bin_internal.h)
영상 하나당 한 번 고르고, 그 안에서 화소마다 필터가 거른다.

| 단계 | 쓰는 곳 | 방식 |
|---|---|---|
| 1 double | A: vmin==0 / B: vmin>0 & S<=41 / C: vmin<0 & S<=41 (207d) | 추정 + 정확한 곱 비교 1회, 영상 전체 증명 |
| 2 필터 | 위에 안 드는 모든 영상 (S>41) | 화소마다 `t^ = fl(fl(v-vmin) * fl(4095/fl(vmax-vmin)))`, 소수부가 경계에서 1e-9 넘게 떨어지면 `floor(t^)` 증명됨 |
| 3a 정수 64비트 | 필터가 못 믿은 화소, 41 < S <= 52 | `X(x)=가수<<(lsb-L)` 정확 int64, `N=4095*D'` 와 `(bin+1)*R'` 정확 uint64, 추정 + 비교 1회 |
| 3b 정수 320비트 | 필터가 못 믿은 화소, S > 52 | 207d 의 정확 경로 |

### 오차 상한 (헤더 주석에 전문)
`D^=D(1+e1)`, `R^=R(1+e2)`, `inv=(4095/R^)(1+e3)`, `t^=D^*inv*(1+e4)`, 모두 |e|<=u=2^-53 → `t^ = t(1+e)`, |e| < 5u. t<=4095 이면 `|t^-t| <= 2.3e-12`. 사라지는 작은 항(Codex #143 의 2^-100)은 뺄셈의 반올림 오차(정확한 차이에 상대적)에 이미 들어 있어 특수 처리 없음. **여유 1e-9 (상한의 440배)**, `static_assert(kFilterMargin >= 100*kFilterAbsErr)`. 소수부가 (1e-9, 1-1e-9) 안이면 t 도 같은 (k,k+1) 안 → `floor(t)=k`. Codex #143 사례: `t^`=1.0 정확히 → 경계 → 정수 경로 (시험으로 확인).

### /fp:fast 와 필터
**필터만 `#pragma float_control(precise, on)` 로 묶었다**(MSVC). 이유: 오차 합이 정확히 반올림되는 연산 네 개를 센 것이라, /fp:fast 가 허용하는 재결합·분배(`v*inv - vmin*inv` 로 풀면 취소가 심함)를 논증으로 배제하기보다 모드를 고정하는 편이 확실하다. 필터는 행 단위 함수라 호출 비용 무시. 단계 1·3 은 정수나 단일 곱/비교라 재배열할 것이 없고(207c 에서 /fp:fast DLL 로 검증) 단계 3 은 정수 연산이다. 실제 `/fp:fast` DLL 로 모든 경로 출력을 Fraction 기준과 비교했다(아래).

### 영상 단위 조건(A/B/C)을 남긴 이유
정수값 영상은 흔하다: 예) CT HU -1024..3071 은 범위가 정확히 4095 라 **모든 화소의 t 가 정수**(경계 위)다. 필터는 이 모든 화소를 "경계 근처" 로 보내므로 영상 단위 증명(1단계)이 없으면 매 화소가 정수 경로를 탄다. 1단계는 그 영상을 필터 없이 처리한다. 없애면 더 단순하지만 정수값 영상이 느려진다 — 남겼다. 3a 도 같은 이유로 둔다.

### 필터와 64비트 경로를 함께 쓰는 이유 (Codex #145 질문)
- 필터만: 연속 분포는 완벽(0 화소가 정수 경로)하나 **경계 화소가 많은 영상**은 모두 320비트로 간다: 정수 HU 범위 4095 + 화소 하나 0.001(S=46) → 628~744 ms (필터만 있던 중간 빌드로 측정).
- 64비트 경로만(필터 없이 S<=52 전체): 연속 분포 영상이 51~56 ms 로 필터(45~47 ms)보다 느리다(화소당 정수 변환·시프트), S>52 연속 영상은 여전히 320비트로 간다(필터 없이는 절벽).
- 둘을 합치면: 연속 → 필터만(빠름), 경계 화소 → 64비트(가능) 또는 320비트. 단순성은 포기했으나 측정으로 정당화됐다.

## 시험 (test_clahe_bin.cpp, 모두 통과)
- 11,100행 Fraction 벡터: 매 행 `exact_bin`(320비트) / `int64_bin`(허용 영역) / `fast_bin`(허용 영역) / `filtered_bin`(항상) / `bin` 이 정확 값과 같음. 대조: 각 경로 행 수 하한.
- Codex 8x8 실제 DLL 64 화소, 실제 DLL 무작위 120건(`e_py_d.txt`) 0 어긋남. 207c·207b 의 훑기도 0.
- 필터 경계: `filter_certifies` 에 경계 안/밖 (0.5e-9 → 불가, 2e-9 → 가능, 정수 → 불가), `filtered_bin` 으로 t=0.5e-9 는 정수 경로, 2e-9 는 필터가 처리, v==vmin·vmax 는 정수 경로 없이 0/4095.
- 3a 경계: 정확 span 52 는 3a, 53 은 아님(`Binner(1, 2^28)` vs `2^29`).
- 점유율(`MeasureTheShareOfPixelsOnTheExactPath`, 3072²): 균일 소수 0.0123..4000 → **0 / 9,437,184 (0 %)**; 화소 하나 0.0123, 최소 30 % 평탄, 음수 최소 → 모두 0 %; 정수 HU + 화소 하나 0.001 → 9,434,870 (99.98 %, 3a 로 처리).

## Gaps
- 실영상 픽스처는 저장소에 없다. (2a)(2b) 는 전처리 코드를 흉내 낸 합성이고, 실제 후처리 입력의 최소·분포는 미관측이다.
- 필터 경계(1e-9)에서 정확히 떨어진 화소는 부동소수점 해상도 때문에 실제 DLL 에서 만들기 어렵다(k=0 쪽만 가능). 경계 안/밖은 순수 술어(`filter_certifies`)와 `t=0.5e-9`/`2e-9` 화소로 확인했고, 임의의 k 에서 경계 거리 1e-9 안의 float 화소는 시험하지 않았다.
- `/fp:fast` 아래에서 단계 3a·1 은 구조상 재배열할 것이 없다고 논증했으나 컴파일러 출력(어셈블리)을 읽지는 않았다. 대신 실제 DLL 시험으로 확인했다.
- CI 에서의 속도는 미관측. 2d 에서는 이 기계의 잡음이 커서 207d 와 207e 의 차이를 구별하지 못한다.

## Residual risk
- 3a 의 `proof_span_bits` 와 단계 1 이 같은 S 를 쓴다: min_lsb 를 모르는 호출(음수 최소 영상의 `min_lsb_exp` 패스)이 틀리면 둘 다 틀린다. `MinLsbExpReadsTheLowestNonzeroPixel` 시험이 있다.
- 최소가 0.0156 미만 양수이고 최대가 2^29·lsb(vmin) 이상인 영상(S>52)에서 경계 화소가 많으면 320비트 경로(화소당 ~60 ns)로 간다. 연속 분포는 필터라 영향 없음.
