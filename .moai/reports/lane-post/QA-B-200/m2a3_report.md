## 1. 보류 1 — 세 mAs 태그가 서로 다를 때의 알림

**규칙.** 읽기 우선순위는 그대로(1153 → 9332 → 1152, 첫 번째 유효한 것). 유효한 값을 모두 mAs 로 환산해 선택값과 비교한다. 두 값이 같다고 볼 허용오차는 각자의 반올림 폭의 합이다:

| 태그 | 표현 | 환산 | 반올림 폭 |
|---|---|---|---|
| (0018,1153) | IS, µAs | ÷ 1000 | ±0.0005 mAs (1 µAs 로 반올림) |
| (0018,9332) | FD | 그대로 | ±0.0001 mAs (이 모듈이 소수 넷째 자리로 썼던 파일) |
| (0018,1152) | IS, mAs | 그대로 | ±0.5 mAs (1 mAs 로 반올림) |

선택값과 다른 유효한 값의 차이가 "두 태그의 반올림 폭의 합 + 1e-9" 를 넘으면 불일치다. 불일치이면 읽기당 WARNING 알림 한 번과 로그 한 줄을 남긴다. 알림 문구(레인 간 계약, 전체 텍스트):

`DICOM exposure attributes disagree: (0018,1153) = 2500 uAs; (0018,9332) = 2.5 mAs; (0018,1152) = 999 mAs; using (0018,1153) = 2.5000 mAs`

유효한 값만 나열하고(없는 태그나 무효한 태그는 이름을 쓰지 않음), 값은 파일에 적힌 그대로(IS 는 정수 문자열, 9332 는 `%.6g`)이다. 하나뿐이거나 유효한 값이 하나뿐이면 비교 대상이 없어 알림이 없다.
**왜 허용오차인가.** 이 모듈이 2.5 mAs 를 쓰면 1152 는 `"3"`, 1153 은 `"2500"` 이다. 허용오차 없이 비교하면 모듈이 쓴 정상 파일이 매번 불일치로 읽힌다. 시험이 그 대조군을 포함한다.
**clients/ 영향.** 이 알림 문구를 매칭하는 코드를 `clients/` 에서 찾지 않았다(M2a 때와 같은 검색 범위: 네이티브 DICOM 알림 텍스트 매칭 없음, 이번 문구에 대한 재검색은 하지 않음 — Gap).
**시험(`DicomExposureTag.ThreeExposureAttributesThatAgree…`).** 모듈이 쓴 2.5 mAs 파일은 알림 0건(대조군), 9332=2.5 와 1152 가 `"3"`·`"2"` 이면 알림 0건(허용오차 안), 1152 `999` 가 1153·9332 와 어긋나면 알림 정확히 1건(WARNING, 세 값과 선택값 문구 포함), 1153 이 없고 9332 12.5 대 1152 80 이면 알림 1건이며 1153 은 이름에 없다, 값이 하나뿐인 파일과 무효한 다른 속성이 있는 파일은 알림 0건.

## 2. 보류 2 — IS 문법과 값 개수

**원인.** 읽기가 `strtod` 의 끝 포인터를 보지 않아 접두사만 맞아도 값으로 받았다(`2500junk`, `7.5`, `0x10`, `1e3`).
**새 규칙.** `parseIntegerString` 이 PS3.5 Table 6.2-1 의 IS 정의 전체를 검사한다(`standards_cited.txt` 6번): 값 전체 길이 12바이트 이하, 앞뒤 공백 허용, 부호 선택, 숫자 하나 이상만, 중간 공백 불가, −2³¹ ≤ n ≤ 2³¹−1. 무효한 1153 은 건너뛰고 9332 → 1152. 9332(FD)는 기존의 유한·비음수 검사 그대로. 음수는 IS 로는 유효하지만 mAs 로는 쓸 수 없어 건너뛴다(기존 규칙).
**시험 중에 드러난 것(수정에 포함).** 세 속성의 VM 은 모두 1 이다. DCMTK 는 `25\00` 같은 다중 값 IS 에서 첫 값 25 를 돌려주므로 문법 검사를 통과했다. 시험이 이를 잡아 값 개수가 1 이 아닌 속성을 무효로 거부하게 했다(1153·9332·1152 모두).
**시험(`…MustMatchTheGrammarCompletelyAndNotJustByItsPrefix`).** 1153 에 `2500junk`·`7.5`·`0x10`·`1e3`·`12 34`·`+`·`-`·13자리·`0000000000007`(13바이트, 범위 안)·`2147483648`·`25\00`(다중 값)·`abc` 를 넣고 1152 `"7"` 이면 7 로 읽힌다(1153 건너뜀). 같은 값들이 1152 에만 있으면 mAs 0. 유효한 철자 `" 2500 "`·`"+2500"`·`"2500"`·`"0"`·`"  100000"` 이 읽힌다.
**한계(동등하게 터지지 않은 팔).** 앞 공백 제거를 끈 팔은 터지지 않았다. DCMTK 의 `findAndGetOFString` 이 IS 의 앞뒤 공백을 읽을 때 이미 제거하기 때문에, 리더 쪽 공백 제거에는 DCMTK 를 통해서는 도달할 입력이 없다(`" 2500 "` 시험이 제거 후에도 통과하는 것으로 관측). 공백 제거는 방어용으로 남겼고 독립적으로 시험되지는 않는다.

## 3. 보류 3 — `xpe_dicom_version`

`dicom_api.h` 에 선언(doxygen: "xpe_dicom 모듈 버전 문자열, 수명은 프로세스, NULL 아님"), `dicom.cpp` 에 `"1.0.0"` 반환(다른 모듈의 `xpe_display_version`·`xpe_enhance_basic_version` 과 같은 시그니처와 형식, 프로젝트 버전 `1.0.0` 과 같음). 헤더 머리말의 "exactly 10" 을 "exactly 11"(버전 함수 + 4개 SWU 의 10개)로 고쳤다.
**시험(`DicomModuleVersion`).** NULL 이 아님, 비어 있지 않음, `major.minor.patch` 뒤에 아무것도 없음, 두 번 호출해 같은 포인터(수명이 프로세스).
**반증.** 빈 문자열 반환, `"v1"` 반환 — 둘 다 터졌다.
**이 커밋 밖에서 바뀌어야 하는 것(레인 소유 밖, 사실로 알림).** `docs/project/api-spec.md` 의 DICOM 절("exports exactly 10 functions", 표의 `xpe_dicom | 10`)과 SPEC-XPE-P1B-DICOM 의 REQ-DICOM-041("All 10 exported functions")은 이제 11 이다 — `docs/`·`.moai/` 는 리더 소유라 건드리지 않았다. `clients/ImageProcTest/Diagnostics/XpeDicomReadinessProbe.cs` 의 필수 심볼 목록은 version 을 요구하지 않으므로 깨지지 않는다(Lane C 소유, 변경 불필요로 판단 — 목록을 읽었고 시험하지는 않음).

## 5. Gap / 잔여 위험

Gap
- 불일치 알림 문구(레인 간 계약)를 `clients/`·`gui/` 가 거르는지 이번에는 다시 검색하지 않았다(M2a 때 DICOM 알림 텍스트를 매칭하는 코드는 없었음).
- 값 개수 검사는 세 mAs 태그에만 적용했다. 다른 IS/DS 읽기(예: kVp, SID)는 같은 DCMTK 첫 값 동작을 갖지만 이 카드의 범위가 아니라 건드리지 않았다. 해당 경로의 동일 결함 여부는 확인하지 않았다.
- 앞 공백 제거의 동작은 DCMTK 를 거치지 않는 입력으로는 시험하지 못했다(§2).
- 엄격한 IOD 검증기로 새 파일을 돌리지는 않았다(M2a2 와 같은 한계).
- 카드 절을 놓친 원인 서술은 추론이다(§0).

잔여 위험
- 다른 시스템이 1153 에 µAs 가 아닌 값을 쓰거나 단위를 틀리면 1153 이 이긴다(가장 정밀하다는 판단). 틀린 단위는 불일치 알림으로만 드러난다.
- 허용오차는 이 모듈이 쓰는 반올림에 맞췄다. 다른 장비가 다르게 반올림하면(예: 내림) 정상 파일에서 불일치 알림이 날 수 있다(알림이고 값은 바뀌지 않음).
