# QA-B-107 게이트 — 가상 그리드 메모리를 요구 안으로 (#180)

커밋 `6aaf8d7`, 미푸시. **출력은 바이트 동일하다.**

## 0. 요구 원문 (카드 §3)

```
### REQ-GSVG-020: Peak Memory
When processing any single frame,
the system shall use no more than 512 MB peak memory.
```
(`.moai/specs/SPEC-XPE-GSVG/spec.md:237-240`. Rationale: Console PC memory constraint)

- 그리드 억제는 **384 MB** 로 한계의 75% 다. 여유 128 MB.
- 가상 그리드는 변경 전 **626 MB** 로 한계를 114 MB 넘었다.

## 1. 주장

### (1) 전 해상도 버퍼 내역 (3072², double 하나 = 75.5 MB)

변경 **전**, 가상 그리드 한 번의 호출에서 살아 있던 것들:

| # | 버퍼 | 크기 | 사는 구간 | 파일 |
|---|---|---|---|---|
| 1 | `original` (uint16) | 18.9 MB | process_impl 시작 ~ 반환 | `src/gsvg.cpp` |
| 2 | `img` (dst 의 double 복사) | 75.5 MB | 가상 그리드 호출 전체 | `src/gsvg.cpp` |
| 3 | `masked` (마스크일 때만) | 75.5 MB | RunVirtualGrid 시작 ~ 반환 | `src/virtual_grid.cpp:685` |
| 4 | `Sf` (업샘플한 산란) | 75.5 MB | 업샘플 ~ 함수 끝 | `:849` |
| 5 | `capF` (LocalSum 일 때만) | 75.5 MB | 같음 | `:850` |
| 6 | `Rf` (업샘플한 Ts/Tp) | 75.5 MB | 업샘플 ~ 함수 끝 | `:861` |
| 7 | `out` (결과) | 75.5 MB | 최종 루프 ~ 반환 | `:866` |
| 8 | 피라미드 `g[0]` (out 복사) | 75.5 MB | PyramidContrast 안 | `:604` |
| 9 | 피라미드 `lap[0]` (g[0] 복사) | 75.5 MB | 같음 | `:611` |
| 10 | 피라미드 `up` / `cur` (0단) | 75.5 MB 씩 | 같음(교대로) | `:609`, `:620` |
| 11 | 축소 격자(Ic·P·T·spr·cap·Sc·Rc) | 각 ~0.6 MB | 반복 구간 | `:731` 이하 |

- 기본 설정(마스크 없음, GlobalSum, 피라미드 6단)에서 동시에 사는 전 해상도 double 은 2·4·6·7·8·9·10 = **7개 ≈ 528 MB**, 여기에 축소 격자·`original`·피라미드 하위 단계가 더해져 측정값 626 MB 와 맞는다.

### (2) 줄인 것 — 세 가지, 모두 값 불변

1. **결과를 제자리에 쓴다**(`out` 제거, 7번).
   - 최종 루프의 각 출력 화소는 자기 입력 화소(`img[i]`)와 같은 인덱스의 `Sf`·`Rf` 만 읽는다. 그래서 호출자 버퍼 `io` 에 바로 써도 값이 같다.
   - **마스크가 있을 때**: 옛 코드는 0 으로 초기화된 새 버퍼를 썼고, 루프가 마스크 밖 화소를 건너뛰어 **0 인 채로 피라미드가 돌았다**. 피라미드는 이웃을 읽으므로 그 0 이 마스크 안 결과에 들어간다. 제자리로 바꾸면 그 자리에 원본이 남아 결과가 달라진다(§2 에서 실제로 4건이 어긋났다).
   - 그래서 마스크일 때는 제외 화소 값을 **압축 배열에 보관하고 0 으로 채운 뒤**, 마지막에 되돌린다. 상태가 옛 코드와 같아져 값이 같다.
2. **`Sf`·`Rf`·`capF` 를 최종 루프 직후 해제한다**(4·5·6번). 피라미드와 수명이 겹치지 않는다.
3. **피라미드에서 복사를 이동으로 바꾼다**(8·9번).
   - `PyramidContrast` 가 입력 벡터를 `std::move` 로 받아 `g[0]` 로 삼는다(끝에서 다시 `img` 로 이동해 돌려준다).
   - `lap[l] = std::move(g[l])`. `g[l]` 은 밴드를 만든 뒤 다시 읽히지 않는다(복원은 `g.back()` 에서 시작한다).

### (3) 측정 (3072², 커밋 차지, 준비 호출 뒤 기준선 대비 최댓값)

| 경로 | 스레드 1 | 자동(4) | 한계 512 MB |
|---|---|---|---|
| 그리드 억제 | 385.0 MB | 383.6 MB | 여유 128 MB |
| 가상 그리드 | **240.5 MB** | **241.9 MB** | 여유 270 MB |
| 가상 그리드(마스크) | 377.4 MB | 354.4 MB | 여유 135 MB |

- 변경 전: 가상 그리드 626.4 / 626.6 MB.
- **마스크 경로는 `masked` 복사(75.5 MB)와 보관 배열이 더 붙어 377 MB 다.** 한계 안이지만 여유가 작다.
- 스레드 1 과 자동의 차이는 1.4 MB 이하다. 병렬화가 메모리를 늘리지 않는다는 QA-B-106 관찰과 같다.

### (4) 반증

- `Sf`/`Rf`/`capF` 해제만 되돌리면: 가상 그리드 241 → **385.9 MB**(스레드 1·자동 모두), 출력 12개는 전부 그대로다.

## 2. 증거

### 출력 동일 (기준 파일 비교)

- 변경 전 코드로 기준 파일 12개를 만들었다(`before/`, BUILD=0): 512²·1024² × 스레드 1·자동 × 세 설정(기본 / 마스크 / 피라미드 없음).
- 변경 후(`after2/`) 12개 전부 일치.
- 첫 시도(`after/`)에서는 **마스크 4건이 어긋났다**. 원인은 위 (2) 1번의 "마스크 밖 0" 이다. 기준 파일 비교가 없었으면 넘어갔을 차이다(기존 gsvg 시험은 이 조합을 잡지 못했다 — 전체 검증은 그 상태에서도 통과했을 것이다).

### 실행 기록

- `_memory_after.log`: 변경 후 측정.
- `_build1.log` 은 **BUILD=1**(제자리 대상을 `img` 로 잡아 const 참조 오류)이라 결과 없이 고쳤다.
- `_verify.log`: ci-post 644 / ci-ai-b20 225 / ci-dicom 194 통과, e2e 28 통과, BUILD 모두 0.
- 임시 시험(`test_tmp_b107_*.cpp`)과 CMake 항목은 커밋 전에 지웠다. 반증 실행이 `modules/gsvg/` 에 남긴 덤프 12개도 지웠다(커밋에는 들어가지 않았다).

## 3. 기준선 귀속

- "변경 전" 626 MB 는 QA-B-106 측정이고, 이번에 같은 방법으로 다시 잰 값(385.9 MB 반증 실행은 해제만 되돌린 상태)과 구분된다.
- "변경 후" 값은 `6aaf8d7` 과 같은 소스의 `build/ci-post` 에서 잰 값이다.
- 측정 방법·기기는 QA-B-106 gate.md §2, QA-B-99 gate.md §1 과 같다.

## 4. 미검증

- 다른 설정(피라미드 단수, 반복 횟수, LocalSum/SmoothFloor 상한)에서의 메모리. LocalSum 은 `capF` 를, SmoothFloor 는 `iMinFull` 을 추가로 잡는다(각 75.5 MB) — 기본값이 아니라 재지 않았다.
- 3072² 보다 큰 영상.
- 속도 영향은 재지 않았다. 제자리 쓰기와 이동은 복사를 줄이므로 느려질 이유가 없지만, 이번 카드에서 시간은 측정하지 않았다.
- 마스크 경로의 압축 보관 배열은 마스크 밖 화소 수에 비례한다. 마스크가 거의 전부를 제외하면 옛 `out` 과 같은 크기가 된다(최악의 경우 이득 없음).
- 억제 경로의 384 MB 내역은 세지 않았다.

## 5. 잔여 위험

- 마스크 경로는 377 MB 로 한계까지 135 MB 남는다. `masked` 복사(75.5 MB)를 없애려면 산란 추정이 마스크를 직접 읽어야 하는데, 값이 바뀌지 않는지 따로 확인해야 한다.
- 제자리 쓰기 때문에 `io` 는 이제 호출 중간에 결과로 덮인다. 실패 경로에서 원본을 되돌리는 것은 `gsvg.cpp` 의 `original` 복사가 담당한다(그 경로는 이번에 바꾸지 않았고 기존 시험이 덮는다).
- "마스크 밖 0 이 피라미드에 들어간다" 는 것은 이제 코드 주석과 이 보고서에만 있다. 이 동작 자체가 옳은지는 별개 문제다(#180 의 마스크 설계 판단).
