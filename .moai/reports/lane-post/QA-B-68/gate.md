## 2. ① meta 없는 경로 — 지금이 아니면 못 쟀다

### 2.1 측정 (`_metaless.log`, 목록 추가 **전**)

```
meta-less .57: open=0 read=-13 pixels=0 0x0
meta-less .70: open=0 read=-13 pixels=0 0x0
```

`open=0` 이다. B-67 이 확인한 `-7` 거절은 **수용 목록을 지나는 경로**의 이야기이고,
이 파일들에서는 성립하지 않는다.

> **정정 (QA-B-70).** 처음에는 이 파일들이 "`DicomReader.cpp:157`(meta-info 가 없을 때)"
> 분기를 지난다고 적었다. **어느 분기를 지났는지는 재지 않았다.** 목록 조회 없이
> Explicit LE 를 기록하는 곳은 두 군데다 — meta 가 NULL 일 때(현재 `:171`)와 meta 는
> 있으나 `TransferSyntaxUID` 가 없을 때(현재 `:192`). DCMTK 의 `getMetaInfo()` 가
> preamble 없는 파일에 NULL 을 돌려주는지는 확인하지 않았다.

### 2.2 화소는 나오지 않는다 — 다만 이유가 중요하다

`read = -13`(`XPE_ERR_DICOM_INVALID`). **조용한 오인 디코드는 일어나지 않는다.**

그러나 막고 있는 것은 **구문 검사가 아니다.** `m_tsUID` 가 Explicit LE 로 기록되므로
native 경로로 떨어지고, 캡슐화된 `PixelData` 를 원시 `uint16` 배열로 읽으려다 실패하는
것으로 **이 카드에서는 코드를 읽어 추론했다.** QA-B-69 가 같은 경로에 캡슐화 파일(화소 0)과
native 파일(화소 1)을 짝지어 넣어 이 추론을 측정으로 확인했다.
**안전하지만 설계가 아니라 우연이다** — 캡슐화 구조가 우연히 native 읽기를 막고 있을 뿐,
"이 구문은 못 읽는다" 고 판단한 결과가 아니다.

대조군 `.70` 도 같다 — 이 경로는 **구문에 무관하게** 동작한다는 뜻이고, 그래서 `.57` 을
목록에 넣어도 이 경로의 동작은 바뀌지 않는다.

## 3. ② 가드는 전송 구문별이다 — 코드에서 확인

```cpp
bool isJPEGLL = (m_tsUID == TS_JPEG_LL);                 // .70 문자열만 비교
...
E_TransferSyntax encKey = EXS_JPEGProcess14SV1;          // .70 키로만 조회
```

**`.57` 은 "압축이니까" 로 아무것도 물려받지 않는다.** 카드의 표현대로 **전자**이고,
따라서 **별도 작업**이다.

### 3.1 한 것

분기 조건에 `.57` 을 명시하고, 캡슐화 표현을 **각자의 키**로 조회하게 했다:

```cpp
bool isJPEGLL = (m_tsUID == TS_JPEG_LL) || (m_tsUID == TS_JPEG_LL_P14);
...
E_TransferSyntax encKey = (m_tsUID == TS_JPEG_LL_P14) ? EXS_JPEGProcess14      // .57
                                                      : EXS_JPEGProcess14SV1;  // .70
```

키를 나눈 것이 중요하다 — `.57` 데이터셋에 `.70` 키를 물으면 **아무것도 못 찾고
#150 크기 가드가 조용히 아무 일도 하지 않는다.** 가드가 "있는데 일하지 않는" 형태가 된다.

**판정 요청**: 카드가 "가드를 적용해야 하는가는 내가 판정한다" 고 했다. 화소가 나오게
하려면 분기 진입이 필수였고, 진입한 이상 가드를 **끄는 쪽이 오히려 명시적 결정**이 되므로
적용해 두었다. 빼야 한다면 되돌리기 쉬운 형태다(조건 하나).

## 4. ③ 목록 추가와 디코드 분기

| 단계 | `open` | `read` | 화소 |
|---|---|---|---|
| 목록 추가 전 (B-67) | **-7** | — | 없음 |
| **목록만** 추가 (분기 미변경) | — | — | **미측정** |
| 목록 + 디코드 분기 | **0** | **0** | **256×256, 원본과 완전 일치(differing=0)** |

> **정정 (QA-B-70, 2026-09-17).** 이 표의 둘째 행은 처음에 `open=0 / read=-3 / 화소 없음`
> 이었고, "`-7` 이 사라졌다 ≠ 읽힌다 가 수치로 나왔다" 는 문장이 뒤따랐다. **둘 다 틀렸다.**
>
> 목록 추가와 디코드 분기 변경은 **하나의 편집으로 함께** 들어갔다. 그 뒤 첫 실행에서
> 나온 `read=-3` 은 **분기가 이미 있는 상태**의 값이고, 원인은 §7 의 `cleanup()` 이었다 —
> 같은 테스트를 단독 실행하면 `read=0` 이었다. 따라서 **"목록만 넣은 상태" 는 한 번도
> 재지 않았다.** 분기 없이 `.57` 이 native 경로로 가서 실패하리라는 것은 코드에서 나온
> 추론이지 측정이 아니다.
>
> 같은 틀린 값이 커밋 `a6a1974` 메시지와 리더에게 보낸 완료 메시지에도 있다. 커밋 메시지는
> 고칠 수 없으므로 이 정정과 #147 코멘트가 기록이다.

화소 단언은 **원본 대조**로 걸었다 — JPEG Lossless 는 무손실이므로 바이트 일치가
가능하고, 그보다 약한 단언은 "에러 없이 돌았다" 에 그친다.

## 5. ④ 저장소가 스스로 비용을 증명했다

목록 추가 후 전체 ctest 에서 **`EverySupportedTransferSyntaxActuallyReads` 가 빨강**이
됐다. 그 테스트는 **수용 목록을 순회하며 각 구문이 실제로 읽힘을 픽스처로 보이라**고
요구한다. 실패 메시지 원문은 **남아 있지 않다** — 이후 실행이 같은 `_verify.log` 를
덮어썼다. `.57` 빌더가 없었다는 것은 테스트 코드
(`whyNot = "this test has no fixture builder for " + uid`)를 읽은 것이고, 빌더를 추가하자
통과했다.

빌더를 추가했다. **목록 한 줄이 최소 세 곳을 부른다** — 목록, 디코드 분기, 픽스처 빌더.
B-67 에서 "비용이 한 줄로 보이는 것이 오히려 위험하다" 고 적은 잔여 위험의 실물이다.

## 6. 테스트 보강 — `UnsupportedTS` 의 과장된 범위

원래 케이스는 **Implicit VR Little Endian**(비압축) 하나만 먹여 **가장 쉬운 입력**에서
목록 검사가 동작한다는 것만 말한다. 이름은 일반적 주장으로 읽힌다.

추가한 것: **JPEG Baseline `.50`** — 압축이고, JPEG 이고, **이 리더가 등록하는 바로 그
코덱으로 디코드 가능**하고, 목록에는 없다. 목록 검사가 언젠가 "JPEG 인가?" 같은 느슨한
것으로 바뀌면 **원래 케이스는 못 보고 이것이 잡는다.** 측정: `open = -7`.

## 7. 내가 만든 결함을 잡았다

B-67 에 쓴 능력 프로브가 `DJDecoderRegistration::cleanup()` 을 불렀다. 리더는
`std::call_once` 로 디코더를 **한 번만** 등록하므로(`DicomReader.cpp:47`), 그 cleanup 이
**프로세스 전체에서 디코더를 영구히 끈다** — once 플래그 때문에 복구되지도 않는다.

그 탓에 진짜 `.57` 파일이 `read = -3` 으로 나왔다. **그대로 읽었으면 "DCMTK 가 `.57` 을
디코드하지 못한다" 고 보고할 뻔했다** — 이미 올바른 증거로 내려진 판정을 반박하는 셈이고,
원인은 제품이 아니라 내 테스트에 있었다.

단독 실행하니 `read=0`, 화소 완전 일치였다. cleanup 을 제거하고 **경위를 파일에 적었다** —
B-61 §3.1 과 같은 형태로, 다음 사람이 같은 함정을 다시 밟지 않도록.

## 10. 미검증 (Gaps)

- **합성 데이터다(#148).** DCMTK 자신의 Process-14 인코딩이고, 실장비 인코더 변형
  (비표준 SOF 배치, 다중 프레임 등)은 보여주지 못한다 — #151 대기.
- **meta 없는 경로를 고치지 않았다.** 측정만 했다. `.57` 지원과 무관하게 그 경로는
  여전히 **구문에 무관하게 Explicit LE 로 간주**하며, 안전이 캡슐화 구조에 의존한다.
  native 로 읽히는 다른 미지원 구문이 있다면 같은 방식으로 막히지 않을 수 있다 —
  **그런 구문이 존재하는지는 재지 않았다.**
- **라벨 불일치 파일이 화소를 낸다** (`.70` 바이트 + `.57` 라벨 → `read=0`). DCMTK 가
  데이터셋의 실제 표현에서 복원하기 때문이다. 이 두 구문 사이에서는 결과가 올바른
  영상이라 결함으로 부르지 않고 `KnownDivergence_` 로 기록했다. #150 가드는 코드상
  라벨(`m_tsUID`)로 조회 키를 고른다 — **라벨이 틀린 파일에서 그 가드가 실제로 무엇을
  조회하고 무엇을 반환하는지는 실행해 보지 않았다.** (정정 QA-B-70: 처음에는 "아무것도
  검사하지 않는다" 고 단정했다.)
- **`.57` 의 #150 가드 동작 자체를 재지 않았다.** 분기에 넣고 키를 맞췄지만, 치수가
  어긋난 `.57` 파일을 만들어 `DICOM_INVALID` 가 나오는지는 확인하지 않았다.
- **`.90`(J2K)에 대한 같은 질문은 하지 않았다** — 카드 범위 밖.

## 11. 잔여 위험 (Residual-risk)

- **`.57` 가드 적용은 내가 내린 판단이다.** 카드가 판정을 유보한 항목이라, 빼야 한다면
  조건 하나를 되돌리면 된다. 그대로 두면 `.70` 과 동일한 보호를 받는다.
- **meta 없는 경로의 안전은 여전히 우연이다.** 구문 검사를 거치지 않는 입구가 남아 있고,
  거기서의 안전은 "캡슐화 데이터를 native 로 못 읽는다" 는 성질에 의존한다.
- **목록이 길어질수록 세 곳을 같이 고쳐야 한다.** 이번에 픽스처 빌더가 잡아 줬지만,
  그 테스트가 없었다면 `.57` 이 읽히지 않는 채로 목록에 앉아 있었을 것이다.
- **라벨을 믿는 구조가 남아 있다.** `m_tsUID` 는 meta 라벨이고, 가드 키 선택이 거기에
  걸려 있다. 라벨과 데이터가 어긋난 파일에서 가드의 동작은 미측정이다.
- 커밋은 push 전까지 미푸시 유일본이다.
