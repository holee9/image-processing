커밋 `4ae7746`, 미푸시.

## 1. 주장

### 빌드 설정 확인 (카드 주의사항)

- `/fp:fast` 는 저장소에서 `modules/enhance_basic/CMakeLists.txt:51` 한 곳뿐이다(`grep -rn "fp:fast" modules/*/CMakeLists.txt CMakeLists.txt cmake/*.cmake`).
- gsvg 는 전역 `/arch:AVX2`(`cmake/Platform.cmake:10`)만 받고 부동소수점은 MSVC 기본(`/fp:precise`)이다.
- 그래서 B-103 의 함정(람다로 감싸면 마지막 자리가 바뀜)은 이 모듈에 해당하지 않는다. 실제로 이번 변경에서 마지막 자리 차이는 나오지 않았다(§2).

### 병렬화한 곳

모두 출력 요소마다 독립이고, 각 출력의 탭 순서·누적 순서는 그대로다.

**`grid_dwt.cpp`**

| 대상 | 분할 |
|---|---|
| `Dwt2` 행 패스 | 행 밴드 |
| `Dwt2` 열 패스(전치본 위) | 열 밴드 |
| `Idwt2` 열 패스, 행 패스 | 열·행 밴드 |
| `Transpose` | 행 밴드(블록 단위 그대로) |
| `LineProfile`(열 축) | **순차 유지**. 행을 가로지르는 누적이라 나누면 덧셈 순서가 바뀐다(B-104 판독) |

**`virtual_grid.cpp`**

| 대상 | 분할 |
|---|---|
| `AddGaussConv` 행 패스·열 패스 | 행/열 밴드 |
| 피라미드 `Resample` 의 행 패스·열 패스 | 행 밴드 |
| 전체 해상도 출력 루프 | 행 밴드. 카운터(`negativePrimary`, 표 범위 초과 화소)는 밴드별로 세어 원자적으로 합산한다(정수라 순서 무관) |
| 피라미드 단계(`Reduce`/`Expand` 반복) | **순차 유지**. 각 단계가 앞 단계 결과에 의존한다 |
| `Mad`(중앙값) | 순차 유지 |

### 진입점 (ABI 추가만)

```
xpe_gsvg_set_max_threads(int32_t) / xpe_gsvg_get_max_threads(void)
```
- 다른 두 모듈과 같은 형태다. 0 = 자동 = `min(4, 논리 프로세서/2)`, 음수는 0.
- 요청값 저장은 `src/thread_config.cpp` 에 두었다. 모듈 시험이 `grid_dwt.cpp`·`virtual_grid.cpp` 를 직접 컴파일하므로(내부 함수를 부른다) 저장소도 시험 바이너리에 링크되어야 한다. 처음에는 `gsvg.cpp` 에 두었다가 링크 오류(LNK2019)로 분리했다.

- 개선 폭은 1.3–1.4 배로, enhance 쪽(2.8–4.7 배)보다 훨씬 작다. 웨이블릿·합성곱 패스가 메모리 대역에 묶여 있어 스레드를 늘려도 8 이후로는 오히려 나빠진다(억제 20스레드 528 ms).
- 두 요구(REQ-GSVG-019 1.0 s, REQ-GSVG-019b 1.0 s) 모두 충족한다. 변경 전에도 충족했다.

### 반증

- 스레드 1: 억제 686 ms(변경 전 713–757 ms 범위), 가상 그리드 627 ms(변경 전 640 ms). 시간이 원래대로 돌아온다.
- 스레드 1 에서의 출력은 기준 파일과 바이트 동일하다(§2).

## 2. 증거

### 출력 동일 (기준 파일 비교)

- 변경 **전** 코드로 기준 파일 6개를 만들었다(`before/`, `_build_before.log` BUILD=0): 억제 4개(512·1024 × 60·103 lpi), 가상 그리드 2개(512²·1024², 제품용 표).
- 변경 후 스레드 1(`after_t1b/`)과 기본 자동(`after_auto/`) 모두 6개 전부 일치.

### 구현 중 잡은 결함

- 첫 빌드 뒤 억제 출력이 크게 어긋났다(512² 에서 262,144 화소 중 259,312 개, 최대 차 4899 DN).
- 스레드 1 에서도 어긋나 병렬 경합이 아니라 로직 오류임을 먼저 갈랐다.
- 원인: `Idwt2` 에서 두 번째 열 합성 뒤 `Transpose(out → hi)` 한 줄을 패치가 빠뜨렸다. 고주파 성분이 0 으로 남았다.
- 기준 파일 비교가 아니었으면 그대로 넘어갔다. 기존 gsvg 시험은 이 결함을 잡지 못했다(전체 검증에서 이 상태로 돌린 적은 없다).

### 스레드 수 독립 (시험으로 고정)

- `GsvgThreads.SuppressionIsBitIdenticalForEveryThreadCount`, `…VirtualGridIsBitIdentical…`: 스레드 1 기준으로 2·3·4·8·자동이 `memcmp` 0. 각 시험에 "처리가 실제로 영상을 바꿨다" 는 대조를 넣었다.
- `GsvgThreads.SetterStoresTheRequest`.
- 영상 384×320 은 쓰는 스레드 수의 배수가 아니다.

- ci-ai-b20: BUILD=0, 225 통과.

## 4. 미검증

- CI 값(푸시 전).
- 제품용 표가 아닌 설정(다른 kVp·격자비·선밀도)에서의 시간.
- 마스크를 넘긴 경로(`xpe_gsvg_process_masked`)의 스레드 수 독립은 시험하지 않았다. 코드상 같은 루프를 지나지만 확인은 안 했다.
- 피라미드를 끈 설정, 반복 횟수가 다른 설정.
- 메모리 사용량(REQ-GSVG-020). 전치본은 B-102 에서 이미 늘렸고 이번에 추가로 늘리지는 않았다.
- 3072² 보다 큰 영상.

## 5. 잔여 위험

- 이득이 작다(1.3–1.4배). 스레드를 늘려도 8 이후 나빠지므로, 자동값 4 가 이 모듈에서는 거의 최적이다. 다른 두 모듈과 합치면 한 프로세스에서 최대 12 스레드가 될 수 있다(gsvg 4 + enhance_basic 4 + enhance_advanced 4).
- `Idwt2` 결함이 보여주듯, 이 파일들은 기준 파일 비교 없이는 리팩터링 결과를 믿을 수 없다.
- 열 축 `LineProfile` 은 순차로 남아 있어 검출 단계(약 30 ms)는 줄지 않았다.
