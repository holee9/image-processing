# QA-B-181b — contrast 타일 크기 계산의 signed overflow (Codex #35 보류)

Refs #233

## 1. 주장

| # | 주장 |
|---|------|
| C1 | `xpe_contrast_enhance` 의 타일 크기 계산이 `INT32_MAX` 근처에서도 정의되지 않은 동작에 걸리지 않는다. |
| C2 | 고친 식은 동작을 바꾸지 않는다(출력이 비트 단위로 같다). |
| C3 | 같은 형태의 올림 나눗셈은 이번 변경 범위에서 하나 더 있었고 같이 고쳤다. |

## 2. 결함

`contrast_enhance.cpp` 의 `tile_w = (w + num_tiles_x - 1) / num_tiles_x` (높이도 같음). 앞선 64비트 창 검사(`w >= 2 * tile_width`)를 통과한 값에서도 `w + num_tiles_x - 1` 이 `INT32_MAX` 를 넘을 수 있다. Codex 의 예 `w = INT32_MAX, tile_width = 2` 는 창 검사를 통과하고, 덧셈이 `int` 를 벗어난다. 정의되지 않은 동작이라 예외 가드로 잡히지 않는다.

같은 함수의 인접 산술도 같은 부류였다:

| 식 | 위험 |
|----|------|
| `x0 = tx * tile_w`, `x0 + tile_w` (높이도) | 너비가 `INT32_MAX` 근처이면 뒤쪽 타일에서 `int` 초과 |
| `ty * num_tiles_x + tx`, `ty_idx * num_tiles_x + tx_idx` | 타일 수의 곱(최대 2^60)이 `int` 를 넘는 구성. 지금은 타일 표 할당이 먼저 실패하므로 닿지 않지만 정의되지 않은 동작 |

## 3. 수정

- 헤더 인라인 `xpe_ceil_div(size, parts)` = `size / parts + (size % parts != 0)` (`enhance_basic_internal.h`). 나눈 뒤에 올리므로 덧셈이 없다.
- 타일 시작·끝은 64비트로 계산한 뒤 영상 가장자리로 잘라 `int` 로 줄인다. 가장자리를 넘는 시작은 가장자리로 잘리며, 이전 산술이 낸 빈 범위와 같은 범위(`x1 = min(x0w + tile_w, w)`)가 된다.
- 타일 표 색인은 `size_t` 산술.

## 4. 증거

### 4.1 동작이 바뀌지 않았다 (C2)

수정 **전** 코드에서 같은 결정적 입력의 출력 해시(FNV-1a)를 먼저 얻어 시험에 고정했고(`before_rewrite_pinned_hashes_run.txt`), 고정값이 수정 전 코드에서 통과하는 것을 확인한 뒤(`ContrastEnhanceOutput…` 1 passed, 같은 빌드) 코드를 고쳤다. 수정 후에도 통과한다.

| 영상 | 타일 | 해시 |
|------|------|------|
| 101×67 (타일 수로 나누어떨어지지 않음) | 8×8 | `0x229DE8749741D30D` |
| 64×64 | 4×4 | `0x8FBE1CD7F07C2A45` |
| 17×9 | 2×2 | `0x8BEBE1B1FBE154F1` |
| 5×8 (마지막 타일이 짧음) | 2×4 | `0xD5831760FDB2011F` |
| 3072×3072 (검출기 한 프레임) | 8×8 | `0x1EDF0E316336B714` |

한계: 해시는 이 기계·이 컴파일러에서 얻은 값이다. 다른 CPU/컴파일러에서 부동소수점 결과가 달라지면(예: 융합 곱셈 덧셈) 이 시험이 깨질 수 있다. 현재 CI 환경에서의 통과는 병합 뒤 확인이 필요하다.

### 4.2 헬퍼 시험과 반증 (C1)

`xpe_ceil_div` 를 영상 없이 직접 시험한다(할당 없음):
- `CeilDivMatchesTheWideReferenceNearIntMax`: `INT32_MAX` 근처의 크기 11개 × 분할 수 9개를, 합이 넘치지 않는 64비트 참조식과 비교. Codex 의 예(`INT32_MAX`, 2 → 1073741824)와 `INT32_MAX`, 1 → `INT32_MAX` 를 명시.
- `CeilDivIsExactAtTheOrdinaryBoundaries`: 9/3, 10/3, 4096/8, 3080/8, 3081/8 등.

반증: 헬퍼를 옛 식 `(size + parts - 1) / parts` 로 되돌림(BUILD=0) → 시험이 빨강. 이 컴파일러의 `/O2` 가 낸 값은 오버플로가 감기는 형태(`-1073741824`, `-2147482`, `-536870911` 등)였다. 정의되지 않은 동작이므로 이 값은 이 도구체인에서 관측한 것이고 보장이 아니다. 기대값은 참조식(64비트)이라 UBSan 없이도 잡힌다. (`arm_old_ceil_div.txt`)

## 5. 같은 형태의 올림 나눗셈 검색 (C3)

범위: `modules/{ai, enhance_basic, enhance_advanced, gsvg}` 의 `src`·`include`. 세 가지 모양을 정규식으로 검색했다.

| 검색 모양 | 일치 | 판정 |
|-----------|------|------|
| A. `(x + y - 1) / y` | 수정 후 0건 (수정 전: `contrast_enhance.cpp` 두 줄) | 해결 |
| B. `ceil` 계열, `(x + (y - 1)) / y` | `edge_enhance.cpp:100`, `noise_reduce.cpp:185` (`std::ceil(2.0f * sigma)`, 시그마 범위 검증 후), `virtual_grid.cpp:423` (`std::ceil(4.0 * sigmaPx)`) | 올림 나눗셈이 아니라 실수 올림 후 `int` 변환. 앞의 둘은 시그마가 검증되어 작은 값. 뒤의 하나는 표 값에 따라 `int` 변환이 범위를 벗어날 수 있다(QA-B-179 에서 코드 읽기로 지적한 `GaussTaps` 부류). **이번에 고치지 않음, 별개 항목** |
| C. `(x + k) / k`, `(x + k) >> n` 의 리터럴 형태 | `virtual_grid.cpp:587` `(p.w + 1) / 2`, `(p.h + 1) / 2` | **같은 형태**: `p.w == INT32_MAX` 이면 정의되지 않은 동작. `p.w / 2 + p.w % 2` 로 같이 고침 (`(w+1)/2 == w/2 + w%2`, w >= 0) |

한계: 위는 소스 텍스트 검색(이름·모양 한 축)이다. 다른 철자(`div_up`, 매크로, 템플릿 도우미)나 뺄셈 형태(`-(-a / b)`)는 검색하지 않았다. 반올림이 아닌 다른 `int` 산술의 오버플로(예: 영상 크기 곱)는 이 카드의 범위가 아니다.

`virtual_grid.cpp:587` 변경은 gsvg 전체 시험(ci-post 안의 gsvg 시험 포함)이 통과했다는 것으로만 뒷받침된다. `p.w == INT32_MAX` 를 직접 시험하지는 않았다(그 크기의 평면은 수 GB 이다).

## 6. Gaps (미검증)

- `xpe_contrast_enhance` 를 `w = INT32_MAX` 로 끝까지 실행한 시험은 없다. 함수는 타일 계산에 앞서 영상 전체의 최소·최대를 읽어야 해서(수십 GB) 시험 크기가 아니다. 따라서 수정은 **헬퍼의 결정적 시험**(경계값)과 **작은 크기의 비트 동일성**, 그리고 코드 읽기로 뒷받침된다.
- 해시 고정 시험의 기계 의존성(4.1 한계).
- 같은 파일의 다른 `int` 산술(`y / tile_h`, `x / tile_w`)은 값이 `h`, `w` 이하라 안전하다고 코드로만 판단했다.
