## 2. 구현 전에 잰 것 — ② 를 무엇으로 판정하나 (`_probe.log`)

② 는 **구문을 모르는 상태**에서 PixelData 캡슐화를 판정해야 한다 — 이 경로에서 믿을 수 없는
것이 바로 구문이기 때문이다. B-71 프로브는 세 신호를 **OR** 로 묶었으므로, 어느 신호가
실제로 일했는지 몰랐다. 나눠서 쟀다:

| 기록한 구문 | 길이 필드 = undefined | `.70` 표현 | `.57` 표현 | 감지 |
|---|---|---|---|---|
| Explicit VR LE | 0 | 0 | 0 | `…1.2.1` |
| Implicit VR LE | 0 | 0 | 0 | `…1.2` |
| Explicit VR BE | 0 | 0 | 0 | `…1.2.2` |
| `.70` | **1** | **0** | **0** | `…1.2.1` |
| `.57` | **1** | **0** | **0** | `…1.2.1` |

**길이 필드 하나로 완전히 갈린다.** 그리고 **구문 키 신호는 캡슐화 파일에서도 0** 이다 —
DCMTK 가 그 파일들을 Explicit LE 로 분류했으므로 JPEG 표현을 만들지 않았다. B-71 의
`encapsulated=1` 은 **전부 길이 필드에서** 나온 것이었다.

**구문 키로 구현했다면 ② 는 아무것도 잡지 못했다.** 게다가 테스트는 그 상황에서도 통과했을
수 있다 — B-71 프로브처럼 OR 로 묶인 판정을 테스트에 썼다면. 나눠서 잰 것이 구현 방향을 정했다.

## 5. 반증 — ①② 를 따로 (`_falsify1.log`, `_falsify2.log`)

| 제거 | BUILD | Implicit/BE | `.70`/`.57` | leaked | FAILED |
|---|---|---|---|---|---|
| ② 의 `return` | **0** | -7 (① 이 잡음) | **open=0 read=-13** (구조로 복귀) | 0 | 표 테스트 1건 |
| ① 의 `return` | **0** | **open=0 화소** (누출 복귀) | -7 (② 가 잡음) | **2** | 표 테스트 + 접두사 뗀 테스트 |

**각 검사가 각자의 케이스를 막는다.** 한쪽을 꺼도 다른 쪽 케이스는 그대로다 — 검사가
중복으로 서로를 가리고 있지 않다는 뜻이다.

### 5.1 첫 ② 반증은 무효였다

`if (false && …)` 로 껐더니 **C4127(상수 조건식)** 이 `/WX` 로 오류가 되어 **`BUILD=1`**
이었고, **낡은 바이너리가 통과를 찍었다.** 그 결과(`.70`·`.57` 이 여전히 `-7`)를 믿었다면
"② 를 꺼도 막힌다 → ② 는 불필요" 로 읽혔을 것이다. 로그의 `===BUILD=` 를 먼저 읽어서
잡았다. 조건 대신 **`return` 만 제거**하는 방식으로 약화해 다시 쟀다(`BUILD=0`).
현재 `_falsify2.log` 는 유효한 두 번째 실행이다.

### 5.2 반증이 드러낸 것 — 다른 테스트의 사각

② 를 껐을 때 `MetaLessEncapsulatedFilesProduceNoPixels`(옛 이름
`…SkipsTheTransferSyntaxCheck`)는 **통과했다.** 그 테스트는 "화소가 안 나온다" 만 단언하므로,
검사가 막든 구조가 막든 구분하지 못한다. **② 의 제거를 볼 수 있는 것은 오류 코드와 위치를
단언하는 표 테스트 하나뿐이다.**

## 7. #168 에 대한 관찰 (카드 §5, 수정 아님)

② 의 신호(PixelData 길이 필드)는 **구문과 무관**하므로, TS 요소가 **있는데 틀린** 파일에도
"PixelData 캡슐화 여부 vs **선언된** 구문의 `usesEncapsulatedFormat()`" 모순을 볼 수 있다.
예: 캡슐화 데이터에 Explicit LE 라벨, 또는 native 데이터에 JPEG 라벨.

**그러나 #168 의 측정 케이스는 이 신호로 갈리지 않는다.** `.70` 바이트 + `.57` 라벨은
**둘 다 캡슐화 구문**이라 캡슐화 여부가 일치한다. 그 경우를 가르려면 비트스트림 수준의
판별(SOF 마커의 예측자 선택값 등)이 필요하다 — 이것은 코드 판독에 의한 관찰이고 측정하지 않았다.

## 9. 미검증 (Gaps)

- **③ 은 실행 시험이 없다.** 도달 입력을 다섯 가지 시도했고 모두 실패했다. 도달 불가능을
  **증명**한 것은 아니다.
- **감지가 정확한 경우의 캡슐화 구문은 재지 않았다.** DCMTK 가 TS 없는 파일에서 JPEG 2000
  (`.90`) 등을 **올바르게** 감지한다면 ② 를 통과하고 `m_tsUID` 에 그 UID 가 기록되어
  readImage 의 해당 분기로 간다 — 이전의 `TS_EXPLICIT_LE` 고정과 다른 동작이다. 측정한 모든
  파일에서 통과 시 감지 UID 는 Explicit LE 였으므로 **측정 범위 안에서는 동작이 같다.**
- **Deflated Explicit VR LE** — 여전히 미측정. 캡슐화가 아닌 압축이므로 ② 의 길이 신호가
  어떻게 나오는지 모른다.
- **길이 필드 신호의 반례를 찾지 않았다.** native PixelData 가 undefined length 로 쓰이는
  경우(표준상 허용되지 않지만 비표준 파일)는 재지 않았다 — 그런 파일은 ② 가 **지원 native**
  도 거절할 수 있다.
- **실장비 파일 없음(#148).**

## 10. 잔여 위험 (Residual-risk)

- **② 는 한 방향 모순만 본다.** "캡슐화인데 native 감지" 만 거절한다. "native 인데 캡슐화
  감지" 는 보지 않는다 — 측정에서 그런 경우는 없었지만, 감지가 그렇게 틀리는 입력이 있다면
  통과한다.
- **표 테스트가 ② 의 유일한 감시자다.** §5.2 대로 다른 테스트는 ② 가 사라져도 통과한다.
  그 테스트가 지워지거나 약해지면 ② 의 회귀는 조용하다.
- **오류 코드가 두 원인을 합친다.** ①(미지원 구문)과 ②(감지 불신)와 ③(meta 없음)이 모두
  `XPE_ERR_UNSUPPORTED_FORMAT` 이다. 호출자는 로그 없이 원인을 가를 수 없다 — REQ-DICOM-005 가
  이 코드를 정하므로 맞췄지만, 진단성은 로그에만 있다.
- 커밋은 push 전까지 미푸시 유일본이다.
