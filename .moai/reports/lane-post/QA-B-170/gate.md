# QA-B-170 (`#130`) — `BONE_SUPPRESS` 를 IPC 로 끝까지. **같은 답을 냅니다**

## 1. 주장

1. **IPC 결과 == in-process 결과.** 같은 모델·같은 입력에서 워커 경유 출력이 `xpe_bone_suppress`
   출력과 원소 단위로 같습니다. 풀 빌드에서 **성공을 필수로** 요구해, "둘 다 같은 코드로 실패"
   가 통과하지 못하게 했습니다. §3.1
2. **모델을 바꾸면 IPC 출력이 바뀌고, 그 값이 독립적으로 맞습니다.** 한 워커를 `models_x2` →
   `models_x3` 로 재-INIT 하면 출력이 `2×` → `3×` 입니다. **in-process 와의 일치가 아니라
   디렉터리 이름에서 유도한 기대값**으로 단언했습니다. §3.2
3. **스텁 구성에서는 다른 답을 냅니다.** 스텁 워커는 에러(`PROCESSING_FAILED`)를 답하고
   출력 버퍼를 안 건드립니다. 같은 시험 묶음의 통과/건너뜀이 두 구성에서 **서로 반대**입니다. §3.3
4. **반증 다섯이 모두 의도한 시험에서 빨개집니다** — 카드가 지목한 *고정값 반환*, 입력 *에코*,
   세션 *캐시 무시*, 스텁의 *capabilities 거짓*, 오류 *코드 매핑 오류*. §4
5. **나머지는 11종이 아니라 5종(번호 10개)입니다.** 카드의 "12종"은 번호 12개이고
   `BONE_SUPPRESS` 가 그중 2개(14/15)를 씁니다. 5종 모두 **in-process 도 스텁**이라 비교할
   참조가 없고, 모델 파일도 저장소에 없습니다. §5
6. 종합: `ci-post` **909 중 908**, `ci-ai` **273/273**. 빨강 1건은 `EdgeEnhance` 20 ms 게이트 —
   **이번엔 미변경 바이너리 대조를 붙였습니다**(20회 중 12회 실패). §6

## 3. 카드 §3 의 세 단언 — 실측

### 3.0 고치기 전 (최종 프로브, 옛 워커)

`QA-B-169` 워커(`BONE_SUPPRESS` → "not handled" 에러)에 **같은 시험 묶음**을 돌렸습니다. 시험을 두 번
조여서 전 측정을 최종 시험으로 **다시** 했습니다(§9).

```
before  ci-post(스텁)  실패 4 / 통과 7 / 건너뜀 3      before  ci-ai(풀)  실패 6 / 통과 7 / 건너뜀 1
  the two paths disagree about whether this succeeds: in-process rc=0, via worker rc=-1
```

응답은 **왔습니다**(`-1`). `QA-B-169` 전에도 응답은 왔습니다(99). **"응답이 왔다"는 성공이 아닙니다.**

### 3.1 IPC == in-process

| | 스텁 | 풀 |
|---|---|---|
| in-process rc / via worker rc | 같음 (`PROCESSING_FAILED`) | `0` / `0` |
| 출력 | 실패 시 **버퍼 무손상**(센티널 유지) | `EXPECT_EQ(ref.out, ipc.out)` — 원소 단위 동일 |

풀에서 `ASSERT_EQ(XPE_OK, …)` 를 먼저 세웠습니다. 없으면 `EXPECT_EQ(ref.rc, ipc.rc)` 는 "둘 다
같은 코드로 실패"로도 초록입니다.

### 3.2 모델을 바꾸면 IPC 출력이 바뀐다

한 워커, 재-INIT: `models_x2` → `models_x3`, 픽셀 `1..9`.

- `EXPECT_NE(a.out, b.out)` — 고정값이면 같음
- **독립 기대값**: `a.out[i] == 2·px[i]`, `b.out[i] == 3·px[i]` — 디렉터리 **이름**에서 유도, 어느 경로도
  안 거침. 일치만으로는 **둘이 같이 틀려도 통과**하고(이 저장소가 여러 번 적은 자기 비교 함정),
  이 값이 그것을 막습니다
- 각각 in-process 결과와도 일치

`DifferentPixelsGiveDifferentIpcOutput` 이 같은 모델·다른 입력(`1..9` vs `50..58`)에서 출력이 다르고
입력의 에코가 아님을 단언합니다.

### 3.3 스텁은 다른 답

```
                                  스텁                        풀
IpcGivesTheSameAnswer…            통과                        통과
ChangingTheModel…                 건너뜀                      통과
DifferentPixels…                  건너뜀                      통과
ANonInferringBuild…               통과                        건너뜀
TheFullBuildIsProvable…           건너뜀 (EXPECT_ONNX=1 없이)   통과 (=1 로 실행, 스텁이면 빨강)
```

스텁 전용 시험은 `rc != XPE_OK` **와** `rc == XPE_ERR_PROCESSING_FAILED`(스텁 `Run()` 이 거절하는 코드)
를 단언합니다. **첫 버전은 `!= OK` 만 단언했고 고치기 전에도 초록이었습니다** — 미구현 메시지의
에러도 `!= OK` 이고 출력을 안 건드리니까요. 조여서 전 측정에서 빨개졌습니다(§9).

**세 수 병기** (`WorkerBoneSuppress.*` + `WorkerProtocolConformance.*`, gtest):

| 구성 | 실행 | 통과 | 건너뜀 | 실패 |
|---|---:|---:|---:|---:|
| 후 / 스텁 (`ci-post`) | 14 | 11 | 3 | 0 |
| 후 / 풀 (`ci-ai`) | 14 | 13 | 1 | 0 |
| 전 / 스텁 | 14 | 7 | 3 | **4** |
| 전 / 풀 | 14 | 7 | 1 | **6** |

## 4. 반증 — 주입은 `grep` 으로 확인(1건) 후 측정, `cmp` 로 복원 확인

풀 빌드에서 재었고(스텁은 `Run` 이 안 성공하므로 무관), C 만 양쪽입니다.

| | 주입 | 빨개진 시험 |
|---|---|---|
| **A** 고정값 | 출력 전부 `7.0f` | `IpcGivesTheSameAnswer…` · `ChangingTheModel…` · `DifferentPixels…` |
| **A2** 에코 | 출력 = 입력 | 같은 셋 |
| **B** 캐시 무시 | `session_dir_ != model_dir_` 제거 | `ChangingTheModel…` · `FailuresCarryTheSameCode…` |
| **C** 능력 거짓 | `capabilities` 항상 1 | **스텁만** `TheInitResponseNames…` 빨강 · 풀 13/13 초록 |
| **D** 코드 오매핑 | 모델 없음 → `CONFIG_INVALID` | `FailuresCarryTheSameCode…` (**양쪽**) |

**A 가 카드가 지목한 반증**("추론 처리를 일부러 고정값 반환으로")이고, 고정값과 에코를 **따로** 잡는 것이
독립 기대값(`2·px`)의 값입니다 — 에코는 in-process 와 다르지만 고정값이 우연히 맞을 수도 있는 입력에서는
`DifferentPixels…` 가 잡습니다. **B 는 세션 캐시**를 겨눕니다: 워커가 한 번 로드한 모델을 디렉터리가 바뀌어도
계속 쓰는 결함은 "한 번만 시험하면" 안 보이고, 재-INIT 시험만 잡습니다. **C 는 구성에 따라 갈립니다.**

## 5. 나머지 — 카드는 "11종" 이라 했습니다. 실제는 **5종(번호 10개)**

`ai_worker_protocol.h` 의 메시지 번호는 18개(생명주기 5 + 추론 8 + 모델관리 4 + 오류 1)입니다. 추론·모델관리
12개는 **요청/응답 쌍 6개**이고 `BONE_SUPPRESS`(14/15)가 한 쌍을 씁니다. 남는 것은 **5종**입니다.

| 메시지 | in-process 는 오늘 | 워커가 처리하려면 **필요한 것** |
|---|---|---|
| `BODYPART_RECOGNIZE` 10/11 | **스텁**: `"UNKNOWN"` + `PROCESSING_FAILED`, 신뢰도 0 | ① **모델 파일** — 저장소의 `.onnx` 는 시험용 스케일 장난감 5개뿐 ② **float 영상 → 라벨 규칙** — 모델이 라벨을 안 줍니다(`QA-B-161` 이 이 함수를 고르지 않은 이유) ③ 응답 스키마는 헤더에 있음 |
| `STITCH_IMAGES` 12/13 | **스텁**: 검증 뒤 즉시 `PROCESSING_FAILED` | ① **여러 영상**을 싣는 이진 레이아웃(지금 규약은 영상 하나) ② 모델 없음 ③ 출력 크기가 입력에 의존 |
| `DL_DENOISE` 16/17 | **스텁**: 검증 뒤 즉시 `PROCESSING_FAILED`, **제자리(in-place)** | ① `XpeImageMetadata`(`bodyPart`·`mAs`)를 와이어로 — 모델 변종 선택에 필요 ② 모델 없음 ③ 제자리 의미를 요청/응답으로 옮기는 규칙 ④ 지연 목표(`REQ-AI-022`) |
| `GET_MODEL_CARD` 20/21 | **스텁**: 고정 JSON(`buildStubModelCard`) | ① 실제 카드 데이터의 **출처** — `model-card.schema` 를 **인용하는 곳은 5곳**(`SPEC-XPE-P3-AI` 의 `spec.md`·`tasks.md`, `docs/project/srs_ai.md`, `ai_api.h`, `ai.cpp`)인데 **그 파일 자체는 없습니다**(`git ls-files 'schemas/*'` 0건, 이름에 model card 가 든 추적 파일은 시험 소스 `test_ai_model_card.cpp` 1건뿐. 범위: 추적 파일 전체) |
| `LIST_MODELS` 22/23 | **대응 C ABI 함수 자체가 없음**(모델 관련 `XPE_API` 는 `xpe_ai_init`·`xpe_ai_get_model_card` 둘뿐) | ① **"로드됨"의 정의** — 워커는 세션 하나를 지연 로드하고 INIT 응답의 `loaded_models` 는 빈 배열 |

**공통**: 5종 모두 **in-process 참조 구현이 없어서** *"같은 답을 내는가"* 를 잴 수 없습니다. `BONE_SUPPRESS`
는 참조가 있는 유일한 종이었다는 카드의 판단이 코드로 확인됩니다. 지금 5종은 **"not handled"** 에러를 답하고,
시험이 그것을 단언합니다(`BODYPART_RECOGNIZE`).

## 8. 미검증 · 잔여 위험

- **영상은 3×3 하나입니다.** 워커 파이프 버퍼를 512 → `XPE_AI_PIPE_BUFFER_SIZE`(64 KB)로 키웠고, 실제
  크기(3072×3072×4 ≈ 37.7 MB)가 페이로드 상한(64 MB) 안이라는 것까지만 계산했습니다. **큰 페이로드의
  왕복 시간과 두 번의 `WriteFile`↔바이트 모드 읽기 맞물림은 재지 않았습니다**
- **브리지 수신은 시간 제한이 없습니다**(`REQ-AI-092` 는 부분 구현 — 이 파일의 머리말). 워커가 멈추면
  호출자가 무한 대기합니다. 시험의 30초 워치독은 **시험 한정**이고 제품 방어가 아닙니다 — `QA-B-171` 전에
  다뤄야 합니다
- **모델은 스케일 장난감**입니다. `REQ-AI-050/051`(U-Net, 결절 민감도 +16.8%)은 여전히 **충족되지
  않았고** 이 카드도 그것을 시험하지 않았습니다. 이 카드가 세운 것은 *경로*입니다
- **모델 입력이 평탄한 `[N]` 벡터**입니다(`QA-B-161` 과 같음). 실제 U-Net 은 2-D 텐서를 기대할 것이라
  워커가 폭·높이를 세션에 전달하는 방식은 그때 다시 정해야 합니다
- **`model_dir` 은 슬래시 경로로만 시험했습니다.** `JsonString` 은 백슬래시 이스케이프를 되돌리게 썼지만
  `C:\\data\\models\\` 형태는 시험하지 않았습니다
- **`JsonString`/`JsonUInt` 는 최소 구현**입니다. 키 이름이 문자열 값 안에 나오면 오인할 수 있고(주석에
  적음), 이 파이프가 받는 단일 로컬 클라이언트와 문서화된 필드만이라는 전제 위에 있습니다
- **제품 호출자는 여전히 0**입니다. `xpe_ai_ipc_bridge_bone_suppress` 는 시험만 부릅니다. DLL 안에
  컴파일되지만 **내보내기(export)되는지는 확인하지 않았습니다**
- **`SHUTDOWN_ACK` 는 추가하지 않았습니다**(카드 §5). 정상 종료와 죽음이 파이프 닫힘으로 구별되지 않는
  문제는 `QA-B-171` 에서 측정으로 보일 몫입니다
- `WorkerStatus.FAILED(2)` ↔ 헤더 `ERROR(3)` 는 여전히 남아 있습니다(`QA-B-171` 로 넘김)
- Windows 전용 시험입니다(프로세스·네임드 파이프)

## 9. 과정에서 고친 제 실수 셋

- **시험 두 개가 고치기 전에도 초록이었습니다**(§3.3 스텁 시험, `AWrongPixelCount…` 의 `error_code:-1`).
  둘 다 "미구현 메시지의 에러"와 구별이 안 됐습니다. 고치기 전 측정이 잡았고 — 측정하지 않았다면
  "시험이 통과한다"는 증거로 남았을 것입니다. 조인 뒤 **전 측정을 최종 시험으로 다시** 했습니다
- **heredoc 안의 따옴표가 셸 파서를 깨뜨렸습니다**(주입 도구가 안 돌았고 아무것도 적용되지 않음).
  이전에 기록해 둔 함정이었고, 파일로 만든 뒤 실행하거나 Edit 도구로 바꿨습니다
- 카드의 "12종/11종"을 그대로 받지 않고 헤더에서 세었습니다(§5) — **번호 12개, 요청 종류 6개, 남은 것 5개**
