# QA-B-198 M1 — AI 워커 최소 권한(REQ-AI-093) 설계 메모

카드: QA-B-198 · 관련: #130 · 코드 변경 없음(제품 소스 무변경). 측정은 시험 전용 도구(`probe`, `launch`)로 했고 소스와 원본 출력을 이 폴더에 둔다.

## 1. 요구 문구와 읽는 방법

`.moai/specs/SPEC-XPE-P3-AI/spec.md:325`:

> **REQ-AI-093** (Ubiquitous): AI inference process shall run with minimum privilege (no network, no file write except sidecar scratch).

두 가지 의무다: ① 네트워크 없음, ② 파일 쓰기는 "sidecar scratch" 에만. 문구에서 정해지지 않은 것이 둘 있다.

- **"sidecar scratch" 는 정의가 없다.** `scratch` 는 SPEC·docs/project 의 AI 문서 전체에서 이 줄에만 나온다(검색 범위: SPEC 폴더, `docs/project/*ai*.md`, `api-spec.md`). 사이드카는 SPEC 에서 추론 결과 메타데이터(REQ-AI-004, 062, 070, 072)를 가리키므로 "추론 중 사이드카 JSON 을 쓰는 임시 위치"로 읽는 것이 자연스럽다. **지금 워커는 파일을 전혀 쓰지 않는다**(§2). 따라서 지금은 "쓰기 없음"이 가장 엄격한 충족이고, 스크래치 디렉터리는 REQ-AI-070(XAI 사이드카)을 구현할 때 필요해진다.
- "minimum privilege" 의 범위(파일 읽기, 자식 프로세스, 레지스트리)는 정해져 있지 않다. 이 메모는 그 셋도 측정했고, 요구 밖이라는 표시를 붙였다.

## 2. 지금 워커가 실제로 가진 권한 (측정)

방법: 감독자(`ai_worker_supervisor.cpp` `StartLocked`)와 같은 방식으로 프로세스를 띄운다(기본 보안 속성, 핸들 상속 없음, 일시 중단 상태로 생성 → `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` 하나뿐인 작업 객체에 넣고 재개). 그 프로세스가 자기 권한을 스스로 시도해 보고한다(`probe.cpp.txt`). 원본: `raw/base_probe.txt`, 한눈에 비교: `matrix.txt`.

**워커가 실제로 쓰는 것**: 제품 소스에 파일을 **쓰는** 코드는 없다(`modules/ai/src` 에서 `ofstream`·`fopen`·`basic_file_sink`·`rotating`·`create_directories`·`CreateFile`·`WriteFile` 검색, 파이프 입출력의 `WriteFile` 과 `ai_log.h` 의 표준 출력 로그뿐이고 모델·사이드카·서명은 읽기만 한다. `enable_profiling` 은 받되 무시). 이것을 **실행으로도 확인했다**: 아래 변형에서 파일·레지스트리 쓰기가 전부 막힌 채로 진짜 워커가 초기화, 뼈 억제 요청, 부위 인식 요청에 답한다(§3). 장난감 모델과 이 세 요청에 한한 확인이다.

**부수 발견(이번 카드의 범위 밖)**: 워커의 파이프가 기본 보안으로 만들어져 Everyone·Anonymous 가 읽을 수 있다. 인스턴스가 하나뿐이라서, 감독자보다 먼저 연결한 다른 프로세스가 그 하나를 차지할 수 있다. 쓰기 권한(`FW`)은 없지만 응답 흐름을 읽거나 감독자의 연결을 막을 수 있는 자리다. DACL 을 명시하는 작은 별도 수정으로 닫을 수 있다(아래 §5 D5).

### 3.1 M3 쓰기 제한 토큰이 취약한 이유 (측정)

- 제한 SID 를 `RESTRICTED`(S-1-5-12) 하나로 하면 **프로세스가 시작도 못 한다**(`STATUS_DLL_INIT_FAILED`, `raw/wr_restricting_RESTRICTED_only_*`). 로그온 SID 를 더해도(`raw/wr2_*`) 진짜 워커는 같은 오류로 죽는다(프로브는 콘솔 없이 띄우면 동작).
- 원인을 DLL 하나씩 올려 보아 `bcrypt.dll`(워커의 서명 검증이 쓰는 CNG)의 초기화가 이 토큰에서 실패함을 확인했다(`raw/wr2_dll_load_test.txt`: `bcrypt.dll=FAILED (error 1114)`, 나머지는 로드됨). 제한 SID 에 `Everyone`(S-1-1-0)을 더하면 로드되고(Users·Authenticated Users 는 안 됨) 진짜 워커가 정상 동작하며 쓰기는 여전히 스크래치 외 전부 막힌다(`raw/wr3_*`). 이때 콘솔 없이 띄워야 한다(`CREATE_NO_WINDOW` → `DETACHED_PROCESS`).
- 즉 동작하는 구성은 "{RESTRICTED, 로그온 SID, Everyone} + 콘솔 없음" 이고 **경험적으로 찾은 것**이다. ORT 나 CNG 가 갱신되어 다른 객체에 쓰기 접근이 필요해지면 조용히 깨진다. M4 와 쓰기 결과가 같으면서 이 약점이 있어 M4 를 먼저 권한다.

### 3.2 M5 AppContainer 가 워커 코드를 바꾸지 않고 되는 방법 (측정)

- 지금 방식 그대로(워커가 전역 이름공간에 파이프를 만든다)는 **파이프 생성 자체가 거부된다**(`CreateNamedPipe` 오류 5, 워커 종료 코드 1, `raw/ac_global_pipe_*`).
- 워커에 **`\\.\pipe\LOCAL\<이름>`** 을 인자로 주면 컨테이너 자기 이름공간에 만들어지고, 호스트가 **`\\.\pipe\Sessions\<세션>\AppContainerNamedObjects\<컨테이너 SID>\<이름>`** 으로 연결해 초기화·뼈 억제·부위 인식이 모두 된다(`raw/aclocal_*`). **워커의 소스 변경은 필요 없고** 감독자가 파이프 이름과 연결 경로를 만드는 곳이 바뀐다.
- 컨테이너는 사용자 프로필 안의 문서 폴더를 읽지도 못한다(`read.list_user_documents` 거부).

### 3.3 M5 AppContainer 의 배포 비용 (측정)

- 컨테이너가 실행 파일, DLL, 모델을 읽으려면 그 폴더에 `ALL APPLICATION PACKAGES`(S-1-15-2-1) 읽기·실행 ACE 가 있어야 한다. `Program Files` 는 기본으로 있다고 알려져 있지만 **이 저장소의 빌드 폴더와 사용자 폴더에는 없다**. 이 시험은 임시 폴더에 복사본을 만들고 ACE 를 직접 부여해서 돌렸다(`launch.sandbox` 줄).
- ACE 가 없을 때: 모델 폴더에 없으면 뼈 억제 요청이 **`-9`(모델 사용 불가)** 로 끝난다(`raw/aclocal_no_grant_on_models_worker.txt`) — 설정 실수가 "모델이 없다"로 보여 조용히 폴백된다. 실행 파일 폴더에 부여를 건너뛴 경우는 임시 폴더가 상속한 ACL 덕에 프로세스가 시작했고 요청이 `-3` 으로 실패했다(`raw/aclocal_no_grant_on_bin_worker.txt`, 원인은 가르지 않았다).
- AppContainer 프로필(`CreateAppContainerProfile`)은 사용자별로 지속되는 항목이다. 프로필 이름과 정리 시점이 설계 항목이 된다.
- 이 저장소의 시험 하네스(`ctest` 가 빌드 폴더의 워커를 쓴다)와 개발자 체크아웃은 ACL 이 없는 위치에 있다. M5 를 켜면 시험이 그 폴더에 ACL 을 부여하거나 복사해서 돌려야 하고, 개발용으로 끄는 스위치가 필요하다.

## 4. 권고 — 가장 작은 단계와 REQ 충족표

| 단계 | 내용 | ① 네트워크 없음 | ② 쓰기는 스크래치만 | 변경 범위 | 배포 의존 |
|---|---|---|---|---|---|
| **S1(권고, 먼저)** | M4 낮은 무결성 토큰 + M1 작업 객체 강화(자식 프로세스 금지) | **충족 못 함** | **충족**(파일·레지스트리. 지금 워커는 쓰지 않으므로 스크래치 없이 충족. 스크래치가 필요해지면 호스트가 만들고 낮은 무결성 표시를 붙인다) | 감독자 `StartLocked` 한 함수(토큰 복제·무결성 낮춤·`CreateProcessAsUser`·속성 목록·작업 객체 제한). 워커 무변경 | 없음 |
| **S2(그 뒤)** | M5 AppContainer + M1 | **충족**(루프백 차단 측정. 외부 차단은 문서화된 동작을 근거로 추정, §7) | **충족** | S1 의 함수에 컨테이너 프로필·능력·이름공간 파이프·ACL 부여 추가, 파이프 이름·연결 경로 변경, 시험 하네스 ACL | 설치 시 ACL 부여 필요 |

S1 은 ②를 채우고 ①을 채우지 못한다는 것이 그대로의 결과다. ①까지 채우는 단일 수단은 측정한 범위에서 AppContainer(S2)뿐이다(방화벽 규칙은 설치 권한이 필요해 범위 밖일 수 있고 시험하지 않았다). S1 을 먼저 하는 이유: 배포 위치와 설치 방식이 정해지지 않아도 되고, 쓰기·레지스트리·자식 프로세스 세 가지를 막으며, 측정에서 진짜 워커의 세 요청이 모두 통과했다. S2 는 배포 결정이 필요하다.

## 5. 리더가 정할 것

- **D1** 출시에 ①(네트워크 없음)이 필수인가. 필수면 S2 가 필요하고, 아니면 S1 로 ②를 닫고 ① 을 알려진 미충족으로 남길 수 있다.
- **D2** 워커 실행 파일과 모델의 배포 위치(`Program Files` 기본 ACL 인가, 사용자 폴더인가, 설치 프로그램이 ACL 을 부여하는가). S2 의 가능 여부를 정한다.
- **D3** "sidecar scratch" 정의: 지금은 쓰기 없음으로 충족하고, REQ-AI-070 구현 때 디렉터리를 정한다(호스트가 만들어 워커에 넘기는 안을 권한다).
- **D4** 개발·시험에서 제한을 끄는 스위치 여부와 위치(설정 키 `sandbox`?), 그리고 시험이 단언할 것(제한이 켜진 워커가 세 요청에 답한다 / 쓰기 시도가 막힌다 / 연결이 막힌다).
- **D5** 파이프 DACL 명시(부수 발견)를 별도 카드로 할지. 워커가 `SECURITY_ATTRIBUTES` 로 사용자와 SYSTEM 만 허용하면 닫힌다. S2 의 컨테이너 파이프는 컨테이너 이름공간이라 별개다.

## 6. gui 영향

- gui 는 `{"use_worker": true}` 로 모듈을 초기화한다(`gui/ImageProcTest/Services/Native/GuiAiRunner.cs:101`). 워커 경로는 모듈 DLL 옆의 `xpe_ai_worker.exe`(`ai.cpp` `workerExePath`)이고 gui 는 워커를 직접 다루지 않는다. 제한은 감독자 안에서 걸리므로 **S1 은 gui 코드 변경이 없다**. S2 도 C ABI 와 gui 호출은 그대로이고, 바뀌는 것은 설치·ACL 이다.
- 워커 실행 파일이 없을 때의 동작은 그대로 유지된다: `-9` 로 세고 세 번이면 꺼진다(QA-B-194b `test_ai_worker_exe_missing.cpp`). 카드가 말한 "C09 의 워커 exe 부재 방식"은 찾지 못했다: `GUI-C-09` 보고서는 `XpeImageBuffer.dataSize` 를 다루고 워커를 언급하지 않는다(같은 검색에서 파일이 읽힘을 확인). 워커 exe 가 CI 산출물에 반드시 들어 있는지 검사하는 곳은 `.github/workflows/ci.yml` 의 GUI-C-184 주석 단락이다. 어느 카드를 말한 것인지 알려 주면 대조한다.
- S2 에서 gui E2E 가 빌드 폴더의 DLL 을 쓰는 방식(`GuiNativeLibraryResolver`)과 충돌하는지는 측정하지 않았다. 빌드 폴더에는 컨테이너가 읽을 ACL 이 없으므로 E2E 환경 준비가 달라질 수 있다.

## 증거 (Evidence)

- `probe.cpp.txt`, `launch.cpp.txt`, `dllload.cpp.txt` — 측정 도구 소스(시험 전용, 출하 코드 아님). 빌드·실행 스크립트 `*.bat.txt`, `runall.py.txt`. 빌드는 이 저장소의 `ai_ipc_bridge.cpp` 를 그대로 컴파일해 넣었다.
- `matrix.txt` — 일곱 변형(기준, 작업 객체 강화, 제한 토큰, 쓰기 제한 토큰, 낮은 무결성, AppContainer, AppContainer+작업 객체)의 프로브 결과를 한 표로.
- `raw/*.txt` — 모든 실행의 원본 출력. 파일 이름이 변형을 말한다. `wr_*`(제한 SID 가 RESTRICTED 하나, 시작 실패), `wr2_*`(+로그온 SID, 콘솔 없음), `wr3_*`(+Everyone, 동작), `*_nogrant_*`(ACL 부여 없음).
- `host_token.txt`(호스트 토큰), `worker_dep_exe.txt`·`worker_dep_ort.txt`(워커와 ORT 의 정적 의존 DLL).
- 반증이 아니라 **측정**이므로 반증 팔은 없다. 대신 각 결과에는 대조가 있다: 같은 도구가 기준 변형에서는 모든 항목을 허용으로 보고하고(`base`), 진짜 워커가 변형마다 똑같은 요청에 답하는지를 같이 봤다.

## 미검증 (Gaps)

- **외부 네트워크는 시도하지 않았다.** AppContainer 의 외부 아웃바운드 차단은 루프백 연결이 막힌 측정(컨테이너 격리 필터가 작동 중이라는 증거)과 능력(`internetClient`)을 주지 않았다는 사실에서의 추정이다. 사용자 기계에서 외부로 연결을 시도하는 것은 이 카드의 범위가 아니라고 보았다.
- 방화벽 규칙(M6)은 시험하지 않았다(관리자 권한 필요, 시스템 전역 변경).
- 장난감 모델과 세 요청(초기화, 뼈 억제, 부위 인식)만 돌렸다. 스티칭·DL 노이즈 제거 요청, 하트비트·종료 경로, 실제 ONNX 모델(크기, 연산 종류에 따른 파일 접근)은 보지 않았다. 실제 모델이 쓰기를 요구하는지는 모른다.
- 낮은 무결성(S1)은 진짜 워커의 세 요청이 통과했지만 감독자(`StartLocked`)에 넣어 본 것이 아니라 시험 도구가 같은 방식으로 띄운 것이다. 감독자의 시작 순서(작업 객체 할당 후 재개, 파이프 연결 재시도, 종료·강제 종료 확인)와의 상호작용은 구현할 때 시험해야 한다.
- AppContainer 에서 `-3`(실행 파일 폴더 ACL 건너뜀)의 원인은 가르지 않았다. AppContainer 에서 `%TEMP%` 쓰기가 성공한 위치(컨테이너 전용 임시 폴더로 보이는 곳)의 경로는 확인하지 않았다.
- Windows 버전·보안 소프트웨어(백신, EDR)가 다른 기계에서의 동작은 모른다. 프로필·ACL 의 정리 방식도 측정하지 않았다.
- 한 번의 측정이다(변형마다 한 번). 반복성은 보지 않았다.

## 잔여 위험

- M3 의 SID 집합과 M5 의 파이프 경로 형식은 Windows 내부 동작에 기댄다. 경로 형식(`AppContainerNamedObjects`)은 문서화된 부분이지만 이 저장소의 시험이 이것을 계속 확인하지 않으면 OS 갱신으로 깨져도 모른다.
- S1 이 ②만 채우는 동안 REQ-AI-093 은 "부분 충족"이다. 추적 문서(`rtm`, `tasks.md`)에 그대로 적혀야 한다.
