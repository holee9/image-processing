## 3. 선택지

preprocess 의 XCal SHA-256 선례(`xcal_reader.cpp`)는 **파일 안의 해시와 대조**한다 — 파일 손상을 잡는 무결성 검사다. 공격자가 파일을 고치면 해시도 다시 계산해 넣을 수 있으므로 **진위(authenticity)** 는 보장하지 않는다. REQ-AI-007 이 묻는 것은 진위(서명)이다. 같은 방식을 쓰면 이 요구를 만족하지 못한다.

| | 내용 | 평가 |
|---|---|---|
| **A** 사이드카에 SHA-256 고정 | 해시를 모델 옆 파일에 두고 적재 시 대조 | 모델과 사이드카를 함께 바꾸는 공격(프로브의 어느 것이든)을 못 막는다. **요구 미충족.** XCal 과 같은 손상 검출용 |
| A′ 해시를 DLL 에 컴파일해 고정 | 모델 id→해시 표를 코드에 | 진위는 되지만 모델을 갱신할 때마다 DLL 을 새로 빌드해야 한다 |
| **B** 서명(공개키) | 모델 옆 분리 서명 파일, 공개키는 DLL·워커에 내장 | 요구를 만족한다. 키 관리가 필요하다(§5 D5) |
| **C** 단계적 조합 | 먼저 A(손상 검출·알림 문구 정비), 이후 B | A 는 요구를 만족하지 않으므로 중간 산출물이 증명하는 것이 없다. **권고하지 않음** |

**권고: B, ECDSA P-256, 키는 DLL·워커에 내장.** 이유: 요구 문구를 만족하는 최소 경로이고(D1), 추가 의존성이 없으며(CNG), 공격자가 모델 폴더에만 쓸 수 있는 흔한 경우(데이터 디렉터리는 사용자 쓰기 가능, DLL 은 설치 디렉터리)를 막는다.

한계를 같은 자리에 적는다: **공개키가 DLL 안에 있으므로 DLL 과 워커 실행 파일 자체를 바꿀 수 있는 공격자는 서명을 건너뛴다.** 이 설계가 막는 것은 "모델 파일(과 사이드카)만 바뀌는" 경우다. 실행 파일의 보호(Authenticode, 설치 디렉터리 권한)는 이 카드 밖이며 서명 검증이 거기에 기댄다.

### 3.1 서명이 덮는 것 — 모델만이 아니다

프로브의 "사이드카만 교체"는 라벨을 `HAND` 로 바꾸어 임상 의미를 바꿨다. 사이드카가 서명 밖이면 B 도 이 공격을 못 막는다. 또 **역할 바꿔치기**: 뼈 억제용으로 서명된 유효 모델을 `bodypart.onnx` 자리에 넣으면 서명은 맞는다. 그래서 서명 대상 메시지는 다음으로 제안한다.

```
msg = "XPE-MODEL-SIG-1\n"
      || role(UTF-8, 길이 접두)          -- "bone_suppress" | "bodypart"
      || u64le(len(model)) || model
      || u8(has_sidecar) [|| u64le(len(sidecar)) || sidecar]
서명 = ECDSA-P256( SHA-256(msg) )          -- r||s 64바이트(IEEE P1363, CNG 가 받는 형식)
```

서명 파일 `<모델 이름>.sig`(예 `bodypart.sig`): 매직 4 + 버전 1 + 알고리즘 1 + 키 id 8(공개키 해시 앞 8바이트) + 서명 64. 키 id 로 키 교체(회전)를 지원한다: DLL 은 키 몇 개를 들고 있고 폐기는 새 DLL 에서 키를 빼는 것이다.

### 3.2 검사한 바이트를 그대로 쓴다 (TOCTOU)

경로로 검증하고 경로로 다시 여는 구조는 검증과 적재 사이에 파일을 바꿀 수 있다. 제안: 파일을 **한 번 읽어 메모리에서 검증하고 그 바이트로** 세션을 만든다(ONNX Runtime 은 메모리 버퍼로 세션 생성을 지원한다). 사이드카도 한 번 읽은 문자열을 검증한 뒤 그 문자열을 파싱한다(지금 `LoadBodyPartLabels` 는 `ifstream(경로)` 로 다시 연다). 변경 지점은 `OnnxSession::Create` 의 ONNX 쪽 가지, 사이드카 읽기 둘.

## 4. 실패했을 때

- **모델 사용 불가로 취급한다**(191 의 "모델을 쓸 수 없음" 경로와 같다): 부위 인식은 `UNKNOWN` + 세션당 한 번의 알림, 뼈 억제는 입력 그대로 + 오류 코드. 검증되지 않은 모델은 **어떤 경우에도 적재하지 않는다**(실패 닫힘).
- **공유 실패 카운트(S+)와의 관계**: 191 이 정한 "모델을 쓸 수 없음은 워커 실패로 세지 않고 카운트를 0 으로 되돌린다"를 그대로 따른다(`model_unavailable` 오류 프레임을 재사용). 서명 실패 때문에 건강한 워커가 꺼지면 안 된다.
- **코드**: 지금 "읽을 수 없는 모델"이 돌려주는 `XPE_ERR_CONFIG_INVALID`(-4)를 쓴다 — 호출자가 이미 "모델 쓸 수 없음 → 대체 경로"로 다루는 코드다. `XPE_ERR_SAFETY_VIOLATION`(-11)은 쓰지 않는다: `enhance_advanced` 가 선량 한계에 쓰는 다른 의미다.
- **알림**: Error 심각도, 역할별 세션당 한 번. 원인 부류를 말한다(서명 파일 없음 / 서명 불일치 / 알 수 없는 키 / 서명 파일 형식 오류). **지금의 알림 없는 -4 와 다르다**: 변조는 안전과 보안에 관련되므로 사용자에게 보여야 한다. 알림 문구는 레인 간 계약이다(클라이언트가 문구를 매칭할 수 있다 — 같은 계약으로 헤더에 기록한다).
- **반복 비용**: 실패한 모델은 같은 호출마다 다시 해시하지 않는다. 실패를 세션에 기억하되 파일의 크기·수정 시각이 바뀌면 다시 본다(그렇지 않으면 큰 모델이 호출마다 125 ms/256 MiB 를 먹는 입력이 된다). 이 키의 선택은 D6.

## 5. 결정이 필요한 것

| ID | 결정 | 권고 |
|---|---|---|
| **D1** | 알고리즘 | **ECDSA P-256 + SHA-256.** Ed25519 는 CNG 에서 열리지 않았다(`0xC0000225`) — 새 의존성이 필요하다. 요구는 둘 중 하나를 허용한다 |
| **D2** | 서명 대상 | 모델 + 사이드카 + **역할**(§3.1). 모델만 서명하면 프로브의 사이드카·역할 공격이 남는다 |
| **D3** | 신뢰 앵커 | 공개키를 DLL·워커에 내장하고 키 id 로 회전. 외부 파일·레지스트리에 두면 그것을 바꾸는 공격자가 키를 바꾼다. 한계는 §3 에 적었다 |
| **D4** | 기본값 | **항상 강제, 끄는 설정 없음.** 설정으로 끌 수 있으면 요구의 "shall"이 비어 있다. 시험은 `XPE_AI_TEST_HOOKS` 아래 **시험 전용 키 주입 함수**(기존 `xpe_ai_test_set_*` 와 같은 틀)로 시험 키를 신뢰시킨다. 시험 키의 개인키는 저장소에 있다 — 그래서 기본 신뢰 목록에는 절대 넣지 않는다 |
| **D5** | **운영 키** | **누가 생성·보관하는가, 서명 절차(HSM 여부, 이중 통제), 회전·폐기.** 이 저장소에 없고 이 레인이 정할 일이 아니다(제품·RA·사이버보안 파일). **운영 키가 정해지기 전에는 운영 신뢰 목록이 비어 있어 실제 모델이 전부 거부된다.** 이 작업의 M1~M3 은 키 없이 가능하고(시험 키), 실모델 출하는 D5 가 막는다. 키를 받으면 상수 한 곳을 채운다 |
| **D6** | 실패 동작 | §4 그대로: 모델 사용 불가(카운트 안 셈), 코드 -4, Error 알림 세션당 역할별 1회, 실패 기억 후 파일 변경 시 재확인 |
| **D7** | 롤백 방어 | **이번 범위 밖.** 유효하게 서명된 옛 모델로 되돌리는 공격은 서명만으로 막히지 않는다. 메시지에 버전을 넣어 최소 버전을 두는 것은 가능하나 "최소 버전"을 누가 정하는지(PCCP)가 D5 와 같은 주체의 결정이라 제안만 한다 |
| **D8** | 파일 크기 상한 | 메모리에 올려 검증하므로 상한이 필요하다. 상한 값의 근거는 없다 — 구현 안전 상한으로 두고(QA-B-194 D5 의 partCount 상한과 같은 성격: 임상 요구 아님) 값은 헤더에 명시 |

## 6. 장난감 모델·시험 자산

`tests/data` 의 `.onnx` 는 **19개**다(카드의 "12벌"과 다르다): 뼈 억제 `models_x2`·`models_x3`·`models_broken`, 부위 인식 13개 디렉터리(`models_bodypart_{a,b,broken,dep,dynamic,labels_mismatch,nhwc,no_labels,nonfinite,range_high,range_low,rank2,runfail}`), 루트의 `min_scale2`·`min_scale3`·`not_a_model`. 이 중 시험이 쓰는 것은 디렉터리 안의 것이고 루트의 셋은 `OnnxSession` 직접 시험이 쓴다.

새 규칙에서의 처리:

- **`.sig` 를 모델과 함께 커밋한다**(모델도 이미 바이너리로 커밋돼 있다). 일부러 깨진 모델(`models_broken`, `not_a_model`, `models_bodypart_broken`)도 **서명한다** — 서명하지 않으면 지금 "읽을 수 없음"을 보는 시험이 "서명 없음"을 보게 되어 시험의 의도가 바뀐다.
- 서명 도구: 개인키를 다루므로 오프라인 스크립트 한 개(Python `cryptography` 49.0.0 이 이 PC 에 있다). 시험 키 쌍을 만들어 두고 `tests/data` 의 모든 모델을 서명한다. 생성 스크립트 `make_min_models.py`·`make_bodypart_models.py` 가 끝에서 서명 도구를 부르게 한다(모델을 다시 만들면 서명도 새로 나온다).
- **낡은 서명 시험**: `tests/data` 를 훑어 모든 `.onnx` 에 유효한 `.sig` 가 있음을 단언한다. 모델을 바꾸고 서명을 안 바꾼 PR 이 빨개진다(해시 갱신 절차를 잊을 수 없게 한다).
- **독립 시험 벡터**: 검증기는 CNG 로 구현하므로, 시험 벡터는 **다른 구현**(Python `cryptography`)으로 만들어 C++ 검증기가 받아들이는지 본다. 같은 구현으로 서명하고 검증하면 규약(DER 대 r‖s, 메시지 구성)이 틀려도 일관되게 통과한다.

## 7. 마일스톤과 규모

| | 내용 | 비고 |

## 8. 미검증 (Gaps)

- 실제 모델 파일 크기를 모른다. 125 ms/256 MiB 는 이 PC 의 CNG 측정이고, 실제 모델의 적재 시간 증가는 크기에 비례한다는 외삽이다.
- ONNX Runtime 의 "메모리 버퍼로 세션 생성"은 API 가 있음을 알고 있으나 이 저장소의 `ai_onnx_session.cpp` 에서 써 보지 않았다(M3 에서 확인). 메모리 사본이 세션 수명 동안 유지되어야 하는지(ORT 가 복사하는지)도 확인하지 않았다.
- 워커 쪽에서 `model_unavailable` 오류 프레임이 사유 문구를 실을 수 있는지는 코드를 열어 보지 않았다(알림 원인 부류를 부모가 어떻게 아는지는 M4 의 일).
- GUI 가 `XPE_ERR_CONFIG_INVALID` 를 어떻게 읽는지(`GuiAiRunner.Classify`)는 확인하지 않았다(`clients/` 시험 확인은 M4 에서 같은 검색으로 다시).
- 프로브는 ONNX 빌드(ci-ai)에서만 돌렸다. 스텁 빌드에는 모델을 여는 일이 없어 검증도 일어나지 않는다 — 스텁에서 서명 시험을 어떻게 둘지(건너뜀, 검증기 단위 시험은 CNG 만 있으면 도는지)는 M1 에서 정한다.
- 서명 키가 없는 상태에서 CI 가 서명된 자산을 어떻게 신뢰하는지는 D4 의 시험 키 주입에 달려 있고 구현해 보지 않았다.
- 루트 디렉터리에 `_probe.obj`·`_probe_dyn.obj`·`g191_probe.obj` 가 untracked 로 남아 있다(이번 카드의 산출이 아니며 건드리지 않았다).

## 9. 잔여 위험

- 키를 DLL 에 내장하는 방식은 실행 파일이 바뀌면 무력화된다(§3). 이 카드는 그것을 막지 않는다.
- D5 가 늦어지면 M3 이후의 운영 빌드가 실제 모델을 거부한다.
- 알림 문구가 클라이언트 계약이므로 M4 이후의 문구 변경은 다른 레인에 통보 대상이다.
