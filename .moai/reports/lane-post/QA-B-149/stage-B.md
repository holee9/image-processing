## 1. `#156` — LINEAR 에 창 배치 보정

### 고친 것

```diff
-const float lo = center - width * 0.5f;
-float val = (px[i] - lo) / width * range + minOut;
+const float c = center - 0.5f;
+const float w = width - 1.0f;
+// 표준의 문턱 세 분기 (width == 1 에서 w == 0 이므로 내부 나눗셈에 안 닿음)
```

`EXACT` 는 **건드리지 않았습니다.** 개정된 `REQ-DISP-009/010/010a` 를 그대로
따릅니다.

### 기대값을 어디서 가져왔는가

**모듈이 아니라 표준의 예제에서.** 리더가 원문에서 확인해 준 두 벡터:

| 예제 | 경계 (측정) | 옛 식이면 |
|---|---|---|
| `c=2048, w=4096` | `f(0)=0`, `f(4095)=1` | `f(4095)=0.999756` |
| `c=0, w=100` | `f(-50)=0`, `f(49)=1` | `f(49)=0.99` |

두 수가 식을 가릅니다. `width == 1` 경계도 넣었습니다 — `REQ-DISP-015` 가
`width <= 0` 만 거부하므로 적법한 입력이고, 0 으로 나누면 안 됩니다.

### 반증

`-0.5`/`-1` 을 **런타임 거짓 조건**으로 끄니:

```
LINEAR vs LINEAR_EXACT maxdiff=0.000998557  →  0
PS3.3 example 1 f(4095)=1  →  0.999756
PS3.3 example 2 f(49)=1    →  0.99
```

**시험 주석이 미리 적어 둔 그 수치로 정확히 돌아갔습니다.**

### 뒤집은 것 / 갱신한 것

- `KnownDivergence_VoiLinearExactEqualsVoiLinear` → `Fixed156_VoiLinearExactDiffersFromVoiLinear`
  (`EXPECT_LT(diff,1e-6)` → `EXPECT_GT(diff,1e-4)`)
- `DISABLED_VoiLinearExactMustDifferFromLinear` → **활성화** +
  `VoiLinearMatchesTheStandardsWorkedExamples_156` 로 개명, 본문을 표준 예제로 교체
- **그 시험의 예측 하나가 빗나갔습니다**: 주석이 *"표준이 오면 EXACT 분기를
  구현하라"* 고 적었는데 고쳐야 했던 것은 **LINEAR** 였습니다. 그 사실을 주석에
  남겼습니다

### 덤으로 깨진 시험 둘 — **스스로 예고돼 있었습니다**

| 시험 | 전 | 후 |
|---|---|---|
| `VoiLut.Linear_CenterWindow` | 127.5 | **127.6276** |
| `DisplayIntegration.FullPipeline_…` | 0.5 → 인덱스 512 | **0.5025126 → 514** |

앞엣것은 QA-B-121 이 허용치를 0.5 → 0.05 로 좁히면서 *"DICOM 식이면 127.628"*
이라고 **미리 적어 둔** 시험입니다. 실측 **127.62762** — 예측이 다섯 자리까지
맞았고, 좁혀 둔 것이 제 일을 했습니다.

DN −160..240 을 덮어 램프 표본 몇 개가 안에 들어갑니다. 추측한 수를 주석에
남기면 다음 사람이 그것을 측정값으로 읽습니다.

## 4. `#179` — **게이트를 넣을 수 없습니다. CI 가 SPEC 예산을 못 지킵니다**

`gh run view --log` 로 최근 벤치마크 8회에서 `ADV061` 줄을 뽑았습니다
(`_ci_adv061.txt`). 전부 `runs=7, order=1.2`, 단위 ms:

| run | min | med | max |
|---|---|---|---|
| 35435692486 | 443.8 | 453.9 | 502.7 |
| 35434160819 | 513.1 | **585.9** | **632.7** |
| 35433030120 | **417.5** | **428.4** | 474.1 |
| 35431916186 | 454.5 | 468.3 | 481.5 |
| 35430772488 | 421.8 | 436.4 | 461.4 |
| 35429115353 | 421.5 | 441.4 | 461.6 |
| 35426901178 | 423.0 | 438.8 | 453.6 |
| 35424904958 | 538.8 | 545.3 | 612.3 |

### 결론이 바뀝니다

**`REQ-ADV-061` 의 400 ms 를 CI 에서 한 번도 못 지켰습니다.** 가장 빠른 관측이
**417.5 ms**(min of mins)입니다. 400 ms 게이트를 넣으면 **첫 실행부터 빨강**이고,
그것은 회귀가 아니라 기계 차이입니다.

SPEC 의 실측 주석은 개발 PC(i7-12700)에서 order 1.2 = **320 ms** 라고 적습니다.
CI 러너는 그보다 **약 1.4배** 느립니다 — "게이트가 잘못된 기계에서 잡혔다"의
**거울상**입니다. 이번엔 게이트가 아니라 **SPEC 예산**이 개발 PC 수치입니다.

### 그래서 두 가지를 갈라야 합니다

| 주장 | 무엇이 필요한가 |
|---|---|
| **SPEC 적합** (400 ms) | **기준 하드웨어**에서의 측정. CI 공유 러너는 그것이 아닙니다 — `#151` 과 같은 종류의 차단 |
| **CI 회귀 검출** | CI 분포에서 뽑은 **절대 예산**. SPEC 수치와 다른 수여야 합니다 |

### 제안 (리더 판단)

**게이트 대상은 `med`**(시험이 7회의 중앙값을 냅니다). max 는 공유 러너의
꼬리를 잡아 흔들립니다.

```
관측 med: 428.4 ~ 585.9   (8회, 폭 1.37배)
제안 게이트: med <= 700 ms   (관측 최댓값의 1.19배)
```

**비율이 아니라 절대값**입니다 — 말씀대로 비율 게이트는 기계 편차에 먹힙니다.
700 ms 는 `585.9 × 1.2` 를 올림한 값이고, 8회 중 가장 느린 실행도 **114 ms**
여유가 남습니다. 두 배 느려지는 회귀는 잡고, 관측된 러너 편차(1.37배)는
통과시킵니다.

**이 커밋에 게이트를 넣지 않았습니다.** 넣으면 CI 를 한 번 거치기 전에는 닫을 수
없고, 푸시는 리더 몫입니다. 넣을 자리와 값만 제안합니다.

### 미검증

- **8회는 이틀치입니다**(2026-09-19 하루). 러너 세대가 바뀌면 분포가 옮겨갑니다.
- **AVX2 120 ms 조항**은 SPEC 이 이미 *"명시적 SIMD 코드가 없으므로 해당 없음"*
  으로 적었습니다. 판단은 SPEC 쪽입니다.

## 5. QA-B-150 — SAF-100 이 AC 의 키로 발동하지 않았습니다

### 전제 4건 전부 참

| # | 전제 | 확인 |
|---|---|---|
| 1 | `forbiddenKeys` 5개 | 참 (`:306-313`) |
| 2 | `overshoot_limit_enabled` 없음 | 참 |
| 3 | AC-EDGE-005 가 그 이름을 지목 | 참 (`acceptance.md:205`) |
| 4 | `test_overshoot_safety.cpp` 없음 | 참 (`tasks.md:82` = `pending`) |

### 전수 대조에서 더 나쁜 것이 나왔습니다

`spec.md` + `acceptance.md` + `tasks.md` 에서 따옴표로 인용된 overshoot 키는
**`"overshoot_limit_enabled"` 단 하나**입니다. 코드가 막던 다섯은 **SPEC 어디에도
없습니다.**

> **목록과 SPEC 의 교집합이 0 이었습니다** — 있어야 할 하나가 없고, 없어도 될
> 다섯이 있었습니다. `XPE_ERR_SAFETY_VIOLATION` 을 요구하는 AC 도 그 하나뿐입니다.

### 왜 안 드러났는가

`nlohmann::json::contains` 는 **정확 일치**라 `"overshoot_limit"` 가
`"overshoot_limit_enabled"` 를 덮지 않습니다 — **접두사가 덮어 줄 것처럼 읽히는
자리**입니다. 그리고 요구·구현·시험이 **같은 이름에서 동시에 비어** 있었습니다.

`T305_AttemptDisableOvershootLimiting` 은 **코드의 목록을 그대로 다섯 케이스로
옮겨 적은** 시험이라 — 자기 자신과 비교하는 형태 — 내내 초록이었습니다.

### T-068 신설 (`test_overshoot_safety.cpp`, 5건)

**키는 AC 문구에서 가져왔습니다.** 값 무관(존재가 위반), 중첩 `safety` 경로,
금지 이름 전수, 그리고 **대조군 둘**:

- 정상 키(`iterations`, 빈 객체, 중첩 정상 키) → `XPE_OK`
  — 전부 거부하는 구현도 거부 시험은 전부 통과하므로
- `overshoot_limit_enabled_note` → `XPE_OK`
  — **정확 일치가 계약**임을 고정(접두사 일치로 바꾸면 여기가 빨개집니다)

### 반증

추가한 키를 다시 빼니:

```
[  FAILED  ] AcEdge005_OvershootLimitEnabledFalseIsRejected_145
[  FAILED  ] AcEdge005_TheKeyIsRejectedWhateverItsValue_145
[  FAILED  ] AcEdge005_KeyInsideTheSafetyObjectIsRejected_145
[  FAILED  ] EveryForbiddenNameIsRejected_145
[       OK ] OrdinaryConfigStillPasses_145          ← 대조군
[       OK ] EdgeEnhancementTest.T305_…             ← 옛 시험, 같은 실행
```

빨강 4건은 **모두 AC 키를 단언하는 것**이고 대조군은 초록입니다. 그리고
**T305 가 같은 실행에서 초록**인 것이 *"옛 시험은 이 결함을 구조적으로 볼 수
없다"* 의 증거입니다.

### 픽스처에서 걸린 것

`xpe_enhance_advanced_init` 없이는 모든 호출이 **`-6`(NOT_INITIALIZED)** 을 냅니다.
안전 가드와 무관한 이유로 거부 시험이 **전부 통과**할 뻔했습니다 — 주석에
남겼습니다.

### 범위 밖 (건드리지 않음)

나머지 5개 키(`gaussian_sigma` 등)는 구현하지 않았습니다. 접두사 일치로
바꾸는 선택지도 버렸습니다 — 아무도 금지하지 않은 키까지 막습니다.
