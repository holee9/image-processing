## 1. 바뀐 동작과 한 가지 결정

**정확한 규칙.** 샤프닝되는 화소(`|입력 − 블러| ≥ threshold`)의 결과는 `min(원본 + amount×(원본−블러), max(원본×2, 원본+amount×threshold))` 의 최댓값을 0 과 취한 값이다. 샤프닝되지 않는 화소는 입력값 그대로다.
**내가 정한 것 — 입력이 음수인 화소.** 카드 문구는 "출력이 0 보다 작으면 0" 이다. 샤프닝되지 않는 화소까지 0 으로 올리면 입력이 음수일 때 이 단계가 샤프닝과 무관한 화소를 고쳐 쓰게 된다. 파이프라인에서 음수 입력은 log 단계가 0 으로 자르므로(REQ-ENH-002) 정상 경로에서는 일어나지 않는다. 그래서 하한은 **샤프닝된 값**에만 적용하고, 샤프닝되지 않는 음수 입력은 그대로 둔다. 이 선택은 시험으로 못 박았고(`APixelThatIsNotSharpened…`) 반증도 한다. 입력이 음수인 화소가 샤프닝 영역에 있으면 하한이 상한 앞의 순서로 적용되므로 결과가 0 이 될 수 있다(상한이 음수이면 상한 위로 올라간다) — 음수 입력은 이 단계의 계약 밖이라 그 경우는 시험하지 않았다.

## 2. 16비트 출력이 바뀌지 않는다 (측정)

바닥이 없는 빌드(HEAD, M2b 상태)와 있는 빌드를 같은 장면에 돌려 결과를 화소 단위로 비교했다(`m3_equiv_16bit.py.txt`, 출력 `m3_equiv_16bit_out.txt`). 장면 4개(해부학, 콜리메이터 띠, 피부선, 어두운 바닥 30 대 밝은 4000) × log 영역·선형 영역 × amount 0.5·1·2·5 × threshold 0·10·100 = 96개 경우, 각 경우는 log(해당 시) → bilateral → CLAHE → USM. 변환은 gui `EnhanceBasicStage` 와 같다(`round half to even`, 0..65535 로 자름).

| 항목 | 값 |
|---|---|
| 16비트 결과가 달라진 경우 | **0 / 96** (달라진 화소 합계 0) |
| 바닥이 없을 때 음수 float 가 있는 경우 | 78 / 96 |
| 바닥이 있을 때 음수 float 가 있는 경우 | 0 / 96 (가장 낮은 값 0.000) |
| 바닥이 바꾼 float 화소 합계 | 216,576 (모두 원래 음수였던 화소) |

M1 의 측정("(b) 0 클램프: 16비트 차이 0 화소")이 구현된 코드에서도 그대로다.

## 3. 시험 (`EdgeEnhanceFloor`, `test_edge_enhance_formula.cpp`)
- `ASharpenedPixelBesideADarkRegionIsNeverBelowZero`: 계단 에지 4가지(바닥 0·30, amount 0.5·1·5, 대비 4000). 독립 참조(공식 그대로)가 **0 아래로 내려가는 것을 전제로 단언**(최소 −8005, −7975, −801, −1601)하고, 모듈의 음수 화소 0개와 어두운 쪽 에지 화소가 입력(30)이 아니라 정확히 0 인 것을 단언.
- `TheFloorDoesNotChangeAnyPixelThatTheFormulaLeavesAtOrAboveZero`(대조군): 아무 화소도 0 아래로 내려가지 않는 장면에서 모듈이 공식과 같다(블러 차이 이내)고 하여 바닥이 0 아래였던 것만 건드린다는 것.
- `TheUpperBoundIsUnchangedByTheFloor`: 상한 시험(2×원본)이 그대로이고 모든 화소가 상한 이하·0 이상.
- `APixelThatIsNotSharpenedKeepsItsInputValueEvenWhenItIsNegative`: §1 의 선택.

## 4. 반증 (`m3_arms_driver.py.txt`, `m3_arms_out.txt`)

| 끈 방어 | 빨개진 시험 |
|---|---|
| 하한 제거 | 바닥 시험, 상한 시험(0 이상 단언) |
| 하한을 입력값으로(`sharpened = orig`) | 바닥 시험(바닥 30 장면) |
| 하한을 1 로 | 바닥 시험(어두운 쪽 에지 화소 == 0) |
| 샤프닝되지 않는 화소까지 0 으로 올림 | 음수 입력 시험 |
| 하한이 아주 큰 음수에서만 작동(`< -1e6`) | 바닥 시험, 상한 시험 |

(두 팔에서 `EdgeEnhance.Performance_3072x3072_Within20ms` 도 함께 빨갰다 — 이 시험은 20 ms 단발 측정이라 재빌드 직후 기계 상태에 흔들린다, §5.)
**터뜨리지 못한 변형**: 하한과 상한의 적용 순서를 바꾸는 팔은 만들지 않았다. 두 순서는 상한이 음수일 때(원본이 음수) 에만 달라지고 그 경우는 이 단계의 계약 밖이다(§1) — 동등 변이가 아니라 시험하지 않은 경우다.

## 5. 성능 (REQ-ENH-022, 20 ms)
수정 직후 `EdgeEnhance.Performance_3072x3072_Within20ms` 가 8회 중 2회 빨갰다(21 ms, 22 ms; 단발 20 ms 예산, 이 기계의 평소가 19~22 ms 근방). 바닥이 비용을 만드는지 알려고 **하한 있음/없음 두 바이너리를 번갈아 40회씩** 돌렸다(`m3_ab_perf.py.txt`, `m3_ab_perf_out.txt`): 둘 다 **40/40 통과**, 실패 0. 따라서 앞의 두 번은 이 한 줄의 비용이 아니다. 원인이 기계 부하(다른 세션의 빌드)라는 설명은 추론이며 그 시점의 부하는 측정하지 않았다. 시험의 정수 ms 해상도로는 바닥의 비용이 있어도 보이지 않을 수 있다(관측: 40/40 대 40/40).

## 6. Gap / 잔여 위험
Gap
- gui·clients 기준선 시험은 돌리지 않았다. 16비트 결과가 같으므로(§2) 영향은 없다고 판단하지만 그것은 이 장면들에 대한 측정이다. 실제 임상 영상으로는 재지 않았다.
- 음수 입력 화소가 샤프닝 영역에 있을 때의 결과(§1 끝)는 시험하지 않았다.
- 성능은 단발 정수 ms 측정이다(§5).
- 루트 `schemas/` 가 없는 이 브랜치에서 ctest 의 모델카드 시험 3개는 빨갛다(QA-B-201 M2 보고서 §4). 검증 때만 임시로 놓았다가 지웠다.

잔여 위험
- 16비트 출력이 같아도 float 를 다른 방식으로 소비하는 새 코드가 있다면, 하한 아래의 undershoot 정보가 사라졌다는 점이 달라진다(지금은 소비자가 없음, M1 §3).
