# QA-B-201 M1 — E1 의 음수 에지 화소: 어느 영역에서 생기고 하류가 어떻게 다루는가 (#251)

카드: `.moai/lanes/post/inbox/QA-B-201.md` M1. 코드 변경 없음. 빌드된 DLL(`build/ci-post`, `build/ci-dicom`)을 Python `ctypes` 로 직접 호출해 관측했다(`m1_probe.py.txt`, 출력 `m1_probe_enhance_out.txt`·`m1_probe_dicom_out.txt`). 입력은 합성 장면이다(§7 Gap).

## 0. 결론

1. **`xpe_edge_enhance` 는 출하된 모든 파이프라인에서 log 변환 뒤에 돈다**(gui·테스트 파이프라인은 고정 순서, 레거시 clients 미리보기는 log 스위치를 끄면 선형 영역에서도 돈다). log 영역에서도 음수가 생긴다 — 기본값(amount 0.5)에서 **조준(콜리메이터)으로 0 카운트가 된 띠 옆**에서 3304 화소(장면의 20 %), 최소 −1363. 해부학적으로 흔한 장면(0 카운트 없음)에서는 기본값으로 음수가 없고 amount 5 에서 15 화소 생긴다.
2. **이번 조사에서 조용히 큰 양수로 되감기는(랩어라운드) 곳은 찾지 못했다.** 음수를 받는 모든 하류 지점은 0 으로 자르거나(gui 변환, e2e 파이프라인, display 의 VOI·표시 LUT, 레거시 미리보기의 8비트 창) 최소값 기준으로 정규화한다. 단, **DICOM 쓰기는 FLOAT32 영상을 거부하지 않고 받는다**(§3, 별도 관찰).
3. 사용자 앱(`EnhanceBasicStage`)의 16비트 변환은 이미 `<0 → 0` 으로 자르므로 **선택지 (b) 0 에서 클램프는 16비트 출력이 한 화소도 달라지지 않는다**(측정: 0 화소). (c) 대칭 하한은 눈에 보이는 영상을 바꾼다(수백~수천 화소).
4. 권고는 §5 표 아래에 적었다. 새 하한 규칙은 요구 추가라 사용자 결정이다.

## 2. 음수가 어디서 얼마나 생기는가 (log 영역, 기본 USM 반경 2·임계값 10)

합성 장면 128×128 (raw 카운트, 노이즈 σ 30): 해부학(부드러운 기울기 + 밝은 원판, 3000 → 12000), 콜리메이터(같은 장면 왼쪽 40열이 0 카운트), 피부선(공기 60000 | 조직 1500). 각각 log(1000) → bilateral(3, 50) → CLAHE(3, 8×8) → USM(amount 달리).

| 해부학 | 5 | −1404 | 15 | |
| 콜리메이터 | 0.5(기본) | −1363 | **3304** | 0 카운트 띠 옆 undershoot |
| 콜리메이터 | 1 · 2 · 5 | −2757 · −5546 · −13914 | 3764 · 3986 · 4529 | |
| 피부선 | 0.5 · 1 · 2 | 2654 · 2122 · 1059 | 0 | |
| 피부선 | 5 | −2130 | 51 | |
| (선형 영역, log 끔) 해부학 | 0.5(기본) · 5 | −2625 · −33995 | 746 · 2755 | |

M2b 이전에는 하한이 `원본 − amount×threshold` 였으므로(`edge_enhance.cpp` 의 옛 클램프, 코드를 읽은 것이며 옛 바이너리로 재측정하지는 않았다) 음수는 기본값에서 최대 −5 정도였다. M2b 로 SPEC 대로 하한이 없어지면서 위 크기의 음수가 나온다.

## 3. 하류는 음수 float 를 어떻게 다루는가 (실제로 흘려 본 결과)

| 지점 | 관측 |
|---|---|
| `xpe_apply_modality_lut` LINEAR (slope 1) | 음수를 **그대로 통과**(−500 → −500, 455 화소 음수 유지, rc OK) |
| `xpe_apply_voi_lut` (창 중심 1500, 폭 4500) | 창 안의 음수는 창 계산대로(−500 → 0.0556), **창 아래로 멀리 떨어진 값은 minOut 으로 잘림**(−5000 → 0.0, minOut 0). 랩어라운드 없음 |
| `xpe_apply_presentation_lut` (입력 −0.5..1.5) | 출력 UINT16, **입력 <0 은 전부 LUT[0](=0)**, >1 은 전부 65535. 되감김 없음(코드도 `clamp(v, 0, 1)`: `presentation_lut.cpp:44-51`) |
| gui `EnhanceBasicStage` 변환 | `MathF.Round(half-even)` 뒤 `<0 → 0`, `>65535 → 65535`, 요약에 "clamped below N above M" 로 남김(`EnhanceBasicStage.cs:119-140`; 리더 전달 사실과 코드가 같음). NaN/Inf 는 거부 |
| e2e 파이프라인 | USM 뒤 `if (v < 0.0f) v = 0.0f; if (v > 65535.0f) v = 65535.0f;` 를 거쳐 GSVG 로(`test_e2e_full_pipeline.cpp:173`) |
| 레거시 미리보기(8비트 그림) | 출력의 min..max 를 창으로 정규화하고 `Math.Clamp(…, 0, 255)`(`RawPreviewService.cs:158-179`). 음수는 0(검정)으로 가지만 **창의 최소가 음수로 내려가 영상 전체의 대비가 줄어든다**(코드를 읽은 것, 화면은 보지 않았다). 레거시 준비도 스모크는 "OK + 화소 유한"만 보아 음수를 통과시킨다(리더 전달) |
| 레거시 표시·내보내기 변환 | `ScaleFloatToUInt16` 이 최소값 기준 정규화 후 `Math.Clamp`(`NativePresentationExportService.cs:517-547`) — 되감김 없음, 단 음수 최소가 레벨을 이동시킨다(코드를 읽음) |
| **`xpe_dicom_write`** | **FLOAT32 영상(−500..4000)을 `XPE_OK` 로 받아** 17432바이트 파일을 쓴다(UINT16 대조군은 9240바이트). 그 파일을 이 모듈의 `xpe_dicom_read_image` 로 읽으면 `BitsAllocated 32 (only 16 is supported …)` 로 거부된다. 즉 float 가 uint16 으로 **되감기지는 않는다** — 32비트로 쓰인다 — 하지만 "쓰기는 받고 읽기는 거부"하는 자체 비일관이다. 이 비일관의 원인·IOD 적합성은 이번에 분석하지 않았다 |

대조군: 같은 쓰기에 호출자가 0..65535 로 자른 UINT16 영상을 주면 읽어 낸 값이 자른 입력과 정확히 같다(`read back == clamped input: True`).

## 4. 다른 단계는 음수를 내고 받는가 (일관성)

음수 51.6 % 의 float 영상(−683..789)을 각 단계에 입력으로 준 결과:

| 단계 | rc | 출력 |
|---|---|---|
| `xpe_log_transform(1000)` | OK | 음수를 0 으로(REQ-ENH-002 대로), 전부 0 이상(0..2898), NaN·Inf 없음 |
| `xpe_noise_reduce` bilateral | OK | 음수를 **그대로 받아 음수를 낸다**(−683..789, 음수 2099 화소) |
| `xpe_contrast_enhance` CLAHE | OK | 음수를 받고 음수를 낸다(−660..789, 음수 1829 화소) |
| `xpe_edge_enhance` 0.5/2/10 | OK | 음수를 받고 음수를 낸다(−1002..1157) |

노이즈 감소·CLAHE·USM 은 음수를 입력으로 거부하지 않고 부호 있는 값을 그대로 다룬다. log 만 0 으로 자른다. 따라서 "USM 의 출력이 음수"가 모듈군 안에서 유일하게 특이한 것은 아니다(입력 음수는 다른 단계도 받는다). 다만 USM 은 **입력에 음수가 없어도 출력에 음수를 만드는** 유일한 단계다(노이즈 감소·CLAHE 는 입력 범위 안에 머문다 — 위 표 §2 의 clahe 열이 0 이상).

## 5. 선택지와 영향 (리더가 사용자에게 물을 때 쓰도록 짧게)

실제 USM 출력을 기준 (a) 로 놓고 나머지를 계산했다(로그 영역, 임계값 10). "16비트 차이" 는 `round → 0..65535 자름` 뒤 (a) 와 달라지는 화소 수.

| 선택지 | 영상에 미치는 효과 (콜리메이터·amount 0.5 / 해부학·amount 5 / 피부선·amount 5) | 위험 |
|---|---|---|
| (a) SPEC 그대로, 하한 없음(지금) | 최소 −1363 / −1404 / −2130, 음수 3304 / 15 / 51 화소 | 음수 float 가 모듈 밖으로 나간다. 지금 소비자는 모두 자르지만(§3) **DICOM 쓰기는 float 를 받고**, 레거시 미리보기는 창이 틀어진다. 새 소비자가 자르지 않으면 되감김 가능 |
| (b) 0 에서 클램프 | 음수였던 3304 / 15 / 51 화소만 0 이 된다. **16비트 출력 차이 0 화소**(gui·e2e 가 이미 같은 일을 함) | SPEC 에 한 줄 추가(요구 추가). 실제 영상 출력은 바뀌지 않는다. float 영역에서 음수 undershoot 정보는 사라진다(소비자가 없음) |
| (c) 상한과 대칭인 하한 `min(원본/2, 원본−amount×threshold)` | 최소 15.9 / 1456 / 1592(콜리메이터 amount 5 는 −18.3, 음수 2716). (a) 와 달라지는 화소 3764 / 847 / 221, **16비트 차이 3762 / 846 / 221 화소** | 눈에 보이는 영상이 바뀐다: 양수인 어두운 쪽 화소도 원본의 절반 아래로 못 내려가게 잘린다. REQ-ENH-021 의 "후광·링잉 금지" 의도를 어두운 쪽에도 적용하는 것이지만 **새 수치 규칙**이고 gui 기준선이 있다면 갱신 대상 |
| (d) 하류가 처리 | (b) 와 같다(gui 의 변환이 이미 이 일을 함). 모듈 출력은 (a) 그대로 | 소비자마다 따로 처리해야 하고 DICOM 쓰기·레거시 미리보기는 하지 않는다. 결정이 모듈 밖에 흩어진다 |

**권고(내 판단, 사용자 결정 사안).** (b) 가 가장 작은 변경이다: 사용자 앱의 16비트 출력은 한 화소도 안 바뀌어 gui 기준선 영향이 없고(측정 0), 음수 float 가 모듈 밖으로 나가는 문 자체를 닫으며, REQ-ENH-002 가 이미 음수를 0 으로 자르는 선례다. (c) 는 REQ-ENH-021 의 "후광 금지" 의도에 더 가깝지만 눈에 보이는 영상이 바뀌고 새 수치 규칙(절반)을 정당화할 근거가 SPEC 에 없다 — 그것을 원하면 SPEC 문구를 먼저 정해야 한다. (a) 는 지금 소비자에게는 안전하지만 DICOM 쓰기가 float 를 받는 것과 겹쳐 새 소비자에 위험을 남긴다.

## 6. 이번 조사에서 부수로 본 것 (별도 판단)
- `xpe_dicom_write` 가 FLOAT32 를 받아 이 모듈의 reader 가 못 읽는 32비트 파일을 쓴다(§3). 이번 카드의 범위가 아니다. 호출 쪽(gui)은 UINT16 만 넘기므로 지금 경로로는 일어나지 않는다. 원하면 별도 카드.

## 7. Gap / 잔여 위험

Gap
- 입력은 **합성 장면**이다(노이즈 시드 고정). 실제 임상 영상으로 음수 화소의 수와 위치는 재지 않았다. 콜리메이터 장면은 "조준 영역의 전처리 출력이 0 카운트"라는 가정을 두었다 — 실제 검출기의 offset 보정이 그 영역을 0 으로 자르는지는 확인하지 않았다(그 가정이 틀리면 기본값에서의 음수 3304 는 줄어든다).
- 레거시 미리보기의 음수 렌더링, gui 앱 화면은 실행하지 않았다(코드와 리더 전달로만 안다).
- 옛(M2b 이전) 모듈로 같은 장면을 돌려 음수 크기를 재지 않았다(§2 의 "최대 −5 정도"는 코드 읽기).
- 선택지 (b)·(c) 의 숫자는 실제 모듈 출력에서 계산했고 모듈 자체에 구현해 본 것이 아니다.
- DICOM 쓰기가 float 를 쓴 파일의 화소 인코딩(PixelRepresentation 등)은 열어 보지 않았다.

잔여 위험
- (a) 를 유지하는 동안 새 소비자가 float 영상을 16비트로 자르지 않고 쓰면 되감김이 일어날 수 있다. 지금 코드베이스에서 그런 소비자는 찾지 못했다(검색은 `static_cast<uint16_t>` 와 `(ushort)` 에 한정).
