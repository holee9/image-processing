## 2. JPEG-LL 입력 다양화

### 2.1 무엇이 좁았나

B-45 는 **DCMTK 인코더의 기본 설정 산출물 한 종류**만 시험했다.
"무손실이 동작한다" 가 아니라 **"이 인코더 설정 하나에서 동작한다"** 였다.
JPEG Lossless(Process 14, first-order)는 예측자 선택값을 여러 개 허용하고,
실제 장비는 벤더가 고른 값을 쓴다.

### 2.2 변종 목록 — 만든 것 / 못 만든 것

| 예측자 선택값 | 생성 | 디코드 | 원본과 바이트 일치 |
|---|---|---|---|
| 1 | O | O | O |
| 2 | O | O | O |
| 3 | O | O | O |
| 4 | O | O | O |
| 5 | O | O | O |
| 6 | O | O | O |
| 7 | O | O | O |

```
[  INFO ] test_dicom_reader.cpp(759): predictor variants produced and verified: 7 of 7
```

**못 만든 것은 없다.** 생성 실패 시에는 `GTEST_LOG_(INFO)` 로 사유를 남기고 건너뛰되
단언하지 않도록 만들어 두었다 — 인코더가 못 만드는 것은 **리더가 못 읽는다는 뜻이 아니므로**
실패로 세지 않는다.

**개수를 로그에 찍는다.** 처음에는 "건너뛴 메시지가 없으니 7종 다 됐다" 로 읽을 수
있었는데, 그것은 **부재로부터의 추론**이다. 읽는 사람이 역산하지 않도록 숫자를 직접 출력했다.

### 2.3 만들지 못한 축 — 비트 깊이

카드가 예로 든 **비트 깊이 8/12/16 변종은 만들지 않았다.** 픽스처의 원본이
`xpe_dicom_write` 산출물(UINT16, `BitsAllocated=16`)이고, 8비트 원본을 만들려면
**writer 가 지원하지 않는 형식**을 손으로 조립해야 한다. 태그만 바꾸면 픽셀 데이터와
어긋난 파일이 되고, 그것은 비트 깊이 변종이 아니라 **손상 파일**이다.
**만들 수 없다고 적고 넘어간다** — 카드의 지시 그대로다.

## 3. 동시 `open()` 실증

### 3.1 설계

8스레드 × 8회, 각 반복이 JPEG-LL 파일을 열고·디코드하고·원본과 비교한다.
실패는 세 축으로 나눠 센다(open / decode / 픽셀 불일치) — 어디서 깨졌는지가 보이도록.

**스레드는 테스트 안에서 전부 `join()` 된다.** 분리 스레드도, 배경 부하도,
생성 프로세스도 남지 않는다(카드 지시).

### 3.2 통과가 증명하지 않는 것 — 코드에도 적었다

```
// WHAT THIS TEST DOES NOT PROVE: passing is not evidence that the code is
// thread-safe. A data race can stay invisible across many runs.
```

**통과가 말해 주는 것은 "이번 실행에서 크래시·디코드 실패·픽셀 손상이 없었다" 까지다.**
초록 체크가 그 이상을 암시하지 않도록 주석과 이 보고서에 같은 문장을 둔다.

### 3.3 반증 — **재현되지 않았다** (`_falsify.log`)

`call_once` 를 동기화 없는 `bool` 플래그로 약화시키고 10회 반복했다:

```
===BUILD=0===                     <- 빌드 성공. 낡은 바이너리가 아니다
Repeating all tests (iteration 10) . . .
[       OK ] DicomReaderTest.ConcurrentOpenOfJpegLossless_NoCorruption (17 ms)
[  PASSED  ] 1 test.
===EXIT=0===
```

**10회 전부 통과했다 — 반증이 재현되지 않았다.**

이것을 **"`call_once` 가 불필요하다" 로 읽지 않는다.** 두 가지 이유다:

1. **경쟁 창이 좁다는 것이 없다는 뜻은 아니다.** 등록은 짧고, 대부분의 실행에서 첫
   스레드가 끝낸 뒤 나머지가 도착한다. 창이 좁을수록 재현이 어려울 뿐이다.
2. **반증이 재현되지 않은 것은 가드가 불필요하다는 증거가 아니라, 이 테스트가 그 종류의
   결함을 잡을 만큼 민감하지 않다는 증거다.** 민감하지 않은 도구로 얻은 음성은 음성이 아니다.

`call_once` 는 유지한다. 비용이 사실상 0이고, 제거의 근거는 "재현 못 했다" 뿐이다.

## 6. 미검증 (Gaps)

- **비트 깊이 변종을 만들지 않았다** (§2.3). 8비트·12비트 원본이 필요한데 writer 가
  UINT16 만 쓴다. 태그만 바꾼 파일은 변종이 아니라 손상 파일이다.
- **컬러·다중 프레임 JPEG-LL 은 범위 밖이다.** 이 모듈은 그레이스케일 단일 프레임만
  다루고, 그것이 요구인지 이 카드에서 확인하지 않았다.
- **실제 장비 인코더 산출물은 여전히 보지 않았다.** 7종 모두 DCMTK 가 만든 것이다.
  다른 구현이 만든 JPEG-LL 이 같은 예측자 값이라도 다른 바이트 배치를 쓸 수 있다.
- **동시성 테스트는 `open()` 만 겹친다.** 같은 핸들을 두 스레드가 공유하는 경우,
  `close()` 와 `read` 가 겹치는 경우는 보지 않았다 — 그것은 다른 계약이다.
- **커버리지는 판독이다**(§4). 측정치가 아니다.
- **`.57`(REQ-IOP-003)은 손대지 않았다** — 카드가 범위 밖으로 명시했고 #147 이 있다.

## 7. 잔여 위험 (Residual-risk)

- **반증이 재현되지 않은 항목이 하나 남는다.** `call_once` 의 필요성은 여전히
  **코드 판독에 기대고 있다.** 이 테스트로는 그 종류의 결함을 잡지 못한다는 것이
  이번에 확인된 것이고, 잡으려면 등록 지점에 지연을 주입하는 등 **테스트가 구현 내부를
  알아야 하는** 방법이 필요하다 — 그러면 테스트가 구현에 묶인다.
- **7종 통과가 "모든 JPEG-LL 을 읽는다" 는 아니다.** 인코더가 하나다.
- **동시성 테스트가 CI 에서 간헐 실패할 수 있다.** 8스레드가 같은 파일을 여는 부하는
  러너 사정에 영향을 받는다. 실패하면 **경쟁의 증거일 수도, 러너의 문제일 수도** 있으므로,
  그때는 원인을 가르기 전에 결론을 내리지 않아야 한다.
- 커밋은 push 전까지 미푸시다.
