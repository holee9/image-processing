# QA-B-169 (`#130`) — 프로토콜 정합. **증상은 있었고, 원인은 번호가 아니라 봉투였습니다**

## 1. 주장

1. **고치기 전 증상을 쟀습니다.** 워커에 헤더 프레이밍 메시지를 보내면 **어떤 종류든**
   워커가 `99`(자기 `ERROR_RESPONSE`)를 돌려주고 **종료 요청도 안 죽습니다.** 스텁·풀 동일. §2
2. **번호 셋이 어긋난 것은 원인의 일부일 뿐이었습니다.** 번호가 **맞는** `INIT`(1==1)도
   실패했습니다 — 원인은 **봉투 모양**입니다. 워커는 헤더 첫 단어(매직)를 자기 메시지
   타입으로 읽었습니다. **번호만 맞췄다면 여전히 깨졌습니다.** §2.2
3. **고쳤습니다.** 워커가 `ai_worker_protocol.h` 의 enum·헤더·JSON 프레이밍만 씁니다.
   사설 enum·구조체 삭제. 전 6건 빨강 → 후 7/7 통과, **스텁·풀 양쪽**. §3
4. **`STUB_VERSION_STRING` 을 같이 고쳤습니다.** 풀 빌드가 `"0.1.0-stub"` 을 답하던 것 →
   빌드에 따라 `-stub` / `-full`. 이 단언은 **두 구성에서 결과가 다릅니다.** §4
5. **반증 셋 모두 의도한 시험 하나만 정확히 빨개집니다.** 번호 틀림 / 버전 거짓(풀에서만) /
   사설 enum 복귀. §5
6. **헤더는 32바이트가 아니라 40바이트입니다.** 주석 세 곳이 틀렸고 `static_assert` 로 고정. §6
7. 종합: `ci-post` **902 중 901** · `ci-ai` **266/266**. 빨강 1건은 `enhance_basic` 의 20 ms
   타이밍 게이트이고 **간헐적**입니다. §7

## 2. 먼저 잰 것 — **고치기 전 증상**

카드 §2 가 요구한 대로 **일부러 붙였습니다.** 시험이 실제 `xpe_ai_worker.exe` 를 띄우고
브리지로 연결합니다(`test_worker_protocol_conformance.cpp`). 워커는 프로세스 가드가 종료를
보장하고, 마지막에 남은 워커 수를 셉니다(**네 번 모두 0**).

### 2.1 대조군 — 하네스가 멀쩡한가

`TheWorkerLaunchesAndTheBridgeConnects` — **전 구성·전후 모두 통과.** 워커가 뜨고, 연결되고,
200 ms 안에 스스로 죽지 않습니다. 이것이 없으면 아래 "메시지가 안 먹었다" 는 단언이
하네스 고장으로도 똑같이 나옵니다.

### 2.2 관측 (전, 옛 워커, 스텁·풀 동일)

```
before  ci-post(스텁)  6 실패 / 1 통과      ===before_STUB_RUN=1===
before  ci-ai  (풀)    6 실패 / 1 통과      ===before_FULL_RUN=1===

  rc=-1 (XPE_ERR_INVALID_INPUT, i.e. not a protocol frame); first word of the reply = 99
  the worker did not exit within 3000 ms of a protocol SHUTDOWN (type 3)
```

| 카드가 든 세 갈래 | 실측 |
|---|---|
| 심박 응답만 하고 **안 죽는다** | **아님 — 심박 응답조차 못 함** |
| `ERROR_RESPONSE` | **이것입니다** — 첫 단어 `99` |
| 교착 | 아님 |

**종료(`SHUTDOWN`)는 안 죽었습니다.** 3초를 기다려도 프로세스가 남았습니다 —
`REQ-AI-003` 격리가 막으려던 실패입니다.

### 이유 — 번호가 아니라 **봉투**

워커는 `WorkerMessage` 구조체를 통째로 `ReadFile` 하고 **첫 4바이트를 메시지 타입**으로
읽습니다. 브리지는 헤더를 보내고, **헤더의 첫 4바이트는 매직**(`0x58504541`)입니다. 그래서
**모든** 헤더 프레이밍 메시지가 "타입 = 매직" 이 되어 `default` 갈래로 떨어지고,
워커는 `ERROR_RESPONSE` 구조체로 답합니다. 브리지는 그 첫 단어(`99`)가 매직이 아니라며 거부합니다.

> **카드의 물음에 대한 답**: *"번호만 맞춰도 본문에서 다시 깨진다면 그것이 이 카드의
> 크기"* — **그렇습니다.** `INIT` 은 번호가 같은데도 실패했으므로(§`InitPerTheHeader…`),
> 번호 정합만으로는 아무것도 고쳐지지 않았습니다. 봉투 교체가 이 카드의 본체입니다.

### 2.3 제 이전 진단의 정정 두 가지 (`QA-B-167` 보고서)

- **"헤더는 32바이트"** — 틀렸습니다. 실측 `sizeof(XpeAiMessageHeader) == 40`
  (`uint32`×6 = 24, `timestamp` 8, `reserved[8]` 8). 헤더 자신의 주석 두 곳과 시험 주석
  두 곳이 같이 틀려 있었고, 제 보고서와 카드가 그것을 옮겨 적었습니다. **§6.**
- **제 첫 시험 문구가 "응답 없음"** 이라 적었습니다 — `rc=-1` 은 침묵이 아니라 **거부된
  응답**입니다. 워커는 답했습니다. 문구를 고쳤습니다(아래).

## 3. 고친 것

`modules/ai/src/ai_worker_main.cpp` — 사설 `enum class MessageType`·`WorkerStatus`·
`WorkerMessage` 삭제, 헤더 프레이밍으로 교체.

| 받는 것 (헤더 enum) | 돌려주는 것 |
|---|---|
| `XPE_AI_MSG_INIT`(1) | `XPE_AI_MSG_INIT_RESPONSE`(2) + JSON |
| `XPE_AI_MSG_HEARTBEAT`(4) | `XPE_AI_MSG_HEARTBEAT_ACK`(5) + `{"state":0}` |
| `XPE_AI_MSG_SHUTDOWN`(3) | **응답 없이 종료** (아래) |
| 그 밖 전부(추론 8종·모델관리 4종 포함) | `XPE_AI_MSG_ERROR`(99) — **"not handled" 라고 말합니다** |

프레임을 신뢰할 수 없을 때(매직·프로토콜 주 버전·페이로드 상한 위반)는 오류로 답하고
**루프를 끝냅니다** — 다음 프레임 경계를 알 수 없어 계속하면 쓰레기를 메시지로 읽습니다.
알 수 없는 **타입**은 프레임은 멀쩡하므로 오류로 답하고 **계속**합니다(시험이 그 뒤 심박이
여전히 응답되는지 단언합니다).

### 3.1 워커에만 있던 것 — **제 결정이고, 되돌릴 수 있습니다**

카드가 물었습니다: `SHUTDOWN_ACK = 6` 과 `WorkerStatus` 에 헤더 대응이 없으면 헤더에
추가할지 워커에서 뺄지는 리더에게 물으라고. **회신이 끊긴 상태라 기다리지 않았고,
헤더를 건드리지 않는 쪽을 골랐습니다**(리더도 "헤더가 정본"이라고 했습니다):

- `SHUTDOWN_ACK` → **뺐습니다.** 헤더에 종료 응답 타입이 없고, 프로세스가 종료하며 파이프가
  닫히는 것이 응답입니다.
- `WorkerStatus`(`IDLE`/`BUSY`/`FAILED`) → 헤더의 `XpeAiWorkerState` 로 대체. **`FAILED=2`
  는 헤더의 `ERROR=3` 과 번호가 다릅니다** — 이번에 `IDLE=0` 만 보내므로 오늘은 드러나지 않습니다.

> **리더 확인 요청**: 종료 응답이 필요하면(예: 호스트가 "정상 종료했다" 와 "죽었다" 를
> 구별해야 한다면) 헤더에 `XPE_AI_MSG_SHUTDOWN_ACK` 를 **추가**해야 합니다. 지금 구조에서는
> 둘이 같은 파이프 EOF 로 보입니다. **`QA-B-171`(HAZ-008 검증)에서 이것이 필요해질 가능성이
> 큽니다.**

### 3.2 INIT 응답 — 문서화된 스키마를 **확장**했습니다

헤더 주석의 INIT 응답 스키마는 `success`/`loaded_models`/`execution_provider`/`worker_pid` 입니다.
옛 사설 `INIT_ACK` 이 실어 나르던 **버전·기능** 정보가 사라지지 않게 `worker_version`,
`mode`, `capabilities` 를 더했습니다(`capabilities: 0` — 추론 메시지가 아직 없으니까).
**문서화된 필드는 그대로이고 추가만 했지만, 스키마 문서에는 반영하지 않았습니다** — §8.

## 4. `STUB_VERSION_STRING` — 같은 성질의 결함

카드 §3 대로 같이 고쳤습니다. 옛 상수는 `#ifdef` 밖이라 **풀 빌드도 `"0.1.0-stub"`** 을
답했고, 시작 로그(`Mode: FULL`)와 응답이 모순이었습니다. 지금은:

```
STUB  "0.1.0-stub"  mode "stub"        FULL  "0.1.0-full"  mode "full"
```

**이 단언은 두 구성에서 결과가 다릅니다**(`TheInitResponseNamesTheBuildTheWorkerReallyIs`):
시험 바이너리와 워커는 같은 CMake 조건으로 설정되므로, 워커가 보고하는 모드는 시험
바이너리의 모드와 같아야 합니다. 둘이 갈라지면 빨강입니다(§5 B).

## 5. 반증 — 셋 모두 **의도한 시험 하나만** 빨개집니다

각 주입은 `grep` 으로 들어갔는지 확인한 뒤 측정했고, 끝나면 `cmp` 로 새 워커와 **바이트
동일함**을 확인해 복원했습니다.

| | 주입 | 결과 |
|---|---|---|
| **A** | `SHUTDOWN` 의 번호를 옛 워커의 5 로(`case XPE_AI_MSG_HEARTBEAT_ACK`) | `ShutdownPerTheHeader…` **1건만** 빨강, 6건 통과 |
| **B** | 풀 빌드가 다시 `"0.1.0-stub"` 를 답하게 | **스텁 7/7 통과 · 풀 6/7** (`TheInitResponseNames…` 만 빨강) |
| **C** | 워커에 `enum class MessageType` 복귀 | `TheWorkerSourceDeclaresNoPrivateMessageEnum` **1건만** 빨강 |

**B 가 카드 §4 의 "구성에 따라 달라져야 맞다" 입니다** — 같은 결함이 한 구성에서는
초록, 다른 구성에서는 빨강입니다.

**전후 대조는 같은 프로브로 했습니다.** 시험을 다듬은 뒤 **진짜 원본 워커**(`git show
HEAD:…`)로 다시 재었습니다 — 먼저 저장해 둔 "옛 워커" 는 헤더만 바꾼 **혼합본**이라
(사설 enum 0건) 전 측정이 될 수 없다는 것을 사설 enum 개수로 확인하고 버렸습니다.

## 6. 헤더 크기 — 32가 아니라 **40**

```
sizeof(XpeAiMessageHeader) = 40      (cl 로 직접 컴파일해 측정)
```

`ai_worker_protocol.h` 주석 2곳과 `test_ai_ipc_bridge.cpp` 주석 2곳을 정정했고,
**`static_assert(sizeof == 40)` 로 고정**했습니다 — 틀린 주석은 어떤 빌드도 못 잡지만
이 `static_assert` 는 잡습니다. C/C++ 양쪽 컴파일러 갈래를 넣었습니다.

**와이어 포맷은 바뀌지 않았습니다** — 코드는 처음부터 `sizeof` 를 썼고 주석만 틀렸습니다.

## 7. 검증

```
ci-post  ===POST_BUILD=0===  902 중 901 통과 (1 실패 — 아래)     직전 보고 895 → +7
ci-ai    ===AI_BUILD=0===    ===AI_CTEST=0===  266/266 통과      직전 보고 259 → +7
WorkerProtocolConformance  전 6실패/1통과 → 후 7/7  (스텁·풀 각각)
남은 xpe_ai_worker 프로세스  전·후·반증 A/B/C·최종  전부 0
```

**시험 수를 이전 보고와 대조했습니다**(`QA-B-169a` 에서 안 센 바로 그것). 차이 7 = 새 시험 7건,
`ci-post` 와 `ci-ai` 양쪽에서 정확히 맞습니다. 두 프리셋 모두 `/WX` 가 붙는 구성입니다.

### 7.1 빨강 1건 — `EdgeEnhance.Performance_3072x3072_Within20ms`

```
ci-post ctest   ***Failed  0.07 sec
단독 3회 재실행  통과(28 ms) · 통과(28 ms) · 실패(`ms <= 20`, 실제 21)
```

**`enhance_basic` 의 20 ms 타이밍 게이트**이고 `modules/ai` 를 링크하지 않습니다. **간헐적**
(4회 중 2회 실패)이고, 실패값이 한계를 1 ms 넘긴 21 입니다. 여유 물리 메모리가 약 1.5 GB인
기계에서 쟀습니다(리더가 메모리가 극도로 빡빡하다고 알렸습니다). 이 저장소가 *"게이트가 잘못된
기계에서 잡혔다"* 를 이미 적은 형태와 같습니다. **제 변경이 원인이 아니라는 것을 증명하지는
못했습니다** — 미변경 트리에서 같은 빈도로 실패하는지는 재지 않았습니다(§8).

## 8. 미검증 · 잔여 위험

- **빨강 1건(§7.1)의 인과를 미변경 트리에서 대조하지 않았습니다.** 다른 모듈이고 간헐적이라는
  것까지가 관측입니다
- **`SHUTDOWN_ACK` 를 뺀 것은 제 결정입니다**(§3.1). 리더 확인이 필요하고, `QA-B-171` 에서
  추가가 필요해질 수 있습니다. `WorkerStatus.FAILED(2)` ↔ 헤더 `ERROR(3)` 번호 불일치는
  오늘 드러나지 않을 뿐 **남아 있습니다**
- **INIT 응답의 `worker_version`/`mode`/`capabilities` 는 스키마 문서(헤더 주석)에 반영하지
  않았습니다.** 문서화된 필드는 그대로이고 추가만 했습니다
- **브리지가 파이프를 `FILE_FLAG_OVERLAPPED` 로 열면서 `ReadFile`/`WriteFile` 에는
  `OVERLAPPED` 를 안 넘깁니다**(`ai_ipc_bridge.cpp`). Win32 문서상 미정의 동작이지만
  이번 측정에서는 정상 동작했습니다 — **손대지 않았고 원인 여부도 확인하지 않았습니다**
- **워커는 아직 추론 12종을 처리하지 않습니다**(`QA-B-170`). 지금 응답은 "not handled" 오류입니다
- **페이로드는 읽고 버립니다** — 지금 받는 세 종류는 페이로드를 안 씁니다. 페이로드를 쓰는
  메시지가 생기면 `INIT` 의 `model_dir` 등을 파싱해야 합니다
- **프레이밍은 두 번의 `WriteFile`(헤더, 페이로드)입니다.** 파이프가 메시지 모드라 두 메시지로
  가는데, 브리지는 바이트 모드로 읽어 지금은 맞물립니다. 페이로드가 큰 메시지에서도 그런지는
  **재지 않았습니다**
- **Windows 전용 시험입니다**(`CreateProcess`·named pipe). 이 프로젝트가 Windows 전용이라
  분기하지 않았습니다
