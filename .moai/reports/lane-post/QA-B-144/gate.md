# QA-B-144 (#155) — 1단계 적용 완료. 그리고 **§5 는 절반만 맞습니다**

## 1. 주장 (Claim)

1. **1단계 적용.** 역순 전사를 표준 Eq 7-2 로 교체했고, 네 설정 전부 **정확 램프에서
   ≤1 카운트** — 새 게이트를 통과합니다.
2. **지문은 게이트에서 뺐습니다.** 정보성 출력으로만 남습니다.
3. **(a) `luminanceValues` 는 최소·최대만 쓰이고 나머지는 버려집니다** —
   `presentation_lut.cpp:99-103`. **단언으로 박았습니다.** 다만 **숨은 결함이
   아닙니다**: `display_api.h` 가 이미 명시하고 있습니다.
4. **(b) LUT 입력 인덱스는 "창처리된 검출기 DN" 에 선형입니다** — SPEC(REQ-DISP-012·017)
   과 유일한 호출자(`MinOut=0, MaxOut=1`) 양쪽이 같은 말을 합니다.
5. **§5 판정: 앞 절반은 맞고, 뒤 절반은 "원리적으로 옳으나 현재 계약으로는 불가능"
   합니다.** 근거 §5.

## 2. 1단계 — 적용과 새 게이트

준비본을 적용했습니다. `presentation_lut.cpp:110-118` 의 3차식 → 표준 Eq 7-2
(8차 다항식, Horner). **상쇄 구조는 한 글자도 안 건드렸습니다.**

| 설정 | 정확 램프와의 최대 차 | 다른 인덱스 수 |
|---|---|---|
| 1..500 | **1** | 1 / 1024 |
| 80..120 | **1** | 19 / 1024 |
| 0.01..10000 | **1** | 2 / 1024 |
| 0.05..4000 | **1** | 2 / 1024 |

시험 이름을 `Stage1_LutBytesAreUnchanged…` → **`Stage1_LutIsStillTheStraightRampAfterTheCoefficientFix_155`**
로 바꿨습니다. 이름이 곧 단언이라, 옛 이름을 두면 다음 사람이 바이트 동일이 조건인 줄
읽습니다. **지문은 `GTEST_LOG_` 로만 나가고 `EXPECT` 가 없습니다.**

**낡은 주석 하나도 고쳤습니다**: 시험의 `ModuleCubicJnd` 가 *"copied from
presentation_lut.cpp:113-118"* 라고 적혀 있었는데, 이제 제품에 그 식이 없습니다.
**"무엇이 있었는지의 기록"** 으로 다시 적었습니다 — 지우면 역순 전사 판정의 증거가
사라집니다.

## 3. (a) `luminanceValues` 는 곡선이 아닙니다 — **끝점 둘뿐입니다**

### 코드

`presentation_lut.cpp:99-103` 이 배열 전체에서 **running min/max** 만 뽑고, 그 뒤로
배열은 **한 번도 읽히지 않습니다**. `count` 는 루프 경계와 `count < 2` 가드에만 쓰입니다.

### 단언 (`KnownDivergence_OnlyTheLuminanceEndpointsAreUsed_155`)

최소 1.0 · 최대 500.0 을 고정하고 **개수·간격·순서·모양**을 전부 바꾼 다섯 입력:

| 변형 | LUT 차이 |
|---|---|
| `{1, 500}` (내부 없음) — 기준 | — |
| `{1, 10, 50, 200, 500}` 로그 간격 | **0** |
| `{1, 2, 3, 4, 500}` 아래로 몰림 | **0** |
| `{1, 496, 497, 498, 500}` 위로 몰림 | **0** |
| `{500, 3, 1, 111, 7}` 순서 뒤섞음 | **0** |

**비트 동일입니다.**

### 그런데 **숨은 결함이 아닙니다** — 이미 문서화돼 있습니다

`display_api.h` 의 파라미터 설명:

> `@param luminanceValues [in] Array of measured luminance values (cd/m^2), count >= 2.
> **Only the minimum and maximum of the array are used; intermediate measurements do not
> affect the resulting LUT.**`

**선언된 계약입니다.** `#155` 의 상쇄(코드가 계산하고 버리는 것)와 **성질이 다릅니다** —
이쪽은 "안 쓴다" 고 **말하고** 안 씁니다. 그 계약이 `REQ-DISP-025` 가 원하는 것인지는
SPEC 질문이고, 제가 정하지 않습니다.

### 대조군이 약할 수밖에 없는 이유 (정직하게)

대조군은 "끝점을 바꾸면 움직인다" 여야 하는데, **끝점조차 반올림으로만 움직입니다** —
그게 `#155` 본문입니다(6 decades 에 1 카운트). 그래서 대조군이 보여 줄 수 있는 것은
**"0 이 아니다"** 까지입니다.

**처음 고른 대조군(500→4000)은 비트 동일이라 실패했습니다.** QA-B-143 이 지문이 다르다고
기록한 쌍(`1..500` 대 `80..120`)으로 바꿔 **1 카운트** 차이를 얻었습니다. 그 경위를
시험 주석에 남겼습니다.

## 4. (b) LUT 입력 인덱스는 무엇에 선형인가

**답: 창처리된 검출기 DN.** 두 출처가 같은 말을 합니다.

- **SPEC**: `REQ-DISP-012` 가 VOI 출력을 `[minOut, maxOut]` 로 규정하고,
  `REQ-DISP-017` 이 창 중심·폭을 **검출기 DN 영역**으로 못박습니다(2026-09-17 개정).
  `REQ-DISP-019` 는 그 값을 `round(input × 1023)` 로 색인합니다.
- **유일한 호출자**: `gui/ImageProcTest/Services/RealXpeBackend.cs:152-160` 이
  `MinOut = 0.0f, MaxOut = 1.0f` 로 VOI 를 호출합니다 — 창처리된 DN 을 [0,1] 에
  **선형으로** 실어 보냅니다.

즉 P-값(LUT 인덱스)은 **영상 신호에 선형**이고, 광도에도 JND 에도 선형이 아닙니다.
**그리고 그것이 GSDF 가 요구하는 바와 충돌하지 않습니다** — PS3.14 에서 P-값은
디스플레이의 **입력 부호**일 뿐이고, 표준이 요구하는 것은 *"P-값 등간격 → 지각 등간격"*
입니다. 인덱스가 물리량에 선형일 필요는 없습니다.

## 5. §5 판정 — **앞 절반 맞고, 뒤 절반은 현재 계약으로 불가능합니다**

### 앞 절반: "인덱스 → `j` 선형" — **맞습니다**

리더가 인용하신 PS3.14 §7 정의(*"equal changes in P-Values will result in the same level
of perceptibility"*)가 곧 **P-값 등간격 = JND 등간격**입니다. 모듈은 **이미 그렇게**
합니다 — `target_jnd = jnd_min + (i/1023)·jnd_range` 가 정확히 인덱스→`j` 선형입니다.

**그래서 빠진 것은 `j → L`(Eq 7-1) 하나입니다.** 그것이 `#155` 의 상쇄이고, 2단계가
없앨 것입니다. **이 부분은 SPEC 이 말합니다.**

### 뒤 절반: "`L → DDL` 은 측정 곡선을 역으로 푸는 일" — **원리는 옳으나 지금은 불가능**

**원리로는 리더가 맞습니다.** 실제 GSDF 교정이 그렇게 돕니다: 각 P-값에 대해 표준이
요구하는 `L` 을 구하고, **측정된 특성 곡선 `L(DDL)`** 에서 그 `L` 을 내는 DDL 을 찾습니다.

**그런데 현재 계약으로는 풀 곡선이 없습니다.** 세 가지가 막습니다:

1. **곡선이 입력에 없습니다.** `display_api.h` 가 중간값을 **안 쓴다고 명시**하고,
   §3 이 그것을 측정으로 확인했습니다.
2. **DDL 연결이 정의돼 있지 않습니다.** 배열은 광도만 나열하고, **원소 `i` 가 어느
   구동 준위에 해당하는지 어디에도 없습니다** — API 문서에도, `REQ-DISP-025` 에도.
   정렬 요구도 없습니다(§3 의 순서 뒤섞기 변형이 그대로 통과합니다).
3. **유일한 호출자가 측정값을 안 보냅니다.** `RealXpeBackend.cs:165` 가
   **하드코딩된** `{0.05, 1.0, 10.0, 100.0, 400.0}` 을 넘깁니다.

> **결론**: 리더의 읽기는 **API 가 무엇을 뜻할 수 있는지**를 말하고, **오늘 무엇을
> 뜻하는지**를 말하지 않습니다. 역으로 풀 곡선이 **존재하지 않습니다.**

### 그래서 "14.8 % 도 44.0 % 도 정답이 아니다" 는 — **맞습니다, 다른 이유로**

리더는 *"둘 다 측정 입력을 무시한 고정 매핑"* 이라 하셨습니다. **맞습니다.** 다만
이유가 "측정 곡선을 써야 하는데 안 써서" 가 아니라 **"쓸 측정 곡선이 애초에 입력에
없어서"** 입니다. 두 수는 QA-B-142 가 규모를 말하려고 고른 **두 해석**이지, 선택지가
아닙니다.

### 2단계가 답해야 할 질문은 셋입니다 (제가 정하지 않습니다)

1. `L → DDL` 을 **고정 매핑**으로 둘 것인가(그러면 어느 것이고 근거는), 아니면
2. **API 계약을 바꿔** 측정 곡선을 받을 것인가(그러면 `(DDL, L)` 쌍 또는 "등간격 N개
   구동 준위" 같은 **순서 계약**이 필요하고, 호출자도 바뀝니다), 아니면
3. `REQ-DISP-025` 의 *"valid luminance measurement values"* 를 **끝점 둘**로 읽고
   `display_api.h` 의 현재 계약을 SPEC 에 명시할 것인가

**2번이 리더의 읽기이고, 그것은 제품 API 변경입니다** — 레인이 결정할 것이 아닙니다.

## 6. baseline 귀속 · 미검증 · 잔여 위험

**귀속**: 트리 `dev/postprocess`, `origin/main a18ab2e` 병합 후. 커밋 `df2acdb`.

**미검증**

- **역순 전사가 의도였을 가능성**을 여전히 배제 못 했습니다 — 계수 넷이 다 맞으니
  우연은 아니지만, 그 배열을 쓰는 문헌은 찾지 않았습니다(커밋 메시지에 기록).
- **식의 이미지 원문은 못 봤습니다.** 형태는 Table B-1 열 점 + 왕복 + 4000 상한이
  지지합니다(QA-B-142 와 동일).
- **±1 이 화면에 보이는지** 여전히 판단 안 했습니다. 리더의 근거("1단계는 종착지가
  아니다")를 그대로 받습니다.
- **호출자를 하나만** 확인했습니다(`RealXpeBackend.cs`). `clients/` 의 진단 코드는
  함수 **존재**만 확인하는 것으로 보이나 전수 확인은 안 했습니다.
- **`REQ-DISP-019` 의 입력이 "창처리된 DN에 선형" 이라는 것**은 SPEC 과 GUI 호출자에서
  읽은 것이고, 다른 호출자가 다른 `MinOut/MaxOut` 을 쓰면 달라집니다.

**잔여 위험**

- 새 게이트(`≤1`)는 **2단계에서 반드시 깨집니다.** 그 커밋에서 이 시험을 은퇴시켜야
  하고, 은퇴가 곧 "곡선이 바뀌었다" 의 가시적 도착입니다. 시험 주석에 적어 두었습니다.
- `KnownDivergence_OnlyTheLuminanceEndpointsAreUsed_155` 의 대조군은 **1 카운트**에
  의존합니다. 2단계 뒤에는 끝점이 크게 움직일 것이므로 이 대조군은 **더 튼튼해집니다**
  — 반대로, 만약 1 카운트가 다른 플랫폼에서 0 이 되면 이 시험이 빨강이 됩니다.
