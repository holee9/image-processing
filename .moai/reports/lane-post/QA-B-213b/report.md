## 1. 극성은 어디서 정해지는가

**SPEC·명세가 말하는 것** (인용):
- `XPE-SRS-001` SRS-FUNC-023: MONOCHROME1 은 `xpe_dicom_read_image` 가 읽을 때 `(2^BitsStored − 1) − 값` 으로 정규화해 MONOCHROME2 의미로 돌려준다. **"이후 파이프라인은 항상 MONOCHROME2 의미의 화소를 받으며 표시 단계는 극성을 바꾸지 않는다."**
- `SRS-DICOM-001` FR-DCM-109 와 `dicom_api.h` 주석: 같은 내용. `xpe_dicom_write` 는 항상 MONOCHROME2 + Presentation LUT Shape IDENTITY 를 쓴다(`DicomWriter.cpp:178`).
- `XPE-SDD-002` "극성 처리" 절과 Edge Case 표: 같은 내용.
- `pipeline-spec.md` 단계 `(5)` 로그 ~ `(17)` DICOM 쓰기: 극성을 바꾸는 단계가 없다. `SPEC-XPE-P1B-ENH`, `SPEC-XPE-P1B-DISP` 본문에는 극성·반전·MONOCHROME 이라는 말이 없다(검색어 `MONOCHROME|photometric|polarity|invert|극성|반전`. 같은 검색어가 DICOM·SRS 문서에서는 위 문장들을 찾아내므로 검색 자체는 작동한다 — 대조군).

**실제 코드가 하는 것**:
- 로그(단조 증가), 노이즈, CLAHE, USM, Modality, VOI(LINEAR)는 모두 값의 순서를 바꾸지 않는다. `minOut > maxOut` 은 QA-B-207 D8 이후 거부되므로 VOI 로 뒤집을 수도 없다.
- Presentation LUT 는 1024칸 임의 표다(REQ-DISP-019). **내림차순 표를 주면 뒤집힌다** — 실측: 내림차순 LUT 출력과 `65535 − 오름차순 출력` 의 차이 나는 화소 0개(`p8_variants.txt`, `v2` 줄).
- 운영자 앱(`clients/ImageProcTest`): `ViewportRenderParams.Invert = false` 가 기본, `EvaluationViewerPanel` 에 사용자가 켜는 "Invert" 체크박스가 있고 `ViewportRenderService.cs:159` 가 `255 − pixel` 로 반전한다. 데이터에 따라 자동으로 켜는 코드는 없다(`Invert` 를 쓰는 곳 전부 확인, 스냅샷·보고서 기록 제외). 앱은 읽기만 했고 실행하지 않았다.
- 입력 영상(원시 `.raw`)에는 DICOM 기록이 없다. `fixture-manifest.json` 등 gui 픽스처의 json·md·txt 에 Photometric Interpretation 이 없다.

**정리**: 검출기 선형 값은 선량에 비례하므로 공기가 높다. XPE 파이프라인은 어디서나 "값이 클수록 밝다(MONOCHROME2 의미)" 를 가정하고 한 곳도 뒤집지 않는다. 그 결과 (a) 원시 검출기 프레임은 공기 흰 영상이 되고, (b) 체인 출력을 `xpe_dicom_write` 로 내보내면 MONOCHROME2·IDENTITY 로 쓰이므로 어떤 뷰어에서도 공기가 희다, (c) MONOCHROME1 DICOM 입력은 읽을 때 뒤집히므로, 선량 비례 값을 MONOCHROME1 로 표기한 파일이면 뼈가 밝은 쪽으로 들어온다(전형적인 경우를 가정한 추정이며 실제 파일로 확인하지 않았다). 즉 **입력 출처에 따라 극성이 달라진다.**

**결정이 필요한 점** (선택지):
- A. Presentation LUT 를 내림차순으로 만든다 — 지금 코드로 되고 DICOM 은 MONOCHROME2 그대로이며 화소값이 이미 뒤집힌 채 저장된다. 단 SRS-FUNC-023 의 "표시 단계는 극성을 바꾸지 않는다" 는 문장과 겉으로 충돌한다(그 문장은 MONOCHROME1 입력을 두 번 뒤집지 않으려는 뜻으로 읽히지만, 문구를 고쳐야 한다).
- B. 공기가 높은 데이터를 MONOCHROME1 로 쓴다 — `xpe_dicom_write` 가 항상 MONOCHROME2 라 쓰기 변경이 필요하고, 읽기 정규화와 앱의 반전이 짝으로 필요하다.
- C. 향상 단계 입구(로그)에서 뒤집는다 — 새 요구가 필요하다. EI/DI 와 선량 의미가 로그 전 선형 영역에 있어 순서에 주의해야 한다.
- D. 앱의 Invert 를 기본으로 켠다 — 앱 안에서만 맞고 내보낸 DICOM 은 여전히 공기가 희다.

## 3. CLAHE 띠·번짐

### 3.1 제품이 표준 알고리즘인가

실영상의 CLAHE 입력(노이즈 출력)에 제품 `xpe_contrast_enhance`(clip 3.0, 8×8)와 QA-B-207 의 독립 참조(`clahe_ref.py.txt`, Zuiderveld 정의로 쓴 numpy 구현)를 각각 적용해 비교했다(`p8_clahe_band.txt` 1절):

```
reference as written in QA-B-207 (bins by float32 truncation):  max|diff|/range = 9.720e-04, 1e-3 넘는 화소 0 / 9437184
reference with float64 bins (exact in practice):                max|diff|/range = 1.565e-07, p99.99 = 1.388e-07
```

제품의 구간 계산은 QA-B-207d 이후 정확한 정수식이라, 같은 방식의 float64 구간을 쓴 참조와 비교하는 것이 맞는 대조이며 그때 차이는 범위의 1.6e-7 이다. 옛 참조(float32 절단)와의 9.7e-4 는 구간 배정 차이이고 207 의 2e-4 허용치를 넘으므로 "이 비교에서는 허용치를 쓰지 않았다" 고 적어 둔다. **제품은 정의대로의 CLAHE 이다 — 구현 결함의 증거는 없다.**

### 3.2 띠는 타일 격자와 맞는가

타일은 3072/8 = 384 화소. 경계는 x = 384·k, 타일 중심은 x = 192, 576, 960, 1344, …. 공기 띠(행 300–2800, 열 0–1250)에서 CLAHE 가 더한 값(로그 단위):

- 타일 열별 평균 변화: 열 0(x 0–384) −68.5, 열 1(384–768) −37.1, 열 2(768–1152) −18.1, 열 3(1152–1250) +36.5 (참조 구현도 같은 값).
- 31화소 평활 프로파일: x=32 에서 −85.5 → x≈544 까지 오르다가 **x≈600–930 에서 −31~−32 로 평탄**, 그 뒤 x≈960 부터 다시 올라 x=1184 에서 +32.3. 평탄 구간의 양 끝(극값 600, 928–935)은 **타일 중심 576 과 960 에서 24–32 화소**에 있다. 즉 띠의 모서리는 타일 경계가 아니라 **타일 중심**에 놓인다.
- 타일 경계(384, 768, 1152)에서의 단차(오른쪽 20화소 평균 − 왼쪽): +2.0, −0.2, +5.8 — 연속이다(이중선형 보간이 의도대로 작동).

해석: 같은 마루(평탄 구간)가 타일 중심 둘 사이에 걸쳐 있고 그 바깥은 비탈이라 사람 눈에는 "밝기가 다른 세로 띠" 로 보인다. 타일마다 히스토그램 모양(공기만 있는 타일 / 사지가 걸친 타일)이 달라 변환표가 다르고, 보간이 그 표들 사이를 잇는다.

**Evidence**: 이 폴더의 `p8_variants.txt`(변형 측정), `p8_clahe_band.txt`(CLAHE 분석), `p8_png_list.txt`. 코드 블록과 표의 수는 그 원문에서 옮겼다. 코드·문서 인용은 위치를 적었다.
**Baseline-attribution**: 하니스 `e035a0b1`, `ci-post` 빌드, 입력 `d152e8eb…fdfd4`(213 에서 `sha256sum` 으로 확인한 같은 파일). 변형 `01` 은 213 의 최종 출력과 SHA-256 이 같다(`e3d2d7e3…`).
**Gaps (미검증)**:
- 영상은 손목 측면 한 장이다. 부위별·선량별 창은 측정하지 않았다.
- 해부 영역은 단순 Otsu 분리다. 콜리메이션 검출·AI 마스크로 가른 영역과 결과가 다를 수 있다. 05 의 연조직 잘림은 이 마스크 때문일 수 있다.
- 표의 대비(p95−p05)는 한 지표일 뿐 진단 가치의 척도가 아니다. 임상 판정은 하지 않았다.
- 운영자 앱은 코드를 읽기만 했고 실행하지 않았다. 앱이 체인 출력을 어떤 경로로 받아 그리는지는 확인하지 않았다.
- MONOCHROME1 DICOM 왕복(읽기→처리→쓰기)을 실제 파일로 돌려 보지 않았다. 동작은 헤더 주석과 SPEC 인용으로만 적었다.
- 변형 PNG 는 사용자·리더 육안 확인 전이다. 축소 미리보기로 본 인상(02 는 통상 방사선 영상에 가깝고, 05 는 대비가 크지만 연조직 일부가 잘리며, 08 은 타일 격자가 보인다)은 저자의 관찰이다.
- CLAHE 띠를 줄이는 방법을 체인에 넣어 처음부터 끝까지 다시 그려 보지 않았다(clip 1 등은 CLAHE 단계 출력의 진폭만 쟀다).
**Residual-risk**: 띠 위치를 타일 중심과 맞춘 해석은 한 영상·한 영역(왼쪽 공기)에서 얻었다. SPEC 인용 중 `#151` 이 가리키는 대상이 다르다는 점은 `gh issue view` 로 제목을 읽은 것뿐이라 이슈 본문 전체를 확인한 것은 아니다.
