# QA-B-191 M4 — `xpe_bodypart_recognize` 워커 경로와 시간 예산(092): 설계 메모

카드: QA-B-191 M4 (설계 메모만, 코드 없음) · 관련: #130, REQ-AI-003, REQ-AI-092 · 근거 파일: `ipc_probe_out.txt`, `ipc_probe_source.txt`

**장난감 모델로 배선만 다루는 카드다. 이 메모의 어떤 수치도 실제 모델의 성능을 말하지 않는다.**

## 결론 먼저

1. **무엇이 필요한가**: 워커 프로토콜에 `BODYPART_RECOGNIZE` 요청·응답 형식 정의, 워커의 처리기와 세션, 브리지 호출, 감독자 진입점, `ai.cpp` 의 `use_worker` 분기. 규모는 뼈 억제의 QA-B-170·171 에 가깝다(§7).
2. **시간 예산(092)은 거의 공짜로 따라온다**: 예산은 브리지가 한 교환 전체에 거는 것이고 감독자가 시작 시간까지 포함한다. 부위 인식은 같은 브리지·감독자를 쓰므로 새 규칙이 필요 없다.
3. **영상을 워커에 보내는 비용을 쟀다**: 3072² float(37.7 MB)의 왕복이 약 68 ms(1.1 GB/s). 부위 인식은 영상만 보내고 몇 바이트를 받으므로 편도 약 34 ms 로 어림한다. 크기 조정(7 ms)을 워커에서 하든 부모에서 하든 큰 차이는 아니라서 **원본을 보내고 워커가 크기를 조정**하는 안을 권한다(§3).
4. **결정이 필요한 것은 연속 실패 카운트를 뼈 억제와 공유할지다(D7).** 선택지 셋(공유 S / 함수별 분리 P / 혼합 H)과 동작 차이를 §4 의 시나리오 표로 적었다. **권고는 S, 단 "부위 모델을 쓸 수 없음"을 실패로 세지 않는 예외 하나를 붙인 것(S+).**
5. 새 알림 문구(워커 실패, 부위 인식 판)와 새 프로토콜 필드가 교차 레인 계약이 된다.

## 1. 지금 있는 것 (코드에서 확인)

- 프로토콜 헤더: `XPE_AI_MSG_BODYPART_RECOGNIZE = 10`, `_RESP = 11` 은 **정의만 있다.** 응답 JSON 예시(`body_part`, `confidence`, `model_id`, `inference_ms`, `sidecar`)가 주석에 있으나 요청 형식은 없다. 뼈 억제는 "길이 접두 JSON + 원시 화소"(`XPE_AI_FLAG_HAS_BINARY_PAYLOAD`)로 정의돼 있다.
- 워커(`ai_worker_main.cpp`): `HandleMessage` 의 `case` 가 `INIT`·`HEARTBEAT`·`SHUTDOWN`·`BONE_SUPPRESS` 넷뿐이고 그 밖은 오류 응답이다. 세션은 뼈 억제용 하나(`session_`, `session_dir_`)다. 워커 타깃은 **nlohmann 을 쓰지 않고** 손으로 만든 최소 JSON 도우미(`JsonString`, `JsonUInt`)만 있다.
- 감독자(`WorkerSupervisor`): 진입점이 `Ping`, `BoneSuppress`, `Stop` 이다. 시작·종료 정책(예산 초과 시 죽이고 다음 호출에서 새로 시작, 응답한 워커는 건강한 것으로 유지)은 함수와 무관하다.
- 브리지: `xpe_ai_ipc_bridge_bone_suppress` 만 요청을 보낸다(122줄). 한 교환 전체에 하나의 예산을 건다.
- `ai.cpp`: 연속 실패 상태가 **모듈 하나**에 있다(`workerConsecutiveFailures`, `workerDisabled`, `workerPublished` 하나의 원자 워드, `kWorkerFailureCeiling = 3`). `xpe_ai_worker_state(state, failures, ceiling)` 가 그 한 쌍을 낸다. 부위 인식은 `use_worker` 를 **읽지 않는다**(M2 는 프로세스 안 경로만).
- 결정 기록(`docs/project/REQ-CHANGE-LOG-P3-AI.md`): 3행 실패마다 Warning + 연속 3회 상한, **4행 모든 non-OK 를 센다(건강한 워커의 모델 오류 포함)**, 6행 유효한 성공 응답의 비유한 출력은 세지 않고 연속 횟수를 0 으로 되돌린다.

## 2. 프로토콜 제안

**요청** `BODYPART_RECOGNIZE`(10), 뼈 억제와 같은 이진 형식:
- JSON `{"width": W, "height": H, "format": "float32"}` + 길이 접두 + 원시 화소 W×H float32. 워커는 같은 검사 순서(형식 → 크기 → 모델)를 따른다.

**응답** `BODYPART_RECOGNIZE_RESP`(11), JSON 만(이진 아님):
- `{"success": true, "outcome": "ok", "body_part": "CHEST", "confidence": 0.75}`
- `outcome` 은 모델 출력 판정(§5 의 공유 판정 함수)의 결과: `ok` | `non_finite` | `out_of_range`. `ok` 가 아니면 `body_part`·`confidence` 는 없다.
- 브리지는 **엄격히** 파싱한다(뼈 억제 응답과 같은 규칙): `success`, `outcome` 은 필수. `outcome == "ok"` 이면 `body_part`(비어 있지 않은 문자열, 63바이트 이하), `confidence`(유한, [0,1])가 필수. 하나라도 어긋나면 프로토콜 장애(`IO_FAILED`, 연결을 끊음, 실패로 센다). 모르는 필드는 무시.
- **모델을 쓸 수 없는 경우**(모델 없음, 읽을 수 없음, 라벨 사이드카 문제, 출력 수 불일치, 입력 모양 거절)는 **오류 프레임**(`MSG_ERROR`)이고 `error_code` 가 프로세스 안 경로의 판정과 같은 갈래를 가진다: 모델 없음 `IO_FAILED`, 읽을 수 없음 `CONFIG_INVALID`, 그 밖 `PROCESSING_FAILED`. 라벨·입력 모양 문제는 `PROCESSING_FAILED` 와 메시지의 이유 문구로 구분한다(코드 갈래를 새로 만들지 않는다).

이 구분의 이유는 뼈 억제 6행과 같다: **모델이 정상적으로 답한 것(비유한·범위 밖)은 워커 고장이 아니라 그 영상의 거절**이다.

**프로토콜 헤더의 낡은 예시**(`"body_part"`, `"confidence"`, `"model_id"`, `"inference_ms"`, `"sidecar"`)는 이 형식으로 대체한다. `sidecar` 는 REQ-AI-004(미구현)이므로 제외한다.

## 3. 어디서 크기를 조정하는가 — 측정과 제안

`xpe_bone_suppress` 의 워커 왕복을 실제 워커로 쟀다(`ipc_probe_out.txt`, 3회; 장난감 모델, RelWithDebInfo, i7-12700, 12회가 아니라 7회 최솟값):

| 한 변 | 편도 크기 | 왕복 최솟값 (3회) |
|---|---|---|
| 512 | 1.0 MB | 2.0 ms |
| 1024 | 4.2 MB | 7.5 ~ 7.7 ms |
| 2048 | 16.8 MB | 30.9 ~ 31.5 ms |
| 3072 | 37.7 MB | 68.3 ~ 68.4 ms |

(영상을 보내고 같은 크기를 받는 왕복이다. 부위 인식은 받는 쪽이 몇 바이트이므로 편도에 가깝다 — 이 환산은 측정하지 않은 어림이다.) 워커의 **첫 호출**(워커 시작 포함)은 세 번 중 두 번 97~112 ms, **한 번 1350 ms** 였다(5 s 예산 안, 원인은 조사하지 않았다).

| 안 | 보내는 양 | 부모의 일 | 워커의 일 | 비고 |
|---|---|---|---|---|
| **(a) 원본을 보내고 워커가 크기 조정** (권장) | 영상 전체(3072²: 약 34 ms 어림) | 없음 | 크기 조정 7 ms + 추론 | 모델 세부(입력 크기)가 워커 안에 머문다. 뼈 억제와 같은 요청 모양이다 |
| (b) 부모가 크기를 조정하고 작은 영상을 보냄 | 약 1 MB | 크기 조정 7 ms | 추론 | 부모가 모델의 입력 크기를 알아야 한다 → 워커가 INIT 응답에 크기를 알리거나 부모가 모델을 열어야 한다(후자는 REQ-AI-003 격리 취지에 어긋남) |

(a)를 권하는 이유: 약 34 ms 는 PRD 의 300 ms 중 11% 이지만 실제 모델의 추론 시간을 모르는 지금 최적화할 근거가 없고, (b)는 프로토콜(INIT 응답 확장)과 상태(부모가 입력 크기를 기억)를 늘린다. **측정이 (b)를 필요로 하게 만들면 그때 바꾼다**(요청 형식은 같은 이진 형식이라 바꾸기 쉽다).

## 4. 연속 실패 카운트를 뼈 억제와 공유할 것인가 (D7)

**전제**: 워커 프로세스는 하나다(감독자 하나). 지금 카운트·중단 플래그·`xpe_ai_worker_state` 의 한 쌍은 모듈에 하나다. SRS 해석문(2026-10-01)은 "연속 3회 실패하면 **그 워커**를 세션 동안 중단"이라고 쓰였다.

### 4.1 선택지

- **S 공유**: 카운트·중단 플래그·`worker_state` 가 하나. 어느 함수의 실패든 센다. 어느 함수의 성공이든 0 으로 되돌린다. 중단되면 **두 함수 모두** 워커를 건너뛴다.
- **P 분리**: 함수마다 카운트·중단 플래그. 워커 프로세스는 하나이고 시작·죽임은 감독자가 한다. `xpe_ai_worker_state` 는 함수별로 보고해야 하므로 **C ABI 확장**(새 함수 또는 필드)이 필요하다.
- **H 혼합**: 전송·프로세스 장애(무응답·종료·프로토콜 위반)는 **공유** 카운트, 워커가 정상적으로 돌려준 오류 프레임은 **함수별** 카운트. 4행("모델 오류도 센다")을 함수별 상한으로 바꾸는 것이라 4행의 문구 수정이 필요하다.

### 4.2 시나리오별 동작 차이 (상한 3)

| 시나리오 | S 공유 | P 분리 | H 혼합 |
|---|---|---|---|
| ① 워커가 멈춘다: 뼈 억제 2번 실패 뒤 부위 인식 1번 실패 | 3회째에 **둘 다** 중단 | 어느 쪽도 3 이 안 돼 계속 시도, **함수당 최대 3번**의 예산 낭비 | S 와 같음(프로세스 장애는 공유) |
| ② 한 영상 흐름에서 뼈 억제 성공·부위 인식 실패(워커 안에 부위 모델이 없음)가 번갈아 | **성공이 0 으로 되돌려** 중단되지 않음. 부위 인식은 매번 실패 알림(영상마다 1건) | 부위 인식만 3회 뒤 중단(알림 3건), 뼈 억제는 영향 없음 | S 와 같지 않음: 부위 인식 오류 프레임이 함수별 카운트라 3회 뒤 부위 인식만 중단 |
| ③ 부위 모델 없음으로 오류 프레임 3연속 **뒤에** 뼈 억제 호출 | **뼈 억제가 건너뛰어짐**(모델은 멀쩡한데) — 가장 나쁜 결합 | 뼈 억제는 정상 | 정상 |
| ④ `xpe_ai_worker_state` | 한 쌍(현행 그대로) | 함수별 보고 → **ABI 확장** | 두 종류 보고 → ABI 확장 |
| ⑤ 복구 | `shutdown` → `init` 로 전부 초기화 | 같음 | 같음 |
| ⑥ 구현 상태 | 새 상태 0, `ai.cpp` 분기만 | 함수별 상태, 원자 워드 두 개, ABI 신설 | S + P 의 합 |
| ⑦ 알림 문구 | 부위 인식 판이 하나 필요 | 같음 | 같음 |

### 4.3 권고: S+ (공유, 단 한 가지 예외)

**S 를 권한다.** 이유: 워커가 하나이므로 건강도 하나로 보는 것이 4행·5행·6행과 SRS 해석문의 서술과 같은 단위다. ABI 를 건드리지 않고(④), 상태가 늘지 않으며(⑥), ①의 최악 낭비(예산 × 상한)가 함수 수에 비례해 커지지 않는다.

그러나 순수 S 는 ③이 위험하다. 부위 모델이 없는 배치에서 부위 인식을 부르면 건강한 워커의 오류 프레임이 뼈 억제를 끌어내린다. 그래서 **예외 하나**를 붙인다(S+):

- **"부위 모델을 쓸 수 없음"을 알리는 오류 프레임**(모델 없음 `IO_FAILED`, 읽을 수 없음 `CONFIG_INVALID`, 라벨·입력 모양 문제의 `PROCESSING_FAILED`)은 **워커 실패로 세지 않는다.** 프로세스 안 경로(M2)가 이미 그렇게 다룬다(스텁과 같은 결과 + 세션당 Warning 1건, 카운트 없음). 워커 경로에서도 같은 결과(`UNKNOWN`, 0.0, `PROCESSING_FAILED` + 같은 "unavailable" Warning 세션당 1건)를 낸다. 워커가 정상적으로 응답했으므로 **연속 실패 횟수를 0 으로 되돌린다**(6행의 논리: 건강한 교환이 고장의 연속을 끊는다).
- **예외가 4행과 충돌**한다: 4행은 뼈 억제의 "모델 없음, 입력 거부"를 센다고 못 박았다. S+ 는 **부위 인식 호출에만** 이 예외를 적용하고 뼈 억제의 규칙은 바꾸지 않는다. 그러면 두 함수의 처리가 달라지는 것이 문서에 적혀야 한다(4행에 예외 한 줄 추가; 6행이 이미 하나를 달았다). 리더 결정 사항이다: 4행을 두 함수 모두에 같이 완화할지(뼈 억제의 "모델 없음"도 세지 않기) 부위 인식에만 둘지.
- **센 것은 계속 센다**: 무응답(예산 초과)·프로세스 종료·프로토콜 위반(봉투 불량)·그 밖의 오류 프레임(`PROCESSING_FAILED` 중 "unavailable" 이 아닌 것, `INVALID_INPUT`)은 공유 카운트에 들어간다.
- **저신뢰·비유한·범위 밖**은 이미 4행·6행의 논리로 실패가 아니다(M3 와 같다).

### 4.4 이 결정이 정해 주는 알림 문구

워커 실패 알림은 뼈 억제용 문구("the input image is returned unchanged")를 그대로 쓸 수 없다. 부위 인식 판(교차 레인 계약, 헤더에 전체 기록):
- 실패 `k of N`: `AI worker failed (code {c}, failure {k} of {N}): body-part recognition returns UNKNOWN; use the deterministic body-part lookup (REQ-AI-002, REQ-AI-092)`
- 중단: `AI worker failed (code {c}, failure {k} of {N}) and is disabled for this session: body-part recognition returns UNKNOWN (REQ-AI-002, REQ-AI-092)`
- 이미 중단된 뒤의 호출: 알림 없이 즉시 `UNKNOWN` + `PROCESSING_FAILED`(뼈 억제의 "중단된 뒤에는 조용히"와 같다).

## 5. 판정 함수를 두 경로가 공유한다

프로세스 안 경로(M2·M3)의 **출력 판정**(유한 → [0,1] → 최대 클래스, 라벨 수 일치)과 **결정 꼬리**(문턱 비교·저신뢰 이벤트·`fallback_mode`)를 새 내부 헤더(`ai_bodypart_decision.h` 등)의 순수 함수로 뽑는다. 프로세스 안 경로, 워커(출력 판정 쪽), 부모의 워커 경로(결정 꼬리 쪽)가 **같은 함수**를 쓰므로 두 경로가 갈라질 수 없다. 이것이 뼈 억제의 `test_worker_protocol_conformance`(두 경로를 서로 비교) 방식이다 — 같은 모델·영상·설정에서 라벨·confidence·알림이 같음을 시험으로 못 박는다.

**결정 꼬리는 부모에 둔다**(워커가 아니라): 문턱과 `fallback_mode` 는 부모의 상태이고 런타임에 `xpe_ai_set_fallback_mode` 로 바뀐다. 워커는 모델의 답(`ok` 일 때 라벨·confidence)만 낸다.

**라벨 사이드카**: 워커가 읽는다(모델과 함께 있는 파일이고 모델 판정의 일부). 워커 타깃에 nlohmann 이 없으므로 **(a) 워커 타깃에 nlohmann 을 추가**(헤더 전용, 같은 버전을 `xpe_ai` 가 이미 쓴다 — 권장)하거나 (b) 최소 배열 파서를 손으로 쓴다. (b)는 JSON 을 직접 파싱하는 새 코드가 라벨이라는 신뢰 경계를 넘나드는 입력을 읽게 하므로 권하지 않는다.

## 10. 미검증 (Gaps)

- **부위 인식의 실제 편도 비용**은 재지 않았다(뼈 억제 왕복의 절반이라는 어림이다). 응답이 작아 반이 맞을 것이나 세션·시작 비용은 따로다.
- **첫 호출 1350 ms 이상치**의 원인(콜드 파일 캐시? 백신? ORT 초기화?)을 조사하지 않았다. 5 s 예산 안이다.
- 워커 타깃에 nlohmann 을 넣는 빌드 변경이 워커 크기·`/WX` 에 닿는지 보지 않았다.
- 뼈 억제의 실제 모델 크기에서 IPC 한계(`XPE_AI_MAX_PAYLOAD_SIZE` 64 MB, 파이프 버퍼 64 KB)가 영상 4096² float(64 MB + 메타)와 맞는지는 QA-B-171 이 시험으로 확인한 것을 다시 열어 보지 않았다.
- S+ 의 "unavailable 오류 프레임이 0 으로 되돌린다"가 4행·6행의 정신에 맞는다는 판단은 읽기이고 승인된 결정이 아니다(D7).
- P 와 H 의 구현 비용은 어림이다(ABI 확장 설계는 하지 않았다).

## 11. 잔여 위험

- 워커 경로의 결정이 프로세스 안 경로와 갈라질 위험 — §5 의 공유 함수와 "두 경로를 서로 비교하는 시험"이 그 방어이고, 그 시험이 없으면 같은 결함 군(두 경로가 따로 진화)이 재발한다.
- 부위 인식과 뼈 억제의 실패 정책이 달라지는 비대칭(S+ 의 예외)이 문서에 적히지 않으면 다음 사람이 "같아야 한다"고 오해하고 지운다.
