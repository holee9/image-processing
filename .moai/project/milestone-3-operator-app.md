# 3단계 — 운영자 앱 사용자 흐름 (통과 조건, 2026-10-08)

순서: pre 기본(1단계, 닫힘) → post 기본(2단계) → **운영자 앱 사용자 흐름(이 문서)** → DICOM(마지막). 고스트·고급 처리(Phase 2)는 보류.

통과 조건은 실행 전에 적는다. 판정은 앱을 실제로 돌린 결과(UIA E2E + 저장 산출물)로만 한다. 전경 입력(Keyboard/Mouse)을 쓰는 시험은 판정 근거로 쓰지 않는다.

근거 요구: `.moai/project/pipeline-spec.md` §6.1(출시 모드에서 건너뛸 수 없음: (1) offset, (2) gain, (EI-0) 전체 영상 EI, (5)~(8) 로그·잡음·대비·선명화, (14)~(17) 표시·DICOM), §성능 `PERF-P1-001` ≤ 3000 ms. 변경 기록 §13(극성은 Presentation LUT 에서 반전, 기본 창은 해부 영역 자동 창).

**비트 동일의 범위.** 기준 영상과의 '비트 동일' 판정(U4)은 같은 DLL·같은 입력에서만 성립한다. 컴파일러가 다른 빌드 사이(CI MSVC 14.51 대 로컬 14.44, QA-B-215: enhance_basic 의 bilateral 에서 최대 7 ulp, CLAHE 뒤 uint16 에서 최대 384)의 동일성은 보장하지 않는다. 기준 영상은 출하 CI DLL 로 만들고, 출처(컴파일러 버전 + DLL sha256)를 함께 기록한다.

### U8 판정 결정 이력

- 2026-10-14 (main `5537f4e5`): 종료점을 프록시(두 번째 합성 틱)로 정하고 프록시 중앙값 ≤ 1500 ms 로 판정. 사유: 이 환경과 CI 러너에서 WPF 창이 화면 복사로 읽히지 않는다고 봤다(GUI-C-236c). 1500 은 프록시와 실제 제시 사이 지연을 덮는 여유분.
- 2026-10-14 18시 (main `be68153a`): CI run 38530320078 에서 화면이 읽혔다(5회 settled=True, 51% 변화, 화면−프록시 +165~+187 ms) — 위 전제가 반증됨. 화면 관측 시 화면 중앙값 ≤ 3000 ms, 아니면 프록시 ≤ 1500 ms 로 개정. 이 개정은 CI 결과(프록시 2277 ms 실패, 화면 2464 ms)를 본 뒤 내렸다.
- 2026-10-14 20시 (Codex #196 발견 1): 개정은 명시적 기준 변경이므로 ① 개정 전 실행을 소급 통과로 보지 않고 ② 화면 값이 이번 처리 영상을 가리키는지 독립 반증(표본/해시 + 렌더 지연 팔, GUI-C-245) 뒤 ③ 후속 CI 에서 사전 고정한 규칙으로 판정한다.
- 2026-10-14 21시 (Codex #197 발견 3, CI f294d752 결과를 보기 **전에** 고정): **U8 의 측정 대상 화면은 `ProcessedOnly` 뷰포트**다(처리 영상만 그려진 화면; GUI-C-245 의 W15). 운영 기본 비교 모드 `SwipeVertical`(원본·처리 좌우 분할)의 표시 시간은 U8 통과 근거로 쓰지 않는다. `SwipeVertical` 은 GUI-C-246 에서 같은 방식으로 재어 **값만 공개**하고, "실사용 가능" 보고에 이 범위 한정을 그대로 적는다. 판정 규칙(① 화면 5회 유효 → 화면 중앙값 ≤ 3000 ms, ② 아니면 프록시 ≤ 1500 ms)은 바꾸지 않으며, ② 로 가서 1500 ms 를 넘으면 U8 실패로 받는다.


범위 밖: DICOM 저장·전송(4단계), 고스트·래그, Phase 2 고급 처리, 레거시 `clients/` 뷰어의 기본값(사용자 결정 전까지 현행 유지).

이 문서의 모든 항목이 통과하면 사용자에게 "실사용 가능" 으로 보고한다(영상 + 따라 하기 절차 포함).
